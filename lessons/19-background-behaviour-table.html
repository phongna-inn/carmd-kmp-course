Background monitor: platform behaviour table

~1.5 h · +0.25 h per extra UI track Milestone: m14 behaviour table written from observed runs Prereq: 18
Why this matters: Lesson 18 built a monitor that asks each platform for a reading every 15 minutes. What it gets depends on the platform and on what the user does: keep the app open, switch away, come back, leave the phone alone until the system reclaims the app's memory, or kill the app by hand. A team that promises "a reading every 15 minutes" without knowing this ships a bug report with every release. Today you run the monitor in those five situations on both platforms, write down what happened, and put it where the team will find it: docs/monitor-behaviour.md, the monitor's behaviour table. No code changes: the m13 monitor already uses each platform's supported mechanism, and the job now is to know, and say, what that mechanism promises. That's milestone m14. The rows only a phone can show stay marked that way until you run them on yours.

Primary source Android's Optimize for Doze and App Standby and Power management restrictions before section 2. Apple's Choosing background strategies for your app before section 4. Lesson 18's sources (WorkManager's Define work requests, Apple's Using background tasks and BGTaskRequest.h) still apply.

Tracks The monitor is shared code, the same on every track: the scheduler adapters are Kotlin in androidMain and iosMain, and the iOS tracks differ only in where the app start calls onAppLaunch(). So the behaviour table holds for every track. We ran every row with the Compose and SwiftUI apps; on a second track, repeat the quick runs with that track's app (the extra 0.25 h). No screen and no code changes today. The excerpts show m13 code, to explain what you'll see; the one new file is in Full files at the end.

1. Five situations, and how to make each one

Appendix A.7 of the course plan names five situations: in the foreground, in the background, on return to the foreground, after the OS ends the app, and after the user force-kills it. Each has a command that produces it on an emulator or a simulator, or the closest thing to it:

SituationAndroid emulatoriOS Simulator
Foreground: the app on screenam start and leave it; adb shell svc power stayon true keeps the screen onxcrun simctl launch and leave it
Background: the user switched away; the process is still thereadb shell input keyevent KEYCODE_HOMEopen another app: xcrun simctl launch booted com.apple.Preferences
Return to the foregroundam start againxcrun simctl launch the app again
OS ends the app to reclaim memoryHome, then adb shell am kill: "kills only processes that are safe to kill and that will not impact the user experience"background, then xcrun simctl terminate: the process ends; the Simulator runs no background tasks, so nothing launches it again
Force-kill by the useradb shell am force-stop: "Force-stop everything associated with package" (Settings → Apps → Force stop on a phone)a phone's app switcher (swipe the app up); only a phone shows what follows

The two am descriptions are from the Android Debug Bridge page's activity manager table. am kill is the closest an emulator gets to the system's own kill, but it isn't the same: section 2 shows the difference Android records. The Simulator's terminate help says only "Terminate an application by identifier on a device", and doesn't say whether it is like a force quit or like the system's kill. On the Simulator that doesn't matter: either way, nothing of the app runs until someone launches it.

How to watch. The log file is the record of what happened: one line per tick, with its time. Around it, each platform tells you which process did what:

  • Android: adb shell run-as com.example.devicemonitor cat files/status-log.jsonl (the records), adb logcat -v time -s DeviceMonitor:I ActivityManager:I WM-ForceStopRunnable:D ("Monitor tick" with the process id, the process starting and being killed, WorkManager's reaction), adb shell pidof com.example.devicemonitor, and adb shell dumpsys jobscheduler | grep 'JobStatus{.*devicemonitor' (the next run's TIME=).
  • iOS: the console of xcrun simctl launch --console-pty (the adapter's println lines) and Library/Application Support/status-log.jsonl in the app's data container (xcrun simctl get_app_container booted com.example.devicemonitor data).

We ran m13's Compose app on the API 36 emulator, one situation after another on one fresh install, and read the log, logcat and dumpsys at each step. Times are the emulator's clock, as logcat and the records show it:

  1. Foreground and background are one row on Android. WorkManager doesn't look at the screen: records 2 and 3 came from the same process, one with the app on screen and one behind the launcher. The gaps, 15 min 2 s and 16 min 59 s, are what "minimum" means: "The interval period is defined as the minimum time between repetitions" (Define work requests).
  2. Return writes nothing. The launch runs onAppLaunch() again in the same process, which calls schedule, and UPDATE keeps the work and its timing (Lesson 18, section 4). The countdown went on from where it was.
  3. A killed process is started again for the work. The schedule lives in WorkManager's database and JobScheduler, not in the process. When the time came, Android started a new process for WorkManager's JobService; Application.onCreate handed over the tick, and the worker ran it 2.6 s after the process started, reading Wi-Fi as connected.
  1. Logcat names the process. Each "Monitor tick" line carries its process id, so I/DeviceMonitor(11085) and I/DeviceMonitor(11710) tell you which process ran which tick, and ActivityManager's "Start proc … for service" tells you why the second one exists.
  2. am kill isn't the low-memory killer. adb shell dumpsys activity exit-info com.example.devicemonitor recorded our kill as reason=10 (USER REQUESTED) subreason=24 (KILL BACKGROUND). The system's own kill under memory pressure is REASON_LOW_MEMORY: "Application process was killed by the system low memory killer" (ApplicationExitInfo). That's why, in the new process, WorkManager logged WM-ForceStopRunnable "Application was force-stopped, rescheduling.": from Android 11 (API 30), WorkManager's ForceStopRunnable reads the app's exit reasons, counts any "user requested" exit since the last one it handled as a force stop, and reschedules its work: harmless here, because the work was still there and kept its timing. A real low-memory kill is a device check.
  3. Force stop is different in kind. A force stop puts the app in the stopped state: Android removed our JobScheduler job on the spot, and nothing ran for 30 minutes. That state is meant "to keep apps in this state until the user explicitly removes the app from this state by directly launching the app or indirectly interacting with the app" (Android 15 behavior changes), and Android's reference says what is lost: ApplicationStartInfo.wasForceStopped() lets an app "know if it should re-register for any alarms, jobs and other callbacks that were cleared when the app was force-stopped" (ApplicationStartInfo). WorkManager does that itself: when the user opened the app, it found the "user requested" exit (subreason FORCE STOP this time), put the work back, and ran the overdue run at once. Only the user opening the app restarts the monitor.
  4. Recents isn't Force stop. Swiping the app away in Recents ended the process, and Android's reference lists it with Force stop under the same reason: "user clicked the "Force stop" button of the application in the Settings, or removed the application away from Recents" (REASON_USER_REQUESTED, ApplicationExitInfo). But on the emulator the app wasn't stopped: the job stayed and the next run came as after am kill. Users swipe apps away far more often than they force-stop them, and a phone maker's Android may handle it differently: that's a row to check on your phone.

What only a phone shows: Doze and App Standby. The emulator was plugged in and awake. A phone on battery, locked and still, goes into Doze, which "defers their jobs, syncs, and standard alarms" and "Doesn't let JobScheduler run. WorkManager uses JobScheduler internally, so WorkManager tasks don't run"; the work waits for a maintenance window, and "Over time, the system schedules maintenance windows less frequently" (Optimize for Doze and App Standby). App Standby buckets also limit how often an app's jobs run on battery, sorted by "how recently and how frequently the apps are used" (App Standby Buckets): from "Up to 20 minutes in a rolling 60 minute period" of job time for an active app to "Once per day for up to 10 minutes" for a restricted one, and "WorkManager uses JobScheduler to schedule tasks when the app is not visible and workers are thus impacted by job resource limits" (Power management restrictions). On a phone, then, expect the 15 minutes to stretch, the longer the phone sits still.

3. iOS: what we saw on the Simulator

The same sequence with m13's SwiftUI app on the iOS 26.2 Simulator, the console captured with --console-pty:

SituationWhat we didWhat we saw

  1. Every activation starts the timer over. Becoming active cancels the old timer and waits a whole interval before the first tick. That's why the second record came 15 minutes after the return, not 15 minutes after the first record. The consequence belongs in the table: a user who opens the app for less than 15 minutes at a time gets no foreground records at all. Changing that (say, a tick on return when the last record is older than the interval) would be a rule of the app, so it would go in MonitoringService with a test, not in the adapter; m14 records the behaviour and changes nothing.
  2. In the background the Simulator runs nothing. The adapter hands over to BGTaskScheduler, and the Simulator rejects the request with error 1, Unavailable, documented for "The app is running on Simulator which doesn’t support background processing" (BGTaskScheduler.h). Apple's debugger commands that launch a task on demand are no help here: "The debug functions work only on devices" (Starting and terminating tasks during development). So what iOS does for the app in the background is a phone row, every time.
  3. The log outlives the process; the timer doesn't. After terminate the two records were still in the file, and the new process started with no timer and no tick until a full interval after it became active.
  • Android (emulator)
  • iOS (Simulator)

What only a phone shows. On an iPhone the background request succeeds (unless Background App Refresh is off), and iOS may launch or wake the app for it. When the system ends a suspended app to reclaim memory ("the system terminates background apps as needed to make those resources available", Preparing your UI to run in the background), a pending request can still bring it back: "If your app isn’t running when an event arrives, the system launches the app and moves it directly to the background" (About the background execution sequence). A force quit is different. No BackgroundTasks page or header mentions it, but Apple's documentation says it for the other ways iOS launches apps in the background: "the system does not automatically launch your app if the user has force-quit it. In that situation, the user must relaunch your app or restart the device before the system attempts to launch your app automatically again" (application(_:didReceiveRemoteNotification:fetchCompletionHandler:)), and "the system does not automatically relaunch apps that were force quit by the user" (background(withIdentifier:)). Apple's Developer Technical Support says the same of background launches in general, with a caveat: "iOS also sets a flag that prevents the app from being launched in the background. That flag gets cleared when the user next launches the app manually", and "In some circumstances iOS will not honour this flag" (iOS Background Execution Limits, Apple Developer Forums). The table writes "expected: no records until the user opens the app" and marks it for a phone.

4. Why iOS gives no fixed interval

Android's 15 minutes is a floor, and the work runs eventually: WorkManager is "intended for work that is required to run reliably" (Lesson 18), and Doze only delays it. iOS's 15 minutes is a floor with no promise behind it at all:

  • Android
  • iOS
  1. "Not sooner", never "at". earliestBeginDate: "the system doesn’t guarantee launching the task at the specified date, but only that it won’t begin sooner", and a refresh request is fulfilled "intelligently based on system conditions and app usage" (BGTaskRequest.h). Apple's strategy guide: "The system decides the best time to launch your background task, and provides your app up to 30 seconds of background runtime" (Choosing background strategies).
  2. What it decides from. Apple's WWDC19 session on background execution: "How often your app is launched and at what times depends on how the user has historically used your app", and the system "monitors various system conditions including battery level, app usage, network connectivity, and more" (Advances in App Background Execution). The user can turn it off: backgroundRefreshStatus tells whether "Background App Refresh—an app’s ability to open in the background to perform refresh tasks—is enabled", and "Background App Refresh is disabled automatically when a device is operating in low-power mode" (backgroundRefreshStatus).
  3. It can be hours. Apple warns developers testing it: "The delay between the time you schedule a background task and when the system launches your app to run the task can be many hours" (Starting and terminating tasks during development).
  4. One request, one launch. "There can be a total of 1 refresh task and 10 processing tasks scheduled at any time" (submit(_:)), so the chain lives only as long as each launch submits the next, which is why Lesson 18's handler calls submit() first.

Why it's built this way is the same reason as Android's floor: a phone's battery and data belong to the user, and the system spends them on the apps the user actually uses. An app can't buy its way out with a cleverer timer. It can only use the mechanism made for what it does, which is the next section.

5. What each platform allows

The behaviour table says what the monitor gets. The team also needs to know what it could ask for, and what it may not:

The app needsAndroidiOS
a reading while the app is on screenany timer, at any interval: the app is running (the iOS adapter's foreground timer)
a reading every N minutes in the backgroundWorkManager periodic work, N ≥ 15, "the minimum time between repetitions": what m13 doesno such mechanism. A refresh task runs "up to 30 seconds", when the system decides: what m13 does
continuous work the user knows abouta foreground service, with its notification and declared type (Lesson 18)only the background modes' own purposes: "VoIP, audio playback, location, task completion, local notifications, etc." (App Review Guideline 2.5.4)
to hear from a connected BLE device in the backgrounda foreground service, for a task the user notices (Lesson 18)the bluetooth-central background mode: "the system wakes up your app when any of the CBCentralManagerDelegate or CBPeripheralDelegate delegate methods are invoked", but "Apps should not use being woken up as an opportunity to perform extraneous tasks" (Core Bluetooth background processing)
to keep running after the user force-kills itnothing: both platforms treat a force-kill as the user saying no until the user opens the app again. Android's stopped state is meant "to keep apps in this state until the user explicitly removes the app from this state by directly launching the app or indirectly interacting with the app" (Android 15 behavior changes); iOS: section 3

Lesson 18's rule stands: use the platform-supported mechanism, and never bypass the OS's limits. Where a platform can't do something, the table says so; that's what Appendix A.7 means by "document that".

6. Write the table into the project

The table goes into the repository, next to the code it describes, so the next person who hears "the monitor skipped an hour" finds the answer before filing a bug:

  1. A "Seen on" column. Each row says how it is known: emulator or Simulator for what we ran, phone, not yet run for what only a phone can show, written from the platform's documentation. A reader can tell an observation from an expectation, and you know which rows to run on your phones.
  2. Behaviour, not timings. The table says "15 minutes or more", not "15 min 59 s": exact gaps differ on every run and every device, and belong in your notes. A row changes when a run contradicts it.
  3. Markdown, in docs/. It's read on GitHub and in the IDE, and it isn't packed into either app. The Android and iOS build files never look at docs/.
Gotcha · "the monitor stopped" after a force stop A tester who force-stops the Android app, or swipes it away on an iPhone, and then waits for records, will file "the monitor stopped working". It did stop, as both platforms intend, and that's the table's force-kill row. Check that row before you look for a bug. On Android the opposite also happens: a tester who uses am kill to "simulate" a force stop sees the monitor carry on, because am kill doesn't put the app in the stopped state.
Gotcha · the emulator's JobScheduler can sit on a due job In Lesson 18's verification run, one emulator left our due job unstarted for over 35 minutes (TIME= negative, "Ready: true"), while the same emulator had run it on time an hour earlier. If a run here waits much longer than 15 minutes, that's what's happening; adb shell cmd jobscheduler run -f -n androidx.work.systemjobscheduler -u 0 com.example.devicemonitor <job id> runs it once the period is up. Say in your notes that you did, because then that row's gap wasn't Android's own.

Answer from memory, without scrolling up.

On Android, the app stays on screen for 40 minutes after a fresh install. How many records do you expect?

WorkManager doesn't look at the screen. A new periodic request runs at once, then at least one interval apart; we saw 15 min 2 s with the app on screen.

An iPhone user opens the app for 5 minutes every 10 minutes all afternoon. How many foreground records does m13 write?

On the Simulator the record after a return came 15 minutes after the return, not 15 minutes after the previous record. Background records, on a phone, are up to iOS.

On the emulator, you press Home and run am kill. What happens to the monitor?

The schedule lives in WorkManager's database and JobScheduler, not in the process. We saw "Start proc 11710 … for service {…SystemJobService}" and a record 2.6 s later.

After am kill, WorkManager logged "Application was force-stopped, rescheduling." Was the app force-stopped?

dumpsys activity exit-info shows the reason. A real force stop removes the job from JobScheduler at once; am kill left it counting down.

Why can't the iOS adapter promise a reading every 15 minutes in the background?

Which rows of the table can't be filled in on the emulator or Simulator?

Mixed review (interleaved)

After simctl terminate and a relaunch, the log file still has both records, but the new process's MonitorStatus has no lastRecord. Why? (Lessons 17–18)

Lesson 18 said it: "The log file is what lasts." Show the log, not lastRecord, for history.

The iOS adapter restarts its timer on UIApplicationDidBecomeActiveNotification. Why that, and not a screen's onAppear? (Lessons 04 and 18)

Pressing Home gives no view callbacks at all; the app and scene levels are where background work hooks in (the platform lifecycles cheatsheet's rule).

A teammate proposes a tick on every return to the foreground when the last record is older than the interval. Where would that go? (Lessons 10 and 18)

Adapters are timers; rules go in a service. The service would need to hear about the return, which is a port question to settle first.

# Background monitor: what each platform does

The status monitor (Lessons 18-19) asks for a reading of the phone's status every 15 minutes and
appends it to the log (status-log.jsonl). This table says what each platform gives it, in each
situation. Written from runs on the Android emulator and the iOS Simulator (Lesson 19), and from
each platform's documentation for what only a phone can show.

"Seen on" says how a row is known:
- emulator / Simulator: we ran it and saw this.
- phone, not yet run: only a physical phone can show it. The row says what the platform's
  documentation says. When you run it, write the phone and OS version here, and correct the row
  if the phone disagrees.

## Android: WorkManager periodic work, 15 minutes

| Situation | What happens | Seen on |
|---|---|---|
| Foreground | A record a moment after the first launch, then one per period, 15 minutes or more apart, from the same process. Being on screen changes nothing. | emulator |
| Background (Home, process alive) | The same: WorkManager runs the work in the running process. | emulator |
| Background, phone locked and still, on battery | Doze defers the work to maintenance windows, which come less often the longer the phone is still; standby buckets limit how often jobs run. Expect gaps longer than 15 minutes. | phone, not yet run |
| Return to foreground | No extra record. The next run keeps its time (UPDATE keeps the schedule). | emulator |
| OS ends the process | At the next run Android starts a new process for the work; Application.onCreate hands over the tick, and the record is written. The schedule is kept. | emulator (am kill) |
| OS ends the process under real memory pressure | Expected the same as the row above; Android records the exit as LOW_MEMORY. | phone, not yet run |
| Force stop (Settings > Apps > Force stop) | No records until the user opens the app again: Android removes the work's job at once. When the app opens, WorkManager reschedules and runs the overdue work: a record at once (sometimes two, a second or two apart: the first run is interrupted and started again), then one per period. | emulator |
| Swipe away in Recents | The process ends, but the app isn't stopped: the job stays, and the next run starts a new process, as when the OS ends it. A phone maker's Android can differ: check yours. | emulator; phone, not yet run |

## iOS: a timer in the foreground, a BGAppRefreshTask request in the background

| Situation | What happens | Seen on |
|---|---|---|
| Foreground | The app's own timer: the first record one interval after the app becomes active, then one per interval while it stays active. | Simulator |
| Return to foreground | The timer starts over: the next record one full interval after the return. Visits shorter than 15 minutes write nothing. | Simulator |
| Background, on the Simulator | iOS suspends the app. The refresh request fails with error 1 (the Simulator doesn't support background tasks): no records until the app is active again. | Simulator |
| Background, on a phone | iOS may launch or wake the app for the refresh task: not before 15 minutes, at a time iOS chooses (it can be hours), or not at all. Each run asks for the next. | phone, not yet run |
| Process ended (Simulator: simctl terminate) | Nothing runs until the user opens the app. The log keeps its records; the new process writes its first record one interval after it becomes active. | Simulator |
| OS ends the app, on a phone | A pending refresh request can still launch the app in the background, when iOS chooses. | phone, not yet run |
| Force quit (swipe up in the app switcher) | Expected: no background launches, so no records, until the user opens the app again. | phone, not yet run |
| Background App Refresh off, or Low Power Mode | No refresh tasks: the request fails with error 1 when Background App Refresh is off; Low Power Mode turns Background App Refresh off. | phone, not yet run |

## What neither platform promises

- An exact interval. Android's 15 minutes is the least time between runs; iOS's is the earliest
  time a run may start, and in the background iOS decides whether it starts at all.
- Records after the user force-kills the app, until the user opens it again.
- A record the moment the app opens. Android writes on the work's schedule (at once only when a
  run is due, as on the first launch or after a force stop); iOS writes one interval after each
  activation.
