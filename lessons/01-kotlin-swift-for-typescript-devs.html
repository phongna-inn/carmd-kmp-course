Part A — Kotlin (~2 h)

A1. Declarations and null safety

val is TypeScript's const; default to it. Types come after names, as in TS. The real upgrade is that null safety is part of the type system and enforced everywhere, with no strictNullChecks toggle and no any escape hatch (Kotlin docs: Null safety).

Kotlin's fallback operator is ?: (the "Elvis" operator), not ??. And name!! really does throw a NullPointerException if name is null. In TS, name! only silences the compiler.

A2. Data classes and sealed interfaces

A data class is a class whose job is to hold values. Kotlin generates equals(), hashCode(), toString() and copy() from the constructor properties (docs). Two devices with the same fields are ==, which never happens with plain TS objects.

data class Device(val name: String?, val address: String, val rssi: Int)

val a = Device("OBD-II Dongle", "AA:01", -48)
a == a.copy()             // true: structural equality
a.copy(rssi = -50)        // a new Device; `a` is untouched

A sealed interface is a closed set of subtypes, all known at compile time (docs). It's TypeScript's discriminated union, without the hand-written kind field:

Because the set is closed, a when expression over it must handle every case, and the compiler checks that for you. TypeScript needs the never trick to get the same guarantee. You'll lean on this constantly: every screen in the app renders a sealed UiState.

A3. Lambdas, collections, extension functions

Collections read like JS arrays: filter, map, joinToString. A lambda's single parameter is implicitly named it. When the last argument is a lambda, it moves outside the parentheses (a "trailing lambda") (docs).

devices.filter { it.rssi > -80 }.map { it.name ?: "Unknown" }

An extension function adds a method to a type you don't own, without subclassing or touching a prototype. It's resolved statically, so it's just a function with nicer syntax (docs):

fun Device.label(): String = "${name ?: "Unknown"} ($address) $rssi dBm"

A4. Coroutines: suspend is not async

This is where TS intuition misleads. In JS, calling an async function starts it immediately and hands back a Promise, which can outlive whoever called it. Kotlin's version differs in two ways (docs):

  1. A suspend fun can only be called from another suspend function or a coroutine. There's no Promise object. It pauses at delay() or another suspend call without blocking the thread, then resumes.
  2. Coroutines are started by a builder (launch) inside a CoroutineScope. The scope owns them: cancel the scope and every coroutine in it is cancelled. This is called structured concurrency, and it's why a screen closing in Lesson 05 automatically stops its BLE scan.

runBlocking { } bridges normal code into coroutines by blocking the current thread until everything inside finishes. Use it in main() and tests only, never in app code.

A5. Flow and StateFlow

A Flow is an asynchronous stream of values. It's cold, like an RxJS Observable: the flow { } body doesn't run until someone calls collect, and it runs again for each collector (docs). A StateFlow is hot and always holds exactly one current value, like a BehaviorSubject. It's how every ViewModel in this course exposes UI state (Android docs: StateFlow).

Here is the whole Part A program. It's a fake BLE scan: devices trickle in, weak ones are filtered out, and a StateFlow tracks the scan's state while main prints each state it sees.

data class Device(val name: String?, val address: String, val rssi: Int)

fun Device.label(): String = "${name ?: "Unknown"} ($address) $rssi dBm"

sealed interface ScanState {
    data object Idle : ScanState
    data class Scanning(val found: Int) : ScanState
    data class Done(val devices: List<Device>) : ScanState
}
  1. The device model is immutable (vals only). A scan result is a snapshot, so nobody should edit it in place.
  2. The extension function gives every Device a display label, using ?: for the nameless ones.
  3. ScanState has three states. Idle carries no data, so it's a data object (a singleton with a readable toString).
fun fakeScan(): Flow<Device> = flow {
    val nearby = listOf(
        Device("OBD-II Dongle", "AA:01", -48),
        Device(null, "BB:02", -91),
        Device("Heart Rate", "CC:03", -67),
    )
    for (device in nearby) {
        delay(300)
        emit(device)
    }
}
  1. fakeScan() is a normal function that returns a Flow. Calling it does nothing yet, because the flow is cold.
  2. Inside flow { } you're in a coroutine, so you can call suspend functions. delay(300) pauses without blocking a thread, standing in for radio latency.
  3. emit(device) pushes one value to whoever is collecting. In Lesson 08, a real BluetoothLeScanner callback takes this line's place.
class Scanner(private val scope: CoroutineScope) {
    private val _state = MutableStateFlow<ScanState>(ScanState.Idle)
    val state: StateFlow<ScanState> = _state.asStateFlow()

    fun start() {
        scope.launch {
            val found = mutableListOf<Device>()
            fakeScan()
                .filter { it.rssi > -80 }
                .collect { device ->
                    found += device
                    _state.value = ScanState.Scanning(found.size)
                }
            _state.value = ScanState.Done(found.toList())
        }
    }
}
  1. The scanner doesn't create its own scope; it's given one. Whoever owns the scope controls its lifetime. That's the seed of dependency injection (Lesson 06).
  2. The backing-property pattern: a private MutableStateFlow that only the class can write, exposed publicly as a read-only StateFlow. Every shared ViewModel in this course does exactly this.
  3. start() is not suspend. It launches a coroutine in the scope and returns immediately, so it's "fire and track".
  4. filter is a Flow operator. It builds a new cold flow and runs nothing yet. collect is the terminal call that actually starts fakeScan()'s body, and it suspends until the flow completes.
  5. Writing _state.value publishes a new state to every collector. After the flow completes, the final Done carries a read-only copy of the list.
fun render(state: ScanState): String = when (state) {
    ScanState.Idle -> "Idle"
    is ScanState.Scanning -> "Scanning… ${state.found} found"
    is ScanState.Done -> "Done: " + state.devices.joinToString { it.label() }
}

fun main(): Unit = runBlocking {
    val scanner = Scanner(scope = this)
    scanner.start()
    scanner.state
        .onEach { println(render(it)) }
        .first { it is ScanState.Done }
}
  1. when is exhaustive with no else. After is ScanState.Scanning, state is smart-cast, so state.found type-checks.
  2. runBlocking provides the scope (this) that the scanner launches into. : Unit tells Kotlin that main returns nothing, whatever the block's last expression is.
  3. A StateFlow never completes, so collecting it forever would hang. first { … } collects until the predicate matches, then stops, and onEach prints every state on the way.

Run it and you get:

Idle
Scanning… 1 found
Done: OBD-II Dongle (AA:01) -48 dBm, Heart Rate (CC:03) -67 dBm
Gotcha · where did "Scanning… 2 found" go? Two devices passed the filter, so the state was set to Scanning(2). But right after that, the flow ended and the same coroutine set Done before the collector got a chance to run. StateFlow is conflated: a collector sees only the latest value, never a backlog. That's exactly right for UI state, because a screen should draw what's true now. It's wrong for events you must not miss, such as "show this error once". The course handles those differently in Lesson 05.

Part B — Swift (~2 h)

B1. Structs are values; classes are references

This is the one idea with no TypeScript equivalent. In TS, every object is a reference. In Swift, a struct is a value type: assigning it or passing it copies it. A class is a reference type, like a TS object (Swift book: Structures and Classes).

struct Counter { var count = 0 }
var a = Counter()
var b = a          // b is a full copy
b.count += 1
print(a.count)     // 0: a was never touched

The rule of thumb the course follows: data is a struct (a scanned device, a reading) and long-lived things with identity are a class (a scanner, a BLE adapter). Everyone holding a scanner must see the same scanner. let is Swift's const. On a struct, let also freezes every field.

B2. Optionals

Optionals work like Kotlin's nullable types (String?, ?.), but Swift kept TypeScript's ??. Swift also adds two unwrapping forms you'll see everywhere (Swift book: The Basics):

if let name = device.name { print(name) }       // name is non-optional inside
guard let name = device.name else { return }    // ...or exit early; name is usable below

B3. Enums with associated values, protocols, extensions

Swift's enum can carry data per case. It's the Swift spelling of Kotlin's sealed interface, and a switch over it must be exhaustive (Swift book: Enumerations).

A protocol is an interface (Swift book: Protocols). In Lesson 06, the Kotlin interface BleScanner becomes a protocol that your Swift adapter conforms to. An extension adds members to an existing type, the same idea as Kotlin's extension functions.

B4. Closures

A closure is { params in body }. Shorthand arguments are $0, $1, and trailing closures move outside the parentheses, exactly as in Kotlin (Swift book: Closures). A key path like \.label can stand in for { $0.label }.

B5. async/await, AsyncStream, and @MainActor

Swift's async/await reads like TypeScript's. An AsyncSequence is consumed with for await, the same keyword pair as JS async iterators. AsyncStream is the easy way to build one by pushing values into a continuation (Apple: AsyncStream). @MainActor marks code that must only run on the main actor, which is where all UI work lives (Apple: MainActor).

The same program in Swift:

struct Device {
    let name: String?
    let address: String
    let rssi: Int
}

extension Device {
    var label: String { "\(name ?? "Unknown") (\(address)) \(rssi) dBm" }
}

enum ScanState {
    case idle
    case scanning(found: Int)
    case done([Device])
}
  1. Device is a struct with let fields, the same immutable-snapshot decision as the Kotlin data class.
  2. The extension adds a computed property. \(…) is string interpolation, Swift's ${…}.
func fakeScan() -> AsyncStream<Device> {
    AsyncStream { continuation in
        Task {
            let nearby = [
                Device(name: "OBD-II Dongle", address: "AA:01", rssi: -48),
                Device(name: nil, address: "BB:02", rssi: -91),
                Device(name: "Heart Rate", address: "CC:03", rssi: -67),
            ]
            for device in nearby {
                try? await Task.sleep(for: .milliseconds(300))
                continuation.yield(device)
            }
            continuation.finish()
        }
    }
}
  1. The closure receives a continuation, a handle for pushing values in from outside.
  2. Task { } starts a piece of async work, much like launch. Unlike launch, it isn't tied to a scope, so nothing cancels it automatically. Keep that difference in mind.
  3. Task.sleep can throw if the task is cancelled, and try? ignores that here. yield is Kotlin's emit, and finish() ends the stream. In Lesson 08, CoreBluetooth's delegate callback calls yield instead.
@MainActor
final class Scanner {
    var onChange: ((ScanState) -> Void)?

    private(set) var state: ScanState = .idle {
        didSet { onChange?(state) }
    }

    func start() async {
        var found: [Device] = []
        for await device in fakeScan() where device.rssi > -80 {
            found.append(device)
            state = .scanning(found: found.count)
        }
        state = .done(found)
    }
}
  1. A class, because a scanner has identity. final means it can't be subclassed. @MainActor means all of its state is read and written only on the main actor, so it's safe to drive UI from.
  2. private(set) is Swift's backing-property pattern in one line: anyone can read state, but only Scanner can write it.
  3. didSet runs after every assignment and calls the optional callback. Here it plays the role of the StateFlow collector. Lesson 05 replaces this hand-made callback with SwiftUI observation.
  4. for await … where loops over the async stream, with an inline filter.
func render(_ state: ScanState) -> String {
    switch state {
    case .idle:
        return "Idle"
    case .scanning(let found):
        return "Scanning… \(found) found"
    case .done(let devices):
        return "Done: " + devices.map(\.label).joined(separator: ", ")
    }
}

let scanner = Scanner()
scanner.onChange = { print(render($0)) }
print(render(scanner.state))
await scanner.start()
  1. case .scanning(let found) pulls the associated value out. The switch is exhaustive, with no default.
  2. The _ before the parameter name means callers write render(x), not render(state: x).
  3. Top-level code in main.swift may use await directly, and it runs on the main actor, which is why it can touch the @MainActor scanner (SE-0343).

Run it and you get one more line than in Kotlin:

Idle
Scanning… 1 found
Scanning… 2 found
Done: OBD-II Dongle (AA:01) -48 dBm, Heart Rate (CC:03) -67 dBm
Kotlin vs Swift · what changed and why The didSet callback runs synchronously on every assignment, so it sees every state. Kotlin's StateFlow collector runs later, as a separate coroutine, and only reads the latest value. Neither is a bug. They're different tools: a callback is a stream of changes, and a StateFlow is "the current truth". When Lesson 05 connects SwiftUI to the shared Kotlin StateFlow, the iOS UI inherits the Kotlin behaviour.

Retrieval check: Part B

var a = Counter(); var b = a; b.count += 1. What is a.count? (Counter is a struct.)

Structs are values: b is a copy. If Counter were a class, the answer would be 1.

Why does Swift print Scanning… 2 found when Kotlin didn't?

A callback fires once per change. A StateFlow collector reads the latest value whenever it next runs.

What does @MainActor on Scanner guarantee?

The compiler enforces it: code off the main actor must await to reach it.
