Why this matters: in m04 the shared ViewModel builds its own scanner: its factory says DeviceListViewModel(FakeDeviceScanner()). Three problems, each of which gets worse as the app grows:

  1. The ViewModel can't be given a different scanner. Lesson 13 needs a different one per platform, and Lesson 11's tests need one they control. A Swift class can implement a Kotlin interface, but commonMain can never import a Swift class. So the ViewModel must ask for an interface, and someone outside it must choose what to pass.
  2. The app's rule is hidden in a fake. "Show devices whose name contains the filter" is a rule of the app, true on both platforms whatever the radio. In m04 it lives in SampleDevices.matching, inside the pretend radio, so it would vanish when the real radio arrives. A real radio also brings a second rule: it can report the same device again and again (Android's scanner can call back for every advertisement it hears, CALLBACK_TYPE_ALL_MATCHES, and CoreBluetooth does when you turn off its duplicate filtering, CBCentralManagerScanOptionAllowDuplicatesKey), so someone has to report each device only once.
  3. A test hook in user input. Typing fail into the filter fakes a radio error. That's handy while the app has no tests, but it mixes what the user typed with what the radio did. From today, an error is something a radio adapter throws; Lesson 11's tests use a fake radio that fails on command, and section 6 shows the dialog by plugging in a failing one.

2. The hexagon in five words

The pattern is older than mobile. Alistair Cockburn named it hexagonal architecture, also called ports and adapters, with this intent: "Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases" (Hexagonal architecture). Swap "devices and databases" for "Bluetooth radios", and that's what the app needs. The course uses five words for it, the same in every lesson from now on:

WordWhat it isIn m05
app corethe part of the shared code that holds the app's models, ports and services, and imports nothing from Android, iOS or any frameworkpackage core
inbound portan interface for what the app offers, one per capability. A service implements it; inbound adapters call itDeviceScanning
outbound portan interface for what the app needs from the outside world, named in the app's terms. Outbound adapters implement itBleScanner
servicea class in the app core that implements an inbound port by applying the app's rules and calling outbound portsScanningService
adapterinbound: code that drives the app through inbound ports (the shared ViewModels, and the tests from Lesson 11). Outbound: one concrete implementation of an outbound port for one platform or technologyDeviceListViewModel (inbound), SimulatedBleScanner (outbound)
  • App core
  • Inbound (port and adapter)
  • Outbound (port and adapter)
  • Android
  • iOS

Why a hexagon? Not for the number six. Cockburn: "The hexagon is not a hexagon because the number six is important, but rather to allow the people doing the drawing to have room to insert ports and adapters as they need". The point of the drawing is that there's an inside, the app core, and an outside, and the outside talks to the inside only through ports. Inbound and outbound are the course's names for Cockburn's two sides: a primary actor "drives the application", and the application drives a secondary actor. "They could be also called driving adapters and driven adapters." You'll meet driving/driven and primary/secondary in other codebases; they mean inbound and outbound.

One rule for where code goes. UI code goes in the screen. A rule of the app goes in a service. Anything that talks to a platform, a library or the network goes in an outbound adapter, behind an outbound port. ViewModels talk only to inbound ports. And the app core imports nothing from Android, iOS or any framework: only Kotlin's standard library and kotlinx.coroutines, whose Flow is how the ports describe a stream, plus the core's own packages. No androidx, no platform.*, no Koin or Ktor.

Try the rule. Where does each of these belong?

interface BleScanner { fun scan(): Flow<Device> }

An outbound port: what the app needs, in its own terms. It sits in the core, in core.outbound, because every radio and every test fake implements it, and the core may not import any of them.

class SimulatedBleScanner : BleScanner

One concrete way of providing what the port promises. Lesson 13's real radios are outbound adapters too, one per platform.

"Show each device once, and only names that contain the filter"

A rule of the app, the same on every screen and both platforms, whatever the radio: a service, ScanningService.

"After 3 s, stop scanning and show what was found"

This screen's behaviour, with its own states (Scanning → Finished): the ViewModel. Another screen could scan with a different timeout, or until the user taps Stop.

"Show the status text in red when nothing was found"

How the state looks. The ViewModel says Finished(emptyList()), and each platform draws that in its own style.

"In this app, BleScanner means SimulatedBleScanner"

The wiring decision. It lives only in the composition root: AppContainer today, Lesson 11's Koin module after that. It's the binding Lesson 13 changes to the real radios.

From TypeScriptIf you've used Angular, you know this shape. A port is an abstract class or an InjectionToken; an adapter is the @Injectable that implements it; constructor injection is constructor(private scanning: DeviceScanning); and the composition root is the providers: [{ provide: BleScanner, useClass: SimulatedBleScanner }] array. The difference is that Angular's injector is built in, and Kotlin has none: today you wire everything by hand, and Lesson 11 adds Koin as the injector.

Why inbound/outbound and not in/out? Some hexagonal code in Java uses in and out: the BuckPal sample application, for example, has packages application.port.in and adapter.out. In Kotlin, in is a hard keyword: Kotlin's keyword list says hard keywords "are always interpreted as keywords and cannot be used as identifiers" (Keywords and operators). A package named core.in doesn't compile:

e: …/DeviceScanning.kt:1:40 Syntax error: Package name must be a '.'-separated identifier list.

You could write core.`in` in backticks, in every package and import line. (out on its own would compile: it's a modifier keyword, which "can be used as identifiers in other contexts".) inbound and outbound need no backticks, read as the words the course uses, and keep the two names symmetrical.

4. The app core

Start with the model and the error. Both are the words the ports speak, so they live in core and depend on nothing:

  1. Device is unchanged except for its package: a model, used by every part of the app.
  2. ScanException moved out of the pretend radio. Adapters throw it and the ViewModel catches it, so it belongs to neither of them: it's part of what both ports promise.

The inbound port is what the ViewModel needs from the app. Look at its one method: it has exactly the shape of m04's FakeDeviceScanner.scan(filter). The ViewModel already used that shape; now it's a promise instead of a class.

  1. One inbound port per capability, not per action. "Device scanning" is a capability. If the app later needs to stop a scan from a button or check whether the radio is on, those become methods on DeviceScanning, not new ports. The finished app has about five inbound ports (section 7).
  2. Start and stop are collect and cancel. A Flow is cold (Lesson 01): collecting it starts the scan, and cancelling the collector stops it. So the scan can't be left running by a forgotten stopScan().
  3. The comment is the contract. An interface can't enforce "each reported once"; the service that implements it must. Lesson 11 turns this comment into tests.

The outbound port is what the app needs from a radio, and it promises only what every radio can do:

  1. Named in the app's terms. Flow<Device>, not Android's ScanResult or iOS's CBPeripheral. Each adapter translates its platform's types into ours, so the core never mentions a platform.
  2. No filter parameter. The radios' own scan filters can't do "name contains this text, ignoring case", so the port doesn't promise it. Filtering is the app's rule, and it moves into the service. Lesson 13 adds what the real radios need, such as whether Bluetooth is on.
  3. Why an interface and not expect/actual? Lesson 05's expect fun platformName() gives exactly one implementation per platform, chosen at compile time, and the iOS one must be Kotlin. This port will have several: simulated, a test fake, and the real radios, one of them in Swift. JetBrains says the same: "With interfaces, you don't limit your design to one implementation per target platform. Also, it's much easier to substitute a fake implementation in tests or provide multiple implementations on a single platform" (Expected and actual declarations).

The service implements the inbound port, holds the rule, and calls the outbound port:

  1. (private val scanner: BleScanner) : DeviceScanning: the service receives an outbound port through its constructor, and implements an inbound port. It never builds a scanner. That's constructor injection, which Android's guide defines as: "you take the dependencies of a class and provide them rather than having the class instance obtain them itself" (Dependency injection in Android).
  2. seen is created inside flow { }, so every collection, every scan, starts with an empty set. As a property of the class, it would remember the previous scan's devices and hide them all on the next scan. The service keeps no state between calls.
  3. seen.add(device.id) returns true only the first time an id is added: one call both checks and records. The filter is m04's rule, trimmed once per scan and case-insensitive.
  4. The imports are the proof. This file imports two core packages and kotlinx.coroutines. Nothing in it could tell an Android radio from a Swift one from a test fake.

5. The adapters

The outbound adapter is the pretend radio, now honest about being a radio: it hears every device over and over, as a real one can:

  1. : BleScanner and override: an adapter plugs into a port by implementing it. Nothing in the app core names this class, and only the composition root does outside its own package.
  2. while (true): after the fifth device, at 1.5 s, it starts again with the first. The rows on screen still look exactly as in m04, five of them, because the service drops the repeats. Exercise 3 shows what happens without that rule.
  3. SampleDevices moves into the same package, without matching: the filter now lives in the service. Its all list and find(id) are unchanged.

The inbound adapter is the ViewModel. Only two things change: its constructor asks for the port, and startScan calls it. The timeout, the copies and the error handling are Lesson 08's, line for line.

  1. private val scanning: DeviceScanning: the type is the inbound port. The ViewModel could be handed ScanningService, or in Lesson 11 a test's own class that implements the port, and it can't tell which. It imports nothing from core.outbound or adapter.outbound.
  2. The Factory is gone from the companion object. It had to name a concrete scanner, which is exactly the knowledge this lesson moves out. SCAN_TIMEOUT stays.
  3. The 3-second timeout stays here, not in the service: it's this screen's behaviour (the sorter in section 2). The scan rule that's true for every screen is in the service.
  4. DeviceListUiState.kt moves into adapter.inbound too: UI state belongs to the ViewModel. Only its package line and the Device import change.

6. Wire it by hand

Someone still has to choose the adapter and call the constructors. Android's Manual dependency injection guide calls that someone a dependencies container, a class "that you use to get dependencies". The one place where the whole graph of objects is built is called the composition root. Ours is a Kotlin object in shared code, so both platforms get the same wiring:

  1. The only file whose code names SimulatedBleScanner and ScanningService, apart from their own files. From Lesson 11 this wiring moves into a Koin module, and in Lesson 13 the scanner binding there becomes "the Android radio on Android, the Swift radio on iOS". One decision, made only in the composition root.
  2. Each property's type is the port (BleScanner, DeviceScanning), and its value is what implements it. Read each line as a binding: "this port means this class".
  3. by lazy builds each one on first use and then reuses it, so the whole app shares one radio and one service. A screen opened twice must not scan with two radios. Sharing the service is safe because it keeps no state between scans (section 4).
  4. The factory is the one Lesson 08's companion object had, moved here. The ViewModel store still keeps the ViewModel; the factory runs only when the store has none. You write the order yourself: scanner, then service, then ViewModel. Android lists that as the first cost of wiring by hand: "Dependencies have to be declared in order". In exchange, a missing dependency is a compile error. Lesson 11 trades that for Koin.

Each screen changes the line that gets the ViewModel:

DeviceDetailScreen.kt changes one import, to com.example.devicemonitor.adapter.outbound.SampleDevices (see the gotcha below).

Two more files change one import each, which keeps the imports sorted: DeviceAdapter.kt imports com.example.devicemonitor.core.Device (after the …android.databinding import), and DeviceDetailFragment.kt imports com.example.devicemonitor.adapter.outbound.SampleDevices (before it).

Swift needs no import changes. Kotlin packages don't reach the Objective-C header, so Device, SampleDevices and ScanState keep their Swift names, and a Kotlin object is reached through .shared (Lesson 05). The ports are there too: the header declares BleScanner and DeviceScanning as Objective-C protocols, which Swift sees as protocols. That's what lets Lesson 13's Swift radio implement BleScanner.

Gotcha · a known shortcut, kept on purpose until the BLE lessons The detail screens still look devices up with SampleDevices.find(id), and so does the UIKit list's cell provider. On Android you can see it in the import, com.example.devicemonitor.adapter.outbound.SampleDevices: a screen reaching straight into an outbound adapter, past every port. Swift gives no such clue, because Kotlin packages don't reach the header. It works only because the simulated radio's devices are a fixed list. When the detail screen becomes the connect screen in the BLE lessons, it gets its own ViewModel and port, and the shortcut goes away. Packages make a shortcut like this visible, but they can't forbid it: Kotlin has no package-private visibility (Visibility modifiers), so any file can import any public class.

7. The finished app, and how to add things

m05 has one port on each side. The plan for the finished app (m15) has five inbound ports, one per capability, and eight outbound ports. The names come from the course plan and may be refined in the lessons that build them, but the shape won't change:

  • App core
  • Inbound
  • Outbound (shared adapters)
  • Android
  • iOS

Every change you'll make to the app after the course is one of four kinds. Each has a fixed recipe:

You're adding…What you writeWhat you don't touch
a new screen (for example, a list of recent scans)an inbound adapter: a ViewModel and its UI state in adapter.inbound, calling the inbound ports that already exist; a factory for it in the composition root; the screen on each UI trackthe app core
a new business rule (for example, hide devices weaker than −80 dBm)the service that owns that capability, and from Lesson 11 a test through its inbound portports, adapters, ViewModels, screens
a new platform capability (for example, the phone's battery level)both port kinds: an outbound port in the app's terms (BatteryProvider) with an adapter per platform (Kotlin in androidMain, Swift in the iOS app); an inbound port method and a service that uses it (a new port only for a new capability); the bindings in the composition rootexisting services that don't need it
a new API request (for example, uploading logs)an outbound port named for what the app needs (LogUploader, never ApiClient or HttpClient), a shared HTTP adapter in adapter.outbound that holds the HTTP client, and the bindingthe app core never mentions HTTP, JSON or URLs

The last row is the one most often done wrong. If the port is called ApiClient with get(url), the app core starts building URLs and parsing JSON, and the rule "the core imports no framework" quietly breaks. Name the port after the job, and the HTTP details stay in the adapter.

Retrieval checks

Answer from memory, without scrolling up.

Why does BleScanner live in the app core, and not with its adapters?

The core uses the port, so the port must be visible to the core. The adapters, including Lesson 13's Swift class, depend on the port, never the other way round.

What does DeviceListViewModel's constructor ask for?

ViewModels talk only to inbound ports. They don't know which service implements the port, and they never see an outbound port.

Why are the packages called inbound and outbound rather than in and out?

Hard keywords can't be identifiers; you'd need backticks in every package and import line. out alone would compile (a modifier keyword), but the pair stays symmetrical.

The team wants to hide devices weaker than −80 dBm on every screen. Which file changes?

It's a rule of the app, true for every screen and every radio: the service. In the adapter it would vanish when Lesson 13 swaps the radio; in the ViewModel, each new screen would need it again.

Why is seen created inside flow { } and not as a property of ScanningService?

The service is shared app-wide. As a property, seen would outlive the scan, and the second scan would treat every device from the first as already seen and show nothing.

Mixed review (interleaved)

What does expect/actual give you that rules it out for BleScanner? (Lesson 05)

The scanner needs several implementations at once (simulated, a test fake, the real radios), and the iOS one is Swift. An interface allows both.

viewModel(factory = AppContainer.deviceListViewModelFactory) runs on every recomposition. How many ViewModels does it create while the list is on the back stack? (Lesson 08)

shared/src/commonMain/kotlin/com/example/devicemonitor/core/ScanningService.kt 
package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.DeviceScanning
import com.example.devicemonitor.core.outbound.BleScanner
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow

// Service: the app's scan rule on top of a raw radio scan. Keep the devices whose name
// contains the filter (ignoring case and surrounding spaces), and report each device once.
class ScanningService(private val scanner: BleScanner) : DeviceScanning {
    override fun scan(nameFilter: String): Flow<Device> = flow {
        val wanted = nameFilter.trim()
        val seen = mutableSetOf<String>()
        scanner.scan().collect { device ->
            if (device.name.contains(wanted, ignoreCase = true) && seen.add(device.id)) {
                emit(device)
            }
        }
    }
}

import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch
import kotlinx.coroutines.withTimeoutOrNull
import kotlin.time.Duration.Companion.seconds

// Inbound adapter: turns the screen's events into calls on the DeviceScanning port, and
// the results into UI state. It knows the port only, never the service or a scanner.
class DeviceListViewModel(
    private val scanning: DeviceScanning,
) : ViewModel() {
    private val _uiState = MutableStateFlow(DeviceListUiState())
    val uiState: StateFlow<DeviceListUiState> = _uiState.asStateFlow()

    private var scanJob: Job? = null

    fun startScan(filter: String) {
        if (scanJob?.isActive == true) return
        _uiState.update { it.copy(scan = ScanState.Scanning(emptyList())) }
        scanJob = viewModelScope.launch {
            val found = mutableListOf<Device>()
            try {
                withTimeoutOrNull(SCAN_TIMEOUT) {
                    scanning.scan(filter).collect { device ->
                        found += device
                        _uiState.update { it.copy(scan = ScanState.Scanning(found.toList())) }
                    }
                }
                _uiState.update { it.copy(scan = ScanState.Finished(found.toList())) }
            } catch (e: ScanException) {
                _uiState.update { it.copy(scan = ScanState.Idle, errorMessage = e.message) }
            }
        }
    }

    fun errorShown() {
        _uiState.update { it.copy(errorMessage = null) }
    }

    companion object {
        val SCAN_TIMEOUT = 3.seconds
    }
}

class DeviceListFragment : Fragment() {

    // Fragment leaves the back stack for good.
    private val viewModel: DeviceListViewModel by viewModels { AppContainer.deviceListViewModelFactory }

    private var binding: FragmentDeviceListBinding? = null
    private var errorDialog: AlertDialog? = null
    private val adapter = DeviceAdapter { device ->
        val nav = findNavController()
        // A fast double tap delivers two clicks; only navigate from the list itself.
        if (nav.currentDestination?.id == R.id.deviceList) {
            nav.navigate(R.id.toDetail, Bundle().apply { putString("deviceId", device.id) })
        }
    }

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        val b = FragmentDeviceListBinding.inflate(inflater, container, false)
        binding = b
        b.deviceList.adapter = adapter
        b.deviceList.addItemDecoration(DividerItemDecoration(requireContext(), DividerItemDecoration.VERTICAL))
        b.scanButton.setOnClickListener { viewModel.startScan(b.filterInput.text.toString()) }
        return b.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { render(it) }
            }
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        errorDialog?.dismiss() // a dismiss() doesn't call the cancel listener, so the error stays in state
        errorDialog = null
        binding?.deviceList?.adapter = null // the adapter outlives the view; don't let it keep the old list
        binding = null
    }

    // The one place that touches views: every new state ends here. The EditText keeps its
    // own text (and restores it after rotation), so render() never sets it.
    private fun render(state: DeviceListUiState) {
        val b = binding ?: return
        val isScanning = state.scan is ScanState.Scanning
        val devices = when (val scan = state.scan) {
            ScanState.Idle -> null
            is ScanState.Scanning -> scan.found
            is ScanState.Finished -> scan.found
        }
        b.scanButton.isEnabled = !isScanning
        b.progress.visibility = if (isScanning) View.VISIBLE else View.GONE
        b.statusText.text = when {
            isScanning -> "Scanning…"
            devices == null -> "Tap Scan to look for devices."
            devices.isEmpty() -> "No devices found. Try another filter."
            else -> "Devices found: ${devices.size}"
        }
        b.statusText.setTextColor(if (devices?.isEmpty() == true && !isScanning) Color.RED else Color.DKGRAY)
        adapter.submitList(devices.orEmpty())
        renderError(state.errorMessage)
    }

    private fun renderError(message: String?) {
        if (message == null) {
            errorDialog?.dismiss()
            errorDialog = null
        } else if (errorDialog == null) {
            errorDialog = AlertDialog.Builder(requireContext())
                .setTitle("Scan failed")
                .setMessage(message)
                .setPositiveButton("OK") { _, _ -> viewModel.errorShown() }
                .setOnCancelListener { viewModel.errorShown() }
                .show()
        }
    }
}

                get: { state.errorMessage != nil },
                set: { if !$0 { viewModel.errorShown() } }
            ),
            actions: { Button("OK") {} },
            message: { Text(state.errorMessage ?? "") }
        )
        .task {
            for await newState in viewModel.uiState {
                self.state = newState
            }
        }
    }

    // SKIE turns the sealed interface into a Swift enum, so this switch is exhaustive.
    private func devices(in scan: ScanState) -> [Device]? {
        switch onEnum(of: scan) {
        case .idle: nil
        case .scanning(let scanning): scanning.found
        case .finished(let finished): finished.found
        }
    }
}

import UIKit
import Shared

final class DeviceListViewController: UIViewController, UITableViewDelegate {
    private let owner = ViewModelOwner()
    private lazy var viewModel: DeviceListViewModel = owner.viewModel(factory: AppContainer.shared.deviceListViewModelFactory)
    private var observation: Task<Void, Never>?

    private let filterField = UITextField()
    private let scanButton = UIButton(configuration: .filled())
    private let spinner = UIActivityIndicatorView(style: .medium)
    private let statusLabel = UILabel()
    private let tableView = UITableView()
    private lazy var dataSource = UITableViewDiffableDataSource<Int, String>(tableView: tableView) {
        tableView, indexPath, deviceId in
        let cell = tableView.dequeueReusableCell(withIdentifier: "device", for: indexPath)
        var content = UIListContentConfiguration.subtitleCell()
        if let device = SampleDevices.shared.find(id: deviceId) {
            content.text = device.name
            content.secondaryText = "\(device.id)   \(device.rssi) dBm"
        }
        cell.contentConfiguration = content
        cell.accessoryType = .disclosureIndicator
        return cell
    }

    override func viewDidLoad() {
        super.viewDidLoad()
        title = "Device Monitor"
        navigationController?.navigationBar.prefersLargeTitles = true
        view.backgroundColor = .systemBackground

        filterField.placeholder = "Device name filter"
        filterField.borderStyle = .roundedRect
        filterField.autocorrectionType = .no
        scanButton.configuration?.title = "Scan"
        scanButton.addAction(UIAction { [weak self] _ in
            guard let self else { return }
            viewModel.startScan(filter: filterField.text ?? "")
        }, for: .touchUpInside)
        statusLabel.numberOfLines = 0
        tableView.register(UITableViewCell.self, forCellReuseIdentifier: "device")
        tableView.delegate = self

        let statusRow = UIStackView(arrangedSubviews: [spinner, statusLabel])
        statusRow.spacing = 8
        let stack = UIStackView(arrangedSubviews: [filterField, scanButton, statusRow, tableView])
        stack.axis = .vertical
        stack.spacing = 12
        stack.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(stack)
        NSLayoutConstraint.activate([
            stack.topAnchor.constraint(equalTo: view.layoutMarginsGuide.topAnchor),
            stack.leadingAnchor.constraint(equalTo: view.layoutMarginsGuide.leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: view.layoutMarginsGuide.trailingAnchor),
            stack.bottomAnchor.constraint(equalTo: view.bottomAnchor),
        ])
        render(viewModel.uiState.value)
    }

    // Collect only while on screen, like repeatOnLifecycle(STARTED) on Android.
    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        observation?.cancel()
        observation = Task {
            for await state in viewModel.uiState {
                render(state)
            }
        }
    }

    override func viewDidDisappear(_ animated: Bool) {
        super.viewDidDisappear(animated)
        observation?.cancel()
        observation = nil
    }

    // The one place that touches views: every new state ends here. The text field owns
    // its own text, so render() never sets it.
    private func render(_ state: DeviceListUiState) {
        let isScanning = state.scan is ScanStateScanning
        // SKIE turns the sealed interface into a Swift enum, so this switch is exhaustive.
        let devices: [Device]? = switch onEnum(of: state.scan) {
        case .idle: nil
        case .scanning(let scanning): scanning.found
        case .finished(let finished): finished.found
        }
        scanButton.isEnabled = !isScanning
        if isScanning { spinner.startAnimating() } else { spinner.stopAnimating() }
        spinner.isHidden = !isScanning
        if isScanning {
            statusLabel.text = "Scanning…"
        } else if let devices {
            statusLabel.text = devices.isEmpty
                ? "No devices found. Try another filter."
                : "Devices found: \(devices.count)"
        } else {
            statusLabel.text = "Tap Scan to look for devices."
        }
        statusLabel.textColor = devices?.isEmpty == true && !isScanning ? .systemRed : .label

        var snapshot = NSDiffableDataSourceSnapshot<Int, String>()
        snapshot.appendSections([0])
        snapshot.appendItems((devices ?? []).map(\.id))
        dataSource.apply(snapshot, animatingDifferences: true)
        renderError(state.errorMessage)
    }

    private func renderError(_ message: String?) {
        guard let message, presentedViewController == nil else { return }
        let alert = UIAlertController(title: "Scan failed", message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default) { [weak self] _ in
            self?.viewModel.errorShown()
        })
        present(alert, animated: true)
    }

    func tableView(_ tableView: UITableView, didSelectRowAt indexPath: IndexPath) {
        tableView.deselectRow(at: indexPath, animated: true)
        guard let deviceId = dataSource.itemIdentifier(for: indexPath) else { return }
        navigationController?.pushViewController(DeviceDetailViewController(deviceId: deviceId), animated: true)
    }
}
