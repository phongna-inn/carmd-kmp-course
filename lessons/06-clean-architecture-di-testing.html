Part A — Layers, ports, and tests (~2 h)

A1. Three layers, one direction

Android's guide starts from one principle: "The most important principle is separation of concerns: separating your app into methods, classes, files, packages, modules and layers that have clearly defined responsibilities and boundaries." It asks for at least a UI layer that "displays application data on the screen" and a data layer that "contains the business logic of your app and exposes application data". In between sits an optional domain layer, used "to simplify and reuse the interactions between the UI and data layers" (Guide to app architecture). In this course the UI layer has two halves: the shared ViewModels and UI state (presentation), and the native screens on top of them.

Look at the arrow between domain and data. It points up: the data layer depends on the domain, not the other way round. This is the one place where the course deliberately differs from Android's guide. There, "use case classes usually depend on repository classes" (Domain layer), so the dependency runs from the domain down to the data layer. The reason is KMP. Our data sources are radios, and the radio code lives on each platform. The interface has to sit in commonMain, next to the code that uses it, because a Swift class can implement a Kotlin interface, but shared code can never import a Swift class. The interface belongs to the core, and the adapters depend on the core. That's the dependency rule: dependencies point toward the domain, and the domain imports nothing from any other layer.

The difference is that Angular's injector is built in, while Kotlin has none: Part A wires everything by hand, and Part B adds Koin as the injector.

A2. Ports and adapters

The pattern is older than mobile. Alistair Cockburn named it Ports and Adapters (also known as hexagonal architecture), with this intent: "Allow an application to equally be driven by users, programs, automated test or batch scripts". "A port identifies a purposeful conversation." "For each external device there is an adapter" that converts between the port and that device. Cockburn's examples include test harnesses and "a 'mock' database, one that sits in memory" (Hexagonal architecture). Swap "database" for "radio" and that's our plan:

Adapter behind BleScannerWhereUsed byFrom
SimulatedBleScannercommonMain (data)both apps, until real radios existtoday

an Android radio adapterandroidMain, Kotlinthe Android appLesson 08
an iOS radio adapteriosApp, Swiftthe iOS appLesson 08
KableBleScannercommonMain, libraryboth apps, as an alternativeExtension E3

Why not expect/actual? The KMP anatomy lesson used it for platformName(). It gives exactly one implementation per platform, chosen at compile time, and the iOS one has to be Kotlin. JetBrains' own guidance points to interfaces: "With interfaces, you don't limit your design to one implementation per target platform. Also, it's much easier to substitute a fake implementation in tests". And for dependencies: "In the common code, a component can express its dependencies using regular Kotlin interfaces. The DI framework can then be configured to inject a platform-specific implementation" (Expected and actual declarations). We need three implementations at once (simulated, fake, real), and one of them in Swift. That calls for an interface.

Use cases. Android defines the domain layer as the place for "complex business logic, or simple business logic that is reused by multiple ViewModels". Its naming convention is "verb in present tense + noun/what (optional) + UseCase", and it suggests making use cases callable through "the invoke() function with the operator modifier" (Domain layer). Our first one is ScanForDevicesUseCase. It holds a rule that m02 didn't need: a real radio hears the same device over and over, once per advertisement packet, so someone has to report each device only once. That rule doesn't change between screens or platforms, so it belongs in the domain, and it's worth testing.

shared/src/commonMain/kotlin/com/example/devicemonitor/domain/BleScanner.kt

package com.example.devicemonitor.domain

import kotlinx.coroutines.flow.Flow

// Port: what the app needs from a Bluetooth radio, in the app's own terms. Adapters
// implement it: a simulated radio for now, the Android and iOS radios from Lesson 08.
interface BleScanner {
    // Cold and never-ending: collecting starts a scan, cancelling the collector stops it.
    // A radio reports the same device again with every advertisement it hears.
    fun scan(): Flow<Device>
}

class ScanException(message: String) : Exception(message)
  1. The port is an interface written in the app's own terms: Flow<Device>, not ScanResult or CBPeripheral. Each adapter translates its platform's types into ours.
  2. No filter parameter. m02's fake took the filter because it was faking the whole feature. Radio-level scan filters can't do "name contains this text, ignoring case": Android's can match an exact advertised name, and CoreBluetooth filters only by service. So the port promises only what every radio can do. The filter moves up into the use case.
  3. Start and stop are collect and cancel. Requirement A.3 lists startScan() and stopScan(). A cold, never-ending Flow gives you both: collecting it starts a scan, and cancelling the collector stops it, so the radio can never be left running by a forgotten stopScan(). Lesson 08 adds isAvailable() and isEnabled() to this port.
  4. ScanException moved here too: it's part of the port's contract, so the domain owns it and adapters throw it.

shared/src/commonMain/kotlin/com/example/devicemonitor/domain/ScanForDevicesUseCase.kt

package com.example.devicemonitor.domain

import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow

// Use case: the app's scan rules on top of a raw radio scan. Keep the devices whose name
// contains the filter (ignoring case and surrounding spaces), and report each device once.
class ScanForDevicesUseCase(private val scanner: BleScanner) {
    operator fun invoke(filter: String): Flow<Device> = flow {
        val wanted = filter.trim()
        val seen = mutableSetOf<String>()
        scanner.scan().collect { device ->
            if (device.name.contains(wanted, ignoreCase = true) && seen.add(device.id)) {
                emit(device)
            }
        }
    }
}
  1. Constructor injection. The use case receives a BleScanner and never builds one. Android defines DI exactly like this: "you take the dependencies of a class and provide them rather than having the class instance obtain them itself" (Dependency injection in Android).
  2. operator fun invoke makes an instance callable like a function. The ViewModel writes scanForDevices(filter), which reads as an action.
  3. seen is created inside flow { }, so every collection (every scan) starts with an empty set. Declared as a class property, it would remember devices from the previous scan and hide them on the next one. Android says use cases "should not contain mutable data" (Domain layer), and this is why.
  4. seen.add(device.id) returns true only the first time an id is added. One call both checks and records.
  5. The filter is trimmed once per scan, and matched case-insensitively. That's the same rule m02's SampleDevices.matching had, which is now deleted.

shared/src/commonMain/kotlin/com/example/devicemonitor/data/SimulatedBleScanner.kt

package com.example.devicemonitor.data

import com.example.devicemonitor.domain.BleScanner
import com.example.devicemonitor.domain.Device
import kotlinx.coroutines.delay
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow

// Adapter: a pretend radio behind the BleScanner port. Like a real one, it hears every
// device over and over, one advertisement every 0.3 s, until the collector cancels.
class SimulatedBleScanner : BleScanner {
    override fun scan(): Flow<Device> = flow {
        while (true) {
            for (device in SampleDevices.all) {
                delay(300)
                emit(device)
            }
        }
    }
}
  1. An adapter: : BleScanner and override. Nothing above the data layer will ever name this class again, except the composition root.
  2. while (true): unlike m02's fake, it repeats every device, the way a radio does. The rows on screen look exactly as before because the use case drops the repeats. Exercises A1a (the tests) and A3 (the apps) show what happens without it.
  3. There's no "fail" test hook any more. The error path is now proven by a test with a fake that fails on command (A5), and exercise B1 shows it on screen by swapping the adapter.

shared/src/commonMain/kotlin/com/example/devicemonitor/presentation/DeviceListViewModel.kt

package com.example.devicemonitor.presentation

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import com.example.devicemonitor.domain.Device
import com.example.devicemonitor.domain.ScanException
import com.example.devicemonitor.domain.ScanForDevicesUseCase
import kotlinx.coroutines.Job
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch
import kotlinx.coroutines.withTimeoutOrNull
import kotlin.time.Duration.Companion.seconds

class DeviceListViewModel(
    private val scanForDevices: ScanForDevicesUseCase,
) : ViewModel() {
    private val _uiState = MutableStateFlow(DeviceListUiState())
    val uiState: StateFlow<DeviceListUiState> = _uiState.asStateFlow()

    private var scanJob: Job? = null

    fun startScan(filter: String) {
        if (scanJob?.isActive == true) return
        _uiState.update { it.copy(scan = ScanState.Scanning(emptyList())) }
        scanJob = viewModelScope.launch {
            val found = mutableListOf<Device>()
            try {
                withTimeoutOrNull(SCAN_TIMEOUT) {
                    scanForDevices(filter).collect { device ->
                        found += device
                        _uiState.update { it.copy(scan = ScanState.Scanning(found.toList())) }
                    }
                }
                _uiState.update { it.copy(scan = ScanState.Finished(found.toList())) }
            } catch (e: ScanException) {
                _uiState.update { it.copy(scan = ScanState.Idle, errorMessage = e.message) }
            }
        }
    }

    fun errorShown() {
        _uiState.update { it.copy(errorMessage = null) }
    }

    companion object {
        val SCAN_TIMEOUT = 3.seconds
    }
}
  1. The constructor asks for the use case instead of a FakeDeviceScanner. The ViewModel now imports only from domain, and there's nothing in it to change in Lesson 08.
  2. scanForDevices(filter).collect is the only changed line in startScan. The timeout, the copies and the error handling are Lesson 05's, line for line, so their tests (A5) also test Lesson 05's reasoning.
  3. The Factory is gone from the companion object. It had to name a concrete scanner, which is exactly the knowledge this lesson moves out. SCAN_TIMEOUT stays, and the tests use it.
Known violation, kept on purpose until Lesson 08 The detail screens still look devices up with SampleDevices.find(id), and so does the UIKit list's cell provider. On Android you can see it in the import line, com.example.devicemonitor.data.SampleDevices: a UI file reaching straight into the data layer. Swift has no such clue, because Kotlin packages don't reach the Objective-C header. It works only because the simulated radio's devices are a fixed list. In Lesson 08 the detail screen becomes the connect screen, gets its own ViewModel, and this shortcut goes away. Packages make a violation visible. Only separate Gradle modules would make it impossible, and this course stays with one shared module.

A4. Wire it by hand

Somebody still has to pick the adapter and call the constructors. Android's Manual dependency injection guide calls that somebody a "dependencies container", a class "that you use to get dependencies". The place where the whole object graph is assembled is called the composition root. Ours is a single object in shared code, so both platforms get the same wiring:

shared/src/commonMain/kotlin/com/example/devicemonitor/di/AppContainer.kt (Part A only)

package com.example.devicemonitor.di

import androidx.lifecycle.ViewModelProvider
import androidx.lifecycle.viewmodel.initializer
import androidx.lifecycle.viewmodel.viewModelFactory
import com.example.devicemonitor.data.SimulatedBleScanner
import com.example.devicemonitor.domain.BleScanner
import com.example.devicemonitor.domain.ScanForDevicesUseCase
import com.example.devicemonitor.presentation.DeviceListViewModel

// The composition root, wired by hand: the one place that knows which adapter backs each
// port. Everything else receives its dependencies through its constructor.
object AppContainer {
    private val bleScanner: BleScanner by lazy { SimulatedBleScanner() }

    val deviceListViewModelFactory: ViewModelProvider.Factory = viewModelFactory {
        initializer { DeviceListViewModel(ScanForDevicesUseCase(bleScanner)) }
    }
}
  1. The only file that names SimulatedBleScanner. In Lesson 08 this line becomes "the Android radio on Android, the Swift radio on iOS". That's the whole point of the lesson: one decision, made in one place.
  2. by lazy builds the scanner on first use and then reuses it, so the whole app shares one radio. A screen that was opened twice must not scan with two radios.
  3. The factory builds a new use case per ViewModel, and the ViewModel store keeps the ViewModel (Lesson 05). The order matters, and you write it yourself: scanner, then use case, then ViewModel. Android lists that as the first cost of wiring by hand: "Dependencies have to be declared in order". In exchange, a missing dependency is a compile error. Part B gives that up.

Each track changes the line that gets the ViewModel and fixes imports for the new packages. Nothing else in the UI changes.

A5. Test the core

Now the payoff. Android's architecture guide promises that a layered app "is easier to test", and the testing guide says to prefer fakes: "Fakes don't require a mocking framework and are lightweight. They are preferred." A fake is "a test double that has a 'working' implementation of the class, but it is implemented in a way that makes it good for tests but unsuitable for production" (Use test doubles). Tests in commonTest are written once and run on every target: on the JVM with JUnit 4, and on iOS as "a test binary that is executed by Kotlin/Native's own test runner" (Test your multiplatform app).

shared/src/commonTest/kotlin/com/example/devicemonitor/fakes/FakeBleScanner.kt

package com.example.devicemonitor.fakes

import com.example.devicemonitor.domain.BleScanner
import com.example.devicemonitor.domain.Device
import com.example.devicemonitor.domain.ScanException
import kotlinx.coroutines.channels.Channel
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.emitAll
import kotlinx.coroutines.flow.flow
import kotlinx.coroutines.flow.receiveAsFlow

// Test double behind the BleScanner port. The test decides what the "radio" hears and when.
class FakeBleScanner : BleScanner {
    private val heard = Channel<Device>(Channel.UNLIMITED)
    var failure: ScanException? = null
    var scansStarted = 0
        private set

    override fun scan(): Flow<Device> = flow {
        scansStarted++
        failure?.let { throw it }
        emitAll(heard.receiveAsFlow())
    }

    fun hear(vararg devices: Device) {
        devices.forEach { heard.trySend(it) }
    }
}
  1. The test is the radio. hear(…) puts devices into a Channel, and the scan flow hands them to the collector in order. UNLIMITED means trySend never waits and never drops, so a device heard before the collector is ready isn't lost.
  2. failure makes the next scan throw, which replaces m02's "fail" filter hack. Production code no longer contains test hooks.
  3. scansStarted counts how often a scan really started. It lets a test check a rule ("don't start a second scan") instead of a state.
  4. It lives in commonTest, so it never ships in either app.

  1. Dispatchers.setMain(StandardTestDispatcher()). viewModelScope runs on Dispatchers.Main, which "will be unavailable" in a local JVM test, and Android's rule is: "The Main dispatcher should be replaced by a TestDispatcher in local unit tests" (Testing coroutines). Do it in @BeforeTest, never in a property initialiser: "If you create a TestDispatcher as a property of a test class, it won't take its scheduler from the Main dispatcher". resetMain() in @AfterTest puts it back.
  2. One clock for everything. "If the Main dispatcher has been replaced with a TestDispatcher, any newly-created TestDispatchers will automatically use the scheduler from the Main dispatcher, including the StandardTestDispatcher created by runTest". So the ViewModel's coroutines, its withTimeoutOrNull(3.seconds) and the test body all share one virtual clock.
  3. Virtual time. runTest "will automatically skip any delays". When every coroutine is waiting, the scheduler jumps the clock straight to the next timer. The 3-second timeout fires at once, and the last assertion proves it fired at exactly currentTime == 3000 ms of virtual time. The whole test takes about 10 ms of real time.
  4. uiState.test { … } (Turbine) collects the flow while the block runs. awaitItem() suspends until the next state arrives and fails the test if none comes within three seconds of wall-clock time ("a wall clock time timeout that ignores runTest's virtual clock time"). At the end of the block, any state you didn't consume fails the test, so you can't silently miss an emission.
  5. Read the first test as a story: idle, tap Scan, the radio hears obd (one row), then hears heart and obd again (two rows, not three: the use case drops the repeat), then silence until the timeout. It tests the ViewModel and the real use case together, and fakes only the port: the edge of the app.
  6. skipItems(1) skips states that this test isn't about. The second test is about the error path and errorShown(), Lesson 05's "errors are state" rule.
  7. testScheduler.runCurrent() runs every coroutine that's ready, without advancing the clock. After the first startScan the scan job is running, so the second call must be ignored. scansStarted == 1 proves it.
  8. @OptIn(ExperimentalCoroutinesApi::class): setMain, resetMain and currentTime are marked experimental, and without the opt-in each use prints a w: This declaration needs opt-in warning. That breaks the course's no-warnings rule, so we opt in once, with a comment saying why.

Part B — Koin: a container instead of hand wiring (~1.5 h)

B1. What a DI container adds

AppContainer is fine for one screen. Android lists what goes wrong as the app grows: "You have to manage AppContainer yourself, creating instances for all dependencies by hand", there's "a lot of boilerplate code", and scopes are manual: "Doing this incorrectly can lead to subtle bugs and memory leaks in your app" (Manual DI). A DI container does that bookkeeping. You declare what each type needs once, and the container works out the order. Android's teams use Hilt, which is Android-only. Koin runs on every KMP target, so the team's shared core uses it.

Koin has three kinds of definitions:

DefinitionGives youOurs
single"One instance, kept for the lifetime of the Koin container"the BleScanner: one radio for the app
factory"A new instance each time it is requested"ScanForDevicesUseCase: cheap, and stateless between scans
viewModela new instance per request, kept by the platform's ViewModelStoreDeviceListViewModel

Quotes: Koin definitions, Koin ViewModel.

Injection versus lookup. Android contrasts DI with a service locator: "with the service locator pattern, classes have control and ask for objects to be injected; with dependency injection, the app has control and proactively injects the required objects". Lookups also hide what a class needs: "Dependencies are encoded in the class implementation, not in the API surface" (DI in Android). Koin can do both. KoinComponent with get() is a lookup, and Koin's docs say to keep it "at the edges", for classes "Koin does not create" (KoinComponent). The course's rule: constructors everywhere, lookups only at the platform boundary. Your ViewModels, use cases and adapters never import Koin.

package com.example.devicemonitor

import androidx.lifecycle.ViewModel
import androidx.lifecycle.ViewModelProvider
import androidx.lifecycle.ViewModelStore
import androidx.lifecycle.viewmodel.CreationExtras
import kotlinx.cinterop.BetaInteropApi
import kotlinx.cinterop.ObjCClass
import kotlinx.cinterop.getOriginalKotlinClass
import org.koin.core.component.KoinComponent
import kotlin.reflect.KClass

// Swift can't pass a KClass, only its Objective-C class. This turns it back into the
// KClass that ViewModelProvider needs. Adapted from Android's KMP ViewModel guide.
@OptIn(BetaInteropApi::class)
@Throws(IllegalArgumentException::class)
fun ViewModelStore.resolveViewModel(modelClass: ObjCClass): ViewModel {
    @Suppress("UNCHECKED_CAST")
    val vmClass = getOriginalKotlinClass(modelClass) as? KClass<ViewModel>
    require(vmClass != null) { "The modelClass parameter must be a ViewModel type." }
    return ViewModelProvider.create(this, KoinViewModelFactory)[vmClass]
}

// The store calls this the first time it needs a ViewModel; Koin builds it from appModule.
private object KoinViewModelFactory : ViewModelProvider.Factory, KoinComponent {
    override fun <T : ViewModel> create(modelClass: KClass<T>, extras: CreationExtras): T =
        getKoin().get(modelClass)
}
  1. The factory parameter is gone. Swift no longer chooses how a ViewModel is built. It asks for a class, and the composition root decides.
  2. KoinViewModelFactory is a KoinComponent: a lookup, at the edge, in a class Koin doesn't create (B1's rule). The store calls create only the first time it needs that ViewModel, so the store still owns its lifetime, and ViewModelOwner's clear() still cancels its scope.
  3. Why not Koin's own KoinViewModelFactory? It exists, and koinViewModel() uses it, but it needs a Koin Scope to resolve from, and Koin's Compose code reaches the root scope through scopeRegistry, which is @KoinInternalApi (the same kind of trap as ViewModelStore.put in Lesson 05). Ours needs no scope: getKoin().get(modelClass) is public API and four lines long.

Both iOS tracks · iosApp/iosApp/ViewModelOwner.swift

import Shared

// iOS has no ViewModelStoreOwner, so this class plays that role. Keep it in a view's
// @State (or a view controller's property). When it is deinitialised, clearing the store
// cancels every viewModelScope in it and calls onCleared().
final class ViewModelOwner {
    private let store = ViewModelStore()

    // Returns the store's instance of VM; Koin creates it on first use.
    func viewModel<VM: ViewModel>() -> VM {
        do {
            return try store.resolveViewModel(modelClass: VM.self) as! VM
        } catch {
            fatalError("Couldn't create \(VM.self): \(error)")
        }
    }

    deinit {
        store.clear()
    }
}

UIKit track · DeviceListViewController.swift: one line

Swift infers VM from the declared type, the same trick as koinViewModel(). With AppContainer deleted, run a search. No file outside di/ and data/ mentions SimulatedBleScanner. Koin is imported in exactly three kinds of place: di/ (main and test), ViewModelResolver.kt, and on Android the one screen file that asks for the ViewModel (DeviceListScreen.kt or DeviceListFragment.kt). Those are the edges.

B5. Test the graph, because the compiler no longer does

Here is the price of a container. With AppContainer, forgetting a dependency was a compile error. With Koin, the module is a list of recipes that Koin reads at run time. We deleted the single<BleScanner> line, and both apps compiled without a warning. The Android app then crashed the moment the list screen appeared:

FATAL EXCEPTION: main
…InstanceCreationException: Could not create instance for '[Factory: '…presentation.DeviceListViewModel']'
Caused by: …InstanceCreationException: Could not create instance for '[Factory: '…domain.ScanForDevicesUseCase']'
Caused by: …NoDefinitionFoundException: No definition found for type '…domain.BleScanner' on scope '['_root_']'.

Read the chain from the bottom up: the missing piece, then each thing that needed it. One test asks the graph for every ViewModel, so that failure shows up in allTests instead of on a user's phone:

shared/src/commonTest/kotlin/com/example/devicemonitor/di/AppModuleTest.kt

package com.example.devicemonitor.di

import com.example.devicemonitor.presentation.DeviceListViewModel
import org.koin.dsl.koinApplication
import kotlin.test.Test
import kotlin.test.assertNotNull

class AppModuleTest {
    // Koin checks the graph only when something asks for an instance, at run time. This
    // test asks for every screen's ViewModel, so a missing binding fails here, not in the app.
    @Test
    fun buildsEveryViewModel() {
        val koin = koinApplication { modules(appModule) }.koin

        assertNotNull(koin.get<DeviceListViewModel>())
    }
}
  1. koinApplication { … } builds a private Koin instance, unlike startKoin, which sets the global one. Tests don't leak into each other, and nothing needs stopping.
  2. Creating a ViewModel here is safe without setMain: nothing touches viewModelScope until startScan.
  3. Keep it current. Every new screen adds one get<…ViewModel>() line here. With the binding deleted, this test fails with the same three-line chain as the crash above.

The other tests didn't change, and they don't use Koin at all. They call constructors with fakes, exactly as in Part A. That's the point of constructor injection: the container is for the app, not for the tests.

B6. What actually happens

Built from the brief below, on the default tracks, with Koin 4.2.2. allTests passed 6 of 6 tests on the JVM and 6 of 6 on the iOS simulator. Both apps behave exactly like m02. On Android, with temporary log lines, one ViewModel instance survived a rotation during a scan, found five devices about 0.3 s apart, finished at the timeout, and was cleared on Back. Retrieval check: Part B

You delete a binding from appModule. When do you find out?

Koin resolves at run time. That's why AppModuleTest exists: it moves the failure from the user's phone into allTests.

Why does Swift call doInitKoin() and not initKoin()?

In Objective-C, init… means an initializer. The Kotlin compiler avoids the clash by adding do, and you can see it in Shared.h.

Why is appModule declared internal?

A public Module drags Koin's classes into the exported header (1,032 extra lines). Tests in the same Gradle module can still see internal declarations.

Where may a class use KoinComponent and get() in this course?

Classes that Koin creates get their dependencies through constructors. Lookups are for entry points that Koin doesn't create, like our iOS ViewModel factory.

Mixed review (interleaved)

Koin now builds the ViewModel. On iOS, what still clears it? (Lesson 05)

Koin's viewModel definition creates a new instance per request. Keeping and clearing it is the store's job, and on iOS the owner's deinit calls store.clear().

In Lesson 08, which source set will hold the Android radio adapter? (KMP anatomy lesson)

The course puts Android adapters in the shared module's androidMain: it can see Android APIs and the port, and it keeps radio code out of the screens. The port stays in commonMain.
