1. What's on a connected device

Lesson 13 drew a peripheral's data as a tree: services, each holding characteristics, each with a UUID, one value and a set of properties. A connected phone doesn't know that tree yet. It has to ask: Android's guide says "The first thing to do once you connect to the GATT Server on the BLE device is to perform service discovery" (Transfer BLE data). Only then can it read: "Once your app has connected to a GATT server and discovered services, it can read and write attributes, where supported."

The two platforms ask differently. Android's discoverServices() "Discovers services offered by a remote device as well as their characteristics and descriptors" in one request (BluetoothGatt, Android's source). CoreBluetooth splits it in two: discoverServices(_:) finds the services, and then discoverCharacteristics(_:for:) "Discovers the specified characteristics of a service", one service per call (Apple). Each answer comes back later, in a callback. So on iOS the second discovery can only start inside the answer to the first: two nested asynchronous discoveries.

  • Android
  • iOS
  1. Discovery is per connection. The tree the phone learns belongs to this link. In this app the detail screen discovers right after "Status: connected", and forgets the tree when the link ends.
  2. Properties decide what a central may do (Lesson 13's table): read, write, notify, indicate. Apple: "Not all characteristics have a readable value. You can determine whether a characteristic’s value is readable by accessing the relevant properties of the CBCharacteristicProperties enumeration" (readValue(for:)). The app checks before it reads.
  3. A read is one more request with a callback: Android's readCharacteristic() "is an asynchronous call. The results are sent to the BluetoothGattCallback function onCharacteristicRead()"; on iOS, readValue(for:) answers in the peripheral delegate's peripheral(_:didUpdateValueFor:error:). What comes back is bytes.

2. The app's words, and the port grows

First the tree, in the app core's terms:

  1. Two meanings of "service". In the hexagon, a service is a class in the app core that implements an inbound port (SessionService). In Bluetooth, a service is a group of characteristics on the device. The model is named DeviceService so the two never meet in one name.
  2. serviceUuid travels with each characteristic, because a characteristic's UUID is only unique inside its service: to read it, both adapters first find the service, then the characteristic in it.
  3. The same bits on both platforms. Android's BluetoothGattCharacteristic.PROPERTY_READ is 0x02, PROPERTY_WRITE_NO_RESPONSE 0x04, PROPERTY_WRITE 0x08, PROPERTY_NOTIFY 0x10, PROPERTY_INDICATE 0x20 (Android's source), and iOS's CBCharacteristicProperties uses the same values (CBCharacteristic.h). So each adapter hands its platform's number to propertiesOf, and the rule that turns bits into properties is written and tested once, in the app core. bits and it.bit != 0 is TypeScript's (bits & bit) !== 0: Kotlin spells bitwise AND as the infix function and.
  4. A List, not a Set: the order of the bit field, so every screen shows "read · notify" in the same order. A Kotlin list reaches Swift as an array; a set would arrive as a Swift Set, with no order.

UUIDs need one rule too. Android reports every UUID in its 128-bit form, in lower case. CoreBluetooth can report a standard UUID in its short form: a CBUUID made from "2A19" has the uuidString "2A19", and one made from the full form keeps the full form, yet the two compare equal (we checked with a Swift snippet on macOS). Lesson 13 explained the short forms: they stand for a full UUID built on the Bluetooth base UUID. The app core picks one spelling:

The outbound port grows by two requests on the link that connect holds open. It keeps Lesson 14's shape: connect is still the only way to open and close the link.

  1. suspend, not a Flow: a discovery or a read is one request with one answer, the shape of a suspend fun (Lesson 01). Lesson 16's notifications are a stream, and will be a Flow.
  2. The port returns bytes. What they mean is the app's business, not the radio's: the adapters copy them and the app core decodes them (section 3).
  3. "One at a time" is part of the contract, written where every adapter author reads it. Section 4 shows who keeps it, and section 5 why Android needs it.
  4. No new exception. ConnectionException's comment now covers "a request on it that failed": the message is still for the user, and the ViewModel still catches one type.

The inbound port gets the plan's two calls, in the app's terms: the services, and a value already decoded.

3. Bytes, decoded in the app core

A characteristic's value is a short array of bytes, and the device doesn't say what they mean. The format of each standard characteristic is published by the Bluetooth SIG, in the GATT Specification Supplement (GSS; the SIG also publishes it as YAML files in its public repository). The app knows four of them:

Characteristic (UUID)The GSS saysThe app shows
Battery Level (0x2A19)uint8, a percentage: "Allowed range is 0 to 100 … All other values are reserved for future use."82 %
Temperature (0x2A6E)sint16, "degrees Celsius with a resolution of 0.01 degrees Celsius"; "A value of 0x8000 represents 'value is not known'."21.50 °C
Manufacturer Name String (0x2A29), Model Number String (0x2A24)utf8s, "UTF-8 string"the text

Anything else is shown as its bytes in hex: 01 02 03 04, the "Received data" line of the course plan's sketch. The names and UUIDs are the SIG's assigned numbers.

  1. A Kotlin Byte is signed. It holds −128 to 127, and the device's byte 0xC8 (200) arrives as −56. toInt() keeps the sign; and 0xFF keeps only the low 8 bits, which gives back 200. TypeScript's Uint8Array hides this, and Swift's Data is made of unsigned UInt8, so it's the trap a Kotlin decoder walks into. The test aReservedBatteryLevelIsShownInHex feeds 0xC8: without and 0xFF the decoder printed "-56 %" and the test failed (we tried).
  2. A private function returns null when the bytes don't fit: the wrong length, or a reserved value. ?: hex(bytes) then shows the bytes as they came, so a surprising device shows its data instead of crashing the screen.
  3. decodeToString() decodes UTF-8 in common Kotlin, on every platform.
  4. Why the app core, and why not the adapters? The adapters' job is to hand over the bytes the radio received. What 0x52 means for a battery is the same on both platforms, so it's written once, in a pure function, and tested once, on the JVM and the iOS simulator (section 10). That's the course plan's refactor rule: no feature logic duplicated across platforms.

The temperature shows the other two things every BLE decoder deals with: byte order and sign.

  • Outbound (the bytes as the adapter hands them over)
  • App core (the decoding)
  1. Little endian. GSS section 2.4: "All fields in a characteristic or descriptor are little endian unless otherwise stated", and fields start at "the Least Significant Octet (LSO, octet 0) of the value". So bytes[0] is the low byte. The simulated device's 66 08 is 0x0866, 2150, so 21.50 °C.
  2. The sign lives in the high byte. bytes[1].toInt() without and 0xFF keeps it: 0xFD becomes −3, and (-3 shl 8) or 243 is −525. shl and or are Kotlin's << and |. 0x8000 arrives as −32768, which the code writes -0x8000.
  3. Formatting by hand. Common Kotlin has no String.format, so the decoder prints whole degrees and hundredths itself. The sign is taken first: −25 hundredths has 0 whole degrees, and -25 / 100 is 0, so printing the quotient alone would lose it. negativeTemperaturesKeepTheirSign checks "-0.25 °C".

4. The session service keeps the rules

SessionService already owns the connection. On the open link it adds four rules, each tested in section 10:

  1. Only on a connected link. connectedDevice() reads the state the service already owns; before "connected", nothing is sent.
  2. Only what can be read. The screen hides Read for a characteristic without the Read property, but that's presentation; the rule lives where every caller passes (Lesson 13's argument again). Android's own readCharacteristic also returns false for one (its source checks PROPERTY_READ first), but the app's message is clearer than "couldn't send".
  3. One request at a time. A Mutex (from kotlinx.coroutines) is a lock for coroutines: withLock suspends, without blocking a thread, until the previous holder is done. Two quick taps on two Read buttons become two reads, one after the other. The test sendsOneRequestAtATime fails without it (we removed it to check).
  4. A failed discovery ends the connection. This screen is useless without the tree, so the service disconnects and says why; Connect is then the retry. The message starts with what the app was doing and ends with the adapter's reason.
  5. Decoding is the last step, after the lock is released: the decoder is a pure function and holds up no one.

5. Android: one discovery, one request at a time

Android's guide: "The service needs to override the onServicesDiscovered() function in the BluetoothGattCallback. This function is called when the device reports on its available services. Once the services have been discovered, the service can call getServices() to get the reported data" (Transfer BLE data). The callback object is the one Lesson 14 wrote for the connection; it gets three more methods.

  1. A CompletableDeferred is a Deferred (Lesson 01's async result) that someone else completes: the request suspends in await(), and the callback, on a background thread, calls complete. It plays the role of a JavaScript Promise whose resolve you keep. It is safe to complete from any thread.
  2. Two onCharacteristicReads. API 33 added one that carries the value and deprecated the old one, which leaves the value in the characteristic object (api-versions.xml: the old one deprecated="33", the new one since="33"). The app runs from API 26, so it overrides both. In Android's source, the new one's default body calls the old one, and from API 33 the system calls only the new one; our override of the new one doesn't call it, so each read completes once. The old override carries @Deprecated and @Suppress("DEPRECATION"), so the build stays free of warnings.
  3. @Volatile: the fields are written on a background thread (the callbacks) and read on the main thread (the requests). @Volatile makes each write visible to the other thread at once.
  1. Why one at a time on Android. BluetoothGatt.readCharacteristic starts with if (mDeviceBusy) return false; mDeviceBusy = true;, and the answer's callback clears it (Android's source, API 35). A second read sent before the first one's answer is simply refused. The guide doesn't mention it, and neither does the method's return value beyond "true, if the read operation was initiated successfully". The service's Mutex (section 4) is what keeps our requests apart, and one answer slot is enough.
  2. answer is set before send(), so a callback that comes back fast still finds it.
  3. The services come from gatt.services, as the guide says, once the callback has reported GATT_SUCCESS. toDeviceService() maps each one with fullUuid(uuid.toString()) and propertiesOf(it.properties).
  4. Finding the characteristic to read: getService(uuid) then getCharacteristic(uuid), with UUID.fromString on the full form. If a device has two instances of the same service, "the first instance of the service is returned" (BluetoothGatt.getService's documentation); the app reads that one.

After close() no callback comes, so a read that was waiting would wait for ever. completeExceptionally ends it with a message instead, whatever closed the link: a drop, Disconnect, or leaving the screen.

Gotcha · the emulator can't show any of this with a real device As Lessons 13 and 14 found, the emulator's simulated beacons never accept a connection, so a real discovery and a real read need your Android phone and LightBlue: they're on the device-check list. On the emulator, the real adapter still shows what it did in Lesson 14 (we ran it: "didn't answer within 10 seconds", then cancelOpen(), close(), unregisterApp()), and the simulated adapters show the screen (section 9).

6. iOS: a new split, and two nested discoveries

In Lesson 14, the Swift class implemented BleConnection and got its Flow from Kotlin. Now the port also has two suspend funs, and implementing those in Swift has two problems, both of which we hit:

  • A Swift error isn't a ConnectionException. We made a Swift class implement a Kotlin suspend fun and throw. Kotlin caught a kotlin.native.internal.ObjCErrorException carrying the Swift message. SessionService and the ViewModel catch only ConnectionException, so a failed read would escape as an unhandled exception.
  • Calling back into Kotlin crosses actors. The fix we tried first, a Swift __read that awaits a Kotlin suspend fun which throws ConnectionException, works in a plain class: the exception crosses Swift and comes back to Kotlin as itself. In IosBleConnection, which is @MainActor, Swift 6 refused to compile it: "sending 'characteristic' risks causing data races". Swift treats the Kotlin suspend fun as running outside the main actor, and the Kotlin objects passed to it aren't Sendable.

So the halves swap roles. The Kotlin half in iosMain becomes the class that implements the port, and the Swift half only does the radio work, through plain calls that all run on the main thread:

  1. connect is Lesson 14's connectFlow, moved into the class. ConnectFlow.kt is gone; IosLink and LinkFeed live here now.
  2. suspendCancellableCoroutine hands its block a continuation (the rest of this coroutine, waiting) and suspends until someone resumes it. The block passes it to Swift wrapped in a reply object, and returns at once.
  3. Who calls what. SessionService calls the port from the ViewModel's coroutines, on the main thread, so link.discover and link.read reach the @MainActor Swift class on the main thread. CoreBluetooth answers on the main queue (queue: nil), so Swift resumes the reply there too.
  1. Kotlin makes the exception, so a failed read reaches the app core as a ConnectionException, like every other failure.
  2. isActive is false once the continuation has been resumed or cancelled. Resuming twice would throw, and a late answer for a coroutine that's gone must be ignored.
  3. The bytes cross as NSData, which Swift sees as Data, so the Swift half passes characteristic.value as it is. usePinned holds the Kotlin array still in memory while memcpy copies into it: the one place in this lesson where Kotlin touches raw memory. Lesson 17's log store is where the course uses Apple's APIs from Kotlin in earnest.
  4. Still an outbound adapter, in two halves: ADR 0001 puts outbound adapters in Kotlin and in Swift, and this one is both. Like IosRadio, IosLink is not a port: the app core never sees it.

The Swift half starts the first discovery, and its delegate callback starts the second:

  1. nil means "all": for discoverCharacteristics, "If the characteristicUUIDs parameter is nil, this method returns all characteristics of the service"; CBPeripheral.h says the same of discoverServices:. Apple's discoverServices(_:) page adds that with a list of UUIDs "the peripheral returns only the services of the peripheral that match": a production app that knows its device asks for just those.
  2. The answers come back as properties. didDiscoverServices carries only an error; the services are in peripheral.services, and each service's characteristics in service.characteristics, which is nil until its own discovery has answered (both are nullable in the headers).
  3. servicesLeft counts the second round down, one didDiscoverCharacteristicsFor per service. Only when it reaches 0 does the reply get the whole tree; the first error ends the discovery with a message.
  4. Kotlin's helpers from Swift: top-level functions appear on a class named after their file, so fullUuid in Uuids.kt is UuidsKt.fullUuid(uuid:) (Lesson 05).
  1. The value is a property too: "If the peripheral successfully reads the value of the characteristic, you can access it through the characteristic’s value property" (readValue(for:)).
  2. The same callback serves notifications. Apple: "A peripheral also invokes this method to notify your app of a change to the value of the characteristic for which the app previously enabled notifications" (peripheral(_:didUpdateValueFor:error:)). That's why the adapter checks that the characteristic is the one it asked to read: in Lesson 16 the others will be notifications.
  3. close() fails what's waiting, as Android's awaitClose does: a discovery or read in progress gets "The link closed before the device answered.", and the peripheral's delegate is set back to nil.

7. The trap: the peripheral's delegate

Lesson 13's trap was the central manager's delegate: a weak reference, so an adapter that nobody kept alive heard nothing. A connected peripheral has a delegate of its own, separate from the manager's, and it is where every answer of this lesson arrives:

  • iOS (CoreBluetooth's objects)
  • Outbound adapter (both halves)
Gotcha · CBPeripheralDelegate: silence, not an error Forget to set it, and discoverServices(nil) is still sent and the peripheral still answers, but there is no one to tell: the screen sits on "Discovering services…" for good. It's weak: @property(weak, nonatomic, nullable) id<CBPeripheralDelegate> delegate (CBPeripheral.h), so a delegate object nobody else holds, such as a helper created in a function, is released and the answers stop. There is only one: a second object that sets itself as the delegate (a view controller that "just wants the value") silently takes every answer away from the adapter. The compiler won't help: Apple's page says the protocol "doesn’t have any required methods", so leaving a method out compiles. A misspelt one only gets a warning: we wrote didDiscoverService without the s and swiftc said "instance method … nearly matches optional requirement". Here the adapter sets itself as the delegate the moment it has the peripheral, Koin keeps it alive through LinkedBleConnection, and close() sets the delegate back to nil. Whether a missing delegate looks exactly like this on a phone is on the device-check list.
Gotcha · services and characteristics are empty until discovered (iOS) A peripheral's services holds only the services discovered so far (CBPeripheral.h: "A list of CBService objects that have been discovered on the peripheral"), and each service's characteristics only what its own discovery has found. Code that reads peripheral.services right after connecting, or reads a characteristic before the second round is complete, finds nothing. Android's single discovery hides that step; iOS makes you wait for both rounds, which is why the adapter counts.

8. The detail screen

The ViewModel decides when to discover and where each answer lands. The UI state grows by three fields: discovering, services (empty while not connected) and values, what to show under each characteristic that was read.

  1. Discovering on "connected" is this screen's choice, not a rule of the app, so it's in the ViewModel; Lesson 13's scan timeout lives there for the same reason. discover() sets discovering, calls session.services(), stores the list, and turns a failure into errorMessage: the "Connection failed" alert, which fits, because the service has just ended the connection.
  2. A rotation doesn't discover again. The ViewModel survives it (Lesson 14), its collector keeps running, and Connected isn't emitted a second time: the list and the values read so far are still there in landscape (we checked on the API 36 emulator, Compose and XML).
  3. A failed read stays next to its characteristic instead of opening an alert: the connection is fine, and the user sees which characteristic refused. The Map uses Characteristic as its key; a data class's equals and hashCode come from its properties, so equal characteristics find the same entry.
  4. The guard on Connected drops an answer that arrives after Disconnect, so a stale value never appears on the next connection.

Every track shows the same thing under the Connect button: "Discovering services…" with a spinner, then one block per service with its full UUID, and per characteristic its UUID, its properties ("read · notify"), a Read button only if it has the Read property, and the answer. The list is a handful of rows, so each track draws it in a scrolling container rather than a lazy list.

10. Tests

The decoder is a pure function, so its tests need no fake and no coroutine: bytes in, text out.

The fake radio learns the new requests. The test decides what the device has and holds, and the fake records what was sent:

  1. Overlap needs time. Without the delay(100) in the fake, each read would finish before the second async even started, and the test couldn't fail. Retrieval checks

Answer from memory, without scrolling up.

A connected device has four services. How many discovery requests does each platform's adapter send to learn every characteristic?

Android's discoverServices() discovers the services "as well as their characteristics and descriptors". On iOS, discoverCharacteristics(_:for:) takes one service, and can only start once didDiscoverServices has answered: two nested discoveries.

Why does the decoder write bytes[0].toInt() and 0xFF for Battery Level?

Byte is −128..127. toInt() keeps the sign; masking with 0xFF keeps only the 8 bits the device sent. The test with 0xC8 fails without it.

A Temperature characteristic (sint16, hundredths of a degree) sends the bytes 66 08. What does the app show?

GSS: "All fields in a characteristic or descriptor are little endian unless otherwise stated." Octet 0 is the low byte: 0x0866 = 2150, so 21.50 °C.

On an iPhone, the screen stays on "Discovering services…" for ever, with no error. What's the likeliest cause?

The peripheral's delegate is a separate, weak property, and the protocol has no required methods. A device with no services would answer with an empty list, and nothing in the adapter times out.

Why does SessionService send one request at a time over the link?

readCharacteristic returns false while mDeviceBusy is set (Android's source). The Mutex in the service keeps the contract for every adapter, and sendsOneRequestAtATime checks it.

Mixed review (interleaved)

package com.example.devicemonitor.core

// A service on a connected device, in the app's terms: a UUID and the characteristics it groups.
// Not to be confused with the app core's services, such as SessionService: this one is the
// device's.
data class DeviceService(val uuid: String, val characteristics: List<Characteristic>)

// One value on the device. serviceUuid says which service it belongs to, because two services
// can each have a characteristic with the same UUID. Every UUID is in the full form (fullUuid).
data class Characteristic(
    val serviceUuid: String,
    val uuid: String,
    val properties: List<CharacteristicProperty>,
)

// What a central may do with a characteristic's value. bit is the property's bit in the
// Characteristic Properties field, the same number on Android and iOS.
enum class CharacteristicProperty(val bit: Int, val label: String) {
    Read(0x02, "read"),
    WriteWithoutResponse(0x04, "write without response"),
    Write(0x08, "write"),
    Notify(0x10, "notify"),
    Indicate(0x20, "indicate"),
}

// The properties set in bits, the Characteristic Properties field both platforms report, in
// the field's order. Bits the app has no use for (broadcast, signed writes, …) are left out.
fun propertiesOf(bits: Int): List<CharacteristicProperty> =
    CharacteristicProperty.entries.filter { bits and it.bit != 0 }

package com.example.devicemonitor.core

// The Bluetooth base UUID, after its first 8 hex digits: a 16- or 32-bit UUID stands for the full
// UUID that puts it in front of this.
private const val BASE_UUID_TAIL = "-0000-1000-8000-00805F9B34FB"

// A UUID in the one form the app core uses: all 128 bits, upper case. Android reports the full
// form in lower case ("0000180f-0000-1000-8000-00805f9b34fb"); iOS can report a standard UUID in
// its short form ("180F"). Both become "0000180F-0000-1000-8000-00805F9B34FB".
fun fullUuid(uuid: String): String {
    val upper = uuid.uppercase()
    return when (upper.length) {
        4 -> "0000$upper$BASE_UUID_TAIL"
        8 -> "$upper$BASE_UUID_TAIL"
        else -> upper
    }
}
shared/src/commonMain/kotlin/com/example/devicemonitor/core/ValueDecoder.kt 
package com.example.devicemonitor.core

import kotlin.math.abs

// Turns a characteristic's bytes into text for the user. The app knows the format of a few
// standard characteristics, from the Bluetooth SIG's GATT Specification Supplement; any other
// value is shown as its bytes in hex. Bytes that don't fit the format are shown in hex too.
object ValueDecoder {
    const val BATTERY_LEVEL = "00002A19-0000-1000-8000-00805F9B34FB"
    const val TEMPERATURE = "00002A6E-0000-1000-8000-00805F9B34FB"
    const val MODEL_NUMBER = "00002A24-0000-1000-8000-00805F9B34FB"
    const val MANUFACTURER_NAME = "00002A29-0000-1000-8000-00805F9B34FB"

    fun decode(characteristicUuid: String, bytes: ByteArray): String = when (characteristicUuid) {
        BATTERY_LEVEL -> batteryLevel(bytes)
        TEMPERATURE -> temperature(bytes)
        MODEL_NUMBER, MANUFACTURER_NAME -> bytes.decodeToString()
        else -> hex(bytes)
    } ?: hex(bytes)

    // "01 02 03 04". A Kotlin Byte is signed (-128..127): and 0xFF gives the 0..255 the device sent.
    fun hex(bytes: ByteArray): String =
        bytes.joinToString(" ") { (it.toInt() and 0xFF).toString(16).uppercase().padStart(2, '0') }

    // uint8, a percentage from 0 to 100; other values are reserved.
    private fun batteryLevel(bytes: ByteArray): String? {
        if (bytes.size != 1) return null
        val percent = bytes[0].toInt() and 0xFF
        return if (percent <= 100) "$percent %" else null
    }

    // sint16, little endian, in hundredths of a degree Celsius; 0x8000 means "not known".
    private fun temperature(bytes: ByteArray): String? {
        if (bytes.size != 2) return null
        val low = bytes[0].toInt() and 0xFF
        val high = bytes[1].toInt() // keeps its sign: the high byte carries it
        val hundredths = (high shl 8) or low
        if (hundredths == -0x8000) return "not known"
        val sign = if (hundredths < 0) "-" else ""
        val magnitude = abs(hundredths)
        return "$sign${magnitude / 100}.${(magnitude % 100).toString().padStart(2, '0')} °C"
    }
}

    fun connect(device: Device): Flow<ConnectionState>

    // The characteristic's value, as the bytes the device sent. Only after discoverServices().

    // no permission, another connection open, no answer, or the link failed or dropped.

    fun disconnect()

    // not connected, or the discovery failed, which also ends the connection.

    // Reads the characteristic and returns its value as text for the user. Throws
    // ConnectionException: not connected, a characteristic without the Read property, or the
    // read failed.

package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.DeviceSession
import com.example.devicemonitor.core.outbound.BleConnection
import com.example.devicemonitor.core.outbound.PermissionChecker
import kotlinx.coroutines.Job
import kotlinx.coroutines.coroutineScope
import kotlinx.coroutines.delay
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.launch
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock
import kotlin.time.Duration.Companion.seconds

// Service: the app's connection rules. Connect only with the Bluetooth permission and to one
// device at a time, and give up on a device that doesn't answer within CONNECT_TIMEOUT. It owns
// the connection state that the screens show. On the open link, it sends one request at a time,
// reads only what can be read, and decodes what it reads.
class SessionService(
    private val connection: BleConnection,
    private val permissions: PermissionChecker,
) : DeviceSession {
    private val state = MutableStateFlow<ConnectionState>(ConnectionState.Disconnected)
    override val connectionState: StateFlow<ConnectionState> = state.asStateFlow()
    private var link: Job? = null
    private val requests = Mutex() // the port takes one request at a time

    override suspend fun connect(device: Device) {
        if (permissions.check(Permission.Bluetooth) != PermissionStatus.Granted) {
            throw ConnectionException("Connecting needs the Bluetooth permission.")
        }
        if (state.value != ConnectionState.Disconnected) {
            throw ConnectionException("Another connection is open. Disconnect it first.")
        }
        state.value = ConnectionState.Connecting(device)
        try {
            coroutineScope {
                link = launch {
                    // iOS never gives up on a connection attempt, so the app does.
                    val giveUp = launch {
                        delay(CONNECT_TIMEOUT)
                        throw ConnectionException("${device.name} didn't answer within 10 seconds.")
                    }
                    connection.connect(device).collect { linkState ->
                        state.value = linkState
                        if (linkState is ConnectionState.Connected) giveUp.cancel()
                    }
                }
            }
        } finally {
            link = null
            state.value = ConnectionState.Disconnected
        }
    }

    // Cancelling the link ends its collection, and the adapter closes the radio's link.
    override fun disconnect() {
        link?.cancel()
    }

    // A device whose services can't be discovered is of no use to the app: end the connection.
    override suspend fun services(): List<DeviceService> {
        val device = connectedDevice()
        return try {
            requests.withLock { connection.discoverServices() }
        } catch (e: ConnectionException) {
            disconnect()
            throw ConnectionException("Couldn't discover the services of ${device.name}. ${e.message}")
        }
    }

    override suspend fun read(characteristic: Characteristic): String {
        connectedDevice()
        if (CharacteristicProperty.Read !in characteristic.properties) {
            throw ConnectionException("This characteristic can't be read: it has no Read property.")
        }
        val bytes = requests.withLock { connection.read(characteristic) }
        return ValueDecoder.decode(characteristic.uuid, bytes)
    }

    private fun connectedDevice(): Device =
        (state.value as? ConnectionState.Connected)?.device
            ?: throw ConnectionException("Connect to the device first.")

    companion object {
        val CONNECT_TIMEOUT = 10.seconds
    }
}

class DeviceDetailViewModel(private val session: DeviceSession) : ViewModel() {
    private val _uiState = MutableStateFlow(DeviceDetailUiState(connection = session.connectionState.value))
    val uiState: StateFlow<DeviceDetailUiState> = _uiState.asStateFlow()

    private var connectJob: Job? = null

    init {
        viewModelScope.launch {
            session.connectionState.collect { connection ->
                _uiState.update { it.copy(connection = connection) }
                when (connection) {
                    // This screen lists the services as soon as the link is up.
                    is ConnectionState.Connected -> discover()
                    ConnectionState.Disconnected -> _uiState.update { it.copy(services = emptyList(), values = emptyMap()) }
                    is ConnectionState.Connecting -> Unit
                }
            }
        }
    }

    // The connection runs in viewModelScope, so it lasts as long as this ViewModel: through a
    // rotation, and until the screen is gone for good, when clearing the ViewModel cancels it.
    fun connect(device: Device) {
        if (connectJob?.isActive == true) return
        connectJob = viewModelScope.launch {
            try {
                session.connect(device)
            } catch (e: ConnectionException) {
                _uiState.update { it.copy(errorMessage = e.message) }
            }
        }
    }

    fun disconnect() {
        session.disconnect()
    }

    // The answer lands under the characteristic: its value, or why the read failed. A read that
    // ends after the link has gone shows nothing.
    fun read(characteristic: Characteristic) {
        viewModelScope.launch {
            val text = try {
                session.read(characteristic)
            } catch (e: ConnectionException) {
                "Read failed: ${e.message}"
            }
            _uiState.update {
                if (it.connection is ConnectionState.Connected) it.copy(values = it.values + (characteristic to text)) else it
            }
        }
    }

    fun errorShown() {
        _uiState.update { it.copy(errorMessage = null) }
    }

    private fun discover() {
        viewModelScope.launch {
            _uiState.update { it.copy(discovering = true) }
            try {
                val services = session.services()
                _uiState.update { if (it.connection is ConnectionState.Connected) it.copy(services = services) else it }
            } catch (e: ConnectionException) {
                // A message already waiting (from connect(), when the link dropped) stays.
                _uiState.update { it.copy(errorMessage = it.errorMessage ?: e.message) }
            } finally {
                _uiState.update { it.copy(discovering = false) }
            }
        }
    }
}

// Outbound adapter: a GATT connection over the phone's Bluetooth LE radio, behind the
// BleConnection port. BluetoothGatt reports to a callback object; callbackFlow turns the link's
// calls into a Flow, and closes the GATT client when the collector cancels. Each request on the
// open link waits for its own callback in a CompletableDeferred.
class AndroidBleConnection(private val context: Context) : BleConnection {
    private val adapter: BluetoothAdapter? =
        context.getSystemService(BluetoothManager::class.java)?.adapter

    // The open link, from the moment it's up until it closes. Callbacks run on a background thread.
    @Volatile private var gatt: BluetoothGatt? = null

    // The request waiting for its callback. The port takes one request at a time, so one is enough.
    @Volatile private var answer: CompletableDeferred<Answer>? = null

    private class Answer(val status: Int, val value: ByteArray)

    // SessionService checks the permission before every connection, so lint's check is suppressed.
    @SuppressLint("MissingPermission")
    override fun connect(device: Device): Flow<ConnectionState> = callbackFlow {
        val adapter = adapter
        if (adapter == null || !adapter.isEnabled) {
            throw ConnectionException("Bluetooth is off. Turn it on, then connect again.")
        }
        // Called on a background thread. trySend and close are safe from any thread.
        val callback = object : BluetoothGattCallback() {
            private var linked = false

            override fun onConnectionStateChange(gatt: BluetoothGatt, status: Int, newState: Int) {
                when {
                    status == BluetoothGatt.GATT_SUCCESS && newState == BluetoothProfile.STATE_CONNECTED -> {
                        linked = true
                        this@AndroidBleConnection.gatt = gatt
                        trySend(ConnectionState.Connected(device))
                    }
                    linked -> close(ConnectionException("The link to ${device.name} was lost (Android status $status)."))
                    else -> close(ConnectionException("The connection failed (Android status $status)."))
                }
            }

            // Discovery found every service, characteristic and descriptor, or failed.
            override fun onServicesDiscovered(gatt: BluetoothGatt, status: Int) {
                answer?.complete(Answer(status, ByteArray(0)))
            }

            // Android 13 (API 33) and later call this one, with the value.
            override fun onCharacteristicRead(
                gatt: BluetoothGatt,
                characteristic: BluetoothGattCharacteristic,
                value: ByteArray,
                status: Int,
            ) {
                answer?.complete(Answer(status, value))
            }

            // Android 12 and earlier call this one: the value is in the characteristic.
            @Deprecated("Replaced at API 33 by the overload with the value")
            @Suppress("DEPRECATION")
            override fun onCharacteristicRead(gatt: BluetoothGatt, characteristic: BluetoothGattCharacteristic, status: Int) {
                answer?.complete(Answer(status, characteristic.value ?: ByteArray(0)))
            }
        }
        send(ConnectionState.Connecting(device))
        // The id is the address the scan reported. false: connect directly, now. Android 17 (API 37)
        // deprecates this connectGatt for a new one that older phones don't have.
        @Suppress("DEPRECATION")
        val gatt: BluetoothGatt = adapter.getRemoteDevice(device.id)
            .connectGatt(context, false, callback, BluetoothDevice.TRANSPORT_LE)
            ?: throw ConnectionException("Android couldn't start the connection.")

        awaitClose {
            // A request still waiting would never get its callback now.
            this@AndroidBleConnection.gatt = null
            answer?.completeExceptionally(ConnectionException("The link closed before the device answered."))
            // Whatever ended the link, close the GATT client, or Android keeps it registered.
            gatt.disconnect()
            gatt.close()
        }
    }

    // One call discovers it all: Android explores the services and their characteristics together.
    @SuppressLint("MissingPermission")
    override suspend fun discoverServices(): List<DeviceService> {
        val gatt = openGatt()
        val answer = request { gatt.discoverServices() }
        if (answer.status != BluetoothGatt.GATT_SUCCESS) {
            throw ConnectionException("Discovery failed (Android status ${answer.status}).")
        }
        return gatt.services.map { it.toDeviceService() }
    }

    @SuppressLint("MissingPermission")
    override suspend fun read(characteristic: Characteristic): ByteArray {
        val gatt = openGatt()
        val target = gatt.getService(UUID.fromString(characteristic.serviceUuid))
            ?.getCharacteristic(UUID.fromString(characteristic.uuid))
            ?: throw ConnectionException("This device has no such characteristic. Discover its services again.")
        val answer = request { gatt.readCharacteristic(target) }
        if (answer.status != BluetoothGatt.GATT_SUCCESS) {
            throw ConnectionException("The device refused the read (Android status ${answer.status}).")
        }
        return answer.value
    }

    private fun openGatt(): BluetoothGatt = gatt ?: throw ConnectionException("Not connected.")

    // Sends one request and waits for its callback. send returns false when Android won't send it,
    // for example while another request on this link is still waiting for its answer.
    private suspend fun request(send: () -> Boolean): Answer {
        val pending = CompletableDeferred<Answer>()
        answer = pending
        try {
            if (!send()) throw ConnectionException("Android couldn't send the request.")
            return pending.await()
        } finally {
            answer = null
        }
    }

    private fun BluetoothGattService.toDeviceService(): DeviceService {
        val serviceUuid = fullUuid(uuid.toString())
        return DeviceService(
            uuid = serviceUuid,
            characteristics = characteristics.map {
                Characteristic(serviceUuid, fullUuid(it.uuid.toString()), propertiesOf(it.properties))
            },
        )
    }
}

class LinkedBleConnection(private val link: IosLink) : BleConnection {

        link.open(device, LinkFeed(this))
        awaitClose { link.close() }
    }

        suspendCancellableCoroutine { link.read(characteristic, ValueReply(it)) }

// What the Swift connection implements: open and close the real link, and the requests on it.
interface IosLink {
    fun open(device: Device, feed: LinkFeed)
    fun close()
    fun discover(reply: ServicesReply)
    fun read(characteristic: Characteristic, reply: ValueReply)
}

// Where the Swift connection reports: each state of the link, or the failure that ends it.
class LinkFeed internal constructor(private val scope: ProducerScope<ConnectionState>) {
    fun changed(state: ConnectionState) {
        scope.trySend(state)
    }

    fun failed(message: String) {
        scope.close(ConnectionException(message))
    }
}

// Where the Swift connection answers a discovery: every service, or the failure.
class ServicesReply internal constructor(private val waiting: CancellableContinuation<List<DeviceService>>) {
    fun found(services: List<DeviceService>) {
        if (waiting.isActive) waiting.resume(services)
    }

    fun failed(message: String) {
        if (waiting.isActive) waiting.resumeWithException(ConnectionException(message))
    }
}

// Where the Swift connection answers a read: the value's bytes, or the failure.
class ValueReply internal constructor(private val waiting: CancellableContinuation<ByteArray>) {
    fun read(value: NSData) {
        if (waiting.isActive) waiting.resume(value.toByteArray())
    }

    fun failed(message: String) {
        if (waiting.isActive) waiting.resumeWithException(ConnectionException(message))
    }
}

// Swift's Data arrives as NSData; copy its bytes into a Kotlin ByteArray.
@OptIn(ExperimentalForeignApi::class)
private fun NSData.toByteArray(): ByteArray {
    val bytes = ByteArray(length.toInt())
    if (bytes.isNotEmpty()) bytes.usePinned { memcpy(it.addressOf(0), this.bytes, length) }
    return bytes
}

class DeviceDetailFragment : Fragment() {
    // Survives rotation; cleared, connection and all, when this Fragment leaves the back stack
    // for good. The views below are rebuilt on every rotation; the connection is not in them.
    private val viewModel: DeviceDetailViewModel by viewModel()

    private var binding: FragmentDeviceDetailBinding? = null
    private var errorDialog: AlertDialog? = null

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        val b = FragmentDeviceDetailBinding.inflate(inflater, container, false)
        binding = b
        val args = requireArguments()
        val device = Device(
            id = args.getString("deviceId").orEmpty(),
            name = args.getString("deviceName").orEmpty(),
            rssi = args.getInt("deviceRssi"),
        )
        b.deviceName.text = device.name
        b.deviceId.text = "ID: ${device.id}"
        b.deviceRssi.text = "Signal: ${device.rssi} dBm"
        // One button: Connect while disconnected, Disconnect while connecting or connected.
        b.connectButton.setOnClickListener {
            if (viewModel.uiState.value.connection is ConnectionState.Disconnected) {
                viewModel.connect(device)
            } else {
                viewModel.disconnect()
            }
        }
        b.backButton.setOnClickListener {
            val nav = findNavController()
            // A fast double tap would otherwise pop the list too and empty the back stack.
            if (nav.currentDestination?.id == R.id.deviceDetail) nav.popBackStack()
        }
        return b.root
    }

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { render(it) }
            }
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        errorDialog?.dismiss() // a dismiss() doesn't call the cancel listener, so the error stays in state
        errorDialog = null
        binding = null
    }

    // The one place that touches views: every new state ends here.
    private fun render(state: DeviceDetailUiState) {
        val b = binding ?: return
        val connection = state.connection
        b.progress.visibility = if (connection is ConnectionState.Connecting) View.VISIBLE else View.GONE
        b.statusText.text = when (connection) {
            ConnectionState.Disconnected -> "Status: not connected"
            is ConnectionState.Connecting -> "Status: connecting…"
            is ConnectionState.Connected -> "Status: connected"
        }
        b.statusText.setTextColor(if (connection is ConnectionState.Connected) Color.BLUE else Color.DKGRAY)
        b.connectButton.text = if (connection is ConnectionState.Disconnected) "Connect" else "Disconnect"
        b.discoveringRow.visibility = if (state.discovering) View.VISIBLE else View.GONE
        renderServices(b.servicesContainer, state.services, state.values)
        renderError(state.errorMessage)
    }

    // Rebuilt from the state each time: a handful of rows, so no RecyclerView. One block per
    // service: its UUID, then each characteristic with its properties, a Read button if it has
    // the Read property, and what the last read gave: the value, or why it failed.
    private fun renderServices(container: LinearLayout, services: List<DeviceService>, values: Map<Characteristic, String>) {
        container.removeAllViews()
        val context = container.context
        for (service in services) {
            container.addView(TextView(context).apply {
                text = "Service ${service.uuid}"
                typeface = Typeface.create(Typeface.MONOSPACE, Typeface.BOLD)
                setPadding(0, 24, 0, 8)
            })
            for (characteristic in service.characteristics) {
                container.addView(TextView(context).apply {
                    text = characteristic.uuid
                    typeface = Typeface.MONOSPACE
                    setPadding(32, 8, 0, 0)
                })
                val row = LinearLayout(context).apply {
                    orientation = LinearLayout.HORIZONTAL
                    setPadding(32, 0, 0, 0)
                }
                row.addView(
                    TextView(context).apply { text = characteristic.properties.joinToString(" · ") { it.label } },
                    LinearLayout.LayoutParams(0, ViewGroup.LayoutParams.WRAP_CONTENT, 1f),
                )
                if (CharacteristicProperty.Read in characteristic.properties) {
                    row.addView(Button(context).apply {
                        text = "Read"
                        setOnClickListener { viewModel.read(characteristic) }
                    })
                }
                container.addView(row)
                values[characteristic]?.let { value ->
                    container.addView(TextView(context).apply {
                        text = value
                        setPadding(32, 0, 0, 0)
                    })
                }
            }
        }
    }

    private fun renderError(message: String?) {
        if (message == null) {
            errorDialog?.dismiss()
            errorDialog = null
        } else if (errorDialog == null) {
            errorDialog = AlertDialog.Builder(requireContext())
                .setTitle("Connection failed")
                .setMessage(message)
                .setPositiveButton("OK") { _, _ -> viewModel.errorShown() }
                .setOnCancelListener { viewModel.errorShown() }
                .show()
        }
    }

import CoreBluetooth
import Shared

// Outbound adapter, the Swift half: the radio work for a link to one peripheral, behind IosLink.
// LinkedBleConnection, its Kotlin half in iosMain, implements the BleConnection port on top. Like
// the scanner, it is its own manager's delegate and Koin keeps it alive (through the Kotlin half).
// It keeps the CBPeripheral while the link lasts: CoreBluetooth cancels a pending connection
// when its peripheral is deallocated. And it is the peripheral's delegate, which hears the
// answers to discovery and reads.
@MainActor
final class IosBleConnection: NSObject, @preconcurrency IosLink,
    @preconcurrency CBCentralManagerDelegate, @preconcurrency CBPeripheralDelegate {
    private var manager: CBCentralManager?
    private var peripheral: CBPeripheral?
    private var device: Device?
    private var feed: LinkFeed?
    // The request waiting for the peripheral's delegate: the port takes one at a time.
    private var discovery: ServicesReply?
    private var servicesLeft = 0
    private var reading: (characteristic: CBCharacteristic, reply: ValueReply)?

    // IosLink: LinkedBleConnection calls these when its Flow is collected and when it is cancelled.
    func open(device: Device, feed: LinkFeed) {
        self.device = device
        self.feed = feed
        let manager = self.manager ?? makeManager()
        // A new manager learns the radio's state a moment later; centralManagerDidUpdateState
        // then calls start.
        if manager.state != .unknown && manager.state != .resetting { start(on: manager) }
    }

    func close() {
        if let peripheral, manager?.state == .poweredOn { manager?.cancelPeripheralConnection(peripheral) }
        peripheral?.delegate = nil
        peripheral = nil
        device = nil
        feed = nil
        // A request still waiting would never get its answer now.
        discovery?.failed(message: "The link closed before the device answered.")
        discovery = nil
        reading?.reply.failed(message: "The link closed before the device answered.")
        reading = nil
    }

    // IosLink: the port's requests, on the open link.
    // The first of two discoveries: the services. didDiscoverServices starts the second.
    func discover(reply: ServicesReply) {
        guard let peripheral, peripheral.state == .connected else { return reply.failed(message: "Not connected.") }
        discovery = reply
        peripheral.discoverServices(nil)
    }

    func read(characteristic: Characteristic, reply: ValueReply) {
        guard let peripheral, peripheral.state == .connected else { return reply.failed(message: "Not connected.") }
        // CBUUID compares by value, so the full form finds a characteristic iOS reported as "2A19".
        let serviceUuid = CBUUID(string: characteristic.serviceUuid)
        let uuid = CBUUID(string: characteristic.uuid)
        guard let target = peripheral.services?.first(where: { $0.uuid == serviceUuid })?
            .characteristics?.first(where: { $0.uuid == uuid }) else {
            return reply.failed(message: "This device has no such characteristic. Discover its services again.")
        }
        reading = (target, reply)
        peripheral.readValue(for: target)
    }

    private func start(on manager: CBCentralManager) {
        guard let device, let feed, peripheral == nil else { return }
        guard manager.state == .poweredOn else { return end(with: message(for: manager.state)) }
        // The scanner found the device with its own manager; this one asks for it by identifier.
        guard let id = UUID(uuidString: device.id),
              let found = manager.retrievePeripherals(withIdentifiers: [id]).first else {
            return end(with: "This iPhone doesn't know \(device.name) any more. Scan again.")
        }
        peripheral = found
        // Without this, discovery and reads are sent and their answers go nowhere. The property
        // is weak: this adapter, kept alive by Koin, is what keeps the delegate alive.
        found.delegate = self
        feed.changed(state: ConnectionStateConnecting(device: device))
        manager.connect(found)
    }

    // Called on the main queue (queue: nil) when the link is up.
    func centralManager(_ central: CBCentralManager, didConnect peripheral: CBPeripheral) {
        guard peripheral === self.peripheral, let device else { return }
        feed?.changed(state: ConnectionStateConnected(device: device))
    }

    func centralManager(_ central: CBCentralManager, didFailToConnect peripheral: CBPeripheral,
                        error: Error?) {
        guard peripheral === self.peripheral else { return }
        end(with: "The connection failed: \(error?.localizedDescription ?? "no reason given").")
    }

    // error is nil when the app asked for the disconnection, in close(): nothing is waiting then.
    func centralManager(_ central: CBCentralManager, didDisconnectPeripheral peripheral: CBPeripheral,
                        error: Error?) {
        guard peripheral === self.peripheral, let error, let device else { return }
        end(with: "The link to \(device.name) was lost: \(error.localizedDescription)")
    }

    func centralManagerDidUpdateState(_ central: CBCentralManager) {
        guard central.state != .unknown, central.state != .resetting else { return }
        if peripheral == nil {
            start(on: central) // open() was waiting for the state
        } else if central.state != .poweredOn {
            end(with: "Bluetooth was turned off.")
        }
    }

    // CBPeripheralDelegate, on the main queue like the manager's calls.
    // The services are known; now each one's characteristics: one more request per service.
    func peripheral(_ peripheral: CBPeripheral, didDiscoverServices error: Error?) {
        guard peripheral === self.peripheral, discovery != nil else { return }
        if let error { return endDiscovery(failure: "Discovery failed: \(error.localizedDescription)") }
        let services = peripheral.services ?? []
        servicesLeft = services.count
        if services.isEmpty { return endDiscovery(failure: nil) }
        for service in services {
            peripheral.discoverCharacteristics(nil, for: service)
        }
    }

    // One call per service. The discovery is done when every service has answered.
    func peripheral(_ peripheral: CBPeripheral, didDiscoverCharacteristicsFor service: CBService,
                    error: Error?) {
        guard peripheral === self.peripheral, discovery != nil else { return }
        if let error { return endDiscovery(failure: "Discovery failed: \(error.localizedDescription)") }
        servicesLeft -= 1
        if servicesLeft == 0 { endDiscovery(failure: nil) }
    }

    // Called after readValue(for:), and in Lesson 16 for each notification.
    func peripheral(_ peripheral: CBPeripheral, didUpdateValueFor characteristic: CBCharacteristic,
                    error: Error?) {
        guard peripheral === self.peripheral, let reading, reading.characteristic === characteristic else { return }
        self.reading = nil
        if let error {
            reading.reply.failed(message: "The device refused the read: \(error.localizedDescription)")
        } else {
            reading.reply.read(value: characteristic.value ?? Data())
        }
    }

    private func endDiscovery(failure: String?) {
        guard let discovery, let peripheral else { return }
        self.discovery = nil
        if let failure {
            discovery.failed(message: failure)
        } else {
            discovery.found(services: (peripheral.services ?? []).map(appService))
        }
    }

    // A CBService in the app's terms: full UUIDs, and the properties as the app core names them.
    private func appService(_ service: CBService) -> DeviceService {
        let serviceUuid = UuidsKt.fullUuid(uuid: service.uuid.uuidString)
        let characteristics = (service.characteristics ?? []).map { characteristic in
            Characteristic(
                serviceUuid: serviceUuid,
                uuid: UuidsKt.fullUuid(uuid: characteristic.uuid.uuidString),
                properties: DeviceServiceKt.propertiesOf(bits: Int32(characteristic.properties.rawValue))
            )
        }
        return DeviceService(uuid: serviceUuid, characteristics: characteristics)
    }

    // Ends the Flow with the message; Kotlin then calls close().
    private func end(with message: String) {
        let feed = self.feed
        close()
        feed?.failed(message: message)
    }

    private func message(for state: CBManagerState) -> String {
        switch state {
        case .unsupported: "This phone has no Bluetooth LE radio."
        case .unauthorized: "Connecting needs the Bluetooth permission."
        default: "Bluetooth is off. Turn it on, then connect again."
        }
    }

    // No system alert when Bluetooth is off: the app shows its own message.
    private func makeManager() -> CBCentralManager {
        let manager = CBCentralManager(
            delegate: self, queue: nil,
            options: [CBCentralManagerOptionShowPowerAlertKey: false]
        )
        self.manager = manager
        return manager
    }
}
