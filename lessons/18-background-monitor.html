Background monitor: build it

~2 h · +0.25 h per extra UI track Milestone: m13 monitor logs status on an interval Prereq: 17
Why this matters: Lesson 17 gave the app the phone's status and a log to keep it in. A device monitor's real job is to keep reading while nobody looks: every 15 minutes, with the app open, in the background, or not running at all. Neither phone lets an app loop forever in the background. Android runs repeating work through WorkManager, at most once every 15 minutes; iOS suspends an app in the background and launches it again only when it decides to, through BGTaskScheduler. Today the app gets a DeviceMonitoring inbound port and a monitoring service that turns each tick into a log record, and a MonitorScheduler outbound port whose two adapters ask each platform for ticks in the way it allows. The monitor starts where the app starts, not where a screen appears, because the launches that matter most never show a screen. That's milestone m13: the monitor logs the status on an interval, on both platforms.

Primary source Android's Task scheduling (WorkManager) and Define work requests ("Schedule periodic work") before section 4. Apple's Using background tasks to update your app before section 5, with the comments in BGTaskScheduler.h (Xcode: Open Quickly, ⇧⌘O). Kotlin's Clock before section 3.

Tracks The ports, the service, both adapters, the launch hook and the tests are shared code, the same on every track, and so is Android's Application class. Only the iOS app start differs: iOSApp.swift (SwiftUI) or AppDelegate.swift (UIKit), each with its own project.yml. No screen changes today: Lesson 20 gives the monitor its buttons. Each excerpt shows only the lines its notes explain; the complete files are in Full files at the end.

1. Who owns the clock

While it's on screen, an app can run whatever timer it likes. Once it leaves the screen, what runs and when is each platform's decision, made in its own way:

  • Android
  • iOS
  1. Android: WorkManager. "WorkManager is intended for work that is required to run reliably even if the user navigates off a screen, the app exits, or the device restarts", and it "lets tasks persist across app restarts and device reboots" (Task scheduling). For repeating work: "The minimum repeat interval that can be defined is 15 minutes (same as the JobScheduler API)", and "The interval period is defined as the minimum time between repetitions. The exact time that the worker is going to be executed depends on the constraints that you are using in your WorkRequest object and on the optimizations performed by the system" (Define work requests).
  2. iOS: two mechanisms. In the foreground the app runs its own timer. In the background, the app is suspended, and "Background tasks give your app a way to run code while the app is suspended" (BGTaskScheduler.h). A refresh task's earliestBeginDate means "the system doesn't guarantee launching the task at the specified date, but only that it won't begin sooner", and "The system will fulfill this request intelligently based on system conditions and app usage" (BGTaskRequest.h). Apple's own example asks for "no earlier than 15 minutes from now" (Using background tasks).
  3. 15 minutes, on both. It's Android's floor, and a sensible rhythm for a phone's battery and network. iOS has no floor in its API, and no promise either: in the background, 15 minutes is the earliest, never the schedule. Lesson 19 measures what each phone actually does.

No bypassing the OS's limits. Each platform has tools that look like a way around them. Each is either meant for something else or not allowed for this:

TemptingWhat the platform says
a coroutine loop with delay in a ViewModel or an ActivityCoroutines are for work "that doesn't need to persist if the app leaves the visible state"; "they stop as soon as the app closes. For work that should persist even after the app closes, use WorkManager" (Task scheduling). The iOS adapter does use a timer, but only in the foreground, where that's exactly right.

It shows a notification while it runs, needs a declared type from Android 14, and an app targeting Android 12 or later "can't start foreground services while the app is running in the background, except for a few special cases" (section 4).

2. Two ports: what the app offers, what it needs

Appendix A.7 of the course plan asks for a monitor that can start at an interval, stop, report where it stands, and show or clear its log. That's the inbound port:

  1. start isn't suspend: it hands the tick to the platform and returns. The ticks come later, on the platform's schedule.
  2. A StateFlow, like the session's connectionState (Lesson 14): a screen can collect it, and a test can read .value. MonitorStatus is sealed for the same reason as ConnectionState: a when over it must handle both states.
  3. "This process". The status lives in memory, so each process has its own. On Android a tick may run in a process WorkManager started while nobody was looking, and the process that shows the screen later never sees that tick's lastRecord. The log file is what lasts.

What the service needs from the platform is a timer it can't build itself:

  1. Named for what the app needs, not for a platform: no "work", no "task", no "job". WorkManager and BGTaskScheduler stay inside their adapters.
  2. The tick is a suspend function the service hands over. The adapter decides when; the service decides what. That split is the whole design: the rules of a tick are tested on the JVM and in the iOS simulator with a fake timer (section 7), and each adapter is only a timer.

3. The monitoring service: one tick, one record

  1. The four status ports again, ConnectionStatus included. The monitor reads "Bluetooth connected" through Lesson 17's port and its bridge, never through DeviceSession: services don't know each other (Lesson 17, section 3). Koin hands both services the same adapters, so a record and the list screen's status line read the same sources.
  2. Why not a bridge to StatusReport? A bridge is for what another capability holds: the session owns the connection state, so the status asks through a bridge. Nobody in the app holds the battery level or the network; the platform does, and the monitor asks the platform's ports directly. What the two services share is rules, and rules shared by two services are written once, as a plain function in the app core:
  1. Still in the app core, still tested through both services. StatusServiceTest didn't change and still passes; MonitoringServiceTest's theRecordFollowsTheStatusRules checks the same two rules in a record. Removing the Wi-Fi rule from readStatus fails one test in each (we tried). internal keeps it out of Swift's header.
  2. A Clock, passed in. kotlin.time.Clock is the standard library's interface with one method, now(). Its reference: "It is not recommended to use Clock.System directly in the implementation. Instead, you can pass a Clock explicitly to the necessary functions or classes. This way, tests can be written deterministically by providing custom Clock implementations" (Clock). The default keeps Koin's binding short; the tests pass a clock they set.
  3. A late tick writes nothing. A platform can be about to call the tick when stop() runs: WorkManager may already have started the worker, or a coroutine may be past its delay. The first line makes "stopped" mean stopped. stopCancelsAndALateTickWritesNothing fails without it (we tried).
  4. A file error is a reading that failed, not a crash. A full disk (LogStoreException, Lesson 17) lands in lastError, and the next tick tries again. Anything else still throws: a bug should be loud.

4. Android: WorkManager

WorkManager comes from Jetpack: implementation("androidx.work:work-runtime:2.12.0") in androidMain's dependencies in shared/build.gradle.kts. Since 2.9, the Kotlin APIs are in that artifact: "work-runtime-ktx is now empty, CoroutineWorker and other Kotlin specific utilities are now available in the main work-runtime artifact" (WorkManager release notes).

  1. Periodic work, at least 15 minutes apart. "The repeat interval must be greater than or equal to PeriodicWorkRequest.MIN_PERIODIC_INTERVAL_MILLIS" (Define work requests). coerceAtLeast makes that the adapter's promise rather than a surprise. The builder that takes a java.time.Duration needs API 26, the app's minimum; toJavaDuration() converts Kotlin's.
  2. Unique work, by name. The app starts the monitor on every launch (section 6), so schedule runs many times. UPDATE: "If there is existing pending (uncompleted) work with the same unique name, it will be updated with the new specification. Otherwise, new work with the given name will be enqueued", and "It preserves enqueue time" (ExistingPeriodicWorkPolicy). KEEP would ignore a new interval; CANCEL_AND_REENQUEUE starts over: with it, our relaunch wrote a second record at once. With UPDATE, a relaunch left the next run where it was (dumpsys jobscheduler still counted down) and wrote no extra record.
  3. The first run is at once. A new periodic request has no initial delay, so the first record appears a moment after the first launch: on the emulator, within a second of am start.
  1. WorkManager builds the worker itself. "ListenableWorker classes are instantiated at runtime by the WorkerFactory specified in the Configuration" (ListenableWorker), and this app keeps the default configuration, whose factory looks up the constructor that takes a Context and WorkerParameters (getDeclaredConstructor in WorkerFactory's bytecode, work-runtime 2.12.0). A lambda can't travel with the request either: "Scheduled work is stored in an internally managed SQLite database" (Task scheduling). So the worker reaches the tick through the one thing it shares with the adapter: the process. @Volatile, because the worker reads it on another thread.
  2. A new process. If the app isn't running, Android starts its process to run the work: on the emulator, logcat said "Start proc … for service {com.example.devicemonitor/androidx.work.impl.background.systemjob.SystemJobService}", WorkManager's JobService. Application.onCreate is "Called when the application is starting, before any activity, service, or receiver objects (excluding content providers) have been created" (Application), so onAppLaunch() has handed over the tick before doWork runs (section 6).
  3. CoroutineWorker lets doWork be suspend, and "defaults to Dispatchers.Default" (Threading in CoroutineWorker). That's fine here: none of Lesson 17's Android status adapters needs the main thread (the network one already keeps its map in a ConcurrentHashMap, because its callbacks arrive on another thread), and the log store moves to Dispatchers.IO itself.
  4. No manifest change. WorkManager's own manifest is merged into the app's: aapt2 dump permissions on our APK lists WAKE_LOCK, RECEIVE_BOOT_COMPLETED and FOREGROUND_SERVICE, and the merge report names work-runtime:2.12.0 for each.
Gotcha · you can't force a periodic run early JobScheduler can run a job on demand (adb shell cmd jobscheduler run -f -n androidx.work.systemjobscheduler com.example.devicemonitor <job id>; on our API 36 emulator WorkManager's jobs sat in that namespace, and without -n the command said "Could not find job"). For our periodic work, WorkManager then refused: "Delaying execution for com.example.devicemonitor.adapter.outbound.MonitorWorker because it is being executed before schedule." (logcat, tag WM-WorkerWrapper), and wrote no record. To see a second tick, wait out the 15 minutes. The job id also changes when WorkManager reschedules, so read it from dumpsys jobscheduler each time.

And the foreground service? The course plan names it next to WorkManager, and it's the right tool for a different monitor: one the user starts and watches, such as live readings from a connected device every few seconds while a notification says so. Android's background-tasks guide puts it that way: "If the task is not invisible to the user, the correct solution may be to use a foreground service. These services run continuously once started", while for work that can wait, "In most cases, your best option for running background tasks is to use WorkManager" (Background tasks overview). Our monitor is invisible and can wait a few minutes, so WorkManager it is. A foreground service would also need, from Android 14, "an appropriate service type for each foreground service" declared in the manifest with its permission (Foreground service types), and couldn't be started from the background: "Apps that target Android 12 (API level 31) or higher can't start foreground services while the app is running in the background, except for a few special cases" (Restrictions on starting a foreground service from the background).

5. iOS: a timer in the foreground, BGTaskScheduler in the background

The iOS adapter is Kotlin in iosMain, like Lesson 17's log store: the port takes a Kotlin Duration and a suspend lambda, which reach Swift's header as an int64_t and an id<SharedKotlinSuspendFunction0> (- (void)scheduleInterval:(int64_t)interval tick:…), while Kotlin/Native imports Apple's BackgroundTasks and UIKit as platform.BackgroundTasks and platform.UIKit. It follows the app's state with UIKit's app-level notifications:

  1. Registered in init, so built at launch. Apple: "Registration of all launch handlers must be complete before the end of applicationDidFinishLaunching(_:)", and "Register each task identifier only once. The system kills the app on the second registration of the same task identifier" (register(forTaskWithIdentifier:using:launchHandler:)). So the app start builds one IosMonitorScheduler() and passes it to doInitKoin, like the other adapters; a Koin single { IosMonitorScheduler() } would build it whenever something first asked, maybe after launch. register "Returns false if the identifier isn't included in the BGTaskSchedulerPermittedIdentifiers Info.plist", and the check after it turns that into a crash at launch with a message that says what to fix, instead of a monitor that silently never runs in the background.
  2. The main queue, and MainScope. Passing nil for the queue would mean "a default background queue". The tick reads Lesson 17's iOS status adapters, which are @MainActor and check at run time that they're called on the main thread, so everything here runs there.
  3. App-level notifications. didBecomeActiveNotification "posts when the app becomes active", and didEnterBackgroundNotification "posts when the app enters the background" (didBecomeActiveNotification, didEnterBackgroundNotification). Both iOS tracks use scenes, and with scenes UIKit doesn't call the app delegate's applicationDidEnterBackground(_:), but "UIKit posts a didEnterBackgroundNotification regardless of whether your app uses scenes" (applicationDidEnterBackground(_:)): the notification works for SwiftUI and UIKit alike, from shared code. A screen's onAppear or viewWillAppear would follow one screen, and wouldn't fire at all in a launch with no screen.
  1. In the foreground, a plain coroutine timer: the first tick one interval after the app becomes active, then one per interval while it stays active. When the app goes to the background the timer is cancelled, and nothing would run it anyway: iOS suspends the app.
  2. Lesson 17's error pattern, again. submitTaskRequest:error: returns NO and fills an NSError **, so the Kotlin side passes error.ptr inside memScoped. "Submitting a task request for an unexecuted task that's already in the queue replaces the previous task request", and "There can be a total of 1 refresh task and 10 processing tasks scheduled at any time" (BGTaskScheduler.h): one identifier, one pending request at most.
  3. The Simulator can't. BGTaskSchedulerErrorCodeUnavailable (1) is documented for "The app is running on Simulator which doesn't support background processing" (BGTaskScheduler.h), and that's what we got on the iOS 26.2 Simulator each time the app went to the background: "Monitor: no background refresh: The operation couldn't be completed. (BGTaskSchedulerErrorDomain error 1.)". On a phone, the header gives code 1 when "The user has disabled background refresh in settings"; a missing background mode or identifier is code 3, NotPermitted, instead.
  1. Apple's own order: the sample's handler schedules a new refresh task first, gives the task an expiration handler that cancels the work, and reports completion when the work ends (Using background tasks). Each refresh asks for the next, so the chain continues for as long as iOS keeps granting them.
  2. Always complete the task. BGTask.h: "The system suspends the app as soon as all background tasks are complete", and "Not calling setTaskCompletedWithSuccess: before the time for the task expires may result in the system killing your app." The expiration handler is "called shortly before the task's background time expires"; cancelling the coroutine there stops a slow tick.
  3. A launch straight into the background runs the app start first: "the system launches the app and moves it directly to the background", then UIKit "calls the app delegate's applicationDidEnterBackground(_:) method" (with scenes, UIKit skips that method but still posts the notification), then "delivers the event that caused the launch" (About the background execution sequence). That background notification comes with no timer running, so the adapter submits nothing then; the refresh task submits the next one.

Apple's article lists two settings: the "Background fetch" mode, and the task identifier in BGTaskSchedulerPermittedIdentifiers. Without the first, a refresh task can't run ("Executing app refresh tasks requires setting the fetch UIBackgroundModes capability", BGTask.h); without the second, register "Returns false if the identifier isn't included in the BGTaskSchedulerPermittedIdentifiers Info.plist". XcodeGen writes both from project.yml, on both iOS tracks:

Run xcodegen generate in iosApp/ afterwards, and check that both keys are in the generated Info.plist. Nothing else in the Xcode project changes: the new adapter is in the Kotlin framework.

Gotcha · NSLog from Kotlin crashed the app Our first version logged the failure with NSLog("Monitor: no background refresh: %@", message), a Kotlin String passed to Foundation's variadic NSLog. The app crashed the moment it went to the background (EXC_BAD_ACCESS inside NSLog, the crash report's address made of the message's own characters): the string didn't arrive as the object %@ expects. Kotlin's println takes no format, and on iOS it writes to the app's standard output: Xcode's console, or xcrun simctl launch --console-pty.

6. Start it where the app starts

Something must call start(interval), and in m13 there's no button yet. The obvious place, a screen appearing, is the wrong one: a screen can go away while the app keeps running, and the launches the monitor depends on, Android starting the process for WorkManager and iOS launching the app for a refresh task, show no screen at all. The hook that runs in every process is the app's start:

  1. An inbound adapter that isn't a ViewModel. It drives the app through an inbound port, which is what makes it an inbound adapter (Lesson 10); the screens' ViewModels are the other kind. It lives in the shared code so the interval is written once and Swift needs no Duration.
  2. On every launch, and that's safe. The Android adapter's UPDATE keeps one schedule; the iOS adapter only stores the tick and, if the app is already active, restarts its timer. What each new process needs is the tick: the lambda the service handed the old process died with it.
  3. Always on, for now. m13's monitor runs whenever the app has run once. Lesson 20's screen adds Start and Stop, which call the same port.

7. Tests: the platform's timer, played by the test

  1. Fifteen minutes in no time. The test doesn't wait for a timer, real or virtual: it is the timer, and calls fire() when it likes. The clock is an object the test sets, so the timestamps are exact.
  2. Seven tests, through the inbound port: startAsksTheSchedulerForTheInterval, eachTickAppendsTheStatusAndTheTime, theRecordFollowsTheStatusRules (Wi-Fi rule, and Connecting isn't connected), stopCancelsAndALateTickWritesNothing, aFileErrorIsReportedAndTheNextTickTriesAgain (with FakeLogStore.failNextAppend), logsAndClearLogsUseTheLogStore, and anIntervalMustBePositive.
  3. The graph. AppModuleTest gains theMonitorLogsWhatTheAppsOneSessionSays: it connects through the graph's session, starts the graph's DeviceMonitoring, fires the fake scheduler, and finds bluetoothConnected = true in the fake log store. A wrong binding, or a bridge on a second session, fails it.
  4. Mutation checks we ran, each failing exactly the named test: no late-tick guard; no require; catching another exception type than LogStoreException; counting Connecting as connected in the record; and the Wi-Fi rule removed from readStatus, which fails one test in each service.

The two scheduler adapters have no unit tests: there's no rule in them to test, only calls to the platform, and the platform's timer is what they're for. They are checked by running them (section 8), and the parts only a phone can show are device checks.

Retrieval checks

Answer from memory, without scrolling up.

Why does the monitor start in the app start, and not when the list screen appears?

A screen hook runs only while that screen exists. The app start runs once in every process, with or without a screen, and starting the monitor again is safe: UPDATE keeps one schedule on Android, and the iOS adapter only stores the new tick.

How does MonitorWorker get the tick it calls?

WorkManager's default factory builds a worker by reflection with only a Context and WorkerParameters, and a lambda can't be stored in its database. The process is what the adapter and the worker share.

The iOS adapter sets a refresh request's earliestBeginDate 15 minutes ahead. When will iOS run it?

BGTaskRequest.h: "the system doesn't guarantee launching the task at the specified date, but only that it won't begin sooner". One request runs once; the handler submits the next one.

Why does MonitoringService take a Clock instead of calling Clock.System.now()?

The default argument keeps the Koin binding short; MonitoringServiceTest passes an object whose now it moves from 10:30 to 10:45.

Both services need the Wi-Fi rule and the "only Connected counts" rule. Where do the rules live in m13?

A service doesn't call another capability's inbound port, and a rule written twice drifts. A bridge is for state another capability holds, like the session's connection; the battery and the network belong to the platform, so both services ask the ports and share the rules.

Why doesn't the Android adapter use a foreground service to tick every minute?

Using a foreground service only to keep the process alive would be bypassing the limits the course says not to bypass. It's the right tool for a monitor the user starts and watches.

On the Simulator, the app goes to the background and the console says "BGTaskSchedulerErrorDomain error 1". What does it mean?

BGTaskScheduler.h documents code 1, Unavailable, for the Simulator and for a user who disabled background refresh. A missing mode or identifier is code 3, and too many requests is code 2.

Mixed review (interleaved)

The iOS adapter is Kotlin calling Apple's frameworks, like IosLogStore. What does error.ptr give submitTaskRequest? (Lesson 17)

Objective-C errors aren't imported as Kotlin exceptions; the Kotlin code checks the return value, then reads error.value, inside the memScoped block that owns the memory.

Why does the test fire the fake scheduler instead of waiting 15 minutes of virtual time with runTest? (Lesson 11)

Virtual time controls delays on the test dispatcher. Here no delay is in the service at all; the adapters own the clock, and the fake plays them.

Which lifecycle does each Android hook follow? (Lessons 03 and 11)

A process can start without any Activity, for a WorkManager job; then only the Application runs, which is why the monitor starts there.

    bluetooth: BluetoothProvider,

        wifiConnected = net.wifiConnected,
        cellularAvailable = net.cellularAvailable,
        bluetoothEnabled = bluetooth.isEnabled(),
        bluetoothConnected = connection.current() is ConnectionState.Connected,
    )

package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.DeviceMonitoring
import com.example.devicemonitor.core.outbound.BatteryProvider
import com.example.devicemonitor.core.outbound.BluetoothProvider
import com.example.devicemonitor.core.outbound.ConnectionStatus
import com.example.devicemonitor.core.outbound.LogStore
import com.example.devicemonitor.core.outbound.MonitorScheduler
import com.example.devicemonitor.core.outbound.NetworkProvider
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlin.time.Clock
import kotlin.time.Duration

// Service: the background monitor's rules. Each tick reads the phone's status through Lesson 17's
// four status ports (ConnectionStatus included, never the session), stamps it with the time,
// and appends it to the log. When it runs is the scheduler's business, not this class's.
class MonitoringService(
    private val battery: BatteryProvider,
    private val network: NetworkProvider,
    private val bluetooth: BluetoothProvider,
    private val connection: ConnectionStatus,
    private val log: LogStore,
    private val scheduler: MonitorScheduler,
    private val clock: Clock = Clock.System,
) : DeviceMonitoring {
    private val _status = MutableStateFlow<MonitorStatus>(MonitorStatus.Stopped)
    override val status: StateFlow<MonitorStatus> = _status.asStateFlow()

    override fun start(interval: Duration) {
        require(interval.isPositive()) { "The monitor's interval must be positive, not $interval." }
        _status.value = MonitorStatus.Running(interval)
        scheduler.schedule(interval) { tick() }
    }

    override fun stop() {
        scheduler.cancel()
        _status.value = MonitorStatus.Stopped
    }

    override suspend fun logs(): List<LogRecord> = log.read()

    override suspend fun clearLogs() = log.clear()

    // One reading. A tick that comes after stop() writes nothing. A file error doesn't stop the
    // monitor: it shows in the status, and the next tick tries again.
    private suspend fun tick() {
        if (_status.value !is MonitorStatus.Running) return
        val record = LogRecord(clock.now(), readStatus(battery, network, bluetooth, connection))
        val error = try {
            log.append(record)
            null
        } catch (e: LogStoreException) {
            e.message
        }
        _status.update { current ->
            when (current) {
                is MonitorStatus.Running ->
                    if (error == null) current.copy(lastRecord = record, lastError = null)
                    else current.copy(lastError = error)
                MonitorStatus.Stopped -> current
            }
        }
    }
}

package com.example.devicemonitor.adapter.outbound

import android.content.Context
import android.util.Log
import androidx.work.CoroutineWorker
import androidx.work.ExistingPeriodicWorkPolicy
import androidx.work.PeriodicWorkRequest
import androidx.work.PeriodicWorkRequestBuilder
import androidx.work.WorkManager
import androidx.work.WorkerParameters
import com.example.devicemonitor.core.outbound.MonitorScheduler
import kotlin.time.Duration
import kotlin.time.Duration.Companion.milliseconds
import kotlin.time.toJavaDuration

// Outbound adapter: the monitor's timer on Android, behind the MonitorScheduler port. WorkManager
// runs MonitorWorker about every interval, with the app open or not, and keeps the schedule
// when the process ends and across reboots. Android picks the moment within each period.
class AndroidMonitorScheduler(context: Context) : MonitorScheduler {
    private val workManager = WorkManager.getInstance(context)

    override fun schedule(interval: Duration, tick: suspend () -> Unit) {
        currentTick = tick
        // Android's floor for periodic work is 15 minutes: never ask for less.
        val period = interval.coerceAtLeast(PeriodicWorkRequest.MIN_PERIODIC_INTERVAL_MILLIS.milliseconds)
        val request = PeriodicWorkRequestBuilder<MonitorWorker>(period.toJavaDuration()).build()
        // One schedule however many launches call this: UPDATE keeps the work that is already
        // scheduled, with its timing, and only changes its period.
        workManager.enqueueUniquePeriodicWork(WORK_NAME, ExistingPeriodicWorkPolicy.UPDATE, request)
    }

    override fun cancel() {
        currentTick = null
        workManager.cancelUniqueWork(WORK_NAME)
    }

    internal companion object {
        const val WORK_NAME = "status-monitor"

        // WorkManager builds MonitorWorker itself, so the worker can't be handed the tick: it
        // finds it here, in the process they share. A new process gets it from onAppLaunch.
        @Volatile
        var currentTick: (suspend () -> Unit)? = null
    }
}

// What WorkManager runs each period, in the app's process: Android starts the process for it
// if it isn't running, and Application.onCreate runs first.
class MonitorWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        val tick = AndroidMonitorScheduler.currentTick
        Log.i("DeviceMonitor", if (tick == null) "Monitor work ran, but the monitor is stopped" else "Monitor tick")
        tick?.invoke()
        return Result.success()
    }
}

// Outbound adapter: the monitor's timer on iOS, behind the MonitorScheduler port. In the
// foreground the app runs as it likes, so a coroutine ticks every interval. In the background
// iOS suspends the app, so the adapter asks BGTaskScheduler to launch it again in about one
// interval, at the earliest; iOS decides when, or whether. Build it in the app start: its
// launch handler must be registered before the app finishes launching.
@OptIn(ExperimentalForeignApi::class, BetaInteropApi::class)
class IosMonitorScheduler : MonitorScheduler {
    private val scope = MainScope() // ticks run on the main thread, like the status adapters
    private val scheduler = BGTaskScheduler.sharedScheduler
    private var tick: (suspend () -> Unit)? = null
    private var interval = Duration.ZERO
    private var timer: Job? = null

    init {
        // Once per process, and during launch: registering after launch is an error, and a second
        // registration of the same identifier ends the app. false: the identifier isn't permitted.
        val registered = scheduler.registerForTaskWithIdentifier(TASK_ID, dispatch_get_main_queue()) { task ->
            refresh(task as BGAppRefreshTask)
        }
        check(registered) { "$TASK_ID isn't in BGTaskSchedulerPermittedIdentifiers (project.yml)." }
        // App-level lifecycle, not a screen's: these fire whichever screen is showing.
        val center = NSNotificationCenter.defaultCenter
        center.addObserverForName(UIApplicationDidBecomeActiveNotification, null, NSOperationQueue.mainQueue) { _ ->
            scheduler.cancelTaskRequestWithIdentifier(TASK_ID) // the timer takes over
            startTimer()
        }
        center.addObserverForName(UIApplicationDidEnterBackgroundNotification, null, NSOperationQueue.mainQueue) { _ ->
            // Leaving the foreground: iOS will suspend the app, so hand over from the timer to
            // BGTaskScheduler. A launch straight into the background posts this too, with no
            // timer running: the refresh task that launched the app then submits the next one.
            if (timer?.isActive == true) {
                timer?.cancel()
                submit()
            }
        }
    }

    override fun schedule(interval: Duration, tick: suspend () -> Unit) {
        this.tick = tick
        this.interval = interval
        // At launch the app isn't active yet, and the notification starts the timer; later, start it now.
        if (UIApplication.sharedApplication.applicationState == UIApplicationState.UIApplicationStateActive) {
            startTimer()
        }
    }

    override fun cancel() {
        tick = null
        timer?.cancel()
        scheduler.cancelTaskRequestWithIdentifier(TASK_ID)
    }

    private fun startTimer() {
        val tick = tick ?: return
        timer?.cancel()
        timer = scope.launch {
            while (true) {
                delay(interval)
                println("Monitor tick (foreground)")
                tick()
            }
        }
    }

    // Asks iOS to launch the app in the background, not before one interval from now.
    private fun submit() {
        val request = BGAppRefreshTaskRequest(identifier = TASK_ID)
        request.earliestBeginDate = NSDate.dateWithTimeIntervalSinceNow(interval.inWholeSeconds.toDouble())
        memScoped {
            val error = alloc<ObjCObjectVar<NSError?>>()
            if (!scheduler.submitTaskRequest(request, error.ptr)) {
                // On the Simulator, always: it "doesn't support background processing".
                println("Monitor: no background refresh: ${error.value?.localizedDescription}")
            }
        }
    }

    // iOS launched (or woke) the app in the background for the refresh task.
    private fun refresh(task: BGAppRefreshTask) {
        val tick = tick
        if (tick == null) {
            task.setTaskCompletedWithSuccess(true)
            return
        }
        submit() // the next one first: this one may be cut short
        val work = scope.launch {
            println("Monitor tick (background)")
            tick()
            task.setTaskCompletedWithSuccess(true)
        }
        task.expirationHandler = {
            work.cancel()
            task.setTaskCompletedWithSuccess(false)
        }
    }

    private companion object {
        // Also listed in Info.plist, under BGTaskSchedulerPermittedIdentifiers (project.yml).
        const val TASK_ID = "com.example.devicemonitor.monitor"
    }
}

        assertEquals(15.minutes, scheduler.interval)

    }

        connection.state = ConnectionState.Connected(obd)
