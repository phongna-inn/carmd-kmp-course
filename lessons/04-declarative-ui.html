Part A — UI as a function of state (~2 h)

A1. Imperative vs declarative, by breaking one

In an imperative toolkit, widgets are objects that hold their own state, and your event handlers mutate them one call at a time: disable the button, show the spinner, set the label. In a declarative toolkit, you describe what the screen should look like for a given state, and the framework works out the changes. Android's docs put it as "conceptually regenerating the entire screen from scratch, then applying only the necessary changes" (Thinking in Compose).

Those two bugs are the whole argument. With n widgets and m events, imperative code has n × m places to forget an update. Declarative code has one function from state to screen. Three rules follow, and every track in this course uses them:

  
    
    
  1. UI is a function of state. The screen shows what the state says, nothing else (Thinking in Compose).
    2. 
    
  2. Single source of truth. Each piece of state lives in exactly one place. Android: "By moving state instead of duplicating it, we're ensuring there's only one source of truth" (State and Jetpack Compose). Apple: "Use state as the single source of truth for a given value type that you store in a view hierarchy" (State).
    3. 
    
  3. Derive, don't store. The status text, the button's enabled flag and the error colour are computed from isScanning and devices. Stored copies are how the two phones above drifted apart.
    4. 
  

  
From TypeScriptThis is React's model, or Angular templates with signals: the template is a function of component state, and you change state, never the DOM. Compose and SwiftUI are the same idea with a compiler plugin instead of a virtual DOM. XML Views and UIKit are jQuery-era: you hold references to widgets and set their properties.


  
A2. Re-running the UI, and where side effects go

  
When state changes, the framework calls your UI code again. Compose calls it recomposition: "the process of calling your composable functions again when inputs change", and it "skips the rest" whose inputs didn't change. SwiftUI re-evaluates a view's body: "When the value changes, SwiftUI updates the parts of the view hierarchy that depend on the value" (Apple: State).

  
The consequence you must design for: your UI function runs often, and you don't control when. Composables "might be re-executed as often as every frame", children "might run in any order", and a recomposition "may be skipped" (Thinking in Compose). So the UI function must have no side effects: no starting a scan, no writing a file, no incrementing a counter. Side effects go in one of two places:

  

  

    
WhereComposeSwiftUIXML / UIKit

    
an event callback (a tap)onClick = { … }, plus rememberCoroutineScope().launch for asyncButton(action:), plus Task { } for asyncclick listener / UIAction, then call render()

    
a lifecycle-bound effect (on appear)LaunchedEffect(key).task { } / .task(id:)onViewCreated / viewDidLoad (Lesson 02)

  

  

  
The scan starts on a tap, so in m01 it lives in a callback. Android's guide says the same: "trigger side-effects from callbacks such as onClick that always execute on the UI thread" (same page).

  
Imperative tracks: render() is your recompositionXML Views and UIKit never re-run your code for you. So the XML and UIKit screens below keep their state in a few properties and route every change through one render() function that sets every widget from that state. It's the declarative column of the toy, written by hand. When the team's legacy screens misbehave, the cause is usually a handler that skips render() and edits one widget directly.

// Stand-in for a real BLE scan until Lesson 08.
object SampleDevices {
    val all: List<Device> = listOf(
        Device(id = "C4:7C:8D:6A:01:10", name = "OBD-II Adapter", rssi = -48),
        Device(id = "C4:7C:8D:6A:01:11", name = "Heart Rate Monitor", rssi = -61),
        Device(id = "C4:7C:8D:6A:01:12", name = "Tire Pressure Sensor", rssi = -67),
        Device(id = "C4:7C:8D:6A:01:13", name = "Thermometer", rssi = -74),
        Device(id = "C4:7C:8D:6A:01:14", name = "Smart Scale", rssi = -85),
    )

    fun matching(filter: String): List<Device> =
        all.filter { it.name.contains(filter.trim(), ignoreCase = true) }

    fun find(id: String): Device? = all.firstOrNull { it.id == id }
}

  
    
    
  1. Device is a data class (Lesson 01), so two devices with the same fields are equal. Its id is the device's stable identity; you'll hand it to every list in B1. The fake ids look like Android MAC addresses. On iOS, real BLE ids are per-app UUIDs (Lesson 08).
    2. 
    
  2. object SampleDevices is a singleton. Swift sees it as SampleDevices.shared (Lesson 03's name table), so Swift calls SampleDevices.shared.matching(filter: query) and SampleDevices.shared.find(id: deviceId). Kotlin parameter names become Swift argument labels.
    3. 
    
  3. List<Device> arrives in Swift as [Device], and rssi: Int as Int32.
    4. 
    
  4. The fake scan has no delay. Waiting is the UI's job in m01. In Lesson 05 the delay moves into shared code as a Flow, and Lesson 08 replaces the fake with a real scanner.

// Stateful: owns the screen's state and the scan side effect.
@Composable
fun DeviceListScreen(onDeviceClick: (Device) -> Unit) {
    var filter by rememberSaveable { mutableStateOf("") }
    var foundIds by rememberSaveable { mutableStateOf<List<String>?>(null) }
    var isScanning by remember { mutableStateOf(false) }
    val scope = rememberCoroutineScope()

    DeviceListContent(
        filter = filter,
        onFilterChange = { filter = it },
        isScanning = isScanning,
        devices = foundIds?.mapNotNull { SampleDevices.find(it) },
        onScan = {
            val query = filter
            isScanning = true
            foundIds = null
            scope.launch {
                delay(1_500)
                foundIds = SampleDevices.matching(query).map { it.id }
                isScanning = false
            }
        },
        onDeviceClick = onDeviceClick,
    )
}

// Stateless: renders whatever it's given, reports events up.

  1. var filter by rememberSaveable { mutableStateOf("") }, read inside out. mutableStateOf creates an observable value: "Any changes to value schedule recomposition of any composable functions that read value". remember keeps it across recompositions. rememberSaveable also keeps it "across activity or process recreation", such as rotation (State and Jetpack Compose). by is a Kotlin property delegate, so you write filter instead of filter.value.
    2. 
    
  2. Why foundIds and not devices? rememberSaveable can only save types a Bundle holds (strings, numbers, Parcelables). A Kotlin Device from shared code isn't one of them. So the screen saves the ids, and devices is derived on each recomposition with SampleDevices.find.
    3. 
    
  3. isScanning uses plain remember on purpose. If the Activity is recreated mid-scan, the scan coroutine is cancelled (next point). A saved true would leave the screen saying "Scanning…" forever.
    4. 
    
  4. rememberCoroutineScope() gives a scope tied to this composable's place on screen. It's cancelled when the composable leaves (navigation, rotation). That's how a callback starts async work in Compose (Side-effects in Compose).
    5. 
    
  5. onScan is the event handler. It changes state synchronously first (isScanning = true, results cleared), and only then launches the slow part. The button is disabled from the very next frame, so a double tap can't start two scans.
    6. 
    
  6. val query = filter captures the filter at tap time. Reading filter after the 1.5 s delay would see whatever the user typed meanwhile.
    7. 
    
  7. Stateful wrapper, stateless content. DeviceListScreen owns state. DeviceListContent only receives values and lambdas: "state goes down … events go up". That's state hoisting and unidirectional data flow (same page). In Lesson 05 a shared ViewModel replaces the wrapper, and DeviceListContent doesn't change.
    8. 
    
  8. OutlinedTextField(value = filter, onValueChange = onFilterChange). The field displays only what state says. This lesson uses value + callback because it shows hoisting plainly and matches SwiftUI's binding.

  9. Column stacks children vertically, Arrangement.spacedBy(12.dp) spaces them, and Modifier.weight(1f) gives the list all the remaining height. Modifiers are applied in order. enabled = !isScanning on the Button is the toy's buttonEnabled, derived.

import android.graphics.Color
import android.os.Bundle
import android.view.LayoutInflater
import android.view.View
import android.view.ViewGroup
import androidx.fragment.app.Fragment
import androidx.lifecycle.lifecycleScope
import androidx.navigation.fragment.findNavController
import androidx.recyclerview.widget.DividerItemDecoration
import com.example.devicemonitor.SampleDevices
import com.example.devicemonitor.android.databinding.FragmentDeviceListBinding
import kotlinx.coroutines.delay
import kotlinx.coroutines.launch

class DeviceListFragment : Fragment() {
    // Screen state lives in fields; render() copies it into the views.
    private var foundIds: ArrayList<String>? = null
    private var isScanning = false

    private var binding: FragmentDeviceListBinding? = null
    private val adapter = DeviceAdapter { device ->
        val nav = findNavController()
        // A fast double tap delivers two clicks; only navigate from the list itself.
        if (nav.currentDestination?.id == R.id.deviceList) {
            nav.navigate(R.id.toDetail, Bundle().apply { putString("deviceId", device.id) })
        }
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        foundIds = savedInstanceState?.getStringArrayList("foundIds")
    }

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        val b = FragmentDeviceListBinding.inflate(inflater, container, false)
        binding = b
        b.deviceList.adapter = adapter
        b.deviceList.addItemDecoration(DividerItemDecoration(requireContext(), DividerItemDecoration.VERTICAL))
        b.scanButton.setOnClickListener { scan(b.filterInput.text.toString()) }
        render()
        return b.root
    }

    override fun onDestroyView() {
        super.onDestroyView()
        binding?.deviceList?.adapter = null // the adapter outlives the view; don't let it keep the old list
        binding = null
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)
        outState.putStringArrayList("foundIds", foundIds)
    }

    private fun scan(query: String) {
        isScanning = true
        foundIds = null
        render()
        lifecycleScope.launch {
            delay(1_500)
            foundIds = ArrayList(SampleDevices.matching(query).map { it.id })
            isScanning = false
            render()
        }
    }

    // The one place that touches views: every state change ends here.
    private fun render() {
        val b = binding ?: return
        val devices = foundIds?.mapNotNull { SampleDevices.find(it) }
        b.scanButton.isEnabled = !isScanning
        b.progress.visibility = if (isScanning) View.VISIBLE else View.GONE
        b.statusText.text = when {
            isScanning -> "Scanning…"
            devices == null -> "Tap Scan to look for devices."
            devices.isEmpty() -> "No devices found. Try another filter."
            else -> "Devices found: ${devices.size}"
        }
        b.statusText.setTextColor(if (devices?.isEmpty() == true) Color.RED else Color.DKGRAY)
        adapter.submitList(devices.orEmpty())
    }
}

  
    
    
  1. ConstraintLayout. Each view pins its edges to the parent or to a sibling (layout_constraintTop_toBottomOf="@id/filterInput"). layout_width="0dp" means "match constraints": stretch between the two horizontal anchors. The RecyclerView's 0dp height stretches from the status line to the bottom. The status text sits 8dp after the progress bar (layout_marginStart). When the bar is GONE, layout_goneMarginStart="0dp" replaces that margin, so the text lines up with the field above it.
    2. 
    
  2. State is two fields: foundIds and isScanning. The views are a copy of it, and render() is the only function that writes to views. That's the declarative column of the A1 toy, by hand.
    3. 
    
  3. ViewBinding. FragmentDeviceListBinding is generated from the layout file name (buildFeatures { viewBinding = true }, B3), with one typed field per view id. No findViewById, no casts.
    4. 
    
  4. binding is nullable. A Fragment outlives its views: when you navigate to the detail screen, the Fragment stays on the back stack but onDestroyView runs. render() returns early when there is no view. When you come back, onCreateView builds fresh views and calls render(), so they show the current state.
    5. 
    
  5. onSaveInstanceState + getStringArrayList is rememberSaveable by hand: the results survive rotation as a list of ids. The EditText saves its own text, because it has an id.
    6. 
    
  6. scan() sets state and renders synchronously, then launches the slow part in the Fragment's lifecycleScope. That scope lives as long as the Fragment, not its views. So a scan started before you open the detail screen finishes while you're there, and its results show when you return. Rotation destroys the Fragment and cancels the scan (A5).
    7. 
    
  7. query is captured at tap time, before the delay.
    8. 
    
  8. The adapter's click handler checks currentDestination before navigating. A fast double tap delivers two clicks, and the second would call navigate(R.id.toDetail) from the detail screen, where that action doesn't exist: the app crashes (B4).
    9. 
    
  9. adapter = null in onDestroyView. The adapter is a Fragment field. When a RecyclerView is given an adapter, it registers itself as the adapter's observer. Without this line, the Fragment on the back stack would keep the destroyed list alive through the adapter.
    10.

In XML, nothing stops a click listener from setting statusText directly and skipping render(). The rememberSaveable line is three methods in XML (onCreate, onSaveInstanceState, the field). struct DeviceListView: View {
    @State private var filter = ""
    @State private var devices: [Device]? = nil
    @State private var isScanning = false

    var body: some View {
        VStack(alignment: .leading, spacing: 12) {
            TextField("Device name filter", text: $filter)
                .textFieldStyle(.roundedBorder)
                .autocorrectionDisabled()
            Button(action: scan) {
                Text("Scan")
                    .frame(maxWidth: .infinity)
            }
            .buttonStyle(.borderedProminent)
            .disabled(isScanning)
            ScanStatus(isScanning: isScanning, devices: devices)
            List(devices ?? [], id: \.id) { device in
                NavigationLink(value: DeviceRoute(id: device.id)) {
                    DeviceRow(device: device)
                }
            }
            .listStyle(.plain)
        }
        .padding()
        .navigationTitle("Device Monitor")
    }

    private func scan() {
        let query = filter
        isScanning = true
        devices = nil
        Task {
            try? await Task.sleep(for: .seconds(1.5))
            devices = SampleDevices.shared.matching(filter: query)
            isScanning = false
        }
    }
}

}

  1. @State private var: "SwiftUI manages the property's storage. When the value changes, SwiftUI updates the parts of the view hierarchy that depend on the value" (Apple: State).     2. 
    
  2. TextField(…, text: $filter). $filter is a Binding, a read-write reference to the state. The field shows filter and writes keystrokes back into it. It's Compose's value + onValueChange in one argument.
    3. 
    
  3. Button(action: scan) { Text("Scan").frame(maxWidth: .infinity) }. The frame sits on the label. Put .frame(maxWidth: .infinity) on the Button instead, and you get a small centred button in a wide invisible frame (see the B4 gotcha).
    4. 
    
  4. .disabled(isScanning) is derived, like Compose's enabled = !isScanning.
    5. 
    
  5. scan() changes state synchronously, then starts a Task for the wait. A View is @MainActor, so the Task inherits the main actor, and the writes after await happen on the main thread (B2). It's an unstructured task (Lesson 01): leaving the screen doesn't cancel it. That's harmless here, because the list is the root screen.     6. 
    
  6. let query = filter captures the filter at tap time.
    7.

            stack.bottomAnchor.constraint(equalTo: view.bottomAnchor),

        let query = filterField.text ?? ""
        isScanning = true
        devices = nil
        render()
        Task {
            try? await Task.sleep(for: .seconds(1.5))
            devices = SampleDevices.shared.matching(filter: query)
            isScanning = false
            render()
        }

        scanButton.isEnabled = !isScanning

        spinner.isHidden = !isScanning

            statusLabel.text = "Scanning…"

        snapshot.appendSections([0])

B1. Lists need stable keys

  
A list widget reuses row views and animates insertions, moves and removals. To do that, it must know which row is which across updates, and position isn't enough. By default Compose keys each item "against the position of the item", so "items which change position effectively lose any remembered state". B2. Async updates and the main-thread rule

  
Every UI toolkit here is single-threaded. Android's two rules are "Don't block the UI thread" and "Don't access the Android UI toolkit from outside the UI thread", because "the Android UI toolkit is not thread-safe" (Processes and threads). On iOS, UIViewController and SwiftUI's View are @MainActor, and the Swift 6 compiler checks it (Lesson 01). The m01 scan follows both rules: delay and Task.sleep suspend without blocking a thread, and the state updates after them run on the main thread.

  
To see what each toolkit does when you break the second rule, we moved the post-scan update onto a background thread on each track:

XMLwithContext(Dispatchers.Default) { render() }Crash: CalledFromWrongThreadException: Only the original thread that created a view hierarchy can touch its views. Expected: main Calling: DefaultDispatcher-worker-1

    
SwiftUITask.detached { devices = … }Compiler warning (Swift 6 mode): main actor-isolated property 'devices' can not be mutated from a nonisolated context. Apple documents @State as safe to mutate from any thread, so it's a warning rather than an error. This course treats warnings as errors.

The rule to carry forward: do slow work off the main thread, and publish UI state on it. In Lesson 08, BLE callbacks arrive on a Binder thread (Android) or a CoreBluetooth queue (iOS), and the adapter's job is to get them back to the main thread before the UI sees them.

B4. What actually happens

  
We built m01 with the brief below (Kotlin 2.4.21, AGP 9.4.1, Compose BOM 2026.09.00, Navigation 2.10.2, Xcode 26.2) and ran it on the Android 16 emulator and the iOS 26.2 simulator. Tap Scan: the button greys out and "Scanning…" shows with a spinner for 1.5 s. Then "Devices found: 5" and five rows, strongest signal first. A filter of sens finds one device, and zzz shows the red error. Tapping a row opens the detail screen, and Back returns to the list with the results still there.

  

    
    
    
    
  

  

    Gotcha · Android: a fast double tap navigates twice
    
    
      
  • Compose: with onClick = { navController.popBackStack() }, two fast taps on our Back button popped the detail screen and then the list, leaving an empty NavHost and a blank app. dropUnlessResumed { … } (from lifecycle-runtime-compose) fixed it: the second tap arrives while the list isn't resumed yet, and it's dropped.
    • 
      
  • Fragments, worse because it's hidden: two truly simultaneous taps on an unguarded Back left the list on screen but popped its back-stack entry too. The next row tap crashed with IllegalArgumentException: Navigation action/destination …:id/toDetail cannot be found from the current destination. An unguarded double tap on a row crashed immediately, the same way. Checking currentDestination?.id before navigate/popBackStack fixed both. Tapping slowly by hand, or through one adb session, never showed the problem. It took two parallel adb sessions.
    • 
    

  

  

    Gotcha · Compose: remember forgets when you navigate away
    Swap rememberSaveable for remember on the results, open a device, come back: the results are gone. We reproduced this. NavHost removes the list screen from composition while the detail is shown, and only saved state is restored. SwiftUI's root view, by contrast, stays alive under the pushed screen.
  

  

    Gotcha · SwiftUI: .task and onAppear run again when you come back
    We logged a .task on the list view. It ran at launch and again after popping back from the detail screen, while the @State was untouched. Don't start a scan in .task or onAppear unless you want it on every return. This is Lesson 02's view lifecycle at work.
  

  

    Gotcha · layout surprises we hit
    
    
      
  • SwiftUI: Button("Scan") { … }.frame(maxWidth: .infinity) rendered a small centred button. The frame belongs on the label inside the button.
    • 
      
  • XML: android:fitsSystemWindows="true" on the FragmentContainerView was ignored, and the title drew under the status bar. Wrapping it in a FrameLayout that has the attribute fixed it.
    • 
      
  • XML: AppCompat buttons render their text in capitals ("SCAN"). UI-automation tools and tests see the capitalised text.
    •
