1. What connecting means

A scan only listens. To read or receive a device's data (Lessons 15–16), the phone has to connect: Android's guide says "To connect to a GATT server on a BLE device, use the connectGatt() method", and "The caller (the Android app) is the GATT client" (Connect to a GATT server). On iOS, CBCentralManager's connect(_:options:) "Initiates a connection to peripheral" (CBCentralManager.h). Today the app only opens and closes that link and shows where it stands.

Lesson 13 listed the four states both platforms name: disconnected, connecting, connected, disconnecting. The app core gets its own ConnectionState, in the app's terms, and it needs only three:

  • App core
  1. No disconnecting state. Once the app has asked to disconnect, it's done with the device and doesn't wait for the radio to confirm. The adapters free what they hold at once (sections 4 and 5).
  2. No failed state either. A failure is a moment, not a place to stay: the state goes back to Disconnected, and the reason travels as a ConnectionException to whoever called connect. The screen shows it with Lesson 08's pattern, errorMessage plus errorShown(), as the list does with ScanException.
  3. The device is in the state, so any screen can say what the app is connected to, not only the screen that connected.

2. Two new ports

First the app's words: the state, and the error.

ConnectionException is ScanException's twin: one class, a message for the user, thrown by the service and the adapters. The outbound port has the shape you met in Lesson 13's BleScanner.scan():

  1. One call, three jobs. Collecting connects, each emitted value reports the link's state, and cancelling disconnects. Both adapters build it with callbackFlow, so awaitClose is where the radio's link is closed, whatever ended it.
  2. Why not connect(), disconnect() and a state flow, as the course plan's Appendix A.3 suggests? The plan calls its names a suggestion and the behaviour the requirement. With three separate calls, every adapter would have to keep state between them, and a forgotten disconnect() would leave a link open. Here, ending the collection always closes it: one rule, the one Lesson 13 used for the radio's scan.

The inbound port is what the ViewModels see. It has the plan's three members:

  1. connectionState is a StateFlow: it always has a value, so a screen that opens later can read where things stand at once (Lesson 08).
  2. connect suspends for the whole connection, not just until the link is up. Whoever calls it decides how long the connection may live: the coroutine it runs in. Section 7 shows why that matters more than anything else in this lesson.
  3. Three ways out of connect: it returns after disconnect(), it throws CancellationException when its caller is cancelled, and it throws ConnectionException on a failure.

3. The session service

The rules go in SessionService: the same on both platforms, and tested once on the JVM.

  1. The service owns the state. Only the service writes it, and the adapters only report. Whatever ends the connection, finally leaves the state at Disconnected, so no screen can be left showing "connected" for a link that's gone.
  2. The permission first, as in ScanningService: Android's connectGatt is declared @RequiresPermission(BLUETOOTH_CONNECT) (Android's source), and Lesson 12's Permission.Bluetooth already covers BLUETOOTH_CONNECT on Android 12 and later.
  3. One device at a time is this app's rule. The screen also hides Connect while a connection is open, but that's presentation (Lesson 13's argument): the rule lives where every caller goes through it.
  4. The state is set to Connecting before the first suspension, so a second connect right behind the first already sees it.
  1. link is a child coroutine inside coroutineScope, and disconnect() cancels it. A cancelled child doesn't fail its parent, so coroutineScope then returns normally and connect returns: a disconnect the app asked for isn't an error.
  2. A failure fails the scope. A ConnectionException from the adapter's flow, or from giveUp, cancels the link and leaves coroutineScope, and so connect, with that exception. Cancelling the collection runs the adapter's awaitClose: the radio's link closes on every path.
  3. Why a timeout? Apple: "Connection attempts never time out" (CBCentralManager.h, connectPeripheral:options:). Without the app's own limit, a device that's switched off would leave the iPhone screen on "connecting…" for good. On our API 30 emulator, Android's own attempt ended after about 30 seconds (section 7), so 10 seconds is the app's choice on both platforms. giveUp is cancelled once the link is up: the limit is for connecting, not for being connected.

4. The Android link: connectGatt

Android's guide: connectGatt takes "a Context object, autoConnect (a boolean indicating whether to automatically connect to the BLE device as soon as it becomes available), and a reference to a BluetoothGattCallback", and "returns a BluetoothGatt instance, which you can then use to conduct GATT client operations" (Connect to a GATT server). Same pattern as the scanner: a callback object, turned into a Flow by callbackFlow.

  1. onConnectionStateChange is the "Callback indicating when GATT client has connected/disconnected to/from a remote GATT server". Its status is "GATT_SUCCESS if the operation succeeds", and newState "Can be one of STATE_DISCONNECTED or STATE_CONNECTED" (BluetoothGattCallback, Android's source). Only one combination means the link is up. Every other call ends the flow with an error.
  2. linked tells the two errors apart: a failure before the link was up ("The connection failed"), or a drop after ("was lost"). The status is in the message, as the scanner put its error code there; Lesson 16 deals with drops properly.
  3. A background thread. With no Handler, "callbacks will happen on an un-specified background thread" (BluetoothDevice.connectGatt's documentation in Android's source). In our API 30 run (section 7), the callback's log lines came from a thread other than the main one. That's fine here: callbackFlow's ProducerScope "can be used from any context", and the service collects on the ViewModel's thread.
  4. Bluetooth off is checked here, as the scanner checks for a missing bluetoothLeScanner. The port has no isEnabled(): the adapter is the one that knows.
  1. getRemoteDevice(device.id): the id is the address from the scan. "A BluetoothDevice will always be returned for a valid hardware address, even if this adapter has never seen that device" (BluetoothAdapter, Android's source). Android's guide connects the same way, from an address.
  2. autoConnect = false: "Whether to directly connect to the remote device (false) or to automatically connect as soon as the remote device becomes available (true)". The user just tapped Connect, so the app connects now.
  3. TRANSPORT_LE is the "preferred transport for GATT connections to remote dual-mode devices": a device that speaks both Bluetooth Classic and BLE is reached over BLE.
  4. @Suppress("DEPRECATION"): the course compiles against API 37, where every Context-taking connectGatt is @Deprecated in favour of connectGatt(BluetoothGattConnectionSettings, Executor, BluetoothGattCallback) (API 37's android.jar and its stub sources). That one doesn't exist on API 36 or below, and the app runs from API 26, so the old call stays, with a comment saying why.
  5. ?: throw: Kotlin sees Java's return type as BluetoothGatt!, and in Android's source connectGatt returns null when it can't reach the system's GATT service. The explicit type and the elvis turn that into a message instead of a crash later.
  6. disconnect() then close(): disconnect "Disconnects an established connection, or cancels a connection attempt currently in progress", and for close, "Application should call this method as early as possible after it is done with this GATT client" (BluetoothGatt, Android's source). The guide's own words: "One important step when dealing with Bluetooth connections is to close the connection when you are finished with it." awaitClose runs on every way out: disconnect(), the caller's cancellation, the timeout and the errors above.

5. The iOS link, in Swift

The same problem as Lesson 13: the port returns a Kotlin Flow, and Swift can't build one. So the same answer: a few lines of Kotlin in iosMain build the Flow, and the Swift class feeds it.

ScanFlow.kt with the names changed: open and close instead of startScan and stopScan, and a feed that reports states instead of devices. Like IosRadio, IosLink is not a port: it's the seam between the two halves of one adapter. The Swift half:

  1. Its own CBCentralManager, created the first time the app connects, after the service has checked the permission (Lesson 13's order rule). makeManager() is the scanner's, with CBCentralManagerOptionShowPowerAlertKey: false.
  2. open may have to wait: a new manager's state is unknown until centralManagerDidUpdateState. Lesson 13's scanner parked a continuation for that; this class has a simpler choice, because open doesn't return anything: it remembers the device and feed, and the delegate callback calls start (next excerpt).
  3. cancelPeripheralConnection "Cancels an active or pending connection to peripheral. Note that this is non-blocking" (CBCentralManager.h). The adapter doesn't wait for the confirmation either: once close has run, it forgets the peripheral.
  1. retrievePeripherals(withIdentifiers:) "Attempts to retrieve the CBPeripheral object(s) with the corresponding identifiers" (CBCentralManager.h). The id the scanner put in Device is the peripheral's identifier UUID (Lesson 13), so the connection doesn't need the scanner's objects. Whether a second manager in the same app gets the peripheral the first one discovered is something only a phone can show: it's on the device-check list.
  2. peripheral = found keeps it alive. "Pending attempts are cancelled automatically upon deallocation of peripheral" (CBCentralManager.h, connectPeripheral:options:). Without the property, found would be a local constant, released when start returns, and its deallocation would cancel the attempt manager.connect had just started. This is Lesson 13's "a discovered peripheral must be retained" again, now with a connection at stake.
  3. Three delegate calls report the outcome: didConnect "when a connection initiated by connectPeripheral:options: has succeeded"; didFailToConnect when it "has failed to complete"; and didDisconnectPeripheral, where "If the disconnection was not initiated by cancelPeripheralConnection, the cause will be detailed in the error parameter" (all CBCentralManager.h). So a nil error means the app's own close(), and nothing is waiting for it.
  4. === compares object identity: a late callback about a peripheral this adapter has already let go of changes nothing.
  5. end(with:) takes the feed, calls close(), then feed.failed(message:), which closes the Kotlin flow with a ConnectionException. Kotlin's awaitClose then calls close() a second time, which does nothing. In centralManagerDidUpdateState, the adapter either calls start (an open was waiting for the state) or, with a link open and the state below poweredOn, ends it with "Bluetooth was turned off.".
Gotcha · the Simulator has no radio to connect with As in Lesson 13, the iOS Simulator's manager reports unsupported, so Connect ends at once with "This phone has no Bluetooth LE radio." (message(for:)). That's the real adapter working. To see a connection succeed without a phone, bind SimulatedBleScanner and SimulatedBleConnection instead (section 8 and the unaided exercise).

6. The detail screen

The ViewModel is the second inbound adapter, and its whole job is to decide where the connection's coroutine runs:

  1. DeviceDetailUiState has two fields: connection (the session's state) and errorMessage. The device itself isn't in it: the screen got it from the list.
  2. No onCleared() override. Clearing a ViewModel cancels viewModelScope (Lesson 08), that cancels session.connect, and the service's link and the adapter's awaitClose follow. The test theConnectionEndsWhenTheScreenIsGoneForGood checks it.
  3. Only ConnectionException is caught. A CancellationException from a cleared ViewModel must go on up, so the coroutine ends as cancelled.

The detail screen needs the whole Device, not just its id: at m08 it looked the id up in SampleDevices, and a real device came out as "Unknown device" (Lesson 13's gotcha). Now the list hands over the device, and the screen shows a status line and one button, Connect or Disconnect, like Scan and Stop.

The route copies the device's three fields rather than holding a Device: a route class is @Serializable, and the app core doesn't depend on kotlinx.serialization.

koinViewModel() inside a composable<DeviceDetail> destination gets a ViewModel scoped to that back stack entry, as the list's is (Lesson 11). ConnectionStatus shows "Status: not connected", "Status: connecting…" with a small progress indicator, or "Status: connected".

The navigation graph declares the two new arguments under deviceDetail: deviceName as a string and deviceRssi as an integer.

by viewModel() scopes the ViewModel to the Fragment: it survives rotation and is cleared when the Fragment leaves the back stack for good (Lesson 11). The layout gains a row with a ProgressBar and statusText, and connectButton, above Back.

XML vs Compose · what changed and whyCompose's route is a @Serializable class with the three fields; the XML graph declares them as arguments and the Fragment reads them from a Bundle. Either way the device crosses as plain values, and the screen rebuilds the Device. The ViewModel, its scope and what clears it are the same.

In Shared.h, SharedDevice derives from SharedBase : NSObject and declares isEqual: and hash, the Kotlin data class's equals and hashCode. NSObject is Hashable in Swift through those two, so the struct gets Hashable for free. The list's NavigationLink now passes DeviceRoute(device: device).

render(_:) switches on onEnum(of: state.connection) for the status text, runs the spinner while connecting, and sets the button's title. The button's action holds [weak self], so the controller can be deallocated when it's popped.

UIKit vs SwiftUI · what changed and whySwiftUI's route carries the Device itself, because a route only has to be Hashable. UIKit passes it to the controller's initialiser. In both, the ViewModelOwner lives exactly as long as the screen (the view's @State, the controller's property), so popping the screen clears the ViewModel.

7. The trap: a connection kept in something that goes away

A BLE connection lives for seconds or minutes. The objects of a screen often live for less. Lesson 03 warned that rotation destroys the Activity, and that "a BLE connection object held in the Activity gets dropped mid-connection while the radio link may still be open". We ran exactly that on the API 30 emulator, with a throwaway screen that kept its BluetoothGatt in Compose's remember (state of the composition, so of the Activity) and called connectGatt on a tap:

StepWhat logcat and the screen showed
Tap Connectconnect() - device: BE:AC:10:00:00:01, auto: false, registerApp(), client 6 registered. The screen holds the BluetoothGatt
Rotatethe new Activity's screen holds nothing: its Close button closed null
Tap Connect againa second registerApp(): client 7, while client 6 was never closed (no close() or unregisterApp() for it in the log)
About 30 s after the first attemptonClientConnectionState() - status=133 for both clients, and the first one's callback, an object from the destroyed screen, still ran and logged

The beacon never answered, so this was only an attempt, but the shape is the same for a live link: after a rotation, nothing in the app can reach the old BluetoothGatt to close it, Android keeps its client registered, and its callback keeps a dead screen's objects reachable. The fix is not "remember harder". It's to put each thing where its lifetime fits:

  • Android (the screen)
  • Inbound adapter (the ViewModel and its scope)
  • App core and adapters, process-wide
  1. The radio's objects live in the adapter. No screen ever sees a BluetoothGatt or a CBPeripheral; the adapter and the session service are Koin singles. Lesson 03's map put the connection there: "Holding a BLE connection belongs in an Android BLE adapter, an outbound adapter behind an outbound port, outside the Activity".
  2. How long the connection lasts is decided by a scope. The ViewModel runs session.connect in viewModelScope. A rotation doesn't clear the ViewModel (Lesson 08), so the connection carries on. When the screen is gone for good, the ViewModel is cleared, the scope is cancelled, and awaitClose closes the link. Nothing has to remember to call close().
  3. We ran it on the API 30 emulator: Connect, rotate during the attempt, rotate back: one registerApp() only, and the screen still said "connecting…". Connect, then Back three seconds later: cancelOpen(), close() and unregisterApp() at once.
Gotcha · the screen's own scope is too short (Android) The scope matters as much as where the objects live. If the screen launched session.connect in Compose's rememberCoroutineScope() instead of the ViewModel's, a rotation would cancel it. Lesson 06 said why: that scope is "tied to this composable's place on screen. It's cancelled when the composable leaves (rotation, navigation)". We tried it with the simulated adapters on the API 36 emulator: connected, rotated, and the screen said "Status: not connected". The app had hung up on its own. The unaided exercise has you see it.
Gotcha · view teardown on iOS iOS doesn't rebuild a screen on rotation, but it has its own ways to lose a connection. An unretained peripheral: CoreBluetooth cancels a pending connection "upon deallocation of peripheral", so a CBPeripheral held only by a local constant, or by a view that goes away, ends the attempt; section 5 keeps it in the adapter. Disappear is not "gone": onDisappear and viewDidDisappear also run when another screen is pushed on top. Lesson 04's logs show it: pushing the detail screen logged ContentView onDisappear on SwiftUI and ViewController viewDidDisappear on UIKit. Disconnecting there would cut the link whenever a later lesson shows something on top of the detail screen. Here, the ViewModelOwner clears the ViewModel only when it is deinitialised: when the screen leaves the navigation stack. viewDidDisappear only stops the UIKit screen's collection of uiState.

8. Wiring: each platform passes its connection

  1. single for the session: its connectionState is the app's one truth about the connection, and its one-device rule only works if there's one service. A factory would give each screen its own state.
  2. The connection adapter goes through platformModule, like the scanner and for the same reasons: Android's needs a Context, and iOS's is a Swift object.

SimulatedBleConnection, in commonMain next to SimulatedBleScanner, is bound nowhere. It connects each sample device after one second and never answers for the Smart Scale. Passing both simulated adapters to initKoin is how you watch a connection on the emulator or the Simulator, where no real device can be reached.

  2. Retrieval checks

Answer from memory, without scrolling up.

Why does DeviceSession.connect(device) suspend for as long as the connection lasts, instead of returning once the link is up?

The connection is the call. In the app the call runs in viewModelScope, so the connection lasts as long as the detail screen's ViewModel, and clearing it closes the link through the adapter's awaitClose.

A screen kept its BluetoothGatt in Compose state and connected from it. The user rotates the phone. What happens to that connection?

Our API 30 run: after the rotation, the new screen held nothing, a second Connect registered a second client, and the first one's callback still logged status 133 thirty seconds later. Only close() unregisters a client.

Why does IosBleConnection keep the CBPeripheral in a property?

CBCentralManager.h: "Pending attempts are cancelled automatically upon deallocation of peripheral". A local constant would be released when start returns.

Where does the 10-second connection timeout live, and why there?

Apple: "Connection attempts never time out". The scan timeout is a screen's choice (how long this screen scans); "a device that doesn't answer has failed" is a rule for every caller, tested once with virtual time.

In centralManager(_:didDisconnectPeripheral:error:), error is nil. What happened?

"If the disconnection was not initiated by cancelPeripheralConnection, the cause will be detailed in the error parameter." So the adapter ends the Flow with a message only when there is an error.

Mixed review (interleaved)

On iOS, what clears DeviceDetailViewModel, and so ends the connection? (Lesson 08)

The owner lives in the view's @State (SwiftUI) or the controller's property (UIKit). Clearing the store cancels viewModelScope, as on Android.

Why is DeviceSession bound with single rather than factory? (Lesson 11)

A factory builds a new instance for each request: each screen would get its own state, and two services could each connect a device.

package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.DeviceSession
import com.example.devicemonitor.core.outbound.BleConnection
import com.example.devicemonitor.core.outbound.PermissionChecker
import kotlinx.coroutines.Job
import kotlinx.coroutines.coroutineScope
import kotlinx.coroutines.delay
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.launch
import kotlin.time.Duration.Companion.seconds

// Service: the app's connection rules. Connect only with the Bluetooth permission and to one
// device at a time, and give up on a device that doesn't answer within CONNECT_TIMEOUT. It owns
// the connection state that the screens show.
class SessionService(
    private val connection: BleConnection,
    private val permissions: PermissionChecker,
) : DeviceSession {
    private val state = MutableStateFlow<ConnectionState>(ConnectionState.Disconnected)
    override val connectionState: StateFlow<ConnectionState> = state.asStateFlow()
    private var link: Job? = null

    override suspend fun connect(device: Device) {
        if (permissions.check(Permission.Bluetooth) != PermissionStatus.Granted) {
            throw ConnectionException("Connecting needs the Bluetooth permission.")
        }
        if (state.value != ConnectionState.Disconnected) {
            throw ConnectionException("Another connection is open. Disconnect it first.")
        }
        state.value = ConnectionState.Connecting(device)
        try {
            coroutineScope {
                link = launch {
                    // iOS never gives up on a connection attempt, so the app does.
                    val giveUp = launch {
                        delay(CONNECT_TIMEOUT)
                        throw ConnectionException("${device.name} didn't answer within 10 seconds.")
                    }
                    connection.connect(device).collect { linkState ->
                        state.value = linkState
                        if (linkState is ConnectionState.Connected) giveUp.cancel()
                    }
                }
            }
        } finally {
            link = null
            state.value = ConnectionState.Disconnected
        }
    }

    // Cancelling the link ends its collection, and the adapter closes the radio's link.
    override fun disconnect() {
        link?.cancel()
    }

    companion object {
        val CONNECT_TIMEOUT = 10.seconds
    }
}

    val uiState: StateFlow<DeviceDetailUiState> = _uiState.asStateFlow()

    init {
        viewModelScope.launch {
            session.connectionState.collect { connection ->
                _uiState.update { it.copy(connection = connection) }
            }
        }
    }

    // The connection runs in viewModelScope, so it lasts as long as this ViewModel: through a

                _uiState.update { it.copy(errorMessage = e.message) }
            }
        }
    }

    fun disconnect() {
        session.disconnect()
    }

    fun errorShown() {

    }

package com.example.devicemonitor.adapter.outbound

import android.annotation.SuppressLint
import android.bluetooth.BluetoothAdapter
import android.bluetooth.BluetoothDevice
import android.bluetooth.BluetoothGatt
import android.bluetooth.BluetoothGattCallback
import android.bluetooth.BluetoothManager
import android.bluetooth.BluetoothProfile
import android.content.Context
import com.example.devicemonitor.core.ConnectionException
import com.example.devicemonitor.core.ConnectionState
import com.example.devicemonitor.core.Device
import com.example.devicemonitor.core.outbound.BleConnection
import kotlinx.coroutines.channels.awaitClose
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.callbackFlow

// Outbound adapter: a GATT connection over the phone's Bluetooth LE radio, behind the
// BleConnection port. BluetoothGatt reports to a callback object; callbackFlow turns those calls
// into a Flow, and closes the GATT client when the collector cancels.
class AndroidBleConnection(private val context: Context) : BleConnection {
    private val adapter: BluetoothAdapter? =
        context.getSystemService(BluetoothManager::class.java)?.adapter

    // SessionService checks the permission before every connection, so lint's check is suppressed.
    @SuppressLint("MissingPermission")
    override fun connect(device: Device): Flow<ConnectionState> = callbackFlow {
        val adapter = adapter
        if (adapter == null || !adapter.isEnabled) {
            throw ConnectionException("Bluetooth is off. Turn it on, then connect again.")
        }
        // Called on a background thread. trySend and close are safe from any thread.
        val callback = object : BluetoothGattCallback() {
            private var linked = false

            override fun onConnectionStateChange(gatt: BluetoothGatt, status: Int, newState: Int) {
                when {
                    status == BluetoothGatt.GATT_SUCCESS && newState == BluetoothProfile.STATE_CONNECTED -> {
                        linked = true
                        trySend(ConnectionState.Connected(device))
                    }
                    linked -> close(ConnectionException("The link to ${device.name} was lost (Android status $status)."))
                    else -> close(ConnectionException("The connection failed (Android status $status)."))
                }
            }
        }
        send(ConnectionState.Connecting(device))
        // The id is the address the scan reported. false: connect directly, now. Android 17 (API 37)
        // deprecates this connectGatt for a new one that older phones don't have.
        @Suppress("DEPRECATION")
        val gatt: BluetoothGatt = adapter.getRemoteDevice(device.id)
            .connectGatt(context, false, callback, BluetoothDevice.TRANSPORT_LE)
            ?: throw ConnectionException("Android couldn't start the connection.")

        awaitClose {
            // Whatever ended the link, close the GATT client, or Android keeps it registered.
            gatt.disconnect()
            gatt.close()
        }
    }
}

package com.example.devicemonitor.adapter.outbound

import com.example.devicemonitor.core.ConnectionException
import com.example.devicemonitor.core.ConnectionState
import com.example.devicemonitor.core.Device
import kotlinx.coroutines.channels.ProducerScope
import kotlinx.coroutines.channels.awaitClose
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.callbackFlow

// Swift can't build a Kotlin Flow, so the Swift connection asks for one here, as the Swift
// scanner does in ScanFlow.kt. Collecting the Flow calls the link's open; cancelling the
// collector calls its close. Not a port: it's the Kotlin half of the iOS adapter.
fun connectFlow(link: IosLink, device: Device): Flow<ConnectionState> = callbackFlow {
    link.open(device, LinkFeed(this))
    awaitClose { link.close() }
}

// What the Swift connection implements for connectFlow: open and close the real link.
interface IosLink {
    fun open(device: Device, feed: LinkFeed)
    fun close()
}

// Where the Swift connection reports: each state of the link, or the failure that ends it.
class LinkFeed internal constructor(private val scope: ProducerScope<ConnectionState>) {
    fun changed(state: ConnectionState) {
        scope.trySend(state)
    }

    fun failed(message: String) {
        scope.close(ConnectionException(message))
    }
}

package com.example.devicemonitor.doubles

import com.example.devicemonitor.core.ConnectionException
import com.example.devicemonitor.core.ConnectionState
import com.example.devicemonitor.core.Device
import com.example.devicemonitor.core.outbound.BleConnection
import kotlinx.coroutines.channels.Channel
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow

// Fake: an outbound adapter written for tests, behind the BleConnection port. The test plays
// the radio and the device: whether and when the device answers, and whether the link fails.
class FakeBleConnection : BleConnection {
    private val events = Channel<Event>(Channel.UNLIMITED)
    var attempts = 0
        private set
    var isLinked = false // true while a collector holds the link
        private set

    override fun connect(device: Device): Flow<ConnectionState> = flow {
        attempts++
        isLinked = true
        try {
            emit(ConnectionState.Connecting(device))
            for (event in events) {
                when (event) {
                    Event.Answer -> emit(ConnectionState.Connected(device))
                    is Event.Fail -> throw ConnectionException(event.message)
                }
            }
        } finally {
            isLinked = false
        }
    }

    // The device answers: the link is up.
    fun answer() {
        events.trySend(Event.Answer)
    }

    // The attempt fails, or the link drops, with this message.
    fun fail(message: String) {
        events.trySend(Event.Fail(message))
    }

    private sealed interface Event {
        data object Answer : Event
        data class Fail(val message: String) : Event
    }
}

import CoreBluetooth
import Shared

// Outbound adapter: a link to one peripheral over the iPhone's radio, behind the Kotlin
// BleConnection port. Like the scanner, it is its own manager's delegate and Koin keeps it alive.
// It also keeps the CBPeripheral while the link lasts: CoreBluetooth cancels a pending
// connection when its peripheral is deallocated.
@MainActor
final class IosBleConnection: NSObject, @preconcurrency BleConnection, @preconcurrency IosLink,
    @preconcurrency CBCentralManagerDelegate {
    private var manager: CBCentralManager?
    private var peripheral: CBPeripheral?
    private var device: Device?
    private var feed: LinkFeed?

    // Swift can't build a Kotlin Flow, so it asks Kotlin for one (ConnectFlow.kt, in iosMain).
    func connect(device: Device) -> SkieSwiftFlow<ConnectionState> {
        connectFlow(link: self, device: device)
    }

    // IosLink: connectFlow calls these when the Flow is collected and when it is cancelled.
    func open(device: Device, feed: LinkFeed) {
        self.device = device
        self.feed = feed
        let manager = self.manager ?? makeManager()
        // A new manager learns the radio's state a moment later; centralManagerDidUpdateState
        // then calls start.
        if manager.state != .unknown && manager.state != .resetting { start(on: manager) }
    }

    func close() {
        if let peripheral, manager?.state == .poweredOn { manager?.cancelPeripheralConnection(peripheral) }
        peripheral = nil
        device = nil
        feed = nil
    }

    private func start(on manager: CBCentralManager) {
        guard let device, let feed, peripheral == nil else { return }
        guard manager.state == .poweredOn else { return end(with: message(for: manager.state)) }
        // The scanner found the device with its own manager; this one asks for it by identifier.
        guard let id = UUID(uuidString: device.id),
              let found = manager.retrievePeripherals(withIdentifiers: [id]).first else {
            return end(with: "This iPhone doesn't know \(device.name) any more. Scan again.")
        }
        peripheral = found
        feed.changed(state: ConnectionStateConnecting(device: device))
        manager.connect(found)
    }

    // Called on the main queue (queue: nil) when the link is up.
    func centralManager(_ central: CBCentralManager, didConnect peripheral: CBPeripheral) {
        guard peripheral === self.peripheral, let device else { return }
        feed?.changed(state: ConnectionStateConnected(device: device))
    }

    func centralManager(_ central: CBCentralManager, didFailToConnect peripheral: CBPeripheral,
                        error: Error?) {
        guard peripheral === self.peripheral else { return }
        end(with: "The connection failed: \(error?.localizedDescription ?? "no reason given").")
    }

    // error is nil when the app asked for the disconnection, in close(): nothing is waiting then.
    func centralManager(_ central: CBCentralManager, didDisconnectPeripheral peripheral: CBPeripheral,
                        error: Error?) {
        guard peripheral === self.peripheral, let error, let device else { return }
        end(with: "The link to \(device.name) was lost: \(error.localizedDescription)")
    }

    func centralManagerDidUpdateState(_ central: CBCentralManager) {
        guard central.state != .unknown, central.state != .resetting else { return }
        if peripheral == nil {
            start(on: central) // open() was waiting for the state
        } else if central.state != .poweredOn {
            end(with: "Bluetooth was turned off.")
        }
    }

    // Ends the Flow with the message; Kotlin then calls close().
    private func end(with message: String) {
        let feed = self.feed
        close()
        feed?.failed(message: message)
    }

    private func message(for state: CBManagerState) -> String {
        switch state {
        case .unsupported: "This phone has no Bluetooth LE radio."
        case .unauthorized: "Connecting needs the Bluetooth permission."
        default: "Bluetooth is off. Turn it on, then connect again."
        }
    }

    // No system alert when Bluetooth is off: the app shows its own message.
    private func makeManager() -> CBCentralManager {
        let manager = CBCentralManager(
            delegate: self, queue: nil,
            options: [CBCentralManagerOptionShowPowerAlertKey: false]
        )
        self.manager = manager
        return manager
    }
}

            guard let self else { return }
            if viewModel.uiState.value.connection is ConnectionStateDisconnected {
                viewModel.connect(device: device)
            } else {
                viewModel.disconnect()
            }
        }, for: .touchUpInside)

        let statusRow = UIStackView(arrangedSubviews: [spinner, statusLabel])
        statusRow.spacing = 8
        let stack = UIStackView(arrangedSubviews: [icon, nameLabel, idLabel, rssiLabel, statusRow, connectButton])
        stack.axis = .vertical
        stack.alignment = .center
        stack.spacing = 12
        stack.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(stack)
        NSLayoutConstraint.activate([
            stack.topAnchor.constraint(equalTo: view.layoutMarginsGuide.topAnchor, constant: 12),
            stack.leadingAnchor.constraint(equalTo: view.layoutMarginsGuide.leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: view.layoutMarginsGuide.trailingAnchor),
            connectButton.widthAnchor.constraint(equalTo: stack.widthAnchor),
        ])
        render(viewModel.uiState.value)
    }

    // Collect only while on screen, like repeatOnLifecycle(STARTED) on Android. Leaving the
    // screen stops the collection, not the connection.
    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        observation?.cancel()
        observation = Task {
            for await state in viewModel.uiState {
                render(state)
            }
        }
    }

    override func viewDidDisappear(_ animated: Bool) {
        super.viewDidDisappear(animated)
        observation?.cancel()
        observation = nil
    }

    // The one place that touches views: every new state ends here. SKIE turns the sealed
    // interface into a Swift enum, so this switch is exhaustive.
    private func render(_ state: DeviceDetailUiState) {
        let disconnected = state.connection is ConnectionStateDisconnected
        switch onEnum(of: state.connection) {
        case .disconnected:
            statusLabel.text = "Status: not connected"
            statusLabel.textColor = .label
        case .connecting:
            statusLabel.text = "Status: connecting…"
            statusLabel.textColor = .label
        case .connected:
            statusLabel.text = "Status: connected"
            statusLabel.textColor = .tintColor
        }
        let connecting = state.connection is ConnectionStateConnecting
        if connecting { spinner.startAnimating() } else { spinner.stopAnimating() }
        spinner.isHidden = !connecting
        connectButton.configuration?.title = disconnected ? "Connect" : "Disconnect"
        renderError(state.errorMessage)
    }

    private func renderError(_ message: String?) {
        guard let message, presentedViewController == nil else { return }
        let alert = UIAlertController(title: "Connection failed", message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default) { [weak self] _ in
            self?.viewModel.errorShown()
        })
        present(alert, animated: true)
    }
