1. BLE in a few words

Two roles first. Android's overview: "the device in the central role scans, looking for advertisement, and the device in the peripheral role advertises." The Device Monitor is a central. The thing it looks for (a sensor, a car adapter, or today LightBlue on your Mac) is a peripheral. A peripheral sends out short advertisements to anyone listening. An advertisement can carry a name, which is how our list shows one.

Once a central connects (Lesson 14), a second pair of roles takes over: "The device in the client role sends requests for data, and the device in the server role fulfills them". The phone is the GATT client, the peripheral the GATT server. GATT is "a general specification for sending and receiving short pieces of data known as 'attributes' over a BLE link" (BLE overview). Its data is a small tree:

  1. Service: "a collection of characteristics", for example a heart-rate service.
  2. Characteristic: it "contains a single value and 0-n descriptors that describe the characteristic's value." Descriptors describe that value, for example "a human-readable description, an acceptable range for a characteristic's value, or a unit of measure".
  3. UUID: every attribute "is uniquely identified by a Universally Unique Identifier (UUID), which is a standardized 128-bit format" (all three: BLE overview). The Bluetooth SIG publishes commonly used UUIDs, "many of which are 16- or 32-bits for convenience". A short one stands for a full UUID built on the Bluetooth base UUID, 00000000-0000-1000-8000-00805F9B34FB: "Core Bluetooth pre-fills the rest of the 128-bit UUID with the Bluetooth base UUID" (CBUUID). Android's public SDK has no constant for the base UUID, so on Android you write the full 128-bit form.

A characteristic's properties say what a central may do with its value. Apple's descriptions, from CoreBluetooth's CBCharacteristic.h header and the CBCharacteristicProperties docs:

Last, connection state. Both platforms name the same four states: Android's BluetoothProfile has STATE_DISCONNECTED, STATE_CONNECTING, STATE_CONNECTED and STATE_DISCONNECTING, and iOS's CBPeripheralState has disconnected, connecting, connected and disconnecting. Lesson 14 turns them into the app core's own ConnectionState. A scan has none of that: it only listens.

3. The port grows

A real radio can be missing (the Simulator) or switched off (the user). The app needs to know before it scans, so BleScanner gets two questions. As Appendix A.3 of the course plan puts it, isAvailable() and isEnabled() "come with the real radios":

  1. Why suspend? Android answers at once, but iOS can't. A new CBCentralManager's state is "initially set to CBManagerStateUnknown", which means "State unknown, update imminent", and the update arrives later, in a delegate callback (CoreBluetooth's CBManager.h). A suspend function lets the iOS adapter wait for it without blocking the main thread. The port is shaped for the slower platform, and the faster one doesn't mind.
  2. "The same device may come again." In m07 the comment promised a device "again with each advertisement it hears". That's true on Android, but iOS by default reports each peripheral once per scan: unless the app asks otherwise, "the central coalesces multiple discoveries of the same peripheral into a single discovery event" (CBCentralManagerScanOptionAllowDuplicatesKey). The port now promises only what both radios do. The service's "each device once" rule doesn't care either way.
  3. name = "" keeps Device as it is. Many peripherals advertise no name at all, and the port says how that looks instead of leaving each adapter to invent its own placeholder.

4. The service owns the scan rules

Should the app scan right now? That's a rule of the app, the same on both platforms, so it goes in ScanningService, next to the filter:

  1. A service can use more than one outbound port. ScanningService now needs PermissionChecker (Lesson 12's outbound port) as well as BleScanner. It asks the outbound port, not PermissionAccess: a service calls outbound ports, and only inbound adapters call inbound ports.
  2. Why check the permission here, when the screen already disables Scan? Disabling a button is presentation, and the next screen might forget. Android's startScan is declared @RequiresPermission(BLUETOOTH_SCAN), and on iOS the radio's first use is what prompts (Lesson 12). The rule "never touch the radio without the permission" belongs where every caller goes through it.
  3. The order matters on iOS. isAvailable() creates the iOS adapter's CBCentralManager. If the permission weren't granted yet, that would show the system prompt with no button tapped.
  4. The errors are ScanExceptions, and they're thrown inside flow { }, so they reach the collector exactly like a radio failure: the ViewModel's existing catch turns each into the "Scan failed" alert. No UI code changes for the three new messages.
  5. Skipping nameless devices is this app's rule: the user finds a device by its name, so a row without one is noise. It isn't the radio's business, so it isn't in the adapters.

5. The Android radio: callbackFlow

Android's guide: "To find BLE devices, you use the startScan() method. This method takes a ScanCallback as a parameter. You must implement this callback, because that is how scan results are returned" (Find BLE devices). The port wants a Flow. First, the two questions:

  1. No adapter, no Bluetooth: "If getAdapter() returns null, then the device doesn't support Bluetooth." And "Call isEnabled() to check whether Bluetooth is currently enabled" (Set up Bluetooth).
  2. FEATURE_BLUETOOTH_LE: Bluetooth Classic and BLE are separate features. Android's permissions page shows this runtime check, for apps that declare the feature with required="false" (Bluetooth permissions). The manifest now does, so a phone without BLE can still install the app and gets the "no Bluetooth LE radio" message:

The guide warns what required="true" would do: "the Google Play store will hide your app from users on devices lacking those features". Now the scan itself:

  1. callbackFlow is Kotlin's bridge from callbacks to a Flow. Its block runs each time someone collects, and the ProducerScope it gets "can be used from any context, e.g. from a callback-based API" (callbackFlow). In Lesson 01, emit(device) pushed each device. Here the radio's callback pushes it, with trySend.
  2. trySend, not send: a callback isn't a coroutine, so it can't suspend. trySend "never suspends and never throws exceptions". If the channel's buffer is full, the element is dropped. Losing one advertisement is fine: the radio will hear that device again.
  3. awaitClose keeps the flow open until the collector cancels, then runs the cleanup. The docs make it compulsory: "Using awaitClose is mandatory in order to prevent memory leaks when the flow collection is cancelled, otherwise the callback may keep running even when the flow collector is already completed." So cancelling the ViewModel's scan job ends up here, and here the radio stops.
  4. close(ScanException(…)) ends the flow with an error: "If the cause is non-null, it will be thrown … from all the attempts to receive from the channel after no elements remain" (close). It travels up through the service to the ViewModel's catch. onScanFailed gets an error code, one of ScanCallback's SCAN_FAILED_* constants, such as 1, "BLE scan with the same settings is already started by the app".
  5. bluetoothLeScanner can be null: "If Bluetooth is not enabled, then getBluetoothLeScanner() returns null" (Find BLE devices). The service checked a moment ago, but the user can switch it off in between.
  6. scanRecord?.deviceName is the name in the advertisement, "the local name of the BLE device". BluetoothDevice.getName() would also work, but it's declared @RequiresPermission(BLUETOOTH_CONNECT), and scanning shouldn't need the connect permission. The id is the device's address, for example "00:11:22:AA:BB:CC" (BluetoothDevice.getAddress()'s docs).
  7. SCAN_MODE_LOW_LATENCY: "Scan using highest duty cycle. It's recommended to only use this mode when the application is running in the foreground." Our scan runs from a screen, for 10 seconds at most.
  8. @SuppressLint("MissingPermission") silences Android lint's check that the permission was granted, because the service checks it. The comment says why, so nobody removes the service's check thinking lint has it covered.

One more piece. We switched Bluetooth off in the middle of a scan (adb shell cmd bluetooth_manager disable, API 36 emulator), with a version of the adapter that only logged. The callback got nothing: no onScanFailed. The screen said "Scanning…" until the timeout, then "No devices found", which is wrong. Android does broadcast the change: "your app can also listen for the ACTION_STATE_CHANGED broadcast intent, which the system broadcasts whenever the Bluetooth state changes" (Set up Bluetooth). So the adapter listens while it scans:

  1. Registered in the flow, unregistered in awaitClose: the receiver lives exactly as long as the scan. Android: "always unregister your broadcast receiver" (Broadcasts overview).
  2. RECEIVER_EXPORTED: "Some system broadcasts come from highly privileged apps, such as Bluetooth and telephony … To receive all system broadcasts, including broadcasts from highly privileged apps, flag your receiver with RECEIVER_EXPORTED" (same page).
  3. Why no isEnabled check before stopScan? isEnabled is true only when Bluetooth is fully on: "Equivalent to: getBluetoothState() == STATE_ON" (BluetoothAdapter.isEnabled). stopScan asks something else. In Android's source it starts with BluetoothLeUtils.checkAdapterStateOn, which passes while Bluetooth LE is still running: on, turning on, turning off, and the BLE-only mode below. The receiver closes the flow on the first state that isn't on, STATE_TURNING_OFF, so awaitClose usually runs before Bluetooth is off. We logged it on the API 36 emulator: in 4 runs out of 4, awaitClose ran while Bluetooth was turning off, isEnabled was false, and stopScan ran without throwing. Some phones also keep a BLE-only mode running for location's "Bluetooth scanning" after the user turns Bluetooth off; there isEnabled stays false, but a scan could still be running. A guard on isEnabled would skip stopScan in both places, so the adapter always calls it.
  4. Why catch IllegalStateException, and only that? Once Bluetooth is fully off, checkAdapterStateOn throws IllegalStateException("BT Adapter is not turned ON"). Android's docs for stopScan don't mention it; its source does. By then there's nothing to stop: when Bluetooth goes fully off, Android's scan service shuts down and drops every app's scan (in Android's source, ScanController.stop clears its scanners). To reach this case on the emulator, we made a throwaway copy of awaitClose wait 3 seconds first: stopScan threw "BT Adapter is not turned ON", the catch held it, and the screen showed "Bluetooth was turned off." as usual. Without the try, that run looked the same: the flow had already ended with our ScanException, and the second exception reached neither the screen nor logcat. Don't count on that. The catch says this one throw is expected; any other exception still goes to the flow. We couldn't put the emulator in BLE-only mode (on the API 36 emulator, adb shell cmd bluetooth_manager enableBle answers "Uid 2000 does not have access"), so whether stopScan ends a scan there needs a phone: the device checks cover it.
Gotcha · Android ignores a scan started too often, silently We tapped Scan and Stop five times within about ten seconds on the API 36 emulator, then Scan once more. That sixth scan never started. Logcat said App 'com.example.devicemonitor' is scanning too frequently, the callback got nothing, and the screen showed "Scanning…" for 10 seconds, then "No devices found". After waiting 31 seconds, scans worked again. Android's source explains the silence: ScanCallback has a SCAN_FAILED_SCANNING_TOO_FREQUENTLY code, but BluetoothLeScanner skips it with the comment "If scanning too frequently, don't report anything to the app." If a real device "can't be found" while you're testing, check logcat for that line before you suspect your code. It's also one more reason to keep scans few and long rather than many and short.

6. The iOS radio, in Swift

On iOS, CBCentralManager "scans for, discovers, connects to, and manages peripherals", and it reports everything to a delegate. Lesson 02 pictured the delegate's callback calling an AsyncStream's yield. That works when Swift code consumes the stream, but here the consumer is Kotlin's ScanningService, and it wants a Kotlin Flow. SKIE shows Kotlin flows to Swift, but "Conversions in the other direction (from AsyncSequence to Flow) are not supported" (SKIE: Flows). So Kotlin builds the Flow, and Swift feeds it. The Kotlin half is a few lines of plain Kotlin in iosMain, no Apple API:

  1. It's Android's callbackFlow again, with the callbacks turned around: Swift calls heard and failed, which are trySend and close underneath, and awaitClose calls Swift's stopScan.
  2. IosRadio is not a port. The app core never sees it, and it says nothing in the app's terms. It's the seam between the two halves of one adapter, in iosMain because only iOS uses it. Methods instead of Kotlin lambdas keep the Swift side plain: in our build, a Kotlin (Device) -> Unit parameter reached Swift as a block returning KotlinUnit.
  3. internal constructor: only scanFlow makes a ScanFeed, so a feed always belongs to a live scan.

The Swift half implements both protocols, BleScanner for the app core and IosRadio for scanFlow:

  1. __isAvailable: Lesson 12's rule for a Kotlin suspend fun: Swift implements the __-prefixed original as async throws. A suspend function's Boolean result crosses as KotlinBoolean: the exported header's completion handler passes a SharedBoolean object, not a plain BOOL. KotlinBoolean(bool:) wraps a Swift Bool.
  2. scan() -> SkieSwiftFlow<Device>: SKIE rewrites the protocol requirement too. Our first try returned the plain Objective-C Kotlinx_coroutines_coreFlow, and the compiler answered "protocol requires function 'scan()' with type '() -> SkieSwiftFlow<Device>'". SKIE also gives scanFlow(radio:) that return type, so the Kotlin Flow passes through Swift and back to Kotlin without Swift ever iterating it.
  3. @MainActor and @preconcurrency, as in Lesson 12's IosPermissionChecker: the manager calls its delegate on the main queue, and the Kotlin side calls the adapter from the ViewModel's coroutines on the main thread.
  1. withServices: nil means every advertising peripheral. Apple: "The recommended practice is to populate the serviceUUIDs parameter rather than leaving it nil" (scanForPeripherals). A product app that knows its peripheral's service UUID should scan for it. The Device Monitor finds devices by name, and a name can only be read once the advertisement has arrived, so it scans for everything and the service filters. Android's startScan(null, …) is the same choice.
  2. CBAdvertisementDataLocalNameKey: "The local name of a peripheral", the same advertised name Android's scanRecord.deviceName reads.
  3. peripheral.identifier is not the device's address. "The first time a local manager encounters a peer, the system assigns the peer a UUID" (CBPeer.identifier). So the same LightBlue device has a MAC-style id on Android and a UUID on iOS, as Lesson 06 warned. The app core treats both as an opaque String.
  4. RSSI is the signal strength "in dBm. A value of 127 is reserved and indicates the RSSI was not available" (CoreBluetooth's CBCentralManager.h). The app shows it as it comes.
  1. Lesson 12's waiting pattern, for a different answer: knownState parks a continuation, and the delegate resumes it once the state is known. resetting means "The connection with the system service was momentarily lost, update imminent", so it waits for that update too.
  2. Bluetooth turned off mid-scan. Apple: "A state with a value lower than poweredOn implies that scanning has stopped" (centralManagerDidUpdateState). Unlike Android, iOS tells the delegate, so the adapter ends the app's scan with a message instead of letting it wait for the timeout.
  3. CBCentralManagerOptionShowPowerAlertKey: false: the key decides "whether the system warns the user if the app instantiates the central manager when Bluetooth service isn't available", and "If the key isn't specified, the default value is true" (docs). The service already shows "Bluetooth is off", so the system's alert would be a second one.
  4. The manager is created on the first isAvailable(), after the service has checked the permission (section 4). This is the scanner's own manager. Lesson 12's permission adapter drops its manager once the user has answered.
Gotcha · the delegate is weak: keep the adapter alive CBCentralManager declares @property(nonatomic, weak, nullable) id<CBCentralManagerDelegate> delegate (CBCentralManager.h). A weak reference doesn't keep its object alive: when nothing else holds the delegate, Swift sets the reference to nil, and every callback after that goes nowhere. A common way to get there is a scanner object created inside a function, or a separate small delegate object that only the manager points to. The scan starts, and no device is ever reported. Here, the adapter is its own delegate, and Koin holds the adapter as a single for the life of the process (as with Lesson 12's adapter). The adapter holds the manager in a property. Lesson 14 meets the same rule for peripherals: "A discovered peripheral must be retained in order to use it; otherwise, it is assumed to not be of interest and will be cleaned up by the central manager."

8. Stop, and the timeout

A scan uses the radio, and the radio uses the battery. Android's guide: "As soon as you find the desired device, stop scanning", and "Never scan on a loop, and always set a time limit on your scan. A device that was previously available may have moved out of range, and continuing to scan drains the battery." Its sample stops after 10 seconds (Find BLE devices). The ViewModel has had a time limit since Lesson 08. It grows from 3 to 10 seconds, the scan period of Android's sample, and the screen gets a Stop:

  1. Why in the ViewModel, not the service? Lesson 10's answer still holds: how long this screen scans, and whether the user can stop it, is this screen's behaviour. The service's rules are true for every screen.
  2. Stop and the timeout end a scan the same way: by cancelling the collection. The timeout cancels the block inside withTimeoutOrNull; Stop cancels the whole job. Either way the cancellation reaches awaitClose in the adapter, which stops the radio (diagram below).
  3. Stop writes Finished itself. A cancelled coroutine doesn't run the line after withTimeoutOrNull, so stopScan sets the final state.

Each screen turns its Scan button into Stop while a scan runs. The button stays enabled while scanning, so the user can always stop.

The click listener is set once, in onCreateView, so it reads the ViewModel's current state when tapped. (The permission button works the other way: every render(), through renderPermission, gives it a new listener holding the status just drawn.) The layout doesn't change.

XML vs Compose · what changed and whyCompose picks the click handler and the label from isScanning each time it recomposes. The XML Fragment sets the label in render() and, since its listener is set once in onCreateView, asks the ViewModel's current state at the moment of the tap.

The UIKit list had a second dependency on the fake radio: its cells looked each id up in SampleDevices, so a real device would have drawn an empty row. Now render() keeps the devices it was given, by id, and the cell reads them. uniqueKeysWithValues is safe because the service reports each id once. [unowned self] avoids a retain cycle: the view controller owns the data source, which owns this closure.

UIKit vs SwiftUI · what changed and whyThe same button rule in both. SwiftUI's List draws each row from the Device it's given, so it needed no change for real devices. UIKit's diffable data source holds only ids, so the controller keeps the devices for its cells to read.

Gotcha · the detail screen still knows only the sample devices Every track's detail screen still looks its device up in SampleDevices by id. On the API 30 emulator we tapped a gDevice-beacon row and the detail screen said "Unknown device". The same happens for LightBlue on a phone. That's expected at m08: this lesson only scans. Lesson 14 is the one that needs the selected device, to connect to it.

Retrieval checks

Answer from memory, without scrolling up.

During a scan, which role does the phone play?

"The device in the central role scans, looking for advertisement, and the device in the peripheral role advertises." Client and server only matter once connected (Lesson 14), and then the phone is the client.

A characteristic has the indicate property. How is that different from notify?

Both push new values from the peripheral. Apple: notify is "without a response from the central to indicate receipt", indicate is "with a response".

Where does the rule "never start the radio without the Bluetooth permission" live, and why there?

The screens disable the button too, but that's presentation. Written once in the service, the rule covers every screen, and neverStartsTheRadioWithoutThePermission tests it on the JVM.

Why does the iOS adapter need ScanFlow.kt, a Kotlin file in iosMain?

SKIE converts flows from Kotlin to Swift only. So Kotlin's callbackFlow builds the Flow, and the Swift class feeds it through ScanFeed. Koin binds the Swift object itself without trouble.

What goes wrong if CBCentralManager's delegate is an object that nothing else keeps?

The delegate property is declared weak, so it doesn't keep the object alive. In the app, Koin keeps the adapter, and the adapter is its own delegate.

Why does AndroidBleScanner's awaitClose call stopScan inside a try instead of only if (adapter.isEnabled)?

isEnabled means fully on. stopScan's own check, in Android's source, passes while Bluetooth LE still runs. On the API 36 emulator, the cleanup ran while Bluetooth was turning off every time we logged it, and stopScan ran there without throwing. A guard would have skipped it, and in BLE-only mode a scan could keep running.

Mixed review (interleaved)

Stop cancels the ViewModel's scan job. How does that stop the Android radio? (Lesson 01)

Structured concurrency: cancelling a collector cancels the flows it collects. The ViewModel knows only the inbound port, so it couldn't call the adapter even if it wanted to.

The same LightBlue device has id 4A:… on Android and a UUID on iOS. Why doesn't the app core care? (Lessons 06 and 10)

The port speaks the app's language, and "each device once" only needs ids to be stable during a scan. What an id looks like is each adapter's business.

package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.DeviceScanning
import com.example.devicemonitor.core.outbound.BleScanner
import com.example.devicemonitor.core.outbound.PermissionChecker
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow

// Service: the app's scan rules on top of a raw radio scan. Start the radio only when the
// permission is granted and the radio is there and on. Then keep the devices that have a
// name containing the filter (ignoring case and surrounding spaces), and report each once.
class ScanningService(
    private val scanner: BleScanner,
    private val permissions: PermissionChecker,
) : DeviceScanning {
    override fun scan(nameFilter: String): Flow<Device> = flow {
        checkReady()
        val wanted = nameFilter.trim()
        val seen = mutableSetOf<String>()
        scanner.scan().collect { device ->
            val named = device.name.isNotBlank()
            if (named && device.name.contains(wanted, ignoreCase = true) && seen.add(device.id)) {
                emit(device)
            }
        }
    }

    // In this order: on iOS, the radio's first use is what shows the permission prompt.
    private suspend fun checkReady() {
        if (permissions.check(Permission.Bluetooth) != PermissionStatus.Granted) {
            throw ScanException("Scanning needs the Bluetooth permission.")
        }
        if (!scanner.isAvailable()) throw ScanException("This phone has no Bluetooth LE radio.")
        if (!scanner.isEnabled()) throw ScanException("Bluetooth is off. Turn it on, then scan again.")
    }
}

import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch
import kotlinx.coroutines.withTimeoutOrNull
import kotlin.time.Duration.Companion.seconds

// Inbound adapter: turns the screen's events into calls on the DeviceScanning and
// PermissionAccess ports, and the results into UI state. It knows the ports only.
class DeviceListViewModel(
    private val scanning: DeviceScanning,
    private val permissions: PermissionAccess,
) : ViewModel() {
    private val _uiState = MutableStateFlow(
        DeviceListUiState(bluetooth = permissions.status(Permission.Bluetooth)),
    )
    val uiState: StateFlow<DeviceListUiState> = _uiState.asStateFlow()

    private var scanJob: Job? = null
    private var permissionJob: Job? = null

    fun startScan(filter: String) {
        if (scanJob?.isActive == true) return
        _uiState.update { it.copy(scan = ScanState.Scanning(emptyList())) }
        scanJob = viewModelScope.launch {
            val found = mutableListOf<Device>()
            try {
                withTimeoutOrNull(SCAN_TIMEOUT) {
                    scanning.scan(filter).collect { device ->
                        found += device
                        _uiState.update { it.copy(scan = ScanState.Scanning(found.toList())) }
                    }
                }
                _uiState.update { it.copy(scan = ScanState.Finished(found.toList())) }
            } catch (e: ScanException) {
                _uiState.update { it.copy(scan = ScanState.Idle, errorMessage = e.message) }
            }
        }
    }

    // The Stop button. Cancelling the scan's coroutine cancels its collection, which stops the
    // service's scan and the radio. The devices found so far stay on screen.
    fun stopScan() {
        val job = scanJob ?: return
        if (!job.isActive) return
        job.cancel()
        _uiState.update { state ->
            val scan = state.scan
            if (scan is ScanState.Scanning) state.copy(scan = ScanState.Finished(scan.found)) else state
        }
    }

    fun errorShown() {
        _uiState.update { it.copy(errorMessage = null) }
    }

    // The screen calls this each time it comes back to the foreground: the user may have
    // changed the permission in Settings meanwhile.
    fun refreshPermission() {
        if (permissionJob?.isActive == true) return
        _uiState.update { it.copy(bluetooth = permissions.status(Permission.Bluetooth)) }
    }

    fun requestPermission() {
        if (permissionJob?.isActive == true) return
        permissionJob = viewModelScope.launch {
            val result = permissions.request(listOf(Permission.Bluetooth))
            _uiState.update { it.copy(bluetooth = result.getValue(Permission.Bluetooth)) }
        }
    }

    fun openSettings() {
        permissions.openSettings()
    }

    companion object {
        // A real radio drains the battery while it scans, so every scan has a time limit.
        val SCAN_TIMEOUT = 10.seconds
    }
}

import android.annotation.SuppressLint
import android.bluetooth.BluetoothAdapter
import android.bluetooth.BluetoothManager
import android.bluetooth.le.ScanCallback
import android.bluetooth.le.ScanResult
import android.bluetooth.le.ScanSettings
import android.content.BroadcastReceiver
import android.content.Context
import android.content.Intent
import android.content.IntentFilter
import android.content.pm.PackageManager
import androidx.core.content.ContextCompat
import com.example.devicemonitor.core.Device
import com.example.devicemonitor.core.ScanException
import com.example.devicemonitor.core.outbound.BleScanner
import kotlinx.coroutines.channels.awaitClose
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.callbackFlow

// Outbound adapter: the phone's Bluetooth LE radio, behind the BleScanner port.
// BluetoothLeScanner reports to a callback object; callbackFlow turns those calls into a Flow.
class AndroidBleScanner(private val context: Context) : BleScanner {
    private val adapter: BluetoothAdapter? =
        context.getSystemService(BluetoothManager::class.java)?.adapter

    override suspend fun isAvailable(): Boolean =
        adapter != null && context.packageManager.hasSystemFeature(PackageManager.FEATURE_BLUETOOTH_LE)

    override suspend fun isEnabled(): Boolean = adapter?.isEnabled == true

    // ScanningService checks the permission before every scan, so lint's check is suppressed.
    @SuppressLint("MissingPermission")
    override fun scan(): Flow<Device> = callbackFlow {
        val scanner = adapter?.bluetoothLeScanner ?: throw ScanException("Bluetooth is off.")
        val callback = object : ScanCallback() {
            override fun onScanResult(callbackType: Int, result: ScanResult) {
                val name = result.scanRecord?.deviceName.orEmpty()
                trySend(Device(id = result.device.address, name = name, rssi = result.rssi))
            }

            override fun onScanFailed(errorCode: Int) {
                close(ScanException("The scan failed (Android error $errorCode)."))
            }
        }
        // Turning Bluetooth off ends the scan without a call to the callback, so listen for it.
        // The broadcast comes from the Bluetooth app, so the receiver must be exported.
        val bluetoothOff = object : BroadcastReceiver() {
            override fun onReceive(context: Context, intent: Intent) {
                val state = intent.getIntExtra(BluetoothAdapter.EXTRA_STATE, BluetoothAdapter.ERROR)
                if (state != BluetoothAdapter.STATE_ON) close(ScanException("Bluetooth was turned off."))
            }
        }
        ContextCompat.registerReceiver(
            context, bluetoothOff, IntentFilter(BluetoothAdapter.ACTION_STATE_CHANGED),
            ContextCompat.RECEIVER_EXPORTED,
        )
        val settings = ScanSettings.Builder().setScanMode(ScanSettings.SCAN_MODE_LOW_LATENCY).build()
        scanner.startScan(null, settings, callback)

        awaitClose {
            context.unregisterReceiver(bluetoothOff)
            // Stop even when isEnabled is false: it's false while Bluetooth is turning off, and in
            // the BLE-only mode some phones keep for location's "Bluetooth scanning".
            try {
                scanner.stopScan(callback)
            } catch (e: IllegalStateException) {
                // Bluetooth is fully off, and going fully off drops every app's scan.
            }
        }
    }
}

// calls the radio's startScan; cancelling the collector calls its stopScan. Not a port: the
// app core never sees it. It's the Kotlin half of the iOS adapter.
fun scanFlow(radio: IosRadio): Flow<Device> = callbackFlow {
    radio.startScan(ScanFeed(this))
    awaitClose { radio.stopScan() }
}

// What the Swift scanner implements for scanFlow: start and stop the real radio.
interface IosRadio {
    fun startScan(feed: ScanFeed)
    fun stopScan()
}

// Where the Swift scanner reports: each device it hears, or the failure that ends the scan.
class ScanFeed internal constructor(private val scope: ProducerScope<Device>) {
    fun heard(device: Device) {
        scope.trySend(device)
    }

    fun failed(message: String) {
        scope.close(ScanException(message))
    }
}

// Outbound adapter: the iPhone's Bluetooth LE radio, behind the Kotlin BleScanner port.
// CBCentralManager reports everything to its delegate, this object, and holds it only weakly:
// Koin keeps this adapter alive for the life of the app, and the adapter keeps the manager.
@MainActor
final class IosBleScanner: NSObject, @preconcurrency BleScanner, @preconcurrency IosRadio,
    @preconcurrency CBCentralManagerDelegate {
    private var manager: CBCentralManager?
    private var waitingForState: [CheckedContinuation<Void, Never>] = []
    private var feed: ScanFeed?

    // The Kotlin suspend funs. As with __request in Lesson 12, Swift implements the
    // originals; a Kotlin Boolean crosses as KotlinBoolean.
    func __isAvailable() async throws -> KotlinBoolean {
        let state = await knownState()
        return KotlinBoolean(bool: state != .unsupported)
    }

    func __isEnabled() async throws -> KotlinBoolean {
        let state = await knownState()
        return KotlinBoolean(bool: state == .poweredOn)
    }

    // Swift can't build a Kotlin Flow, so it asks Kotlin for one (ScanFlow.kt, in iosMain).
    // SKIE shows a Kotlin Flow to Swift as SkieSwiftFlow, in both directions.
    func scan() -> SkieSwiftFlow<Device> {
        scanFlow(radio: self)
    }

    // IosRadio: scanFlow calls these when the Flow is collected and when it is cancelled.
    func startScan(feed: ScanFeed) {
        guard let manager, manager.state == .poweredOn else {
            feed.failed(message: "Bluetooth is off.")
            return
        }
        self.feed = feed
        manager.scanForPeripherals(withServices: nil)
    }

    func stopScan() {
        feed = nil
        if manager?.state == .poweredOn { manager?.stopScan() }
    }

    // Called on the main queue (queue: nil) for each advertisement the radio hears.
    func centralManager(_ central: CBCentralManager, didDiscover peripheral: CBPeripheral,
                        advertisementData: [String: Any], rssi RSSI: NSNumber) {
        let name = advertisementData[CBAdvertisementDataLocalNameKey] as? String ?? ""
        feed?.heard(device: Device(id: peripheral.identifier.uuidString, name: name, rssi: RSSI.int32Value))
    }

    // Called on the main queue whenever the radio's state changes: first when the manager
    // learns it, then each time Bluetooth is turned off or on.
    func centralManagerDidUpdateState(_ central: CBCentralManager) {
        guard central.state != .unknown, central.state != .resetting else { return }
        let waiting = waitingForState
        waitingForState = []
        waiting.forEach { $0.resume() }
        // Below poweredOn, scanning has stopped: end the scan the app is waiting on.
        if central.state != .poweredOn, let feed {
            self.feed = nil
            feed.failed(message: "Bluetooth was turned off.")
        }
    }

    // A new manager starts in .unknown and learns the radio's state a moment later, in
    // centralManagerDidUpdateState. Wait for that before answering.
    private func knownState() async -> CBManagerState {
        let manager = self.manager ?? makeManager()
        if manager.state == .unknown || manager.state == .resetting {
            await withCheckedContinuation { waitingForState.append($0) }
        }
        return manager.state
    }

    // No system alert when Bluetooth is off: the app shows its own message (ScanningService).
    private func makeManager() -> CBCentralManager {
        let manager = CBCentralManager(
            delegate: self, queue: nil,
            options: [CBCentralManagerOptionShowPowerAlertKey: false]
        )
        self.manager = manager
        return manager
    }
}
