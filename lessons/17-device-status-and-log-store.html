Device status and the log store

~2.5 h · +0.25 h per extra UI track Milestone: m12 live status reported; log lines written and read back Prereq: 16
Why this matters: so far the app has watched other devices. A device monitor also needs the phone's own state: how much battery is left, whether Wi-Fi and a cellular network are up, whether Bluetooth is on and the app holds a link. Today that becomes a capability of its own, the StatusReport inbound port, read by the list screen and answered by a service over three small outbound ports, one adapter each per platform. One answer, whether the app holds a link, belongs to another capability, the BLE session, and how one service asks another without knowing it is a lesson of its own: a bridge adapter. Then the app gets somewhere to keep what it sees: a LogStore outbound port with a JSON Lines file behind it. Its iOS adapter is the course's iosMain Kotlin/Native example: an outbound adapter that does all its work through Apple's Foundation, called from Kotlin, pointers and all. Lesson 18's monitor reads the status on a timer and writes each reading to this log. That's milestone m12: live status on screen, and log lines written and read back on both platforms.

Primary source Android's Read network state before section 4. For iOS, Apple's NWPathMonitor and UIDevice.batteryLevel before section 5. For the log store, JSON Lines before section 7, and Kotlin's Interoperability with C ("Memory allocation") and Interoperability with Swift/Objective-C ("Errors and exceptions") before section 9.

Tracks The ports, the service, the bridge, the adapters, the log store and the tests (sections 1–5 and 7–10) are the same on every track; only the app start differs between SwiftUI and UIKit, and the XML track's root build file gains one line (section 7). The tracks differ in the list screen (section 6), which gets one line of status and a Refresh button. Each excerpt shows only the lines its notes explain; the complete files are in Full files at the end.

1. One capability, three questions for the platform

Appendix A.6 of the course plan asks for the battery level, Wi-Fi enabled and connected, cellular available, and Bluetooth enabled and connected. In the app's terms that is one model and one inbound port:

  1. Three nullable fields, because "I can't tell" is an honest answer the app must be able to give, and it isn't false. A battery level of -1 or 0 would be a lie the screen and the log would repeat. Sections 4 and 5 show where each null comes from.
  2. suspend, because one of the answers takes a moment on iOS: a new CBCentralManager learns the radio's state in a callback (Lesson 13). The other two are instant reads.

The service needs three things from the platform, each a small outbound port named for what it answers:

  1. Why not reuse BleScanner.isEnabled()? It answers the scanning service's question and lives with the scan; it would drag the scanner into the status report, and its iOS adapter creates a CBCentralManager the first time it's asked, which shows the permission prompt to a user who hasn't answered yet. One port per question keeps each adapter small and each rule where it belongs.
  2. "As the system last reported them." Both platforms push network changes to the app (sections 4 and 5), so the adapter keeps the latest and current() only reads it. That's why it isn't suspend.

2. The status service: the app's rules for the status

  1. The Wi-Fi rule is the app's, not a platform's: a phone connected over Wi-Fi has Wi-Fi switched on. On iOS, where the adapter can't say whether Wi-Fi is on (section 5), this turns most nulls into an honest true. Only "not connected, and the platform can't say" stays unknown. aWifiConnectionMeansWifiIsOn checks it; with the ?: part removed it fails with "expected:<true> but was:<null>" (we tried).
  2. "Bluetooth connected" is the session's to say. What a device monitor cares about is whether this app holds a link to its device, and Lesson 14 made SessionService the one owner of that state. Asking a platform instead wouldn't even give the same answer on both: CoreBluetooth's retrieveConnectedPeripherals(withServices:) "Retrieves all peripherals that are connected to the system and implement any of the services listed" (CBCentralManager.h), so it needs service UUIDs to search for, and it includes other apps' links.
  3. But the service asks its own port. StatusService takes a fourth outbound port, ConnectionStatus, not DeviceSession and not SessionService. How the session's answer reaches that port is the next section.
  4. Connecting isn't connected. The port hands over the whole ConnectionState, and the rule "only an open link counts" is this line, in this service. onlyAnOpenLinkCountsAsConnected walks it through Connecting, Connected and Disconnected; with !is ConnectionState.Disconnected in place of is ConnectionState.Connected it fails (we tried).
  5. A snapshot, read once per call. Each call reads everything again, which is what "live" means here: eachCallReadsAgain checks it.
Gotcha · you won't see "device connected" on the list screen yet The status line lives on the list screen, and leaving the detail screen clears its ViewModel, which ends the connection (Lesson 14). So whenever the list reads the status, no link is up. The rule is still right, and onlyAnOpenLinkCountsAsConnected proves it with each connection state. The record Lesson 18's monitor writes on a timer is where it starts to matter.

3. Services meet through a bridge adapter

The status needs one fact the session holds. The shortest code would hand StatusService the session's inbound port and read session.connectionState.value. It compiles, and it breaks a rule every lesson since Lesson 10 has kept: a service calls outbound ports. The app's answer, from today on, is one sentence:

The rule Services don't know each other. When one capability needs something another capability holds, its service asks through an outbound port named in its own terms, and a small bridge adapter in the shared code implements that port by calling the other capability's inbound port.
  • App core
  • Inbound
  • Outbound ports and adapters
  1. A port in the asking service's terms. ConnectionStatus has the one call the status needs, in the app core's own model, ConnectionState. Its fake, FakeConnectionStatus, is one property and one method; a stand-in for DeviceSession would also need connect, disconnect, services, read and subscribe (TestDeviceSession, grown over Lessons 14–16, is 72 lines).
  2. The bridge holds no rules. It passes the session's state on as it is: what counts as connected stays in StatusService (section 2), and the connection-state machine stays in SessionService (Lesson 16). If a bridge ever seems to need an if, that rule belongs in one of the two services, where their tests can see it.
  3. An outbound adapter, in the shared code. It sits in adapter/outbound next to the simulated radio: an outbound adapter whose "outside world" is another capability. It touches no platform API, so one copy in commonMain serves both platforms.
  4. One definition widens. Lesson 10's table says inbound adapters call an inbound port; from today, a bridge adapter can too. Everything else still holds: every outbound port is implemented by an outbound adapter, and a service calls only outbound ports.

4. Android: three adapters, two install-time permissions

  1. The battery. BATTERY_PROPERTY_CAPACITY is the "Remaining battery capacity as an integer percentage of total capacity". If the property isn't supported, getIntProperty returns "(a) 0 if targetSdkVersion < VERSION_CODES.P or (b) Integer.MIN_VALUE if targetSdkVersion >= VERSION_CODES.P" (BatteryManager). The app targets 36, so the unsupported answer is Int.MIN_VALUE, and takeIf turns it into null: the adapter's job is to translate the platform's terms into the port's.
  2. Bluetooth on or off is Lesson 13's adapter?.isEnabled. Android's source marks BluetoothAdapter.isEnabled() @RequiresNoPermission (with the legacy BLUETOOTH permission up to Android 11, which the manifest already has), so the status report works before the user allows Nearby devices.

The network adapter is the interesting one. Android's guide: "the synchronous ConnectivityManager methods don't tell your app about anything happening after a call", and "Apps can register a callback with ConnectivityManager to be alerted to changes that the app cares about" (Read network state).

  1. A map the callbacks keep up to date. onCapabilitiesChanged arrives for each network the request matches, and again when its capabilities change; the guide says it's "called immediately after onAvailable() on devices running Android 8.0 (API level 26) and higher", the app's minimum. onLost removes it. Then current() is a read, not a query.
  2. ConcurrentHashMap, because "By default, the callback methods are called on the connectivity thread of your app, which is a separate thread used by ConnectivityManager" (the guide), while current() runs on the main thread. A plain HashMap shared by two threads can be read half-updated.
  3. The default NetworkRequest isn't "every network". In Android's source, a new NetworkCapabilities starts with NOT_RESTRICTED, TRUSTED and NOT_VPN (and NOT_BANDWIDTH_CONSTRAINED from Android 15): VPNs and networks reserved for privileged apps are left out, which is what a status line wants.
  4. Never unregistered: the adapter is built once in Application.onCreate and Koin keeps it for the life of the process, so the registration lives exactly as long. An adapter with a shorter life would call unregisterNetworkCallback; the reference warns that an app has a limit on registered callbacks.

Why the cellular network disappears while it's still up: Android's ConnectivityService source says "Apps without the CHANGE_NETWORK_STATE permission can't use background networks, so make all their listens include NET_CAPABILITY_FOREGROUND. That way, they will get onLost and onAvailable callbacks when networks move in and out of the background." The guide agrees from the other side: "If your app wants to use a background network, it needs the CHANGE_NETWORK_STATE permission." With that permission added to the manifest, our emulator reported "cellular available" next to Wi-Fi (we tried, then took it out again). The app doesn't ask for it: it wants to report, not to change the phone's networks, and the port's comment says what "available" means.

  1. Install-time, not runtime. Android's framework manifest gives both the normal protection level (ACCESS_WIFI_STATE as android:protectionLevel="normal", ACCESS_NETWORK_STATE as "normal|instant", which also lets instant apps hold it): the system grants them at install, with no prompt and nothing for Lesson 12's PermissionAccess to do.
  2. Both are enforced. registerNetworkCallback is annotated @RequiresPermission(android.Manifest.permission.ACCESS_NETWORK_STATE), and WifiManager.isWifiEnabled is checked by the Wi-Fi service. We removed each line in turn: without the first, the app crashed at launch with "SecurityException: ConnectivityService: Neither user … nor current process has android.permission.ACCESS_NETWORK_STATE"; without the second, at the first status read, with the same message from WifiService and ACCESS_WIFI_STATE.
Gotcha · the guide says no permission; the reference and the app disagree Android's Read network state guide says "Using NetworkCallback and other ways of finding out about the connectivity state of the device doesn't require any particular permission." The API reference annotation and our crash say otherwise for registerNetworkCallback. When a guide and a method's own reference page disagree, trust the reference, then run it.

5. iOS: three Swift adapters

On iOS the three status adapters are Swift classes in the iOS app implementing the Kotlin protocols, Lesson 12's pattern. They share one file, used by both iOS tracks:

  1. Battery monitoring is off by default. Apple: "Battery level ranges from 0.0 (fully discharged) to 1.0 (100% charged). Before accessing this property, ensure that battery monitoring is enabled. If battery monitoring is not enabled, battery state is unknown and the value of this property is –1.0" (batteryLevel). On the iOS 26.2 Simulator it stayed –1.0 with monitoring on, so the screen says "Battery unknown" there; a real level waits for your iPhone (a device check).
  2. KotlinInt?: a Kotlin Int? can't be a Swift Int? in an Objective-C header, so it crosses as a boxed number (the header has - (SharedInt * _Nullable)level, which Swift sees as KotlinInt?). A non-null Boolean stays a plain Bool, as NetworkStatus's constructor shows below.
  3. @MainActor, because UIDevice is UIKit, and UIKit is main-thread code. The @preconcurrency conformance (Lesson 12) checks at run time that Kotlin calls it on the main thread, which the list screen's viewModelScope does.
  1. One monitor per kind of interface. NWPathMonitor is "An observer that you use to monitor and react to network changes"; init(requiredInterfaceType:) "Initializes a path monitor to observe a specific interface type"; currentPath is "The currently available network path observed by the path monitor"; and start(queue:) "Starts monitoring path changes" (NWPathMonitor). A .satisfied path over Wi-Fi means connected; over cellular, a cellular network the app can use. Like the Android adapter, it keeps listening and current() reads.
  2. No "Wi-Fi switched on". An NWPath has a status, the interfaces it uses, gateways, and whether it's expensive or constrained, among other topics in Apple's reference, but no property that says whether the Wi-Fi radio is on. The nearest is unsatisfiedReason, whose wifiDenied case the header describes as "The user has disabled Wi-Fi"; but a reason comes only with an unsatisfied path, and "In many cases, the path may be unsatisfied with no reason available" (path.h), so it can't answer "on or off". So the adapter says nil, and section 2's rule fills in true whenever Wi-Fi is connected.
  3. On the Simulator, with our Mac on Wi-Fi, the Wi-Fi monitor was satisfied ("Wi-Fi connected") and the cellular one wasn't ("no cellular"). What an iPhone on Wi-Fi reports for cellular is a device check: don't assume it matches Android's answer in section 4.
  1. Guard first. Lesson 12: reading CBManager.authorization never prompts, and the prompt appears when the app first uses Bluetooth, by creating a CBCentralManager. The list screen reads the status as soon as it appears; without the guard, the status line would show the system prompt before the user ever tapped "Allow Bluetooth". The port's comment promises "Never shows a permission prompt", and this line keeps it.
  2. Lesson 13's wait, copied: a new manager is .unknown until centralManagerDidUpdateState, so the call waits for that callback. On the Simulator the state then is .unsupported: "Bluetooth unknown", even after you allow Bluetooth.
  3. __isEnabled, the Kotlin suspend fun as Swift implements it (Lesson 12's __request), returning KotlinBoolean? for Kotlin's Boolean?.

Both iOS app starts pass the three adapters to Koin, after the BLE ones; Android's DeviceMonitorApplication does the same with named arguments, now that there are six:

IosStatusProviders.swift is a new file, so run xcodegen generate in iosApp/ (Lesson 13): project.yml lists the folder, not the files. 6. One line on the list screen

The list ViewModel gets the inbound port and turns each DeviceStatus into one line of text, the same on every track:

  1. Read when it can have changed: the screen appearing (including on the way back from the detail screen), the app returning to the foreground (the user may have toggled Wi-Fi in Settings), and Refresh. Nothing polls: the list is the app's first screen and stays in memory under the detail screen, so a timer in its ViewModel would keep running while nobody looks. Timers are Lesson 18's subject.
  2. The words live in the ViewModel, not in four screens: "unknown" for a null battery or Bluetooth state, and for Wi-Fi, "off", "connected", "on, not connected", or just "not connected" when the platform can't tell. showsThePhoneStatusAsOneLine and saysWhatThePhoneCantTell pin the exact text.
  3. phoneStatus starts as "Reading the phone's status…" in DeviceListUiState. The existing ViewModel tests only gain the new TestStatusReport in the constructor: none of them call refreshStatus(), so their Turbine sequences see no extra state.

ON_RESUME comes when the screen first shows, on return to the foreground, and when the list is back on top after the detail screen: on the emulator, changing the battery level while the detail screen was open and pressing Back showed the new level without a tap on Refresh. Modifier.weight(1f) gives the text the room the button doesn't need, so a long line wraps instead of pushing Refresh off screen.

A horizontal LinearLayout with a weighted TextView is the shortest way to put text and a button side by side when the text may wrap: two views constrained side by side in the ConstraintLayout would need a barrier so the filter field sits below whichever is taller. In DeviceListFragment, the button calls viewModel.refreshStatus(), onResume() calls it next to refreshPermission(), and render sets b.phoneStatusText.text = state.phoneStatus. scenePhase covers the return to the foreground, but not the way back from the detail screen, where the scene stays active; onAppear covers that, and the first appearance. We checked with a throwaway battery adapter that counted its reads: two at launch (both hooks fired), then one for Refresh and one for Back from the detail screen. PhoneStatusRow is an HStack of the text, .frame(maxWidth: .infinity, alignment: .leading), and a Refresh button.

Without the two priorities, a long status line can squeeze the button in a horizontal stack view. 7. The log store: a port, and a file format

A monitor that reads the status every few minutes needs somewhere to keep each reading, across launches. In the app's terms that's an outbound port with three calls:

  1. LogRecord is data class LogRecord(val timestamp: Instant, val status: DeviceStatus): a status and the moment it was read. kotlin.time.Instant is the standard library's moment in time ("Since Kotlin 2.3"), so the app core needs no date library.
  2. Errors in the app's terms. A full disk or a broken file becomes LogStoreException, a core exception like Lesson 13's ScanException, with a message that says what failed. The caller never sees IOException or NSError: those are each platform's words.
  3. suspend, because file calls block the thread they run on; the adapters move them to Dispatchers.IO, and a coroutine that calls from the main thread suspends until the file call is done, while the main thread stays free (Lesson 07).

JSON Lines is the format: UTF-8 text, each line one valid JSON value, lines ended by \n. Appending is writing one more line at the end, nothing else in the file is touched, and a reader can go line by line. The fields are the course plan's example record:

  • Outbound port and shared adapter code
  • Android adapter
  • iOS adapter
  • Tests
  1. The JSON class lives in the adapter. @Serializable makes the kotlinx.serialization compiler plugin generate the encoder and decoder for Line. Putting it on LogRecord instead would make the app core import a serialization library and bend its models to a file format; Appendix B's refactor checklist says the app core imports no framework. JsonLines is internal: visible to both platforms' adapters in the shared module, and to its tests, but not to Swift.
  2. Unknowns are written as null. kotlinx.serialization's explicitNulls "Specifies whether null values should be encoded for nullable properties and must be present in JSON object during decoding", and it is "true by default" (JsonBuilder.explicitNulls). So every line has every field, and a line without "battery" is not a record.
  3. The timestamp ends in Z. Instant.toString() "Converts this instant to the ISO 8601 string representation, for example, 2023-01-02T23:40:57.120Z" (Instant): UTC, so a log read in another time zone means the same moments. The course plan's example record leaves the zone out; ours keeps it, and aRecordIsOneLineOfJsonWithTheExampleFields checks the whole line.
  1. The blank line is mostly the last one: a file that ends with \n, as every line we write does, splits into the lines and one empty string after them.
  2. Catching IllegalArgumentException is the library's own advice: "SerializationException is a subclass of IllegalArgumentException", and "For general "catch-all" patterns around deserialization of potentially untrusted/invalid/corrupted data it is recommended to catch IllegalArgumentException" (SerializationException). Instant.parse throws the same type for a bad timestamp.
  3. One bad line fails the read, naming the line. A half-written last line after a crash is the classic case; this app reports it rather than hiding it, and clear() starts afresh. A monitor that must keep going could skip bad lines instead: that would be a rule in the port's contract, with a test.

The plugin goes into shared/build.gradle.kts as id("org.jetbrains.kotlin.plugin.serialization"), next to implementation("org.jetbrains.kotlinx:kotlinx-serialization-json:1.12.0") in commonMain. The Compose track's root build.gradle.kts already declares the plugin, version "2.4.20" apply false, for Lesson 07's navigation routes; the XML track's root file gains that one line, or Gradle can't find the plugin.

8. Android: java.io and a lock

  1. A File, not a Context. The adapter uses nothing from Android, only java.io, so the JVM tests run it on a real temporary file. When the app binds it (Lesson 18), it can pass a file in its private storage, File(filesDir, …).
  2. Dispatchers.IO is the coroutine dispatcher "designed for offloading blocking IO tasks to a shared pool of threads" (Dispatchers.IO). Lesson 07's rule: don't block the main thread.
  3. Lesson 15's Mutex again: two appends at once on a thread pool could interleave their bytes. Holding the lock around each whole call keeps every line whole.

9. iOS: Kotlin calling Foundation

Every iOS adapter so far did its platform work in Swift; their Kotlin halves in iosMain build the Flows and pass calls across. The log store needs nothing a Swift class does better: no delegate, no main thread, just files. And in Kotlin it shares JsonLines with Android and runs in iosSimulatorArm64Test from Gradle. Lesson 05 showed the idea in one line, import platform.UIKit.UIDevice: Kotlin/Native ships Apple's frameworks as Kotlin packages, and "system frameworks are imported by default" (Interoperability with Swift/Objective-C).

  1. Objective-C, seen from Kotlin. NSFileManager.defaultManager is the class property. NSString.create(string = …) is the initializer -initWithString:: "A Swift/Objective-C initializer is imported to Kotlin as constructors or as factory methods named create. The latter happens with initializers declared in the Objective-C category", and NSString.h declares this one in a category. dataUsingEncoding returns NSData? because the header says nullable. The names are Objective-C's, not Swift's: FileManager.default in Swift is NSFileManager.defaultManager here.
  2. Two opt-ins. Kotlin's guide: "Native platform libraries shipped with Kotlin/Native (like Foundation, UIKit, and POSIX) require opt-in only for some APIs". Here, memScoped, alloc, .ptr and every Foundation call that takes a pointer need @ExperimentalForeignApi (without it, the build fails), and NSString.create and reading the error variable's .value need @BetaInteropApi (without it, a warning). One @OptIn on the class covers both.
  3. Two constructors, because an Objective-C header has no default arguments: the class declares the no-argument one itself, and the header has both init() and init(path:). The app will use IosLogStore() once Lesson 18 binds it; the tests pass a temporary path. We ran the no-argument one once in a throwaway iOS test: two appends, two records, cleared.

Foundation's file calls report failure the Objective-C way. Kotlin's guide is clear that it won't translate: "Swift/Objective-C error-throwing methods aren't imported to Kotlin as exception-throwing." So the Kotlin code does what Objective-C code does, and passes the address of a variable for the error:

  1. memScoped, alloc, .ptr. Kotlin's guide: "you can use memScoped { }. Inside the braces, the temporary placement is available as an implicit receiver, so it's possible to allocate native memory with alloc and allocArray, and the allocated memory will be automatically freed after leaving the scope"; .ptr "takes the lvalue and returns the pointer to it" (Interoperability with C). NSError ** in the Objective-C header becomes a pointer to an ObjCObjectVar<NSError?>, and .value reads what Foundation put there.
  2. Check the return value, then read the error: the Cocoa rule, and the header's: the method "returns NO if a failure occurs at any stage of the operation. If an error parameter was provided, a presentable NSError will be returned by reference" (NSFileManager.h).
  3. The folder first. In a freshly installed app's container on the Simulator, Library held Caches, Preferences and folders the system adds at launch, but no Application Support: the app must create it. Apple's NSSearchPathForDirectoriesInDomains warns that "The directory returned by this method may not exist." With true for intermediate folders, the call also succeeded when the folder was already there (every second append in the tests does that). We removed the call: three of the five iOS tests failed with "Couldn't create the log file."
  4. createFileAtPath has no error parameter: - (BOOL)createFileAtPath:(NSString *)path contents:(nullable NSData *)data attributes:…. So that failure has no reason to pass on, only false.
  5. Seek, then write. Apple: "If the handle represents a file, writing takes place at the file pointer’s current position" (FileHandle.write(_:)), and for a handle from fileHandleForWritingToURL, "The file pointer is set to the beginning of the file" (FileHandle(forWritingTo:)). We removed seekToEndReturningOffset: the second line overwrote the first, and readsBackWhatWasAppendedInOrder failed on iOS.
  6. The error: versions. writeData:error:, seekToEndReturningOffset:error: and closeAndReturnError: came with iOS 13 (NSFileHandle.h), and the header marks the older seekToEndOfFile and closeFile "to be deprecated", naming these as the replacements. The old seek "Raises fileHandleOperationException … if any other error occurs while seeking" (seekToEndOfFile()): an Objective-C exception, with no return value or NSError for the code above to turn into a LogStoreException.
Gotcha · Dispatchers.IO needs an import in iosMain On Kotlin/Native, Dispatchers.IO is an extension property, kotlinx.coroutines.IO, and the file must import it. Without the import our build failed with "Cannot access 'val IO: CoroutineDispatcher': it is internal in 'kotlinx.coroutines.Dispatchers'". On Android the same name resolves without one, so code copied from androidMain breaks only on iOS.

read() uses NSString.stringWithContentsOfFile(path, NSUTF8StringEncoding, error.ptr) and hands the text to JsonLines.decode; clear() uses removeItemAtPath(path, error.ptr). Both return early when fileExistsAtPath says there's no file: an empty log isn't an error.

Retrieval checks

Answer from memory, without scrolling up.

Where does "Bluetooth connected" in DeviceStatus come from?

It means "this app holds a link", and the session service owns that state. iOS can only list connected peripherals for service UUIDs you name, including other apps' links, so a platform answer wouldn't mean the same on both.

A new capability's service needs one fact that another capability's service holds. What does the new service depend on?

Services don't know each other: a service calls only outbound ports, and every outbound port is implemented by an outbound adapter. The bridge is that adapter, and it holds no rules.

Why doesn't SessionService simply implement ConnectionStatus as well, and save the bridge file?

The bridge keeps both definitions true. The other near options break a rule too: a direct call breaks "a service calls outbound ports", a shared holder leaves "who may write" to convention, and domain events would need replay to give the current state.

On the API 36 emulator, dumpsys connectivity still lists a connected cellular network, but a minute after Wi-Fi came back the status says "no cellular". Why?

ConnectivityService adds NET_CAPABILITY_FOREGROUND to the listens of apps without that permission, so they get onLost when a network moves to the background. "Available" in this app means "a network this app can use".

Why does IosBluetoothProvider return nil before the user has allowed Bluetooth, instead of asking the radio?

Reading CBManager.authorization never prompts (Lesson 12); creating a manager does. The port promises "Never shows a permission prompt".

In IosLogStore.append, what does error.ptr give Foundation?

Objective-C error-throwing methods aren't imported as Kotlin exceptions, so the code passes an NSError ** as Objective-C does: check the return value, then read error.value. The memory is freed when memScoped ends.

Why is @Serializable on a private class inside JsonLines, and not on LogRecord?

Appendix B: the app core imports nothing from any framework. The adapter maps between the core's LogRecord and its own Line, so either can change on its own.

Mixed review (interleaved)

Lesson 12's adapters and today's status adapters on iOS are Swift classes. What makes a Swift class an outbound adapter here? (Lessons 10 and 12)

Swift sees a Kotlin interface as a protocol. Koin binds the Swift object like any other adapter; the app core only knows the port.

The log store tests and the session tests both use runTest. Why do the log store tests take real time, when Lesson 16's 100 ms waits didn't? (Lesson 11)

Virtual time controls coroutines on the test dispatcher. Work sent to another dispatcher runs for real, and the test waits for it; for a few small files that's milliseconds.

import kotlin.time.Instant
import kotlinx.serialization.Serializable
import kotlinx.serialization.json.Json

// The log store's file format, shared by both platforms' LogStore adapters: JSON Lines, one JSON
// object per line, with the fields of the course's example record. The @Serializable class
// lives here, in the adapter, so the app core's models carry no JSON annotations.
internal object JsonLines {
    @Serializable
    private class Line(
        val timestamp: String,
        val battery: Int?,
        val wifiEnabled: Boolean?,
        val wifiConnected: Boolean,
        val cellularAvailable: Boolean,
        val bluetoothEnabled: Boolean?,
        val bluetoothConnected: Boolean,
    )

    // One record as one line of JSON, without the line break.
    fun encode(record: LogRecord): String {
        val s = record.status
        val line = Line(
            record.timestamp.toString(), s.battery, s.wifiEnabled, s.wifiConnected,
            s.cellularAvailable, s.bluetoothEnabled, s.bluetoothConnected,
        )
        return Json.encodeToString(line)
    }

    // Every record in the file's text, in order. Blank lines are skipped; any other line that
    // isn't a record fails the whole read, with its line number.
    fun decode(text: String): List<LogRecord> =
        text.lines().mapIndexedNotNull { index, line ->
            if (line.isBlank()) return@mapIndexedNotNull null
            try {
                val l = Json.decodeFromString<Line>(line)
                val status = DeviceStatus(
                    l.battery, l.wifiEnabled, l.wifiConnected, l.cellularAvailable,
                    l.bluetoothEnabled, l.bluetoothConnected,
                )
                LogRecord(Instant.parse(l.timestamp), status)
            } catch (e: IllegalArgumentException) { // kotlinx.serialization's errors, and Instant.parse's
                throw LogStoreException("Line ${index + 1} of the log isn't a record: ${e.message}")
            }
        }
}

// Inbound adapter: turns the screen's events into calls on the DeviceScanning, PermissionAccess
// and StatusReport ports, and the results into UI state. It knows the ports only.
class DeviceListViewModel(
    private val scanning: DeviceScanning,
    private val permissions: PermissionAccess,
    private val statusReport: StatusReport,
) : ViewModel() {
    private val _uiState = MutableStateFlow(
        DeviceListUiState(bluetooth = permissions.status(Permission.Bluetooth)),
    )
    val uiState: StateFlow<DeviceListUiState> = _uiState.asStateFlow()

    private var scanJob: Job? = null
    private var permissionJob: Job? = null
    private var statusJob: Job? = null

    fun startScan(filter: String) {
        if (scanJob?.isActive == true) return
        _uiState.update { it.copy(scan = ScanState.Scanning(emptyList())) }
        scanJob = viewModelScope.launch {
            val found = mutableListOf<Device>()
            try {
                withTimeoutOrNull(SCAN_TIMEOUT) {
                    scanning.scan(filter).collect { device ->
                        found += device
                        _uiState.update { it.copy(scan = ScanState.Scanning(found.toList())) }
                    }
                }
                _uiState.update { it.copy(scan = ScanState.Finished(found.toList())) }
            } catch (e: ScanException) {
                _uiState.update { it.copy(scan = ScanState.Idle, errorMessage = e.message) }
            }
        }
    }

    // The Stop button. Cancelling the scan's coroutine cancels its collection, which stops the
    // service's scan and the radio. The devices found so far stay on screen.
    fun stopScan() {
        val job = scanJob ?: return
        if (!job.isActive) return
        job.cancel()
        _uiState.update { state ->
            val scan = state.scan
            if (scan is ScanState.Scanning) state.copy(scan = ScanState.Finished(scan.found)) else state
        }
    }

    fun errorShown() {
        _uiState.update { it.copy(errorMessage = null) }
    }

    // The screen calls this each time it comes back to the foreground: the user may have
    // changed the permission in Settings meanwhile.
    fun refreshPermission() {
        if (permissionJob?.isActive == true) return
        _uiState.update { it.copy(bluetooth = permissions.status(Permission.Bluetooth)) }
    }

    fun requestPermission() {
        if (permissionJob?.isActive == true) return
        permissionJob = viewModelScope.launch {
            val result = permissions.request(listOf(Permission.Bluetooth))
            _uiState.update { it.copy(bluetooth = result.getValue(Permission.Bluetooth)) }
        }
    }

    fun openSettings() {
        permissions.openSettings()
    }

    // The screen calls this when it appears, when the app comes back to the foreground, and from
    // its Refresh button: each call reads the status again.
    fun refreshStatus() {
        if (statusJob?.isActive == true) return
        statusJob = viewModelScope.launch {
            val current = statusReport.current()
            _uiState.update { it.copy(phoneStatus = describe(current)) }
        }
    }

    // One line of text for the screen, the same on every track.
    private fun describe(s: DeviceStatus): String {
        val battery = s.battery?.let { "Battery $it %" } ?: "Battery unknown"
        val wifi = when {
            s.wifiEnabled == false -> "Wi-Fi off"
            s.wifiConnected -> "Wi-Fi connected"
            s.wifiEnabled == true -> "Wi-Fi on, not connected"
            else -> "Wi-Fi not connected"
        }
        val cellular = if (s.cellularAvailable) "cellular available" else "no cellular"
        val bluetooth = when (s.bluetoothEnabled) {
            true -> "Bluetooth on"
            false -> "Bluetooth off"
            null -> "Bluetooth unknown"
        } + if (s.bluetoothConnected) ", device connected" else ""
        return listOf(battery, wifi, cellular, bluetooth).joinToString(" · ")
    }

    companion object {
        // A real radio drains the battery while it scans, so every scan has a time limit.
        val SCAN_TIMEOUT = 10.seconds
    }
}

// Outbound adapter: Wi-Fi and cellular, behind the NetworkProvider port. Android reports each
// network that comes, changes or goes to a callback; the adapter keeps the networks it was told
// about, so current() only reads them. Android tells an app only about networks it can use:
// not a cellular network kept up in the background behind Wi-Fi. Needs ACCESS_NETWORK_STATE
// and ACCESS_WIFI_STATE.
class AndroidNetworkProvider(context: Context) : NetworkProvider {
    private val wifi = context.getSystemService(WifiManager::class.java)
    private val networks = ConcurrentHashMap<Network, NetworkCapabilities>() // callbacks run on another thread

    init {
        // One registration for the life of the process: Koin keeps this adapter as long.
        context.getSystemService(ConnectivityManager::class.java).registerNetworkCallback(
            NetworkRequest.Builder().build(), // the default request: no VPNs, no restricted networks
            object : ConnectivityManager.NetworkCallback() {
                override fun onCapabilitiesChanged(network: Network, capabilities: NetworkCapabilities) {
                    networks[network] = capabilities
                }

                override fun onLost(network: Network) {
                    networks.remove(network)
                }
            },
        )
    }

    override fun current(): NetworkStatus {
        val up = networks.values
        return NetworkStatus(
            wifiEnabled = wifi?.isWifiEnabled,
            wifiConnected = up.any { it.hasTransport(NetworkCapabilities.TRANSPORT_WIFI) },
            cellularAvailable = up.any { it.hasTransport(NetworkCapabilities.TRANSPORT_CELLULAR) },
        )
    }

// Outbound adapter: the log store on iOS, a JSON Lines file behind the LogStore port. Kotlin,
// not Swift: Kotlin/Native calls Apple's Foundation directly (the platform.Foundation imports),
// so this adapter shares JsonLines with Android and runs in the iOS tests from Gradle.
@OptIn(ExperimentalForeignApi::class, BetaInteropApi::class)
class IosLogStore(private val path: String) : LogStore {
    // For the app: status-log.jsonl in the app's Application Support folder.
    constructor() : this(applicationSupportFile("status-log.jsonl"))

    private val files = NSFileManager.defaultManager
    private val folder = path.substringBeforeLast('/')
    private val lock = Mutex() // one file operation at a time, so lines never interleave

    override suspend fun append(record: LogRecord) = io {
        val text = NSString.create(string = JsonLines.encode(record) + "\n")
        val data = checkNotNull(text.dataUsingEncoding(NSUTF8StringEncoding))
        memScoped {
            val error = alloc<ObjCObjectVar<NSError?>>()
            // Application Support doesn't exist until an app creates it.
            if (!files.createDirectoryAtPath(folder, true, null, error.ptr)) {
                throw failure("Couldn't create the log's folder", error)
            }
            if (!files.fileExistsAtPath(path)) {
                if (!files.createFileAtPath(path, data, null)) throw LogStoreException("Couldn't create the log file.")
                return@memScoped
            }
            val handle = NSFileHandle.fileHandleForWritingToURL(NSURL.fileURLWithPath(path), error.ptr)
                ?: throw failure("Couldn't open the log file", error)
            try {
                if (!handle.seekToEndReturningOffset(null, error.ptr)) throw failure("Couldn't open the log file", error)
                if (!handle.writeData(data, error.ptr)) throw failure("Couldn't write to the log", error)
            } finally {
                handle.closeAndReturnError(null)
            }
        }
    }

    override suspend fun read(): List<LogRecord> = io {
        if (!files.fileExistsAtPath(path)) return@io emptyList()
        memScoped {
            val error = alloc<ObjCObjectVar<NSError?>>()
            val text = NSString.stringWithContentsOfFile(path, NSUTF8StringEncoding, error.ptr)
                ?: throw failure("Couldn't read the log", error)
            JsonLines.decode(text)
        }
    }

    override suspend fun clear() = io {
        if (!files.fileExistsAtPath(path)) return@io
        memScoped {
            val error = alloc<ObjCObjectVar<NSError?>>()
            if (!files.removeItemAtPath(path, error.ptr)) throw failure("Couldn't clear the log", error)
        }
    }

    // Foundation reports a failure the Objective-C way: the call returns NO (false) or nil, and
    // writes an NSError into the variable whose address (error.ptr) it was given.
    private fun failure(what: String, error: ObjCObjectVar<NSError?>) =
        LogStoreException("$what: ${error.value?.localizedDescription}")

    // File calls block their thread, so they run on Dispatchers.IO, never on the main thread.
    private suspend fun <T> io(block: () -> T): T = lock.withLock { withContext(Dispatchers.IO) { block() } }

    private companion object {
        fun applicationSupportFile(name: String): String {
            val folders = NSSearchPathForDirectoriesInDomains(NSApplicationSupportDirectory, NSUserDomainMask, true)
            return "${folders.first()}/$name"
        }
    }
}

@MainActor
final class IosBatteryProvider: @preconcurrency BatteryProvider {
    init() {
        // Without this, batteryLevel is always -1.0.
        UIDevice.current.isBatteryMonitoringEnabled = true
    }

    // batteryLevel runs from 0.0 to 1.0, or is -1.0 when iOS can't tell (on the Simulator,
    // always). A Kotlin Int? crosses as KotlinInt?.
    func level() -> KotlinInt? {
        let level = UIDevice.current.batteryLevel
        guard level >= 0 else { return nil }
        return KotlinInt(int: Int32((level * 100).rounded()))
    }
}

// Outbound adapter: Wi-Fi and cellular, behind the Kotlin NetworkProvider port. Each
// NWPathMonitor watches the paths over one kind of interface and keeps the latest in
// currentPath, so current() only reads them.
@MainActor
final class IosNetworkProvider: @preconcurrency NetworkProvider {
    private let wifi = NWPathMonitor(requiredInterfaceType: .wifi)
    private let cellular = NWPathMonitor(requiredInterfaceType: .cellular)

    init() {
        wifi.start(queue: .main)
        cellular.start(queue: .main)
    }

    // The Network framework reports paths, not whether the Wi-Fi radio is switched on, so
    // wifiEnabled is nil: unknown.
    func current() -> NetworkStatus {
        NetworkStatus(
            wifiEnabled: nil,
            wifiConnected: wifi.currentPath.status == .satisfied,
            cellularAvailable: cellular.currentPath.status == .satisfied
        )
    }
}

// Outbound adapter: Bluetooth on or off, behind the Kotlin BluetoothProvider port.
@MainActor
final class IosBluetoothProvider: NSObject, @preconcurrency BluetoothProvider,
    @preconcurrency CBCentralManagerDelegate {
    private var manager: CBCentralManager?
    private var waiting: [CheckedContinuation<Void, Never>] = []

    // The Kotlin suspend fun, as Swift implements it (Lesson 12's __request). A Kotlin
    // Boolean? crosses as KotlinBoolean?.
    func __isEnabled() async throws -> KotlinBoolean? {
        // Creating a CBCentralManager is what shows the Bluetooth prompt, and only an allowed
        // app learns the radio's state: until then, say "unknown" and create nothing.
        guard CBManager.authorization == .allowedAlways else { return nil }
        let manager = self.manager ?? makeManager()
        if manager.state == .unknown || manager.state == .resetting {
            await withCheckedContinuation { waiting.append($0) }
        }
        switch manager.state {
        case .poweredOn: return KotlinBoolean(bool: true)
        case .poweredOff: return KotlinBoolean(bool: false)
        default: return nil // unsupported (the Simulator) or unauthorized
        }
    }

    // A new manager starts in .unknown and learns the radio's state a moment later, here.
    func centralManagerDidUpdateState(_ central: CBCentralManager) {
        guard central.state != .unknown, central.state != .resetting else { return }
        let answered = waiting
        waiting = []
        answered.forEach { $0.resume() }
    }

    private func makeManager() -> CBCentralManager {
        let manager = CBCentralManager(
            delegate: self, queue: nil,
            options: [CBCentralManagerOptionShowPowerAlertKey: false]
        )
        self.manager = manager
        return manager
    }
}

    private var observation: Task<Void, Never>?

    private let phoneStatusLabel = UILabel()
    private let refreshStatusButton = UIButton(configuration: .plain())
    private let filterField = UITextField()
    private let permissionLabel = UILabel()
    private let permissionButton = UIButton(configuration: .plain())
    private let scanButton = UIButton(configuration: .filled())
    private let spinner = UIActivityIndicatorView(style: .medium)
    private let statusLabel = UILabel()
    private let tableView = UITableView()
    // The rows' devices by id, from the last state rendered: the snapshot holds only the ids.
    private var devicesById: [String: Device] = [:]
    private lazy var dataSource = UITableViewDiffableDataSource<Int, String>(tableView: tableView) {
        [unowned self] tableView, indexPath, deviceId in
        let cell = tableView.dequeueReusableCell(withIdentifier: "device", for: indexPath)
        var content = UIListContentConfiguration.subtitleCell()
        if let device = devicesById[deviceId] {
            content.text = device.name
            content.secondaryText = "\(device.id)   \(device.rssi) dBm"
        }
        cell.contentConfiguration = content
        cell.accessoryType = .disclosureIndicator
        return cell
    }

    override func viewDidLoad() {
        super.viewDidLoad()
        title = "Device Monitor"
        navigationController?.navigationBar.prefersLargeTitles = true
        view.backgroundColor = .systemBackground

        filterField.placeholder = "Device name filter"
        filterField.borderStyle = .roundedRect
        filterField.autocorrectionType = .no
        scanButton.configuration?.title = "Scan"
        // One button: Scan while idle, Stop while scanning.
        scanButton.addAction(UIAction { [weak self] _ in
            guard let self else { return }
            if viewModel.uiState.value.scan is ScanStateScanning {
                viewModel.stopScan()
            } else {
                viewModel.startScan(filter: filterField.text ?? "")
            }
        }, for: .touchUpInside)
        permissionLabel.numberOfLines = 0
        permissionLabel.font = .preferredFont(forTextStyle: .callout)
        permissionButton.contentHorizontalAlignment = .leading
        permissionButton.addAction(UIAction { [weak self] _ in
            guard let self else { return }
            if viewModel.uiState.value.bluetooth == .permanentlyDenied {
                viewModel.openSettings()
            } else {
                viewModel.requestPermission()
            }
        }, for: .touchUpInside)
        statusLabel.numberOfLines = 0
        phoneStatusLabel.numberOfLines = 0
        phoneStatusLabel.font = .preferredFont(forTextStyle: .footnote)
        phoneStatusLabel.textColor = .secondaryLabel
        refreshStatusButton.configuration?.title = "Refresh"
        refreshStatusButton.addAction(UIAction { [weak self] _ in
            self?.viewModel.refreshStatus()
        }, for: .touchUpInside)
        // The label takes the room the button doesn't need.
        refreshStatusButton.setContentHuggingPriority(.required, for: .horizontal)
        refreshStatusButton.setContentCompressionResistancePriority(.required, for: .horizontal)
        tableView.register(UITableViewCell.self, forCellReuseIdentifier: "device")
        tableView.delegate = self

        let statusRow = UIStackView(arrangedSubviews: [spinner, statusLabel])
        statusRow.spacing = 8
        let permissionRow = UIStackView(arrangedSubviews: [permissionLabel, permissionButton])
        permissionRow.axis = .vertical
        permissionRow.alignment = .leading
        let phoneStatusRow = UIStackView(arrangedSubviews: [phoneStatusLabel, refreshStatusButton])
        phoneStatusRow.spacing = 8
        phoneStatusRow.alignment = .center
        let stack = UIStackView(arrangedSubviews: [
            phoneStatusRow, filterField, permissionRow, scanButton, statusRow, tableView,
        ])
        stack.axis = .vertical
        stack.spacing = 12
        stack.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(stack)
        NSLayoutConstraint.activate([
            stack.topAnchor.constraint(equalTo: view.layoutMarginsGuide.topAnchor),
            stack.leadingAnchor.constraint(equalTo: view.layoutMarginsGuide.leadingAnchor),
            stack.trailingAnchor.constraint(equalTo: view.layoutMarginsGuide.trailingAnchor),
            stack.bottomAnchor.constraint(equalTo: view.bottomAnchor),
        ])
        render(viewModel.uiState.value)
        // Back from Settings (or anywhere else): the permission and the status may have changed.
        NotificationCenter.default.addObserver(
            self, selector: #selector(sceneDidActivate),
            name: UIScene.didActivateNotification, object: nil
        )
    }

    @objc private func sceneDidActivate() {
        viewModel.refreshPermission()
        viewModel.refreshStatus()
    }

    // Collect only while on screen, like repeatOnLifecycle(STARTED) on Android. Shown, and back
    // from the detail screen: the status may have changed.
    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        viewModel.refreshStatus()
        observation?.cancel()
        observation = Task {
            for await state in viewModel.uiState {
                render(state)
            }
        }
    }

    override func viewDidDisappear(_ animated: Bool) {
        super.viewDidDisappear(animated)
        observation?.cancel()
        observation = nil
    }

    // The one place that touches views: every new state ends here. The text field owns
    // its own text, so render() never sets it.
    private func render(_ state: DeviceListUiState) {
        let isScanning = state.scan is ScanStateScanning
        // SKIE turns the sealed interface into a Swift enum, so this switch is exhaustive.
        let devices: [Device]? = switch onEnum(of: state.scan) {
        case .idle: nil
        case .scanning(let scanning): scanning.found
        case .finished(let finished): finished.found
        }
        phoneStatusLabel.text = state.phoneStatus
        renderPermission(state.bluetooth)
        scanButton.configuration?.title = isScanning ? "Stop" : "Scan"
        scanButton.isEnabled = isScanning || state.bluetooth == .granted
        if isScanning { spinner.startAnimating() } else { spinner.stopAnimating() }
        spinner.isHidden = !isScanning
        if isScanning {
            statusLabel.text = "Scanning…"
        } else if let devices {
            statusLabel.text = devices.isEmpty
                ? "No devices found. Try another filter."
                : "Devices found: \(devices.count)"
        } else {
            statusLabel.text = "Tap Scan to look for devices."
        }
        statusLabel.textColor = devices?.isEmpty == true && !isScanning ? .systemRed : .label

        devicesById = Dictionary(uniqueKeysWithValues: (devices ?? []).map { ($0.id, $0) })
        var snapshot = NSDiffableDataSourceSnapshot<Int, String>()
        snapshot.appendSections([0])
        snapshot.appendItems((devices ?? []).map(\.id))
        dataSource.apply(snapshot, animatingDifferences: true)
        renderError(state.errorMessage)
    }

    // One message and at most one action per permission status. SKIE makes the Kotlin enum a
    // Swift enum, so this switch is exhaustive.
    private func renderPermission(_ status: PermissionStatus) {
        let (message, action): (String, String?) = switch status {
        case .granted: ("Bluetooth permission: allowed", nil)
        case .notRequested: ("Device Monitor needs Bluetooth permission to find nearby devices.", "Allow Bluetooth")
        case .denied: ("Bluetooth permission was denied. Scanning needs it to find nearby devices.", "Ask again")
        case .permanentlyDenied: ("Bluetooth permission is off. You can turn it on in Settings.", "Open Settings")
        case .restricted: ("Bluetooth is restricted on this device, so scanning isn't available.", nil)
        }
        permissionLabel.text = message
        permissionLabel.textColor = switch status {
        case .granted: .secondaryLabel
        case .notRequested: .label
        case .denied, .permanentlyDenied, .restricted: .systemRed
        }
        permissionButton.configuration?.title = action
        permissionButton.isHidden = action == nil
    }

    private func renderError(_ message: String?) {
        guard let message, presentedViewController == nil else { return }
        let alert = UIAlertController(title: "Scan failed", message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default) { [weak self] _ in
            self?.viewModel.errorShown()
        })
        present(alert, animated: true)
    }

    func tableView(_ tableView: UITableView, didSelectRowAt indexPath: IndexPath) {
        tableView.deselectRow(at: indexPath, animated: true)
        guard let deviceId = dataSource.itemIdentifier(for: indexPath), let device = devicesById[deviceId] else { return }
        // The detail screen gets the whole device: it needs all of it to connect.
        navigationController?.pushViewController(DeviceDetailViewController(device: device), animated: true)
    }
