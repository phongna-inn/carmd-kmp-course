Platform Fundamentals

~3.5 h · +0.5 h per extra UI track Part A: Android · Part B: iOS Milestone: scratch apps logging lifecycles Prereq: 01
Why this matters: the OS, not your code, decides when your app's screens are created, hidden, and destroyed. Two real bugs follow from that. A BLE connection kept in the wrong object silently disappears when the phone rotates. And a background monitor hooked to the wrong lifecycle never notices that the app went to the background. Today you build two tiny apps that log every lifecycle event, then watch the logs while you poke them.

Primary sources Android's The activity lifecycle and Apple's Managing your app's life cycle, plus SwiftUI's ScenePhase.

Tracks Use the switchers above to pick your UI stack. Most of today's ideas are the same on both tracks. Only the code that puts something on screen differs.

A2. Activity, Context, Intent, Manifest

An Activity is one entry point with a window and a lifecycle. Our app has exactly one, and so will the Native Device Monitor. A Context is your handle to the system: resources, system services (the Bluetooth service, later), and starting other components (reference). An Activity is a Context. An Intent is a message asking the OS to start something. It can be explicit (a class you own) or implicit ("anyone who can view a web page") (Android: Intents):

startActivity(Intent(Intent.ACTION_VIEW, "https://developer.android.com".toUri()))

The Manifest declares components to the OS. The MAIN + LAUNCHER intent filter is what puts the app's icon in the launcher (Android: App manifest). Permissions get declared here as well, from Lesson 07.

<manifest xmlns:android="http://schemas.android.com/apk/res/android">
    <application
        android:label="Lesson 02"
        android:theme="@android:style/Theme.Material.Light.NoActionBar"android:theme="@style/Theme.AppCompat.Light.NoActionBar">
        <activity android:name=".MainActivity" android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.intent.category.LAUNCHER" />
            </intent-filter>
        </activity>
    </application>
</manifest>

XML track: AppCompatActivity crashes at launch unless the theme is an AppCompat theme.

A3. The activity lifecycle, logged

The OS calls six callbacks as an Activity is created, shown, hidden and destroyed: onCreate → onStart → onResume on the way in, and onPause → onStop → onDestroy on the way out (Android: Activity lifecycle). This app logs each one with tag Lifecycle. In Android Studio's Logcat, filter on tag:Lifecycle (Logcat docs).

Compose track · app/src/main/java/com/example/lesson02/MainActivity.kt

package com.example.lesson02

import android.content.Intent
import android.os.Bundle
import android.util.Log
import androidx.activity.ComponentActivity
import androidx.activity.compose.setContent
import androidx.compose.foundation.layout.Arrangement
import androidx.compose.foundation.layout.Column
import androidx.compose.foundation.layout.fillMaxSize
import androidx.compose.foundation.layout.padding
import androidx.compose.material3.Button
import androidx.compose.material3.Text
import androidx.compose.ui.Modifier
import androidx.compose.ui.unit.dp
import androidx.core.net.toUri

private const val TAG = "Lifecycle"

class MainActivity : ComponentActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Log.d(TAG, "onCreate (restored=${savedInstanceState != null})")
        setContent {
            Column(
                modifier = Modifier.fillMaxSize().padding(24.dp),
                verticalArrangement = Arrangement.spacedBy(16.dp),
            ) {
                Text("Lesson 02: watch Logcat, filter tag:Lifecycle")
                Button(onClick = { openWebPage() }) {
                    Text("Open a web page")
                }
            }
        }
    }

    private fun openWebPage() {
        val intent = Intent(Intent.ACTION_VIEW, "https://developer.android.com".toUri())
        startActivity(intent)
    }

    override fun onStart() {
        super.onStart()
        Log.d(TAG, "onStart")
    }

    // onResume, onPause, onStop: identical shape, one Log.d each

    override fun onDestroy() {
        super.onDestroy()
        Log.d(TAG, "onDestroy (changingConfigurations=$isChangingConfigurations)")
    }
}

package com.example.lesson02

import android.content.Intent
import android.os.Bundle
import android.util.Log
import android.widget.Button
import androidx.appcompat.app.AppCompatActivity
import androidx.core.net.toUri

private const val TAG = "Lifecycle"

class MainActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Log.d(TAG, "onCreate (restored=${savedInstanceState != null})")
        setContentView(R.layout.activity_main)
        findViewById<Button>(R.id.openWebButton).setOnClickListener { openWebPage() }
    }

    private fun openWebPage() {
        val intent = Intent(Intent.ACTION_VIEW, "https://developer.android.com".toUri())
        startActivity(intent)
    }

    override fun onStart() {
        super.onStart()
        Log.d(TAG, "onStart")
    }

    // onResume, onPause, onStop: identical shape, one Log.d each

    override fun onDestroy() {
        super.onDestroy()
        Log.d(TAG, "onDestroy (changingConfigurations=$isChangingConfigurations)")
    }
}
  1. Every override calls super first. The framework does its own work in these methods, and skipping super throws at runtime.
  2. savedInstanceState is non-null when the OS is recreating this Activity after destroying an earlier instance. Logging restored= makes recreation visible.
  3. setContent { } hands the window to Compose. The UI is a function call tree, not an XML file. Lesson 04 explains it properly.setContentView inflates the XML layout into View objects, and findViewById fetches one by its @+id. Lesson 04 replaces this with ViewBinding.
  4. isChangingConfigurations in onDestroy tells you why the Activity is dying: true means a configuration change such as rotation (it's coming straight back), and false means it's really finishing.

XML vs Compose · what changed and whyOnly the lines that put UI on screen differ: setContentView + findViewById + a listener, versus setContent { … } with the click handler inline. The Activity, its lifecycle, the Manifest and Intents are identical, which is why the lifecycle you learn today holds on both tracks.

A4. What actually happens

We ran this app on an Android 16 emulator (targetSdk 36) and drove it step by step. The log, condensed:

You doLogcat showsMeaning
LaunchonCreate (restored=false) · onStart · onResumeFresh instance, now interactive
Press HomeonPause · onStopHidden but alive: no onDestroy
ReopenonStart · onResumeSame instance; onCreate doesn't run again
Open a web pageonPause · onStopAnother app covers yours, just like Home
RotateonPause · onStop · onDestroy (changingConfigurations=true) · onCreate (restored=true) · onStart · onResumeDestroyed and rebuilt, in under a second
Back on the main screenonPause · onStop · onDestroy (changingConfigurations=false)Finished; the next launch starts with onCreate
Gotcha · rotation destroys the Activity By default, a configuration change such as rotation, a dark-mode toggle, or a font-size change destroys the Activity and creates a new instance (Android: Handle configuration changes). Anything stored in the old instance's fields is gone. A BLE connection object held in the Activity gets dropped mid-connection while the radio link may still be open. That's why, from Lesson 05, state lives in a ViewModel, which survives configuration changes, never in the Activity.
Gotcha · Back is not as stable as Home Android 12 documented that pressing Back on a launcher activity at the root of its task moves the task to the background instead of finishing it (Android 12 behaviour changes). On our Android 16 / targetSdk 36 test run it was finished (onDestroy, changingConfigurations=false), and the next launch was a cold onCreate. Back handling has kept changing (predictive back). Don't build anything that depends on Back keeping you alive, and check Logcat on your own device.

Gotcha · XML track: the right layout fileAndroid Studio's multi-screen templates put the Activity's layout (holding a nav host) and each screen's layout (fragment_*.xml) in separate files. Adding widgets to the Activity layout can push out the container that hosts your screens, and then the screen you expect never appears. Always edit the file the lesson names.

B2. Info.plist

Info.plist is the app's metadata dictionary: display name, version, launch screen, and later the usage-description strings that iOS shows in permission prompts (Apple: Information property list). Requesting Bluetooth without NSBluetoothAlwaysUsageDescription doesn't get you a polite denial; the app is terminated. You'll add it in Lesson 07.

B3. Two lifecycles, not one

Android tied "is this screen visible?" and "is the app in front?" to the same Activity callbacks. iOS separates them:

  • App/scene level: is the app's window active, inactive, or in the background? SwiftUI exposes this as scenePhase.UIKit delivers it to the scene delegate (sceneDidBecomeActive, sceneDidEnterBackground, …).
  • View level: did this screen appear or disappear inside the app? onAppear / onDisappear.viewDidLoad, viewWillAppear, viewDidAppear, viewWillDisappear, viewDidDisappear.

Logging uses Apple's Logger, the counterpart of Android's Log.d(TAG, …): subsystem + category ↔ tag. Output shows in Xcode's console, where you can filter on Lifecycle. The subsystem is any string you choose (here com.example.lesson02, not the bundle ID), so filter on it or on the category.

SwiftUI track · Lesson02App.swift

import SwiftUI
import os

let lifecycleLog = Logger(subsystem: "com.example.lesson02", category: "Lifecycle")

@main
struct Lesson02App: App {
    @Environment(\.scenePhase) private var scenePhase

    init() {
        lifecycleLog.notice("App init")
    }

    var body: some Scene {
        WindowGroup {
            ContentView()
        }
        .onChange(of: scenePhase) { _, newPhase in
            switch newPhase {
            case .active: lifecycleLog.notice("scenePhase → active")
            case .inactive: lifecycleLog.notice("scenePhase → inactive")
            case .background: lifecycleLog.notice("scenePhase → background")
            @unknown default: lifecycleLog.notice("scenePhase → unknown")
            }
        }
    }
}

SwiftUI track · ContentView.swift

import SwiftUI

struct ContentView: View {
    var body: some View {
        NavigationStack {
            VStack(spacing: 16) {
                Text("Lesson 02: watch the Xcode console")
                NavigationLink("Open detail screen") {
                    DetailView()
                }
            }
            .navigationTitle("Lifecycle")
            .onAppear { lifecycleLog.notice("ContentView onAppear") }
            .onDisappear { lifecycleLog.notice("ContentView onDisappear") }
        }
    }
}

struct DetailView: View {
    var body: some View {
        Text("Detail screen")
            .onAppear { lifecycleLog.notice("DetailView onAppear") }
            .onDisappear { lifecycleLog.notice("DetailView onDisappear") }
    }
}
  1. @main struct … : App is the entry point. There's no AppDelegate; SwiftUI owns the app object.
  2. @Environment(\.scenePhase) reads a value SwiftUI provides. Watching it with .onChange(of:) at the Scene level gives you the app-level lifecycle.
  3. Each log message is a fixed string per case. Logger treats interpolated values as private by default and can show them as <private> in stored logs. Fixed strings never are.
  4. @unknown default handles phases Apple may add in future iOS versions. ScenePhase isn't a closed enum the way your own are.
  5. onAppear/onDisappear are attached to views. They report what happens inside the app (navigation), not whether the app is in front.

UIKit track · SceneDelegate.swift

import UIKit

final class SceneDelegate: UIResponder, UIWindowSceneDelegate {
    var window: UIWindow?

    func scene(_ scene: UIScene, willConnectTo session: UISceneSession,
               options connectionOptions: UIScene.ConnectionOptions) {
        guard let windowScene = scene as? UIWindowScene else { return }
        let window = UIWindow(windowScene: windowScene)
        window.rootViewController = UINavigationController(rootViewController: ViewController())
        window.makeKeyAndVisible()
        self.window = window
        lifecycleLog.notice("scene willConnect")
    }

    func sceneWillEnterForeground(_ scene: UIScene) { lifecycleLog.notice("sceneWillEnterForeground") }
    func sceneDidBecomeActive(_ scene: UIScene) { lifecycleLog.notice("sceneDidBecomeActive") }
    func sceneWillResignActive(_ scene: UIScene) { lifecycleLog.notice("sceneWillResignActive") }
    func sceneDidEnterBackground(_ scene: UIScene) { lifecycleLog.notice("sceneDidEnterBackground") }
}

UIKit track · ViewController.swift

import UIKit

final class ViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        lifecycleLog.notice("ViewController viewDidLoad")
        title = "Lifecycle"
        view.backgroundColor = .systemBackground

        let button = UIButton(type: .system)
        button.setTitle("Open detail screen", for: .normal)
        button.addAction(UIAction { [weak self] _ in
            self?.navigationController?.pushViewController(DetailViewController(), animated: true)
        }, for: .touchUpInside)
        button.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(button)
        NSLayoutConstraint.activate([
            button.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            button.centerYAnchor.constraint(equalTo: view.centerYAnchor),
        ])
    }

    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        lifecycleLog.notice("ViewController viewWillAppear")
    }

    // viewDidAppear, viewWillDisappear, viewDidDisappear: identical shape, one log each
}

final class DetailViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()
        lifecycleLog.notice("DetailViewController viewDidLoad")
        view.backgroundColor = .systemBackground
        let label = UILabel()
        label.text = "Detail screen"
        label.translatesAutoresizingMaskIntoConstraints = false
        view.addSubview(label)
        NSLayoutConstraint.activate([
            label.centerXAnchor.constraint(equalTo: view.centerXAnchor),
            label.centerYAnchor.constraint(equalTo: view.centerYAnchor),
        ])
    }

    // viewWillAppear, viewDidAppear, viewWillDisappear, viewDidDisappear: one log each,
    // prefixed "DetailViewController"
}
  1. AppDelegate owns process-level events. The scene configuration names the delegate class (via Info.plist) that runs each window.
  2. SceneDelegate creates the window and its root: a UINavigationController, which gives you push/pop navigation and a back button.
  3. The four scene… methods are the app-level lifecycle you'd hook a background monitor into.
  4. The UI is built in code (no storyboard): create a view, add it, constrain it. [weak self] avoids a retain cycle between the view controller and its own button's action.
  5. Info.plist needs a UIApplicationSceneManifest entry pointing at $(PRODUCT_MODULE_NAME).SceneDelegate; see the agent brief.

UIKit vs SwiftUI · what changed and whyUIKit splits the lifecycle across three objects you write yourself (AppDelegate, SceneDelegate, view controllers). SwiftUI turns both levels into state you observe: scenePhase for the app, and onAppear/onDisappear modifiers for views. The two-lifecycle model underneath is the same.

Gotcha · backgrounding fires no view callbacks Press Home and no view-level "disappear" callback fires. Only the scene/app level changes. View callbacks report navigation inside the app, not the app leaving the screen. So a background monitor (Lesson 12) built on view callbacks would silently never notice the app going away: hook the app/scene level. Also note the order during navigation: the new view's onAppear runs before the old view's onDisappear.Also note the order during navigation: the two screens' callbacks interleave (old viewWillDisappear, new viewWillAppear, old viewDidDisappear, new viewDidAppear). Don't write code that depends on either screen's callbacks running first.
Gotcha · no callback when a suspended app is killed Swiping the app away in the app switcher, or the OS reclaiming memory, ends a suspended app with no notice at all. applicationWillTerminate isn't called for suspended apps (Apple docs). Save anything important when you enter the background, not "on exit".
