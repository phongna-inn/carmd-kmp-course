1. What's in an Android project

Today's Gradle project is a handful of build files plus one module, app. Your code, the manifest and the resources live under app/src/main/.

The module build file is where you'll spend most of your Gradle time (Android: Gradle build overview). Each excerpt below shows only the lines its notes explain, and the complete files are in Full files at the end.

  1. No Kotlin plugin. Since Android Gradle Plugin 9, Kotlin support is built in. Applying the old org.jetbrains.kotlin.android plugin now fails the build, so delete it if older tutorials tell you to add it (Android: Migrate to built-in Kotlin). The Compose track still applies the Compose compiler plugin.The XML track needs no other plugin.
  2. Three SDK numbers, three different jobs. compileSdk is which Android APIs your code can see (current Compose libraries require 37). minSdk is the oldest Android version that can install the app. targetSdk is which version's runtime behaviour you opt into.
  3. The BOM (bill of materials) pins one tested set of Compose library versions, which is why material3 has no version of its own.appcompat provides AppCompatActivity and backward-compatible themes for the View system. core-ktx provides Kotlin helpers such as String.toUri(). Declare it explicitly instead of relying on another library to pull it in for you.

2. Activity, Context, Intent, Manifest

An Activity is one entry point with a window and a lifecycle. Our app has exactly one, and so will the Native Device Monitor. A Context is your handle to the system: resources, system services (the Bluetooth service, later), and starting other components (reference). An Activity is a Context. An Intent is a message asking the OS to start something. It can be explicit (a class you own) or implicit ("anyone who can view a web page") (Android: Intents).

The Manifest declares components to the OS. The MAIN + LAUNCHER intent filter is what puts the app's icon in the launcher (Android: App manifest). Permissions get declared here as well, from Lesson 12.

  1. The MAIN action and LAUNCHER category are what make this Activity the one the launcher starts. android:exported="true" lets another app, here the launcher, start it. If the app targets Android 12 (API 31) or higher, as ours does, you must say so explicitly on any Activity that has an intent filter, or the app won't install (Android 12 behaviour changes, <activity> reference).
  2. The XML track's AppCompatActivity crashes at launch unless the theme is an AppCompat theme.

The Intent in the app is the one the button sends. Opening a web page is an implicit intent: you name the action and the data, not a class, and the OS finds an app that can handle it.

3. The activity lifecycle, logged

The OS calls a callback on your Activity at each step of its life (Android: Activity lifecycle). This app logs six of them with tag Lifecycle: onCreate → onStart → onResume on the way in, and onPause → onStop → onDestroy on the way out. A seventh, onRestart, runs when a stopped Activity comes back. You add it in the exercise. In Android Studio's Logcat, filter on tag:Lifecycle (Logcat docs).

  1. Every override calls super first. The framework does its own work in these methods, and skipping super throws at runtime.
  2. savedInstanceState is non-null when the OS is recreating this Activity after destroying an earlier instance. Logging restored= makes recreation visible.
  3. setContent { } hands the window to Compose. The UI is a function call tree, not an XML file. Lesson 06 explains it properly.setContentView inflates the XML layout into View objects, and findViewById fetches one by its @+id. Lesson 06 replaces this with ViewBinding.
  4. isChangingConfigurations in onDestroy tells you why the Activity is dying: true means a configuration change such as rotation (it's coming straight back), and false means it's really finishing.

XML vs Compose · what changed and whyOnly the lines that put UI on screen differ: setContentView + findViewById + a listener, versus setContent { … } with the click handler inline. The Activity, its lifecycle, the Manifest and Intents are identical, which is why the lifecycle you learn today holds on both tracks.

4. What actually happens

We ran this app on an Android 16 emulator (targetSdk 36) and drove it step by step. The log, condensed:

You doLogcat showsMeaning
LaunchonCreate (restored=false) · onStart · onResumeFresh instance, now interactive
Press HomeonPause · onStopHidden but alive: no onDestroy
ReopenonStart · onResumeSame instance; onCreate doesn't run again
Open a web pageonPause · onStopAnother app covers yours, just like Home
RotateonPause · onStop · onDestroy (changingConfigurations=true) · onCreate (restored=true) · onStart · onResumeDestroyed and rebuilt, in under a second
Back on the main screenonPause · onStop · onDestroy (changingConfigurations=false)Finished; the next launch starts with onCreate
Gotcha · rotation destroys the Activity By default, a configuration change such as rotation, a dark-mode toggle, or a font-size change destroys the Activity and creates a new instance (Android: Handle configuration changes). Anything stored in the old instance's fields is gone. A BLE connection object held in the Activity gets dropped mid-connection while the radio link may still be open. That's why, from Lesson 08, state lives in a ViewModel, which survives configuration changes, never in the Activity.
Gotcha · Back is not as stable as Home Android 12 documented that pressing Back on a launcher activity at the root of its task moves the task to the background instead of finishing it (Android 12 behaviour changes). On our Android 16 / targetSdk 36 test run it was finished (onDestroy, changingConfigurations=false), and the next launch was a cold onCreate. Back handling has kept changing (predictive back). Don't build anything that depends on Back keeping you alive, and check Logcat on your own device.

Gotcha · XML track: the right layout fileAndroid Studio's multi-screen templates put the Activity's layout (holding a nav host) and each screen's layout (fragment_*.xml) in separate files. Adding widgets to the Activity layout can push out the container that hosts your screens, and then the screen you expect never appears. Always edit the file the lesson names.

Where this goes in the app

In the Native Device Monitor the Activity is a thin Android shell that the OS can rebuild at any moment, so it owns nothing that has to outlive a rotation. Each thing you'd be tempted to keep in it has a home elsewhere. Colours are the course's colour code, the same as in Lessons 00–02.

You press Home, then reopen the app. Which callback does not run again?

Home only stops the Activity. The same instance resumes, so one-time setup in onCreate is skipped.

After a rotation, what is savedInstanceState in onCreate?

The OS is recreating a destroyed instance, so it passes the saved state bundle.

Which SDK number decides the oldest Android version that can install your app?

compileSdk = which APIs you can see; targetSdk = which runtime behaviour you opt into.

package com.example.lesson03

import android.content.Intent
import android.os.Bundle
import android.util.Log
import android.widget.Button
import androidx.appcompat.app.AppCompatActivity
import androidx.core.net.toUri

private const val TAG = "Lifecycle"

class MainActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Log.d(TAG, "onCreate (restored=${savedInstanceState != null})")
        setContentView(R.layout.activity_main)
        findViewById<Button>(R.id.openWebButton).setOnClickListener { openWebPage() }
    }

    private fun openWebPage() {
        val intent = Intent(Intent.ACTION_VIEW, "https://developer.android.com".toUri())
        startActivity(intent)
    }

    override fun onStart() {
        super.onStart()
        Log.d(TAG, "onStart")
    }

    override fun onResume() {
        super.onResume()
        Log.d(TAG, "onResume")
    }

    override fun onPause() {
        super.onPause()
        Log.d(TAG, "onPause")
    }

    override fun onStop() {
        super.onStop()
        Log.d(TAG, "onStop")
    }

    override fun onDestroy() {
        super.onDestroy()
        Log.d(TAG, "onDestroy (changingConfigurations=$isChangingConfigurations)")
    }
}
