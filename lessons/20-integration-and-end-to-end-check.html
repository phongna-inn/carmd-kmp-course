1. One screen, every feature

Appendix A.1 asks for a UI that is simple and "enough to operate and test every feature", and sketches it as one screen: filter, Scan, the devices, Connect, the status, the received data, Disconnect. m14 has two screens (Lesson 07): the list, and a device screen for the device you tap. It also has one feature with no screen at all: the monitor, which Lesson 18 started from the app's launch and left without buttons. Here is where each feature is operated in m15:

  • inbound ports and adapters
  1. The main screen is where every feature starts. The phone's status, the monitor (new today), the permission and the scan are operated there; the connection is one tap away, on the screen of the device you tapped. That is what "one screen operates every feature" means in m15.
  2. Why not move Connect onto the main screen? A.1 also asks for "basic navigation between screens/sections", and a connection belongs to the device the user picked: the detail ViewModel holds it, and leaving the screen ends it (Lesson 14). Putting it on the list would mean rebuilding Lessons 14–16's screen on four tracks. m15 keeps the two screens.
  3. The parts A.1 lists are all there: a text label and a text field (the filter), buttons, a list (the devices), an image (the device screen's Bluetooth image), navigation, a loading indicator (scanning, connecting, discovering), and status and error messages (the permission line, the alerts, and today the monitor's problem line).

3. The monitor section

The monitor gets its own shared ViewModel, the same on every track. It calls one inbound port, DeviceMonitoring, which already had everything A.7 asks for: start, stop, status, logs() and clearLogs().

  1. The first frame is already right. The state starts from the port's current status, as the detail ViewModel's starts from the session's (Lesson 14), so the section never flashes "stopped" while the monitor runs.
  2. Start uses the launch's interval. MONITOR_INTERVAL becomes internal in AppLaunch.kt, so the two inbound adapters that start the monitor ask for the same 15 minutes.
  3. The status drives a log read. Each change of status (Start, Stop, a record saved by a tick in this process) reads the log again, so a new record shows without a tap.
  1. Show the log, not lastRecord. MonitorStatus lives in memory, one per process. On Android, a tick that ran while the app was closed ran in a process Android started for the work (Lesson 19, section 2); its record is in the file, but no screen's process ever saw it in a status. The file is what lasts, so the section reads it: when the status changes, and each time the screen comes back to the foreground.
  2. The newest read wins. Two reads can overlap (a tick and a return to the foreground); cancelling the older one keeps an older answer from landing last.
  3. Errors reach the UI as state. A record that couldn't be saved (lastError, set by the service since Lesson 18) and a log that couldn't be read or cleared both end in problem, which the section shows in red. A good read puts back the save error, if there is one, so the newest thing that went wrong stays on screen until it goes right.
  4. The time in UTC. The log stores Instant.toString(), which is UTC with a Z (Lesson 17), and the shared code has no time-zone library. The line says "UTC" rather than pretend it's local time.
  5. describe moved. The list ViewModel's status wording is now StatusText.kt, an internal function both ViewModels call: two copies of the same words would drift. Lesson 17's tests that pin the text still pass unchanged.

The screens differ only in how they place the section and when they ask for a fresh read:

A slot is a composable parameter: Compose's docs call them slot APIs, and Material components such as Scaffold and Button take their content that way. DeviceListContent stays stateless: it places whatever it's given, and a preview or a test can pass {}. koinViewModel() scopes the monitor's ViewModel to the list's back stack entry, next to the list's own. ON_RESUME comes on the first frame, on return to the foreground, and after Back from the device screen.

Two flows, two launches. collect on a StateFlow never returns, so a second collect written after the first inside repeatOnLifecycle would never run. The layout adds a vertical LinearLayout, monitorSection, under the status row, then a one-pixel divider; filterInput now sits below the divider. A Fragment asks Koin for the second ViewModel the same way as the first, with by viewModel(): one of each class, both scoped to the Fragment.

SwiftUI's slot is a generic view parameter, as in VStack<Content>: Swift infers Monitor as MonitorSection at the call. MonitorSection (a new file) keeps its own ViewModelOwner in @State, collects uiState in .task, and calls refreshLog() when scenePhase becomes .active, like the list's permission check.

The controller's one ViewModelOwner serves both: ViewModelProvider keys each ViewModel by its class, so asking for MonitorViewModel creates a second one in the same store, cleared with the first. The section is a vertical UIStackView of two rows (summary and Start/Stop; count and Clear) and two multi-line labels, placed after the status row, then a one-point divider. viewDidDisappear cancels both observation tasks.

Gotcha · "Monitor running" and no record After Start, Android writes a record within seconds: a new periodic work request runs at once. iOS writes the first one a whole interval after Start, because the foreground timer waits one interval before its first tick (Lesson 19, section 3). Both are right, and both are in the behaviour table. A tester who taps Start on an iPhone and sees "Records in the log: 0" for 15 minutes hasn't found a bug.

4. A Stop that lasts

Stop has to outlive the process that heard it. The monitor's state lives in memory; the schedule lives in the platform (WorkManager's database on Android, nothing at all on iOS while the app is in the foreground); and every new process runs onAppLaunch(). So the user's choice needs a home that survives the process, and the launch needs to read it:

  1. The rule is the service's: a Stop lasts until Start, and a monitor nobody stopped runs. restore is a new member of the inbound port, called once per process by onAppLaunch() in place of start.
  2. "Never chose" means running. That keeps m14's behaviour, so every row of Lesson 19's behaviour table stays true, including "a record a moment after the first launch" on Android.
  3. A stopped launch schedules nothing. On Android, Stop's cancel() already removed the work, so no process is started for it; a later launch by the user leaves the status Stopped and hands no tick to anyone. On iOS, no timer starts and no refresh request is submitted.
  • inbound adapters
  • app core
  • outbound port and adapters
  1. A port, because storage is the platform's. Lesson 10's recipe for a platform capability: an outbound port in the app's terms, one adapter per platform. The port stores a fact (the last tap was Stop); the service decides what it means.
  2. A plain Boolean, false until set, so the adapters need no "missing" case: SharedPreferences returns the default you pass "if the key isn't present", and UserDefaults.bool(forKey:) returns "false if the key isn't present in the defaults database". It also crosses into Swift as a Bool; a Kotlin Boolean? would arrive as KotlinBoolean? (Lesson 17).
  3. Not suspending. The launch must know the answer before Android's worker reads the tick: MonitorWorker takes currentTick when it runs, and the only moment sure to come before that is Application.onCreate (Lesson 18). A suspending read would have to finish later, in a coroutine, and a worker could run first and find no tick.

Shared code, so the same on both Android tracks; DeviceMonitorApplication passes AndroidMonitorSettings(this) to initKoin. Android's guide: "apply() changes the in-memory SharedPreferences object immediately but writes the updates to disk asynchronously", while commit() is synchronous and "you should avoid calling it from your main thread". The same guide recommends DataStore: "a modern data storage solution that you should use instead of SharedPreferences", which "uses Kotlin coroutines and Flow to store data asynchronously". That is the right default for an app's settings; here the one value must be read synchronously during Application.onCreate (walk 6), which is what SharedPreferences offers. On the emulator, after Stop, adb shell run-as com.example.devicemonitor cat shared_prefs/monitor.xml shows <boolean name="stoppedByUser" value="true" />.

The Android settings adapter is shared code in androidMain, the same as on the Compose track (switch Android to Compose to see its excerpt), and DeviceMonitorApplication, which both Android tracks share, passes AndroidMonitorSettings(this) to initKoin.

A Swift adapter, as the course's iOS adapters are unless there's a reason not to: the port's types cross cleanly, a Bool each way. (Lesson 18's scheduler is Kotlin in iosMain because its Duration and suspend lambda don't; Lesson 17's log store is the course's one planned Kotlin/Native example.) Apple: the defaults system "is a persistent store for app-specific and system-wide settings", and "When you write values to a UserDefaults object, the object updates its in-memory version of that information right away, and writes the value to disk asynchronously": the same shape as apply(). The app start passes IosMonitorSettings() to doInitKoin; run xcodegen generate so the project includes the new file.

The Swift adapter, IosMonitorSettings.swift, is one file for both iOS tracks (switch iOS to SwiftUI to see its excerpt). AppDelegate's didFinishLaunchingWithOptions passes IosMonitorSettings() to doInitKoin; run xcodegen generate so the project includes the new file.

Gotcha · asking the platform instead On Android it is tempting to skip the setting and ask WorkManager whether the work is still scheduled. iOS has nothing to ask: in the foreground the schedule is a coroutine in the process, and the refresh request is cancelled while the app is active. The answer would also differ by platform, and the rule would move into two adapters. One port, one rule in the service, one fact per platform.

5. A rule out of a ViewModel: the scan's time limit

Lesson 13 put the 10-second limit around the list ViewModel's collection, with the comment "A real radio drains the battery while it scans, so every scan has a time limit." "Every scan" is a rule of the app, and a second screen that scanned would have to remember to copy it. The session's connect timeout has been the session service's since Lesson 14. The scan's moves to its service:

  1. The same mechanism, one level down. withTimeoutOrNull cancels its block when time runs out and returns null instead of throwing. Cancelling the block cancels the collection of BleScanner.scan(), which stops the radio in the adapter's awaitClose (Lesson 13), and the service's Flow then completes normally.
  2. The ViewModel just waits for the end. When the Flow completes, collect returns and the state becomes Finished, as before. Stop still cancels the ViewModel's job, and the cancellation travels down the same way. On the emulator, with the simulated radio, five devices appeared and "Devices found: 5" came 10 seconds after Scan, as in m14.
  3. The port says so. DeviceScanning.scan's comment now reads "The scan ends by itself after 10 seconds, and the Flow completes; cancelling the collector stops it sooner." A caller learns the rule from the port, not from a ViewModel.
  4. The tests move with the rule. ScanningServiceTest gains aScanEndsByItselfAtTheTimeLimitAndStopsTheRadio (10 s of virtual time, then awaitComplete() and the fake radio stopped), and its old test that waited "an hour of virtual time" for a scan that never ends now waits 5 seconds. The list ViewModel's timeout test becomes showsDevicesAsTheyArriveThenFinishesWhenTheScanEnds: TestDeviceScanning gains finish(), which ends the scan as the service would.

Retrieval checks

Answer from memory, without scrolling up.

A user taps Stop, then opens the app the next morning. In m14 with a Stop button added, and nothing else changed, what would they see?

The service's memory ends with the process, and the launch starts it again. m15 keeps the user's Stop in MonitorSettings and calls restore.

Where does the rule "a Stop lasts until Start; a monitor nobody stopped runs" live in m15?

Adapters keep facts; services apply rules. A plain Boolean, false until set, needs no rule in the adapter at all.

Why does the monitor section read the log file instead of showing MonitorStatus.Running.lastRecord?

The file is what lasts (Lesson 18). The section reads it when the status changes and each time the screen comes back.

Why must MonitorSettings.isStoppedByUser() answer synchronously?

Swift implements Kotlin suspend functions (Lesson 12's __request), and DataStore has a Kotlin Multiplatform version. The reason is the order of events in a process Android starts for the work.

After the scan's time limit moves into ScanningService, how does the list ViewModel learn that the scan is over?

withTimeoutOrNull returns null instead of throwing, and the flow builder's block then ends: a normal completion.

Removing androidx.core:core-ktx from androidApp/build.gradle.kts: what happens to androidx.core in the app?

dependencyInsight showed androidx.core:core:1.18.0, from androidx.activity and others, where the line had asked for 1.19.1. "Unused" means nothing in that module imports it.

Mixed review (interleaved)

The monitor section's ViewModel is built by Koin, like the others. What fails, and when, if you forget viewModelOf(::MonitorViewModel)? (Lesson 11)

Koin resolves at run time. That's why the graph test asks for every ViewModel, and why m15's version asks for the new one.

In the XML Fragment, why does each collect get its own launch inside repeatOnLifecycle? (Lessons 01 and 08)

A StateFlow is hot and never ends; collect suspends until its coroutine is cancelled, which repeatOnLifecycle does when the Fragment stops.

That's what the outbound port is for. The permission check still runs, through PermissionChecker, which stays real.

    suspend fun logs(): List<LogRecord>

    // Removes every record from the log.

package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.DeviceMonitoring
import com.example.devicemonitor.core.outbound.BatteryProvider
import com.example.devicemonitor.core.outbound.BluetoothProvider
import com.example.devicemonitor.core.outbound.ConnectionStatus
import com.example.devicemonitor.core.outbound.LogStore
import com.example.devicemonitor.core.outbound.MonitorScheduler
import com.example.devicemonitor.core.outbound.MonitorSettings
import com.example.devicemonitor.core.outbound.NetworkProvider
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlin.time.Clock
import kotlin.time.Duration

// Service: the background monitor's rules. Each tick reads the phone's status through Lesson 17's
// four status ports (ConnectionStatus included, never the session), stamps it with the time,
// and appends it to the log. When it runs is the scheduler's business, not this class's. Whether
// it runs after a launch is the user's: a Stop lasts until Start.
class MonitoringService(
    private val battery: BatteryProvider,
    private val network: NetworkProvider,
    private val bluetooth: BluetoothProvider,
    private val connection: ConnectionStatus,
    private val log: LogStore,
    private val scheduler: MonitorScheduler,
    private val settings: MonitorSettings,
    private val clock: Clock = Clock.System,
) : DeviceMonitoring {
    private val _status = MutableStateFlow<MonitorStatus>(MonitorStatus.Stopped)
    override val status: StateFlow<MonitorStatus> = _status.asStateFlow()

    override fun start(interval: Duration) {
        require(interval.isPositive()) { "The monitor's interval must be positive, not $interval." }
        settings.setStoppedByUser(false)
        run(interval)
    }

    override fun stop() {
        settings.setStoppedByUser(true)
        scheduler.cancel()
        _status.value = MonitorStatus.Stopped
    }

    // A monitor the user never stopped runs from the first launch on; a stopped one stays stopped.
    override fun restore(interval: Duration) {
        require(interval.isPositive()) { "The monitor's interval must be positive, not $interval." }
        if (!settings.isStoppedByUser()) run(interval)
    }

    override suspend fun logs(): List<LogRecord> = log.read()

    override suspend fun clearLogs() = log.clear()

    private fun run(interval: Duration) {
        _status.value = MonitorStatus.Running(interval)
        scheduler.schedule(interval) { tick() }
    }

    // One reading. A tick that comes after stop() writes nothing. A file error doesn't stop the
    // monitor: it shows in the status, and the next tick tries again.
    private suspend fun tick() {
        if (_status.value !is MonitorStatus.Running) return
        val record = LogRecord(clock.now(), readStatus(battery, network, bluetooth, connection))
        val error = try {
            log.append(record)
            null
        } catch (e: LogStoreException) {
            e.message
        }
        _status.update { current ->
            when (current) {
                is MonitorStatus.Running ->
                    if (error == null) current.copy(lastRecord = record, lastError = null)
                    else current.copy(lastError = error)
                MonitorStatus.Stopped -> current
            }
        }
    }
}

package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.DeviceScanning
import com.example.devicemonitor.core.outbound.BleScanner
import com.example.devicemonitor.core.outbound.PermissionChecker
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow
import kotlinx.coroutines.withTimeoutOrNull
import kotlin.time.Duration.Companion.seconds

// Service: the app's scan rules on top of a raw radio scan. Start the radio only when the
// permission is granted and the radio is there and on. Then keep the devices that have a
// name containing the filter (ignoring case and surrounding spaces), and report each once,
// for at most SCAN_TIMEOUT.
class ScanningService(
    private val scanner: BleScanner,
    private val permissions: PermissionChecker,
) : DeviceScanning {
    override fun scan(nameFilter: String): Flow<Device> = flow {
        checkReady()
        val wanted = nameFilter.trim()
        val seen = mutableSetOf<String>()
        // The timeout cancels the radio's collection, which stops the radio, and the Flow completes.
        withTimeoutOrNull(SCAN_TIMEOUT) {
            scanner.scan().collect { device ->
                val named = device.name.isNotBlank()
                if (named && device.name.contains(wanted, ignoreCase = true) && seen.add(device.id)) {
                    emit(device)
                }
            }
        }
    }

    // In this order: on iOS, the radio's first use is what shows the permission prompt.
    private suspend fun checkReady() {
        if (permissions.check(Permission.Bluetooth) != PermissionStatus.Granted) {
            throw ScanException("Scanning needs the Bluetooth permission.")
        }
        if (!scanner.isAvailable()) throw ScanException("This phone has no Bluetooth LE radio.")
        if (!scanner.isEnabled()) throw ScanException("Bluetooth is off. Turn it on, then scan again.")
    }

    companion object {
        // A real radio drains the battery while it scans, so every scan has a time limit,
        // whichever screen starts it.
        val SCAN_TIMEOUT = 10.seconds
    }
}

// The phone's status as one line of text, the same on every track: the list screen's status
// line and each record the monitor section shows. Words for the screen, so an inbound adapter's
// business, written once.
internal fun describe(s: DeviceStatus): String {
    val battery = s.battery?.let { "Battery $it %" } ?: "Battery unknown"
    val wifi = when {
        s.wifiEnabled == false -> "Wi-Fi off"
        s.wifiConnected -> "Wi-Fi connected"
        s.wifiEnabled == true -> "Wi-Fi on, not connected"
        else -> "Wi-Fi not connected"
    }
    val cellular = if (s.cellularAvailable) "cellular available" else "no cellular"
    val bluetooth = when (s.bluetoothEnabled) {
        true -> "Bluetooth on"
        false -> "Bluetooth off"
        null -> "Bluetooth unknown"
    } + if (s.bluetoothConnected) ", device connected" else ""
    return listOf(battery, wifi, cellular, bluetooth).joinToString(" · ")
}

import kotlinx.coroutines.Job
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch

// Inbound adapter: turns the screen's events into calls on the DeviceScanning, PermissionAccess
// and StatusReport ports, and the results into UI state. It knows the ports only.
class DeviceListViewModel(
    private val scanning: DeviceScanning,
    private val permissions: PermissionAccess,
    private val statusReport: StatusReport,
) : ViewModel() {
    private val _uiState = MutableStateFlow(
        DeviceListUiState(bluetooth = permissions.status(Permission.Bluetooth)),
    )
    val uiState: StateFlow<DeviceListUiState> = _uiState.asStateFlow()

    private var scanJob: Job? = null
    private var permissionJob: Job? = null
    private var statusJob: Job? = null

    fun startScan(filter: String) {
        if (scanJob?.isActive == true) return
        _uiState.update { it.copy(scan = ScanState.Scanning(emptyList())) }
        scanJob = viewModelScope.launch {
            val found = mutableListOf<Device>()
            try {
                // The scan ends by itself after its time limit (the scanning service's rule).
                scanning.scan(filter).collect { device ->
                    found += device
                    _uiState.update { it.copy(scan = ScanState.Scanning(found.toList())) }
                }
                _uiState.update { it.copy(scan = ScanState.Finished(found.toList())) }
            } catch (e: ScanException) {
                _uiState.update { it.copy(scan = ScanState.Idle, errorMessage = e.message) }
            }
        }
    }

    // The Stop button. Cancelling the scan's coroutine cancels its collection, which stops the
    // service's scan and the radio. The devices found so far stay on screen.
    fun stopScan() {
        val job = scanJob ?: return
        if (!job.isActive) return
        job.cancel()
        _uiState.update { state ->
            val scan = state.scan
            if (scan is ScanState.Scanning) state.copy(scan = ScanState.Finished(scan.found)) else state
        }
    }

    fun errorShown() {
        _uiState.update { it.copy(errorMessage = null) }
    }

    // The screen calls this each time it comes back to the foreground: the user may have
    // changed the permission in Settings meanwhile.
    fun refreshPermission() {
        if (permissionJob?.isActive == true) return
        _uiState.update { it.copy(bluetooth = permissions.status(Permission.Bluetooth)) }
    }

    fun requestPermission() {
        if (permissionJob?.isActive == true) return
        permissionJob = viewModelScope.launch {
            val result = permissions.request(listOf(Permission.Bluetooth))
            _uiState.update { it.copy(bluetooth = result.getValue(Permission.Bluetooth)) }
        }
    }

    fun openSettings() {
        permissions.openSettings()
    }

    // The screen calls this when it appears, when the app comes back to the foreground, and from
    // its Refresh button: each call reads the status again.
    fun refreshStatus() {
        if (statusJob?.isActive == true) return
        statusJob = viewModelScope.launch {
            val current = statusReport.current()
            _uiState.update { it.copy(phoneStatus = describe(current)) } // StatusText.kt
        }
    }
}

import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch

// Inbound adapter: turns the monitor section's Start, Stop and Clear into calls on the
// DeviceMonitoring port, and the monitor's status and log into UI state. It knows the port only.
class MonitorViewModel(private val monitoring: DeviceMonitoring) : ViewModel() {
    private val _uiState = MutableStateFlow(MonitorUiState().showing(monitoring.status.value))
    val uiState: StateFlow<MonitorUiState> = _uiState.asStateFlow()

    private var logJob: Job? = null

    init {
        viewModelScope.launch {
            monitoring.status.collect { status ->
                _uiState.update { it.showing(status) }
                // Start, Stop, or a new record from a tick in this process: read the log again.
                refreshLog()
            }
        }
    }

    fun start() {
        monitoring.start(MONITOR_INTERVAL)
    }

    fun stop() {
        monitoring.stop()
    }

    // The status says only what this process saw. The log file is what lasts: records a tick
    // wrote in another process (Android starts one for the work when the app isn't running) or
    // while the screen was away. The screen calls this each time it comes back to the foreground.
    fun refreshLog() {
        logJob?.cancel() // the newest read wins
        logJob = viewModelScope.launch {
            try {
                val records = monitoring.logs()
                _uiState.update {
                    it.copy(
                        recordCount = records.size,
                        newest = records.takeLast(SHOWN).reversed().map(::line),
                        problem = savingError(),
                    )
                }
            } catch (e: LogStoreException) {
                _uiState.update { it.copy(problem = e.message) }
            }
        }
    }

    fun clearLog() {
        viewModelScope.launch {
            try {
                monitoring.clearLogs()
                refreshLog()
            } catch (e: LogStoreException) {
                _uiState.update { it.copy(problem = e.message) }
            }
        }
    }

    private fun MonitorUiState.showing(status: MonitorStatus): MonitorUiState = when (status) {
        MonitorStatus.Stopped -> copy(running = false, summary = "Monitor stopped", problem = null)
        is MonitorStatus.Running -> copy(
            running = true,
            summary = "Monitor running, about every ${status.interval.inWholeMinutes} min",
            problem = status.lastError,
        )
    }

    // Why the newest tick's record couldn't be saved, if it couldn't.
    private fun savingError(): String? = (monitoring.status.value as? MonitorStatus.Running)?.lastError

    // "2026-09-11 10:30:00 UTC · Battery 82 % · …": the time as the log stores it, in UTC.
    private fun line(record: LogRecord): String =
        record.timestamp.toString().take(19).replace('T', ' ') + " UTC · " + describe(record.status)

    companion object {
        // How many records the section shows.
        const val SHOWN = 3
    }
}

// Outbound adapter: the user's Stop, kept in SharedPreferences, a small key-value file in the
// app's private storage that outlives the process. Read synchronously: Application.onCreate must
// know the answer before WorkManager runs the monitor's work in that process.
class AndroidMonitorSettings(context: Context) : MonitorSettings {
    private val preferences = context.getSharedPreferences("monitor", Context.MODE_PRIVATE)

    override fun isStoppedByUser(): Boolean = preferences.getBoolean(STOPPED_BY_USER, false)

    override fun setStoppedByUser(stopped: Boolean) {
        // apply() changes the value in memory now and writes the file in the background.
        preferences.edit().putBoolean(STOPPED_BY_USER, stopped).apply()
    }

    private companion object {
        const val STOPPED_BY_USER = "stoppedByUser"
    }
}

// Test implementation of the DeviceScanning inbound port. It stands in for the whole app
// core, so a ViewModel test tests the ViewModel only. The test decides what a scan finds.
class TestDeviceScanning : DeviceScanning {
    private val found = Channel<Device>(Channel.UNLIMITED)
    var failure: ScanException? = null
    val filters = mutableListOf<String>() // one entry per scan started
    var isScanning = false
        private set

    override fun scan(nameFilter: String): Flow<Device> = flow {
        filters += nameFilter
        failure?.let { throw it }
        isScanning = true
        try {
            emitAll(found.receiveAsFlow())
        } finally {
            isScanning = false
        }
    }

    fun find(vararg devices: Device) {
        devices.forEach { found.trySend(it) }
    }

    // The scan ends by itself, as the service's ends at its time limit.
    fun finish() {
        found.close()
    }
}

import SwiftUI

// Stateful: connects the monitor's shared ViewModel to the content below, with its own
// ViewModelOwner. The list screen puts it in its monitor slot.
struct MonitorSection: View {
    @Environment(\.scenePhase) private var scenePhase
    @State private var owner = ViewModelOwner()
    @State private var state: MonitorUiState?

    var body: some View {
        let viewModel: MonitorViewModel = owner.viewModel()
        let state = self.state ?? viewModel.uiState.value
        MonitorContent(
            state: state,
            onStart: { viewModel.start() },
            onStop: { viewModel.stop() },
            onClear: { viewModel.clearLog() }
        )
        .task {
            for await newState in viewModel.uiState {
                self.state = newState
            }
        }
        // Back in the foreground: a tick may have written records while the screen was away.
        .onChange(of: scenePhase) { _, phase in
            if phase == .active { viewModel.refreshLog() }
        }
    }
}

// Stateless: the monitor's state, Start or Stop, and the log's newest records with Clear.
struct MonitorContent: View {
    let state: MonitorUiState
    let onStart: () -> Void
    let onStop: () -> Void
    let onClear: () -> Void

    var body: some View {
        VStack(alignment: .leading, spacing: 4) {
            HStack {
                Text(state.summary)
                    .frame(maxWidth: .infinity, alignment: .leading)
                // One button: Stop while running, Start while stopped.
                Button(state.running ? "Stop" : "Start", action: state.running ? onStop : onStart)
                    .buttonStyle(.bordered)
            }
            HStack {
                Text("Records in the log: \(state.recordCount)")
                    .font(.footnote)
                    .frame(maxWidth: .infinity, alignment: .leading)
                Button("Clear", action: onClear)
                    .disabled(state.recordCount == 0)
            }
            ForEach(state.newest, id: \.self) { line in
                Text(line)
                    .font(.caption)
                    .foregroundStyle(.secondary)
            }
            if let problem = state.problem {
                Text(problem)
                    .font(.caption)
                    .foregroundStyle(.red)
            }
        }
    }
}

    // Collect only while on screen, like repeatOnLifecycle(STARTED) on Android. Shown, and back
    // from the detail screen: the status may have changed.
    override func viewWillAppear(_ animated: Bool) {
        super.viewWillAppear(animated)
        viewModel.refreshStatus()
        observation?.cancel()
        observation = Task {
            for await state in viewModel.uiState {
                render(state)

        monitorObservation?.cancel()
        monitorObservation = Task {
            for await state in monitorViewModel.uiState {
                renderMonitor(state)
            }
        }
    }

        super.viewDidDisappear(animated)
        observation?.cancel()
        observation = nil
        monitorObservation?.cancel()
        monitorObservation = nil
    }

    // The one place that touches views: every new state ends here. The text field owns
    // its own text, so render() never sets it.
    private func render(_ state: DeviceListUiState) {
        let isScanning = state.scan is ScanStateScanning
        // SKIE turns the sealed interface into a Swift enum, so this switch is exhaustive.
        let devices: [Device]? = switch onEnum(of: state.scan) {
        case .idle: nil
        case .scanning(let scanning): scanning.found
        case .finished(let finished): finished.found
        }
        phoneStatusLabel.text = state.phoneStatus
        renderPermission(state.bluetooth)
        scanButton.configuration?.title = isScanning ? "Stop" : "Scan"
        scanButton.isEnabled = isScanning || state.bluetooth == .granted
        if isScanning { spinner.startAnimating() } else { spinner.stopAnimating() }
        spinner.isHidden = !isScanning
        if isScanning {
            statusLabel.text = "Scanning…"
        } else if let devices {
            statusLabel.text = devices.isEmpty
                ? "No devices found. Try another filter."
                : "Devices found: \(devices.count)"
        } else {
            statusLabel.text = "Tap Scan to look for devices."
        }
        statusLabel.textColor = devices?.isEmpty == true && !isScanning ? .systemRed : .label

        devicesById = Dictionary(uniqueKeysWithValues: (devices ?? []).map { ($0.id, $0) })
        var snapshot = NSDiffableDataSourceSnapshot<Int, String>()
        snapshot.appendSections([0])
        snapshot.appendItems((devices ?? []).map(\.id))
        dataSource.apply(snapshot, animatingDifferences: true)
        renderError(state.errorMessage)
    }

    // The monitor section: every new monitor state ends here.
    private func renderMonitor(_ state: MonitorUiState) {
        monitorSummaryLabel.text = state.summary
        monitorButton.configuration?.title = state.running ? "Stop" : "Start"
        recordCountLabel.text = "Records in the log: \(state.recordCount)"
        clearLogButton.isEnabled = state.recordCount > 0
        newestRecordsLabel.text = state.newest.joined(separator: "\n")
        newestRecordsLabel.isHidden = state.newest.isEmpty
        monitorProblemLabel.text = state.problem
        monitorProblemLabel.isHidden = state.problem == nil
    }

    // One message and at most one action per permission status. SKIE makes the Kotlin enum a
    // Swift enum, so this switch is exhaustive.
    private func renderPermission(_ status: PermissionStatus) {
        let (message, action): (String, String?) = switch status {
        case .granted: ("Bluetooth permission: allowed", nil)
        case .notRequested: ("Device Monitor needs Bluetooth permission to find nearby devices.", "Allow Bluetooth")
        case .denied: ("Bluetooth permission was denied. Scanning needs it to find nearby devices.", "Ask again")
        case .permanentlyDenied: ("Bluetooth permission is off. You can turn it on in Settings.", "Open Settings")
        case .restricted: ("Bluetooth is restricted on this device, so scanning isn't available.", nil)
        }
        permissionLabel.text = message
        permissionLabel.textColor = switch status {
        case .granted: .secondaryLabel
        case .notRequested: .label
        case .denied, .permanentlyDenied, .restricted: .systemRed
        }
        permissionButton.configuration?.title = action
        permissionButton.isHidden = action == nil
    }

    private func renderError(_ message: String?) {
        guard let message, presentedViewController == nil else { return }
        let alert = UIAlertController(title: "Scan failed", message: message, preferredStyle: .alert)
        alert.addAction(UIAlertAction(title: "OK", style: .default) { [weak self] _ in
            self?.viewModel.errorShown()
        })
        present(alert, animated: true)
    }

    func tableView(_ tableView: UITableView, didSelectRowAt indexPath: IndexPath) {
        tableView.deselectRow(at: indexPath, animated: true)
        guard let deviceId = dataSource.itemIdentifier(for: indexPath), let device = devicesById[deviceId] else { return }
        // The detail screen gets the whole device: it needs all of it to connect.
        navigationController?.pushViewController(DeviceDetailViewController(device: device), animated: true)
    }
