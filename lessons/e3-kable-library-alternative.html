Kable: the library alternative

~2 h · no extra time per UI track Milestone: e3 BLE stack switchable between hand-written and Kable Prereq: 20 (m15)
Why this matters: Lessons 13–16 wrote the Bluetooth LE code by hand, once per platform: a callback object turned into a Flow on Android, a Swift delegate with a Kotlin half on iOS. That's the best way to learn what the radio does, and the team's apps still contain code like it. But a real project can also take a library. Kable is a Kotlin Multiplatform BLE library: one coroutine API over Android's BluetoothGatt and Apple's CoreBluetooth. This extension writes a second pair of adapters over Kable, behind the same BleScanner and BleConnection outbound ports, and switches the whole app to them with one Koin line. Nothing in the app core, the ViewModels or the screens changes. Then it compares the two stacks on what you'd actually weigh: lines of code, connection state, errors and iOS behaviour, measured where we could. That gives milestone e3: a BLE stack you can switch between hand-written and Kable.

Primary source Kable's README (scanning, connectivity, observation, background support and Android permissions) before section 2, and its API docs for Peripheral and Scanner before sections 3–5. Kable's release notes for 0.44.0 (section 3). Koin's Modules page, "Load order and overrides", before section 6.

Tracks Every file this extension touches is in the shared module, so it's the same on Compose, XML Views, SwiftUI and UIKit, and no screen changes. The tracks differ only in how you run the checks. Each excerpt shows only the lines its notes explain; the complete files are in Full files at the end.

Did E1 or E2 first? Every extension starts from m15, and the full files here are m15 plus E3. If your project already has e1 or e2, three files have both extensions' lines: keep theirs and add E3's. Those files are shared/build.gradle.kts (Kable's dependency next to Ktor's or ExifInterface's), di/AppModule.kt (kableBleModule and the initKoin line, next to their bindings) and di/AppModuleTest.kt (the Kable test, next to their ViewModels). This page's code was built from m15 alone, so check the merged files with the tests.

1. The same ports, a second stack

Lesson 10 promised that the app core doesn't care what's behind an outbound port. Lesson 20 used that promise once, to swap in the simulated radio for a run. This extension uses it for real: a whole second set of adapters for the two BLE ports, written against a library instead of against the platforms.

  • app core
  • outbound adapters (shared)
  • Android
  • iOS

Why can the Kable adapters live in commonMain when the hand-written ones can't? Because the platform code has moved into the library. Kable's commonMain declares a Scanner and a Peripheral, and Kable's own androidMain and appleMain implement them over BluetoothLeScanner/BluetoothGatt and CBCentralManager/CBPeripheral. That's the same expect/actual split as Lesson 05's, one layer down, inside someone else's code. Our adapters translate between Kable's types and the app's: Device, ConnectionState, DeviceService, ScanException, ConnectionException. It's the job every outbound adapter has; ADR 0001 places a shared one, like E1's Ktor client, in commonMain.

2. Kable in the build

Kable describes itself as "a simple Coroutines-powered API for interacting with Bluetooth Low Energy devices". Scanning is a Flow of advertisements; a Peripheral has suspend functions for connect, read and write, a state StateFlow, and observe, a Flow of a characteristic's notifications. One dependency in commonMain:

  1. No permissions come with it. Kable's README: "Kable does not declare any permissions; it is expected that the consuming app declares any necessary permissions." A separate artifact, kable-default-permissions, would add some; the app doesn't use it, because its manifest has declared exactly what it needs since Lesson 12. We compared the merged Android manifests of m15 and e3: the same permission lines.
  2. What it does add on Android. Two entries in the merged manifest, both under AndroidX Startup's InitializationProvider: com.juul.kable.KableInitializer, and TuulboxCoroutinesInitializer from tuulbox, a JuulLabs library Kable uses. The first is how Kable gets the application Context without our code passing one, which is why KableBleScanner and KableBleConnection take no Context. Gradle's dependency tree (./gradlew :androidApp:dependencies) also shows what Kable brings along on Android: kotlinx-io, atomicfu, tuulbox, AndroidX Startup, core-ktx (which Lesson 20 had removed from the app's own build file) and the parcelize runtime.
  3. 0.45.0, pinned. Kable is 0.x: its releases still make breaking changes (0.44.0 turned Bluetooth.availability into a compile error, section 3). Pin the version, and read the release notes before you upgrade.

3. The scanner: a Flow that's already there

Lesson 13's Android scanner was a callbackFlow around a ScanCallback, plus a broadcast receiver; the iOS one was a Swift delegate feeding a Kotlin callbackFlow. Kable's Scanner already has a Flow, advertisements, so the adapter only translates:

  1. Collecting starts the scan, cancelling stops it. That's the port's contract from Lesson 10, and Kable's advertisements already keeps it: on Android it's a callbackFlow whose awaitClose calls stopScan (in Kable's source), much like ours. On the emulator, a scan that ran out after 10 s and one we stopped after 2 s both show as stopped in adb shell dumpsys bluetooth_manager ("LE scans (started/stopped): 2 / 2").
  2. The name is the advertised one. Kable's Advertisement.name is ScanRecord.getDeviceName on Android and CBAdvertisementDataLocalNameKey on Apple, the same fields Lesson 13 read. Kable also has peripheralName, the system's cached name, which can differ; the adapter keeps the advertised one, so the list shows the same names with either stack.
  3. The identifier is text. Kable's Identifier is an expect type whose actuals are typealiases: a String (the MAC address) on Android, a Uuid on Apple. A string template turns either into the String a Device holds, and kablePeripheral turns it back (section 4).
  4. Failures in the app's words. catch sees what Kable throws when the scan starts or fails: UnmetRequirementException with a reason (BluetoothDisabled, or LocationServicesDisabled, which Kable's docs say is "only applicable on Android 11 (API 30) and lower"), or an IllegalStateException (a missing permission, a failed scan). catch doesn't see the collector's own cancellation, so Stop and the 10 s limit still end the scan quietly.
  5. isAvailable and isEnabled come from another port. Kable doesn't answer them any more: 0.44.0's release notes say "Escalate deprecation of Bluetooth.availability", and "you'll now need to maintain your own version in your codebase"; the deprecation message says it "has inconsistent behavior across platforms". Kable's experimental Bluetooth.isSupported() "always returns true on Apple". The app already has the answer: Lesson 17's BluetoothProvider port, whose null means "the app can't tell: the phone has no radio, or (iOS) the user hasn't allowed Bluetooth". ScanningService checks the permission first, so by the time it asks, an iPhone's null means no radio. The adapter holds no rule by asking: it passes the question on, and Koin passes in whichever BluetoothProvider the platform built. The alternative, each platform's own isAvailable and isEnabled, would bring platform code back into a shared adapter.
  6. internal. Koin builds both Kable adapters in shared code (section 6), so they're internal, like E1's Ktor adapter. The iOS framework's header has no Kable class in it (grep -c Kable Shared.h prints 0).

Two things the shared code can't say, because Kable's builder options differ per platform: how to build the scanner, and how to get a device's Peripheral back from its id. Each is an expect with one actual per platform, part of the adapter as E1's httpEngine() was:

  1. Kable's defaults aren't Lesson 13's. On Android, Kable's scanSettings defaults to ScanSettings.Builder().build(). We built a copy with a bare Scanner() and scanned on the API 36 emulator: dumpsys bluetooth_manager showed ScanMode=LOW_POWER; with the line above, ScanMode=LOW_LATENCY, as AndroidBleScanner asks. Kable marks scanSettings @ObsoleteKableApi: its KDoc says it "will be replaced by a Kable provided DSL", hence the opt-in.
  2. On iOS, Kable reports every advertisement unless told not to. Its allowDuplicateKeys defaults to true. CoreBluetooth's own default is false: the central "coalesces multiple discoveries of the same peripheral into a single discovery event", and Apple warns that turning that off "can have an adverse effect on battery life; use it only if necessary". IosBleScanner keeps Apple's default, so this does too. The port allows either (Lesson 13: "the same device may come again"), and ScanningService reports each device once anyway.
  3. One CBCentralManager, configured before first use. Kable makes one manager for the whole app, on first use (a scan, or creating a Peripheral), on a dispatch queue of its own. Without configure, it passes no options, and Apple's default for CBCentralManagerOptionShowPowerAlertKey is true: "If the key isn't specified, the default value is true", so iOS would show its own alert if Bluetooth is off as the manager is made. Any configure call makes Kable pass false (in Kable's source), so the app keeps showing its own message, as the hand-written adapters do. Kable's README: "attempts to configure it after initialization will result in an IllegalStateException". The lazy runs it once, before the first scanner or peripheral. In this app, ScanningService checks that Bluetooth is on before the first scan, so Kable's manager is normally made with Bluetooth on; configure makes sure the alert can't appear either way.
  4. Back from an id to a Peripheral. On Android, Peripheral(identifier) calls getRemoteDevice with the address, as AndroidBleConnection does. On iOS, it asks Kable's manager to retrieve the peripheral by UUID, as IosBleConnection asks its own, and Kable's docs say it throws NoSuchElementException if iOS doesn't know it: "a scan will be necessary". The connection adapter turns that into "Scan again".

4. The connection: suspend, don't call back

Lessons 14–16's connection adapters had the most machinery: a callbackFlow for the link, a CompletableDeferred for each request's answer, a delegate that had to be kept alive. Kable's Peripheral does all of that inside: connect(), read() and the rest are suspend functions that return the answer or throw. So connect is a plain flow { }:

  1. connect() returns when the link is ready, discovery included. Kable's README: "A connection is considered ready when connected, services have been discovered, and observations (if any) have been re-wired. Service discovery occurs automatically upon connection." So this adapter emits Connected later than the hand-written ones, which emit it as soon as the link is up and discover services as a separate request. The screens show the same states, but "connecting…" now lasts until discovery is done, and SessionService's 10-second limit (Lesson 14) now also covers discovery.
  2. The flow's life is the link's life. After Connected, the flow suspends on Kable's state until it's Disconnected: a drop. That becomes the port's ConnectionException, which SessionService reports, as in Lesson 16. A Disconnect tap doesn't get there: it cancels the collector, so first is cancelled and only finally runs.
  3. Every way out frees the radio. finally calls disconnect(), which "cancels an in-flight connection attempt" too, and then close(): Kable's Peripheral "should be disposed (via close) when no longer needed". disconnect() suspends, and this finally often runs because the collector was cancelled, so it runs under NonCancellable, as SessionService's unsubscribe did in Lesson 16. On the API 30 emulator, a timed-out attempt ended with BluetoothGatt: cancelOpen(), then close() and unregisterApp() in logcat.
  4. disconnect() waits for the radio. It "suspends until the peripheral has settled on a disconnected state", for up to the peripheral's disconnectTimeout, 5 seconds by default (in Kable's source, Android and Apple alike). A pending attempt that's cancelled never reports a disconnection on Android, so there it waits the full 5 s. Section 8 measures what that does to the screen.
  5. The link holds the scope. connect() returns a CoroutineScope that Kable cancels on disconnect. The adapter keeps it with the peripheral in Link, for the subscriptions (section 5).
  1. discoverServices() asks nothing of the device. Kable's services is a StateFlow that's "null until services have been discovered", and after connect() it's filled. The port still has the function, so the session service and the screens work unchanged; this adapter just answers from what it already knows.
  2. A characteristic by its two UUIDs. characteristicOf(service, characteristic) names one the way the app does; Kable then uses "the first found characteristic with [Read] property matching the service UUID and characteristic UUID" (its KDoc). No search through the platform's GATT objects, which AndroidBleConnection.find and the Swift target(for:) did by hand.
  3. One request at a time is still the service's rule. Kable serializes its own requests too (a Mutex in its Connection, on both platforms, in its source), but the port's contract says callers send one request at a time ("callers wait for each to finish before sending the next"), and SessionService's lock keeps it. Nothing here depends on that lock, or works around it.
  4. Every failure becomes a ConnectionException, except cancellation. kable { } wraps each call: a cancellation passes through, as E1's adapter does (Kotlin's docs: "if you must catch it, rethrow it"), and anything else gets the app's words first, then Kable's: NotConnectedException is "the link closed first", NoSuchElementException is "no such characteristic", UnmetRequirementException is "Bluetooth is off". KableTranslationTest pins the closed-link words and the fallback without a radio; Kable's UnmetRequirementException has an internal constructor, so a test can't make one.

5. Notifications: a Flow, split into requests

Kable has no subscribe. Its observe(characteristic) returns a Flow<ByteArray>: collecting it turns the notifications on (Kable writes the CCCD descriptor, as Lesson 16 did by hand), and cancelling the collection turns them off. The port, since Lesson 16, splits that into requests and data: subscribe and unsubscribe, each one request under the session's lock, and notifications, a Flow you collect first. So the adapter starts the collection inside subscribe, and lets it run in the link's scope:

  1. onSubscription says when they're on. Kable runs observe's onSubscription action "after the observation is spun up (i.e. after enabling notifications or indications)". Completing on there makes subscribe return when the device has accepted, as the port promises. If enabling fails, the observe flow fails, and on carries the failure to subscribe's caller. If the link closes first, the job completes, and invokeOnCompletion fails on (a CompletableDeferred ignores a second completion, so this only matters when nothing came first).
  2. In the link's scope, so it ends with the link. Kable's README says an observe flow "will remain active" across a drop and resumes after a reconnect. The port promises the opposite: "The link ending ends the values". Launching the collection in the scope connect() returned does that, because Kable cancels that scope on disconnect.
  3. Cancel and join is Kable's unsubscribe. When the last collector of an observation goes away while connected, Kable turns the notifications off (its Observation.onCompletion, under NonCancellable). cancelAndJoin waits for that, so unsubscribe returns after the CCCD write, as the hand-written one did.
  4. The values go out as before. notified is a MutableSharedFlow, and notifications(characteristic) filters it by the two UUIDs, exactly as AndroidBleConnection and LinkedBleConnection do. SessionService still collects first, then subscribes (Lesson 16).
Gotcha · a library's shape isn't your port's It's tempting to change the port to fit the library: make subscribe return Kable's Flow and drop unsubscribe. Then the hand-written adapters, the fake and SessionService all change, and the session's one-request-at-a-time lock no longer covers the CCCD write. The port is named in the app's terms (ADR 0001), so the adapter bends: here, a small bridge from "a Flow whose collection is the subscription" to "a request, then a stream". If two libraries both fit a port badly, then it's worth asking whether the port is wrong. One awkward fit isn't that.

6. One Koin line

The platform still builds its hand-written adapters and passes them to initKoin, as in m15. A third module, in shared code, binds the same two ports to the Kable adapters, and it's listed last:

  1. The module loaded last wins. Koin's Modules page: "When two loaded modules declare the same type, the module loaded last wins. In a DSL start block, this is the order of modules(...)." platformModule binds BleScanner and BleConnection to what the platform passed; kableBleModule, after it, rebinds both. KableBleScanner(get()) gets the platform's BluetoothProvider, which nothing overrides.
  2. One line, both platforms. initKoin is shared code, so the line switches Android and iOS together. Delete it, and the app is m15's again; nothing else in the app knows. That's the refactor checklist's "swapping an adapter is one line" (Lesson 20), for a whole stack.
  3. The platform's adapters are still built. Each app start still constructs AndroidBleScanner, IosBleConnection and the rest, and passes them to initKoin, where the Kable bindings replace them, so Koin never hands them out. They're cheap: IosBleScanner and IosBleConnection make their CBCentralManager on first use, which never comes. Moving the choice into each app start instead (pass Kable's adapters to initKoin) would need the adapters to be public, and two lines per platform; keeping it in shared code is one line.

The graph test (Lesson 11) gets one more case: with the fakes passed in as the platform's adapters and kableBleModule after them, Koin hands out the Kable adapters, and a ViewModel that needs the session still builds on top. Building them touches no radio: KableBleScanner stores its BluetoothProvider, and Kable's scanner and CBCentralManager are made only when a scan or a connection starts. platformFakes() is the old inline module, moved into a function so both tests use it. KableTranslationTest covers the translations: a Kable DiscoveredService (an interface, so a test can make one) becomes the app's DeviceService with full upper-case UUIDs and the right properties, and three failures get the app's words.

Gotcha · the Kable line overrides Lesson 20's simulated run Lesson 20 ran the end-to-end BLE rows by passing SimulatedBleScanner and SimulatedBleConnection to initKoin from each app start. With kableBleModule in the list, that swap does nothing: the Kable bindings come later, and they win, as kableBleModuleReplacesThePlatformsBleAdapters shows with fakes. For a simulated run on e3, delete the Kable line too, then put both back.

9. When to choose which

Neither stack is the right one everywhere. What the runs and the code above suggest:

  1. Choose a library like Kable when the app's BLE needs are ordinary (scan, connect, read, write, notify) and the team writes Kotlin on both platforms: one copy of the adapters instead of one per platform, under a quarter of the code lines (118 against 202 + 321), no Swift-to-Kotlin seam, and errors as typed exceptions. It suits a team that would otherwise maintain the same state machine twice.
  2. Write it by hand when you need a platform's behaviour exactly: background modes and state restoration on iOS, a phone maker's quirk to work around on Android, a precise moment to report Connected, or a reaction to Bluetooth going off mid-scan, which Kable's scanner doesn't watch for. Also when the team owns iOS in Swift and wants CoreBluetooth in its own language.
  3. Either way, keep the port. The choice stayed cheap here because the app core never saw BluetoothGatt, CBPeripheral or a Kable type. With the port in place, you can start with a library and drop to hand-written code for one platform later, or the other way round, one Koin line at a time.
  4. Read its defaults. Most differences we met were defaults: low-power scanning, duplicates on, a 5-second disconnect wait, the power alert. A library decides things for you; the adapter is where you decide them back.

Retrieval checks

Answer from memory, without scrolling up.

Why can KableBleScanner and KableBleConnection live in commonMain, when Lesson 13's adapters needed one per platform?

The platform code didn't disappear; it moved into the library. The two small actuals that remain are the per-platform choices Kable's builders leave to us.

initKoin lists appModule, platformModule(…), then kableBleModule. Which BleScanner does ScanningService get?

Koin's "Load order and overrides". To make an accidental override fail instead, Koin has allowOverride(false); this app relies on the override, and the graph test pins it.

When does KableBleConnection emit Connected, compared with AndroidBleConnection?

Kable's README: "Service discovery occurs automatically upon connection." So the session's 10-second limit now covers discovery too, and discoverServices() answers without asking the device.

With the Kable stack on Android, Bluetooth goes off two seconds into a scan. What does the screen show?

Kable checks Bluetooth before it starts the scan, not during it, and Android's scan callback reports nothing when the radio goes off (Lesson 13). The hand-written adapter listens for the broadcast; Kable's scanner doesn't.

Why does subscribe launch Kable's observe collection in the link's scope instead of returning Kable's Flow?

Kable's own observe flow survives a drop and resumes after a reconnect; the port says "The link ending ends the values". The scope connect() returns is cancelled on disconnect, so the collection ends with the link.

Why does the iOS actual call CentralManager.configure { }, with nothing inside, before Kable's first scan?

Apple: "If the key isn't specified, the default value is true." The lazy makes sure it runs once, first.

Mixed review (interleaved)

Why did AndroidBleScanner register a receiver for ACTION_STATE_CHANGED? (Lesson 13)

The same silence is what the Kable stack runs into in section 8.

You add kableBleModule to initKoin but forget to bind BluetoothProvider anywhere. When do you find out? (Lesson 11)

Koin resolves get() when it builds the definition, which is why Lesson 11 added a graph test, and why this extension adds a case to it.

Why does the Kable adapter's finally wrap peripheral.disconnect() in withContext(NonCancellable)? (Lesson 16)

The same reason SessionService sends its unsubscribe under NonCancellable when the collector goes away.

Unaided exercise

Unaided exercise (no agent, on your e3 project)
  1. Predict, then switch. Write down what the screen will say when Bluetooth goes off two seconds into a scan, first with the Kable line, then without it. Run both on the emulator (adb shell cmd bluetooth_manager disable, then enable). Then run ./gradlew :shared:allTests without the line: which test still passes, and why doesn't it need the line in initKoin?
  2. Close the gap. Make KableBleScanner end the scan with ScanException("Bluetooth was turned off.") when Bluetooth goes off, without changing the port. A first idea that needs nothing new: while the scan runs, ask BluetoothProvider every second, and fail when it stops saying true. Write it so a test can check it with FakeBluetoothProvider and a fake advertisement source, then try it on the emulator. What does polling cost, and what would an actual per platform listen to instead?
  3. The 5-second wait. On the API 30 emulator, time the "didn't answer" dialog after Connect on a gDevice-beacon. Then give the Android Peripheral a shorter wait (Peripheral(device.id) { disconnectTimeout = 1.seconds }) and time it again. What could a too-short wait cost on a real phone with a live link?

// Outbound port: what the app needs from a Bluetooth radio, in the app's own terms.
// One adapter per platform: Kotlin in androidMain, Swift in the iOS app. Or one shared adapter
// over the Kable library, KableBleScanner in commonMain (Extension E3).
interface BleScanner {
    // Whether this phone has a Bluetooth LE radio the app can use.
    suspend fun isAvailable(): Boolean

    // Whether that radio is switched on.
    suspend fun isEnabled(): Boolean

    // Every device the radio hears, as it hears it; the same device may come again. A device
    // that advertises no name comes with name "". Collecting starts the radio scan, and
    // cancelling the collector stops it. Throws ScanException.
    fun scan(): Flow<Device>
}

package com.example.devicemonitor.core.outbound

import com.example.devicemonitor.core.Characteristic
import com.example.devicemonitor.core.ConnectionState
import com.example.devicemonitor.core.Device
import com.example.devicemonitor.core.DeviceService
import kotlinx.coroutines.flow.Flow

// Outbound port: what the app needs from a Bluetooth radio to hold a link to one device, in the
// app's own terms. One adapter per platform: Kotlin in androidMain; on iOS, a Kotlin half in
// iosMain (LinkedBleConnection) over a Swift half in the iOS app. Or one shared adapter over the
// Kable library, KableBleConnection in commonMain (Extension E3).
interface BleConnection {
    // The link to device, as its state changes: Connecting, then Connected once it's up.
    // Collecting starts the connection, and cancelling the collector ends it and frees what the
    // radio held for it. Throws ConnectionException when the attempt fails or the link drops.
    fun connect(device: Device): Flow<ConnectionState>

    // The requests below go over the link that connect() holds open, one at a time: callers wait
    // for each to finish before sending the next. Each throws ConnectionException when there's
    // no link, when the link closes first, or when the device or the radio reports an error.

    // Every service on the device with its characteristics, all UUIDs in the full form (fullUuid).
    suspend fun discoverServices(): List<DeviceService>

    // The characteristic's value, as the bytes the device sent. Only after discoverServices().
    suspend fun read(characteristic: Characteristic): ByteArray

    // Asks the device to send the characteristic's value each time it changes (it must notify):
    // from then on the values arrive in notifications(characteristic). Only after
    // discoverServices().
    suspend fun subscribe(characteristic: Characteristic)

    // Asks the device to stop sending them.
    suspend fun unsubscribe(characteristic: Characteristic)

    // Not a request: the values the device sends for characteristic, as they arrive, for as long
    // as it is collected. A value that arrives while nobody collects is lost, so collect first,
    // then subscribe. The link ending ends the values, not this Flow.
    fun notifications(characteristic: Characteristic): Flow<ByteArray>
}

// Outbound adapter: the phone's Bluetooth LE radio through the Kable library, behind the
// BleScanner port. Shared code, the same Kotlin on Android and iOS. Kable's Scanner is already a
// Flow, so there's no callback here: the adapter translates Kable's advertisements and failures
// into the app's Device and ScanException.
internal class KableBleScanner(private val bluetooth: BluetoothProvider) : BleScanner {
    // Kable doesn't answer these two: 0.44.0 made Bluetooth.availability a compile error (it
    // behaved differently on each platform), and its experimental isSupported() is always true on
    // iOS. So they ask the BluetoothProvider port (Lesson 17), whose null means no radio to use.
    override suspend fun isAvailable(): Boolean = bluetooth.isEnabled() != null

    override suspend fun isEnabled(): Boolean = bluetooth.isEnabled() == true

    // Collecting starts Kable's scan and cancelling the collector stops it, as the port asks.
    // Kable's name is the advertised name, as in the hand-written adapters; none becomes "".
    // The identifier is the address (a String) on Android and a Uuid on iOS: "$" makes it text.
    override fun scan(): Flow<Device> =
        kableScanner().advertisements
            .map { Device(id = "${it.identifier}", name = it.name.orEmpty(), rssi = it.rssi) }
            .catch { failure -> throw ScanException(scanFailure(failure)) }
}

// Kable's failures, in the words the app shows. catch never sees the collector's cancellation.
internal fun scanFailure(failure: Throwable): String = when {
    failure is UnmetRequirementException && failure.reason == UnmetRequirementReason.BluetoothDisabled ->
        "Bluetooth is off. Turn it on, then scan again."
    failure is UnmetRequirementException ->
        "Scanning needs Location turned on on this phone (Android 11 and lower)."
    else -> "The scan failed (Kable: ${failure.message})."
}

import com.example.devicemonitor.core.Characteristic

// Outbound adapter: a link to one device through the Kable library, behind the BleConnection
// port. Shared code, the same Kotlin on Android and iOS. Kable's Peripheral suspends where the
// platforms call back, so there's no callback object and no request waiting for its answer here:
// each port function calls Kable and translates the answer, and the failure, into the app's terms.
internal class KableBleConnection : BleConnection {
    // The open link: the device's Peripheral, the scope Kable keeps for this one connection, and
    // the subscriptions running in it. The session service sends one request at a time.
    private class Link(val peripheral: Peripheral, val scope: CoroutineScope) {
        val subscriptions = mutableMapOf<Characteristic, Job>()
    }

    @Volatile private var link: Link? = null

    // Every value a subscribed characteristic sends on the link; nobody collecting, it's dropped.
    private val notified = MutableSharedFlow<Notified>(extraBufferCapacity = 64)

    private class Notified(val characteristic: Characteristic, val value: ByteArray)

    // Kable's connect() suspends until the link is up and every service is discovered, then
    // returns. Kable's state then says when the link drops. However the Flow ends, finally
    // disconnects and closes the Peripheral, which frees what the radio held for it.
    override fun connect(device: Device): Flow<ConnectionState> = flow {
        val peripheral = try {
            kablePeripheral(device)
        } catch (e: Exception) {
            throw ConnectionException("Kable couldn't find ${device.name} (${e.message}). Scan again.")
        }
        try {
            emit(ConnectionState.Connecting(device))
            val scope = kable("The connection failed") { peripheral.connect() }
            link = Link(peripheral, scope)
            emit(ConnectionState.Connected(device))
            val ended = peripheral.state.first { it is State.Disconnected } as State.Disconnected
            val reason = ended.status?.toString() ?: "no reason given"
            throw ConnectionException("The link to ${device.name} was lost (Kable: $reason).")
        } finally {
            link = null
            withContext(NonCancellable) { peripheral.disconnect() }
            peripheral.close()
        }
    }

    // Not a request any more: Kable discovered everything before connect() returned.
    override suspend fun discoverServices(): List<DeviceService> {
        val services = openLink().peripheral.services.value
            ?: throw ConnectionException("Discovery failed: Kable has no services for this link.")
        return services.map { it.toDeviceService() }
    }

    override suspend fun read(characteristic: Characteristic): ByteArray {
        val peripheral = openLink().peripheral
        return kable("The device refused the read") { peripheral.read(characteristic.inKable()) }
    }

    // Kable has no subscribe: observe() returns a Flow, and collecting it writes the CCCD
    // descriptor. So subscribing starts a collection in the link's scope, and waits until Kable
    // says notifications are on (observe's onSubscription) or the collection fails or ends.
    override suspend fun subscribe(characteristic: Characteristic) {
        val link = openLink()
        val on = CompletableDeferred<Unit>()
        val job = link.scope.launch {
            try {
                link.peripheral.observe(characteristic.inKable()) { on.complete(Unit) }
                    .collect { notified.emit(Notified(characteristic, it)) }
            } catch (e: CancellationException) {
                throw e
            } catch (e: Exception) {
                on.completeExceptionally(e)
            }
        }
        job.invokeOnCompletion { on.completeExceptionally(NotConnectedException("The link closed first.")) }
        link.subscriptions[characteristic] = job
        kable("The device refused to turn on its notifications") { on.await() }
    }

    // Cancelling the collection is Kable's unsubscribe: it writes the CCCD to turn them off.
    override suspend fun unsubscribe(characteristic: Characteristic) {
        openLink().subscriptions.remove(characteristic)?.cancelAndJoin()
    }

    override fun notifications(characteristic: Characteristic): Flow<ByteArray> =
        notified
            .filter { it.characteristic.serviceUuid == characteristic.serviceUuid }
            .filter { it.characteristic.uuid == characteristic.uuid }
            .map { it.value }

    private fun openLink(): Link = link ?: throw ConnectionException("Not connected.")
}

// The app's characteristic as Kable names one: by its service's UUID and its own.
private fun Characteristic.inKable() = characteristicOf(Uuid.parse(serviceUuid), Uuid.parse(uuid))

// A service Kable discovered, in the app's terms: full upper-case UUIDs (fullUuid), and the
// properties from the same Characteristic Properties bits both platforms report.
internal fun DiscoveredService.toDeviceService(): DeviceService {
    val serviceUuid = fullUuid(serviceUuid.toString())
    return DeviceService(
        uuid = serviceUuid,
        characteristics = characteristics.map {
            Characteristic(serviceUuid, fullUuid(it.characteristicUuid.toString()), propertiesOf(it.properties.value))
        },
    )
}

// Runs one Kable call, and gives any failure to the app core as a ConnectionException: the
// user's words first, Kable's after. Cancellation passes through as it is.
private suspend fun <T> kable(what: String, call: suspend () -> T): T =
    try {
        call()
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        throw ConnectionException(connectionFailure(what, e))
    }

internal fun connectionFailure(what: String, failure: Exception): String = when (failure) {
    is UnmetRequirementException -> "Bluetooth is off. Turn it on, then connect again."
    is NotConnectedException -> "$what: the link closed first."
    is NoSuchElementException -> "This device has no such characteristic. Scan and connect again."
    else -> "$what (Kable: ${failure.message})."
}

// that, Kable passes no options, and iOS then shows its own alert if Bluetooth is off as the
// manager is made. Any configure call passes ShowPowerAlert false, so the app shows its own
// message instead, as the hand-written adapters do. configure throws once the manager exists,
// so it runs once, first.
private val managerSetUp = lazy { CentralManager.configure { } }

// Kable turns off iOS's duplicate filtering unless told otherwise: an event for every
// advertisement, which costs battery. IosBleScanner keeps iOS's default, each device once per
// scan, and so does this.
internal actual fun kableScanner(): PlatformScanner {
    managerSetUp.value
    return Scanner { allowDuplicateKeys = false }
}

// The id is the identifier the scan reported. Kable asks its manager for that peripheral, as
// IosBleConnection asks its own, and throws NoSuchElementException if iOS doesn't know it.
internal actual fun kablePeripheral(device: Device): Peripheral {
    managerSetUp.value
    return Peripheral(device.id.toIdentifier())
}

// The composition root, as a Koin module: which service implements each inbound port,
// which adapter implements each outbound port, and how to build each ViewModel.
internal val appModule = module {
    single<DeviceScanning> { ScanningService(get(), get()) }
    // One session for the whole app: every screen sees the same connection state.
    single<DeviceSession> { SessionService(get(), get()) }
    single<PermissionAccess> { PermissionService(get()) }
    single<StatusReport> { StatusService(get(), get(), get(), get()) }
    // The bridge adapter: the status asks ConnectionStatus, and the one session answers.
    single<ConnectionStatus> { SessionConnectionStatus(get()) }
    // The monitor reads the same four status ports, writes to the log store, and keeps the
    // user's Stop in the settings.
    single<DeviceMonitoring> { MonitoringService(get(), get(), get(), get(), get(), get(), get()) }
    viewModelOf(::DeviceListViewModel)
    viewModelOf(::DeviceDetailViewModel)
    viewModelOf(::MonitorViewModel)
}

// The outbound adapters that each platform builds itself and passes to initKoin.
internal fun platformModule(
    permissionChecker: PermissionChecker,
    bleScanner: BleScanner,
    bleConnection: BleConnection,
    batteryProvider: BatteryProvider,
    networkProvider: NetworkProvider,
    bluetoothProvider: BluetoothProvider,
    logStore: LogStore,
    monitorScheduler: MonitorScheduler,
    monitorSettings: MonitorSettings,
) = module {
    single { permissionChecker }
    single { bleScanner }
    single { bleConnection }
    single { batteryProvider }
    single { networkProvider }
    single { bluetoothProvider }
    single { logStore }
    single { monitorScheduler }
    single { monitorSettings }
}

// The other BLE stack: the Kable adapters, shared code that each platform doesn't build itself.
// Listed after platformModule, its two definitions replace the platform's BleScanner and
// BleConnection: when two modules define the same type, Koin keeps the one loaded last.
internal val kableBleModule = module {
    single<BleScanner> { KableBleScanner(get()) }
    single<BleConnection> { KableBleConnection() }
}

// Call once, when the app process starts (Android: Application.onCreate; iOS: at launch).
fun initKoin(
    permissionChecker: PermissionChecker,
    bleScanner: BleScanner,
    bleConnection: BleConnection,
    batteryProvider: BatteryProvider,
    networkProvider: NetworkProvider,
    bluetoothProvider: BluetoothProvider,
    logStore: LogStore,
    monitorScheduler: MonitorScheduler,
    monitorSettings: MonitorSettings,
) {
    startKoin {
        modules(
            appModule,
            platformModule(
                permissionChecker, bleScanner, bleConnection, batteryProvider, networkProvider, bluetoothProvider,
                logStore, monitorScheduler, monitorSettings,
            ),
            kableBleModule, // the BLE stack: delete this line for the hand-written adapters
        )
    }
}

package com.example.devicemonitor.adapter.outbound

import com.example.devicemonitor.core.CharacteristicProperty
import com.juul.kable.DiscoveredCharacteristic
import com.juul.kable.DiscoveredDescriptor
import com.juul.kable.DiscoveredService
import com.juul.kable.ExperimentalKableApi
import com.juul.kable.NotConnectedException
import kotlin.test.Test
import kotlin.test.assertEquals
import kotlin.uuid.Uuid

// The Kable adapters' translations, without a radio: Kable's discovered services and its
// failures, in the app's terms. Kable's discovered types are interfaces, so a test can make one.
class KableTranslationTest {
    @OptIn(ExperimentalKableApi::class)
    private fun battery(): DiscoveredService {
        val serviceUuid = Uuid.parse("0000180f-0000-1000-8000-00805f9b34fb")
        val level = object : DiscoveredCharacteristic {
            override val serviceUuid = serviceUuid
            override val characteristicUuid = Uuid.parse("00002a19-0000-1000-8000-00805f9b34fb")
            override val descriptors = emptyList<DiscoveredDescriptor>()
            override val properties = com.juul.kable.Characteristic.Properties(0x12) // read, notify
        }
        return object : DiscoveredService {
            override val serviceUuid = serviceUuid
            override val characteristics = listOf(level)
        }
    }

    @Test
    fun aDiscoveredServiceComesInTheAppsTerms() {
        val service = battery().toDeviceService()

        assertEquals("0000180F-0000-1000-8000-00805F9B34FB", service.uuid)
        val level = service.characteristics.single()
        assertEquals(service.uuid, level.serviceUuid)
        assertEquals("00002A19-0000-1000-8000-00805F9B34FB", level.uuid)
        assertEquals(listOf(CharacteristicProperty.Read, CharacteristicProperty.Notify), level.properties)
    }

    @Test
    fun aDroppedLinkSaysWhatFailed() {
        val message = connectionFailure("The device refused the read", NotConnectedException("gone"))

        assertEquals("The device refused the read: the link closed first.", message)
    }

    @Test
    fun anyOtherFailureKeepsKablesWords() {
        val message = connectionFailure("The device refused the read", IllegalStateException("Read failed"))

        assertEquals("The device refused the read (Kable: Read failed).", message)
    }

    @Test
    fun aScanFailureKeepsKablesWords() {
        assertEquals("The scan failed (Kable: Scan failed).", scanFailure(IllegalStateException("Scan failed")))
    }
}
