Camera and media

~2.5 h · +1 h per extra UI track Milestone: e2 capture + pick + display Prereq: 20 (m15)
Why this matters: a phone app that inspects something in the real world sooner or later wants a picture of it: a damaged connector, a dashboard light, a label with a serial number. This extension gives the Native Device Monitor a photo screen: take a photo with the camera, or choose one from the library, and see it with its media info (the course plan's Appendix A.4). The interesting part isn't the picture. It's that the camera and the photo library are the system's own screens, which only a screen of yours can open, while the decision to open them belongs to the app. The extension shows how a MediaPicker outbound adapter and the screen cooperate, how the camera permission joins the permission code from Lesson 12, and the traps on the way: files the camera app writes for you, and photos stored on their side. That gives milestone e2: capture, pick and display, on both platforms.

Primary source Android: Photo picker and TakePicture before section 3, FileProvider and MediaStore.ACTION_IMAGE_CAPTURE before section 4. Apple: Requesting authorization to capture and save media before section 2, PhotosPicker, PHPickerViewController and UIImagePickerController before section 5.

Tracks The ports, the service, the ViewModel and every test are shared code, the same on every track. The Android adapter lives in androidMain and the iOS adapter in the iOS app, so both tracks of a platform share them. The tracks differ in the photo screen, in who lends the adapter its way to the system's screens, and in the button that opens the screen (sections 3, 5 and 7); the extra hour per track is those on XML or UIKit. Each excerpt shows only the lines its notes explain; the complete files are in Full files at the end.

Did E1 first? Every extension starts from m15, and the full files here are m15 plus E2. If your project already has e1, a few files have both extensions' lines: keep E1's lines and add E2's. Those files are shared/build.gradle.kts (Ktor's dependencies and ExifInterface), di/AppModule.kt (both bindings, both ViewModels), the main screen (an "API test" and a "Photo" button side by side), the Android manifest and docs/checklists.md. On Compose, DeviceMonitorApp.kt also gets both routes; on XML, nav_graph.xml gets both destinations. AppModuleTest builds both ViewModels too. This page's code was built from m15 without e1, so check the merged files with the tests and both apps.

1. Two trips to the system, one port

Appendix A.4 gives the shape: an inbound port MediaCapture with capturePhoto() and pickMedia(), each returning a MediaInfo, and an outbound port MediaPicker with "the same two calls, one adapter per platform". What makes this capability different from the others is where the work happens. An app could draw its own camera screen (CameraX on Android, AVFoundation on iOS) or read the library itself; this one doesn't. It asks the system to show its camera or its photo picker, waits while the user is there, and gets one answer back. So each call is a trip: out of the app, and back with a photo or with nothing.

  • inbound port and adapter
  • app core
  • outbound ports
  • Android
  • iOS
  1. A trip has three endings, and only one is a photo. Closing the camera is something users do all the time; it isn't a failure, so it's a value of its own, Cancelled. A failure carries the platform's reason. Because every ending is a value, the port has no exceptions to document, and the Swift adapter returns plain Kotlin objects (section 5).
  2. hasCamera() is the same kind of question as Lesson 13's BleScanner.isAvailable(): a fact about the device that the service needs before it starts anything.
  3. The app keeps its own copy. What the system hands back isn't a file the app owns: on Android, the photo picker's answer is a content URI the app may read for a while (until "the device is restarted or until your app stops", the photo picker guide says); on iOS, the picker hands over the image's bytes. Each adapter writes a file in the app's cache, and MediaInfo.path points there, a plain string the core can hold without knowing anything about URIs.
  4. Media info, measured once. Type, pixel size and file size are read by the adapter, where the platform's image APIs are. The width and height are the photo the way up it's shown (section 8 says why that's not the same as the pixels stored).

2. The service and the camera permission

The service holds the rules, and there are two: the camera opens only on a device that has one and with the camera permission granted; and the library needs no permission at all.

  1. The camera permission goes through the port Bluetooth already uses. ScanningService checks PermissionChecker before it starts the radio (Lesson 13); MediaCaptureService does the same before it opens the camera. A port is not another service, so this is allowed by the refactor checklist's "services don't know each other". The service only checks: asking is the screen's choice, through PermissionAccess, exactly as for Bluetooth.
  2. No permission for the library, on either platform. Android's photo picker lets users "grant your app access to only selected images and videos, instead of their entire media library", and our app declares no media permission. Apple's PHPickerViewController, which SwiftUI's PhotosPicker shows too, runs in a separate process, so "it's private by default. The user doesn't need to explicitly authorize your app to select photos". An app that reads the whole library itself needs a library permission; this one never does.
  3. The inbound port speaks to the ViewModel the way DeviceScanning does: a MediaInfo, null for "closed without a photo", or a MediaException with words for the user, like ScanException. The outbound port's three values become those three.

Permission gains a second case, Camera, and each platform's PermissionChecker maps it. Nothing else in Lesson 12's permission code changes: PermissionService's rule (prompt only when the system can still prompt) and the five statuses work for any permission.

  1. The m15 iOS checker answered every permission with Bluetooth's status: there was only one. It now switches on the permission, and SKIE makes the Kotlin enum a Swift enum, so a third case would be a compile error here, not a wrong answer.
  2. iOS asks once. "The system remembers the user's response to each access alert, so subsequent uses of the corresponding capture device don't cause the alert to appear again" (Apple's authorization guide). So .denied is PermanentlyDenied, and the screen offers Open Settings, as it does for Bluetooth. Android lets the app ask again after a first refusal, as in Lesson 12.
  3. The prompt's text is required. iOS shows NSCameraUsageDescription in the prompt, and an app without it that "requests authorization or attempts to use a capture device" is terminated. Both iOS tracks add it to project.yml, and xcodegen generate writes it into Info.plist.

3. Only a screen can open the system's screens

Here is the problem the port has to solve. The service decides when the camera opens, and the adapter does the opening, but neither is a screen. On Android, only an Activity or a Fragment can register for a result, "and only while it is being created", as Lesson 12's MainActivity says. On iOS, only a view (SwiftUI) or a view controller (UIKit) can present another screen. So the screen lends the adapter its way to the system's screens, and passes the system's answer on. Lesson 12 did exactly this for the permission prompt; e2 does it twice more, for the camera and the picker.

  1. The same three moves as AndroidPermissionChecker: attach takes the launchers, the callbacks complete a CompletableDeferred, and the suspended call resumes. The ViewModel's coroutine waits the whole time the camera app is in front.
  2. The answer says almost nothing. TakePicture "returns true if the image was saved into the given Uri", and the photo picker returns a Uri or null. Everything else (where the file is, what it is) the adapter knows already or reads afterwards.
  3. A cancelled camera leaves an empty file, because the adapter names the file before the camera opens (section 4). It deletes it.

Compose has one Activity, so it lends the launchers for the whole app, as it does the permission launcher. DeviceMonitorApplication (the same file on both Android tracks) builds one AndroidMediaPicker for the process, keeps it in a property next to permissionChecker, and passes it to initKoin.

On the XML track each Fragment registers its own launchers, as DeviceListFragment does since Lesson 12, so the photo screen lends a permission launcher too: while it's on screen, the camera prompt comes from it. detach ignores a launcher that is no longer the attached one, so the order in which one Fragment stops and the next starts doesn't matter.

4. Android: a file for the camera app, a copy from the picker

TakePicture doesn't hand a photo back: it asks the phone's camera app (whichever app answers MediaStore.ACTION_IMAGE_CAPTURE; on the emulator, its built-in Camera) to write "the full-sized image" into a URI the app provides. Another app can't write into our private files directly, so the app shares one folder through a FileProvider, which turns a file into a content:// URI:

  1. Only media/ in the cache is shared. cache-path "represents files in the cache subdirectory of your app's internal storage area", the folder getCacheDir() returns. The adapter writes nowhere else, and the provider can make URIs for nothing else.
  2. The authority is the app's ID plus .files; the adapter builds the same string from context.packageName, which is the application ID at run time.
  3. MediaFileProvider is an empty subclass. AndroidX's FileProvider reference says to extend FileProvider, and that using it directly "is not reliable" and crashes on some devices. One line in each Android track's app.
  4. The camera app gets write access for this one URI only. We didn't add a grant flag: the platform does. ACTION_IMAGE_CAPTURE's reference says the URI is copied into the intent's ClipData "for you when calling Context.startActivity", and the emulator's log showed the intent going out with flg=0x3 (read and write grants) and a ClipData holding our URI.
  5. Two features, both required="false". For Google Play, requesting CAMERA implies the features android.hardware.camera and android.hardware.camera.autofocus, and Play hides an app from devices without them. The <uses-feature> guide's fix is to declare both with required="false", which we do. (Android itself doesn't check features at install; they're "informational only".) The adapter's hasCamera() checks FEATURE_CAMERA_ANY at run time instead, as Lesson 13 does for Bluetooth LE.
Gotcha · the permission you didn't need, until you declared it An app that only asks the camera app for a photo doesn't need CAMERA at all: the camera app holds that permission. Appendix A.4 asks the app to request the camera permission, so we declare it, and that changes the rules. The reference for ACTION_IMAGE_CAPTURE: "if you app targets M and above and declares as using the CAMERA permission which is not granted, then attempting to use this action will result in a SecurityException." We tried it: a build without the service's permission check, the permission revoked with adb shell pm revoke, Take photo, and the app crashed with java.lang.SecurityException: Permission Denial: starting Intent { act=android.media.action.IMAGE_CAPTURE … } … with revoked permission android.permission.CAMERA. The service's check is what keeps that from happening. It also matters later: an app that grows a CameraX screen needs CAMERA, and from then on its old capture intent needs it too.
  1. The photo picker, images only. PickVisualMedia shows the system photo picker on Android 11 and later (and on older phones that got it through Google Play); where there is none, "the library automatically invokes the ACTION_OPEN_DOCUMENT intent action instead". Either way the answer is a URI the app may read for a while, so the adapter copies the bytes, unchanged, into its own file. Copying is file work, so it runs on Dispatchers.IO.
  2. Media info without decoding the picture. inJustDecodeBounds makes BitmapFactory read only the header: the size and outMimeType, no pixels in memory. A file it can't read has no size, and becomes Failed.
  3. Only the newest copy stays. After a successful trip, the adapter deletes every other file in media/. A cancelled trip deletes nothing, so the photo on screen keeps its file.

5. iOS: the adapter and its presenter

The iOS adapter is Swift, in the iOS app, like the other platform adapters. It does the same work as the Android one: ask its presenter for a trip, write the answer to a file in Caches, read the media info, keep only the newest copy.

  1. MediaPresenter is the iOS version of the lent launchers. The adapter holds it weak: the screen owns itself, and when it goes, the adapter has no presenter and reports Failed instead of presenting from a screen that isn't there.
  2. One adapter, two tracks, two presenters. The adapter never touches a view: SwiftUI's presenter flips state that the view's modifiers read; UIKit's presenter is the view controller itself (section 7). That's how A.4's "one adapter per platform" works with two UI toolkits on iOS.
  3. shared, because the screen has to find it. Android's screens reach their adapter through the Application; an iOS screen has no such object, so the adapter is one static instance that the app start passes to initKoin and the photo screen lends itself to.
  4. Swift returns Kotlin objects. SKIE keeps the Kotlin names for the async functions Swift calls, so the ones Swift implements are __capturePhoto and __pickMedia, as for __request in Lesson 12. A Kotlin data class is PickedMediaPhoto(info:) in Swift, a data object is PickedMediaCancelled.shared, and Int and Long are Int32 and Int64.
  5. Camera pixels become a JPEG; library bytes stay as they are. The camera gives a UIImage, which has to be encoded to be a file. The picker gives the file's own bytes, which may be HEIC, JPEG or PNG; ImageIO's CGImageSourceGetType says which, and UTType turns that into a MIME type and an extension.

6. Koin and the ViewModel

Each platform builds its adapter and passes it in, like the nine before it: Android with mediaPicker = mediaPicker in DeviceMonitorApplication.onCreate, iOS with mediaPicker: IosMediaPicker.shared in its app start. Swapping the picker for another one is still one line.

  1. The ViewModel calls two inbound ports: MediaCapture for photos and PermissionAccess for the camera permission, as DeviceListViewModel calls DeviceScanning and PermissionAccess. Its permission functions are the list screen's, with Permission.Camera.
  2. The first trip wins. A second tap while the camera or picker is open does nothing. (E1's API screen let the newest request win; here a second trip can't even start, because the system shows one picker at a time.)
  3. The words are the ViewModel's, the same on every track: "From the camera · 1440 × 1920 px · image/jpeg · 62 KB". Sizes use 1 KB = 1,024 bytes and one decimal for megabytes, worked out with whole numbers, because commonMain has no String.format.
  4. MediaUiState.canTakePhoto is !busy && camera == Granted, a computed property every screen uses for the Take photo button, so the button and the service's rule can't disagree about the permission.

7. The screen

One screen per track, all showing the same MediaUiState: the camera permission row (one message and at most one action per status, worded like Lesson 12's Bluetooth row), Take photo and Choose from library, "Waiting for the photo…" while a trip is on, the error in red, and the photo with its media info. A "Photo" button at the top of the main screen opens it.

The screen opens nothing itself: the Activity's launchers do, through the adapter. produceState decodes the file off the main thread, once per path, and every photo has a new path. The route is a data object Photo in DeviceMonitorApp.kt, and DeviceListScreen and its stateless DeviceListContent each gain an onPhoto parameter: the title becomes a Row with a TextButton("Photo"), wrapped in dropUnlessResumed so a double tap navigates once.

render runs for every new state, so showPhoto decodes only when the path changes. The layout, fragment_photo.xml, is a ScrollView around a vertical LinearLayout: the title, the permission text and button, the two buttons, the busy row (hidden until needed), the error, an ImageView 360 dp high with fitCenter, and the details. nav_graph.xml gains a photo destination and a toPhoto action from the list; fragment_device_list.xml gets a photoButton at the title's end, and DeviceListFragment navigates only while the list is the current destination.

  1. SwiftUI presents through state. There's no "present now" call: .photosPicker(isPresented:selection:) and .fullScreenCover(isPresented:) show their screen while a Bool is true. So the presenter's takePhoto() stores a continuation and sets showingCamera; the cover's callback sets it back and resumes the continuation with the photo or nil.
  2. The library trip ends one of two ways. A selection sets chosen; closing the picker sets showingLibrary to false. libraryChanged() runs on both changes and resumes once: with the item if there is one, with nil if the picker closed empty. Our runs on the Simulator picked a photo, then closed the picker with Cancel, and each ended as it should.
  3. The picker hands over a placeholder. A PhotosPickerItem is not the image; loadTransferable(type: Data.self) loads its bytes, and can fail ("for example, if the picker tries to download data from iCloud Photos without a network connection", Apple's PhotosPicker page). We load Data, not SwiftUI's Image, because Image's Transferable "supports only PNG and JPEG".
  4. SwiftUI has no camera view, so CameraPicker wraps UIKit's UIImagePickerController in a UIViewControllerRepresentable, with a coordinator as its delegate. That's SwiftUI's general way to host a UIKit view controller: makeUIViewController builds it once, and the coordinator receives its delegate calls.

ContentView adds NavigationLink("Photo") { PhotoView() } to the main screen's toolbar. The image is UIImage(contentsOfFile:) in a small PhotoImage view, loaded in .task(id: path); it shows a ProgressView until then, which also gives .task a view to run on, as an empty Group doesn't (our first build showed no photo at all for that reason).

  1. The view controller is the presenter. UIKit presents with a call, present(_:animated:), and answers through delegates; each delegate method dismisses the picker and resumes the waiting continuation.
  2. Cancel is an empty result. PHPickerViewController calls the same didFinishPicking for a pick and for Cancel; Cancel gives no results.
  3. The bytes are loaded in the delegate. PHPickerResult isn't Sendable, so Swift 6 refuses to hand the results through a continuation ("sending 'results' risks causing data races"). The delegate starts loadDataRepresentation itself and resumes with the Data, which is Sendable.

DeviceListViewController.viewDidLoad gets a rightBarButtonItem titled "Photo" that pushes a PhotoViewController. Popping it releases the controller and its owner, which clears the ViewModel, and the adapter's weak presenter becomes nil.

8. Showing the photo, the right way up

A JPEG can store its pixels one way and say, in an EXIF orientation tag, how to turn them for display; many cameras save a portrait photo as landscape pixels plus that tag. Viewers that read the tag show the photo upright; code that ignores it shows it on its side, and reports its width and height swapped.

  • Android
  • iOS
  1. Size first. A decoded bitmap takes 4 bytes per pixel (ARGB_8888), so a 12-megapixel photo is 48 MB in memory, for a view a few hundred pixels wide. inSampleSize decodes every 2nd, 4th, … pixel; the loop picks the largest power of two that keeps the longer side at least maxSide, the method in Android's "Loading large bitmaps efficiently".
  2. Then the way up. AndroidX's ExifInterface.rotationDegrees reads the tag as 0, 90, 180 or 270; a Matrix turns the bitmap. The adapter reads the same tag to report the width and height as shown (section 4).
  3. It's screen code, so it's in the app, not the shared module. PhotoBitmap.kt is the same file on both Android tracks, and androidApp/build.gradle.kts adds androidx.exifinterface:exifinterface:1.4.2 next to the shared module's.
Gotcha · the photo on its side The emulator's camera app wrote upright pixels with no orientation tag (1440 × 1920), so camera photos alone never show the bug. We made a test photo that does: landscape pixels and orientation 6 (the agent brief has the recipe). With a build that skipped the rotation, Android showed it on its side; with loadPhoto as above, upright and "600 × 800 px". On iOS, nothing to do: UIImage's size "takes the image's current orientation into account", and both iOS tracks showed it upright. Phones' own camera apps differ in which way they store photos, so the device check takes a portrait photo on a real phone.

Gotcha · Android stops the app while the camera is in front While the camera app is in front, our app is in the background, and Android may end its process to free memory. Retrieval checks

Answer from memory, without scrolling up.

Why does the photo screen lend AndroidMediaPicker its launchers (or IosMediaPicker a presenter), instead of the adapter opening the camera by itself?

The adapter in androidMain uses Android APIs freely; what it lacks is a screen. Lesson 12's permission checker borrows a launcher the same way.

The user opens the camera and closes it without a photo. What does each layer report?

Closing the camera is an ordinary ending, not a failure, so it's a value on both ports. Only Failed becomes a MediaException.

The Android app declares CAMERA, the user has revoked it, and the code launches TakePicture anyway. What happens?

The first answer is right only for an app that doesn't declare CAMERA. Once it does, the service's permission check is what stands between the button and the crash.

Which permission does choosing a photo from the library need?

Apple: the picker is "private by default"; Android's picker grants "access to only selected images and videos". An app that reads the whole library itself is a different case.

A JPEG stores 800 × 600 pixels with EXIF orientation 6. What do BitmapFactory.decodeFile and iOS's UIImage give you?

That's why Android's adapter swaps the width and height when the tag says 90 or 270, and the Android screens rotate the bitmap, while the iOS code just reads size.

Why do both adapters copy the photo into the app's cache instead of handing the core the picker's URI or item?

MediaInfo holds app terms only: a path and plain numbers. A Uri or a PhotosPickerItem would bring a platform into the app core.

Mixed review (interleaved)

On the iPhone, the user taps Don't Allow on the camera prompt. Why does the screen offer Open Settings and not Ask again? (Lesson 12)

The same mapping as Bluetooth's in Lesson 12. On Android a first refusal is Denied, and the app may ask once more.

You add MediaViewModel but forget viewModelOf(::MediaViewModel). Which test fails? (Lesson 11)

Where does the rule "open the camera only with the camera permission" live, and where would a rule "refuse photos over 10 MB" go? (Lesson 10)

The refactor checklist's "every rule of the app lives in a service". The adapter measures the size; deciding what's too big is the app's call.

package com.example.devicemonitor.core

import com.example.devicemonitor.core.inbound.MediaCapture
import com.example.devicemonitor.core.outbound.MediaPicker
import com.example.devicemonitor.core.outbound.PermissionChecker

// Service: the app's photo rules. Open the camera only when the device has one and the camera
// permission is granted. Choosing from the library needs no permission: the system picker shows
// the library, and the app receives only the photo the user picks. A closed camera or picker
// is nothing; a failure is a MediaException with words for the user.
class MediaCaptureService(
    private val picker: MediaPicker,
    private val permissions: PermissionChecker,
) : MediaCapture {
    override suspend fun capturePhoto(): MediaInfo? {
        if (!picker.hasCamera()) throw MediaException("This device has no camera.")
        if (permissions.check(Permission.Camera) != PermissionStatus.Granted) {
            throw MediaException("Taking a photo needs the camera permission.")
        }
        return outcome(picker.capturePhoto(), "The photo couldn't be saved")
    }

    override suspend fun pickMedia(): MediaInfo? =
        outcome(picker.pickMedia(), "The photo couldn't be loaded")

    private fun outcome(picked: PickedMedia, failure: String): MediaInfo? = when (picked) {
        is PickedMedia.Photo -> picked.info
        PickedMedia.Cancelled -> null
        is PickedMedia.Failed -> throw MediaException("$failure: ${picked.reason}")
    }
}

// Outbound adapter: the system camera app and photo picker behind the MediaPicker port. As with
// permissions, only an Activity or a Fragment can register for a result, so one of them lends
// this adapter its two launchers (attach) and passes each answer on (onPhotoTaken, onImageChosen).
// The camera writes into a file the adapter names; a picked photo is copied into one. Both live
// in the app's cache, under media/, which the FileProvider in the manifest shares.
class AndroidMediaPicker(private val context: Context) : MediaPicker {
    private var camera: ActivityResultLauncher<Uri>? = null
    private var library: ActivityResultLauncher<PickVisualMediaRequest>? = null
    private var photoTaken: CompletableDeferred<Boolean>? = null
    private var imageChosen: CompletableDeferred<Uri?>? = null

    private val folder = File(context.cacheDir, "media")

    fun attach(camera: ActivityResultLauncher<Uri>, library: ActivityResultLauncher<PickVisualMediaRequest>) {
        this.camera = camera
        this.library = library
    }

    fun detach(camera: ActivityResultLauncher<Uri>) {
        if (this.camera !== camera) return
        this.camera = null
        this.library = null
    }

    // The TakePicture launcher's callback: true if the camera app saved a photo into the file.
    fun onPhotoTaken(saved: Boolean) {
        photoTaken?.complete(saved)
        photoTaken = null
    }

    // The PickVisualMedia launcher's callback: the photo's content URI, or null if none was picked.
    fun onImageChosen(uri: Uri?) {
        imageChosen?.complete(uri)
        imageChosen = null
    }

    override fun hasCamera(): Boolean =
        context.packageManager.hasSystemFeature(PackageManager.FEATURE_CAMERA_ANY)

    override suspend fun capturePhoto(): PickedMedia {
        val launcher = camera ?: return PickedMedia.Failed("no screen has attached a camera launcher")
        val file = newFile("jpg")
        val uri = FileProvider.getUriForFile(context, "${context.packageName}.files", file)
        val answer = CompletableDeferred<Boolean>()
        photoTaken = answer
        try {
            launcher.launch(uri)
        } catch (e: ActivityNotFoundException) {
            photoTaken = null
            return PickedMedia.Failed("no camera app on this phone")
        }
        if (!answer.await()) {
            file.delete()
            return PickedMedia.Cancelled
        }
        return describe(file, MediaSource.Camera)
    }

    override suspend fun pickMedia(): PickedMedia {
        val launcher = library ?: return PickedMedia.Failed("no screen has attached a photo picker launcher")
        val answer = CompletableDeferred<Uri?>()
        imageChosen = answer
        launcher.launch(PickVisualMediaRequest(PickVisualMedia.ImageOnly))
        val uri = answer.await() ?: return PickedMedia.Cancelled
        val type = context.contentResolver.getType(uri)
        val file = newFile(MimeTypeMap.getSingleton().getExtensionFromMimeType(type) ?: "img")
        return try {
            withContext(Dispatchers.IO) {
                val input = context.contentResolver.openInputStream(uri) ?: throw IOException("the photo can't be opened")
                input.use { from -> file.outputStream().use { to -> from.copyTo(to) } }
            }
            describe(file, MediaSource.Library)
        } catch (e: IOException) {
            file.delete()
            PickedMedia.Failed(e.message ?: "the copy failed")
        }
    }

    // A fresh name for every photo, so a screen never shows an old picture under a new path.
    private fun newFile(extension: String): File {
        folder.mkdirs()
        return File(folder, "photo-${System.currentTimeMillis()}.$extension")
    }

    // Reads the copy's size and type without decoding its pixels, then keeps only this copy.
    private suspend fun describe(file: File, source: MediaSource): PickedMedia = withContext(Dispatchers.IO) {
        val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
        BitmapFactory.decodeFile(file.path, bounds)
        if (bounds.outWidth <= 0 || bounds.outHeight <= 0) {
            file.delete()
            return@withContext PickedMedia.Failed("Android can't read this file as an image")
        }
        // A camera often stores a portrait photo as landscape pixels plus an EXIF orientation tag.
        val turned = ExifInterface(file.path).rotationDegrees % 180 != 0
        folder.listFiles()?.filter { it != file }?.forEach { it.delete() }
        PickedMedia.Photo(
            MediaInfo(
                path = file.path,
                source = source,
                type = bounds.outMimeType ?: "image/*",
                width = if (turned) bounds.outHeight else bounds.outWidth,
                height = if (turned) bounds.outWidth else bounds.outHeight,
                sizeBytes = file.length(),
            ),
        )
    }
}

import kotlinx.coroutines.CompletableDeferred

// Outbound adapter: Android's runtime permissions behind the PermissionChecker port.
// Android lets only an Activity or a Fragment register for a result, so one of them lends
// this adapter its launcher (attach), and tells it when the user answered (onResult).
class AndroidPermissionChecker(private val context: Context) : PermissionChecker {
    private var activity: Activity? = null
    private var launcher: ActivityResultLauncher<Array<String>>? = null
    private var answer: CompletableDeferred<Unit>? = null

    // Android has no "refused for good" status to read back, so the adapter remembers, across
    // launches, which permissions the user has refused.
    private val refusals = context.getSharedPreferences("permission-refusals", Context.MODE_PRIVATE)

    fun attach(activity: Activity, launcher: ActivityResultLauncher<Array<String>>) {
        this.activity = activity
        this.launcher = launcher
    }

    fun detach(launcher: ActivityResultLauncher<Array<String>>) {
        if (this.launcher !== launcher) return
        this.activity = null
        this.launcher = null
    }

    // The launcher's callback. It passes its own Activity too, so that whichever of attach and
    // onResult runs first after a rotation, the answer is read through the new Activity.
    fun onResult(activity: Activity) {
        this.activity = activity
        answer?.complete(Unit)
        answer = null
    }

    override fun check(permission: Permission): PermissionStatus {
        val names = permission.androidNames()
        return when {
            names.all { isGranted(it) } -> {
                refusals.edit().remove(permission.name).apply()
                PermissionStatus.Granted
            }
            // Refused before, and Android suggests explaining why: its dialog still shows.
            shouldShowRationale(names) -> {
                refusals.edit().putBoolean(permission.name, true).apply()
                PermissionStatus.Denied
            }
            // Refused before, and no explanation suggested any more: no dialog either.
            refusals.getBoolean(permission.name, false) -> PermissionStatus.PermanentlyDenied
            else -> PermissionStatus.NotRequested
        }
    }

    override suspend fun request(permissions: List<Permission>): Map<Permission, PermissionStatus> {
        val launcher = checkNotNull(launcher) { "No Activity or Fragment has attached a permission launcher." }
        val answered = CompletableDeferred<Unit>()
        answer = answered
        launcher.launch(permissions.flatMap { it.androidNames() }.toTypedArray())
        answered.await()
        return permissions.associateWith { check(it) }
    }

    override fun openSettings() {
        val intent = Intent(
            Settings.ACTION_APPLICATION_DETAILS_SETTINGS,
            Uri.fromParts("package", context.packageName, null),
        ).addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
        context.startActivity(intent)
    }

    private fun isGranted(name: String) =
        ContextCompat.checkSelfPermission(context, name) == PackageManager.PERMISSION_GRANTED

    private fun shouldShowRationale(names: List<String>): Boolean {
        val activity = activity ?: return false
        return names.any { ActivityCompat.shouldShowRequestPermissionRationale(activity, it) }
    }

    // Android 12 (API 31) gave Bluetooth its own runtime permissions. Before that, a BLE scan
    // needed fine location instead. The camera is one runtime permission on every version.
    private fun Permission.androidNames(): List<String> = when (this) {
        Permission.Bluetooth ->
            if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
                listOf(Manifest.permission.BLUETOOTH_SCAN, Manifest.permission.BLUETOOTH_CONNECT)
            } else {
                listOf(Manifest.permission.ACCESS_FINE_LOCATION)
            }
        Permission.Camera -> listOf(Manifest.permission.CAMERA)
    }
}

// Inbound adapter: turns the photo screen's events into calls on the MediaCapture and
// PermissionAccess ports, and the results into UI state. It knows the ports only.
class MediaViewModel(
    private val media: MediaCapture,
    private val permissions: PermissionAccess,
) : ViewModel() {
    private val _uiState = MutableStateFlow(MediaUiState(camera = permissions.status(Permission.Camera)))
    val uiState: StateFlow<MediaUiState> = _uiState.asStateFlow()

    private var mediaJob: Job? = null
    private var permissionJob: Job? = null

    fun takePhoto() = fetch { media.capturePhoto() }

    fun choosePhoto() = fetch { media.pickMedia() }

    // One trip at a time: the system shows one camera or picker.
    private fun fetch(call: suspend () -> MediaInfo?) {
        if (mediaJob?.isActive == true) return
        _uiState.update { it.copy(busy = true, errorMessage = null) }
        mediaJob = viewModelScope.launch {
            try {
                val photo = call()
                // Null: the user closed the camera or the picker, and the last photo stays.
                if (photo != null) _uiState.update { it.copy(photo = photo, details = describe(photo)) }
            } catch (e: MediaException) {
                _uiState.update { it.copy(errorMessage = e.message) }
            } finally {
                _uiState.update { it.copy(busy = false) }
            }
        }
    }

    // The screen calls this each time it comes back to the foreground: the user may have
    // changed the permission in Settings meanwhile.
    fun refreshPermission() {
        if (permissionJob?.isActive == true) return
        _uiState.update { it.copy(camera = permissions.status(Permission.Camera)) }
    }

    fun requestPermission() {
        if (permissionJob?.isActive == true) return
        permissionJob = viewModelScope.launch {
            val result = permissions.request(listOf(Permission.Camera))
            _uiState.update { it.copy(camera = result.getValue(Permission.Camera)) }
        }
    }

    fun openSettings() {
        permissions.openSettings()
    }

    // The media info as one line, the same on every track.
    private fun describe(photo: MediaInfo): String {
        val source = when (photo.source) {
            MediaSource.Camera -> "From the camera"
            MediaSource.Library -> "From the library"
        }
        return "$source · ${photo.width} × ${photo.height} px · ${photo.type} · ${size(photo.sizeBytes)}"
    }

    // 1 KB is 1,024 bytes here; one decimal for megabytes, without platform number formatting.
    private fun size(bytes: Long): String {
        val kb = 1024L
        val mb = kb * kb
        if (bytes < mb) return "${(bytes + kb / 2) / kb} KB"
        val tenths = (bytes * 10 + mb / 2) / mb
        return "${tenths / 10}.${tenths % 10} MB"
    }
}

import android.graphics.Bitmap
import android.graphics.BitmapFactory
import android.graphics.Matrix
import androidx.exifinterface.media.ExifInterface

// Decodes a photo for the screen, off the main thread. Two things a plain decode gets wrong:
// size (a 12-megapixel photo is 48 MB as a bitmap, so it's decoded at a power-of-two fraction
// that keeps its longer side at least maxSide pixels) and the way up (a camera often stores a
// portrait photo as landscape pixels plus an EXIF orientation tag, which BitmapFactory ignores).
fun loadPhoto(path: String, maxSide: Int = 1024): Bitmap? {
    val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeFile(path, bounds)
    var sample = 1
    while (maxOf(bounds.outWidth, bounds.outHeight) / (sample * 2) >= maxSide) sample *= 2
    val bitmap = BitmapFactory.decodeFile(path, BitmapFactory.Options().apply { inSampleSize = sample })
        ?: return null
    val degrees = ExifInterface(path).rotationDegrees
    if (degrees == 0) return bitmap
    val turn = Matrix().apply { postRotate(degrees.toFloat()) }
    return Bitmap.createBitmap(bitmap, 0, 0, bitmap.width, bitmap.height, turn, true)
}

        mediaPicker.onImageChosen(uri)

        }
    }

    override fun onDestroy() {
        permissionChecker.detach(permissionLauncher)
        mediaPicker.detach(cameraLauncher)

    }

    // being created, so the Fragment registers here and lends the launcher to the adapter.
    // It decides nothing: the adapter reads the answer.
    private val permissionChecker by lazy {
        (requireActivity().application as DeviceMonitorApplication).permissionChecker
    }
    private val permissionLauncher = registerForActivityResult(RequestMultiplePermissions()) {
        permissionChecker.onResult(requireActivity())
    }

    private var binding: FragmentDeviceListBinding? = null
    private var errorDialog: AlertDialog? = null
    private val adapter = DeviceAdapter { device ->
        val nav = findNavController()
        // A fast double tap delivers two clicks; only navigate from the list itself.
        if (nav.currentDestination?.id == R.id.deviceList) {
            // The selected device travels in the arguments: the detail screen needs all of it.
            val args = Bundle().apply {
                putString("deviceId", device.id)
                putString("deviceName", device.name)
                putInt("deviceRssi", device.rssi)
            }
            nav.navigate(R.id.toDetail, args)
        }

        val b = FragmentDeviceListBinding.inflate(inflater, container, false)

        b.deviceList.addItemDecoration(DividerItemDecoration(requireContext(), DividerItemDecoration.VERTICAL))
        // One button: Scan while idle, Stop while scanning.
        b.scanButton.setOnClickListener {
            if (viewModel.uiState.value.scan is ScanState.Scanning) {
                viewModel.stopScan()
            } else {
                viewModel.startScan(b.filterInput.text.toString())
            }
        }
        b.refreshStatusButton.setOnClickListener { viewModel.refreshStatus() }
        // One button: Stop while running, Start while stopped.
        b.monitorButton.setOnClickListener {
            if (monitorViewModel.uiState.value.running) monitorViewModel.stop() else monitorViewModel.start()
        }
        b.clearLogButton.setOnClickListener { monitorViewModel.clearLog() }
        b.photoButton.setOnClickListener {
            val nav = findNavController()
            // A fast double tap delivers two clicks; only navigate from the list itself.
            if (nav.currentDestination?.id == R.id.deviceList) nav.navigate(R.id.toPhoto)
        }

// Outbound adapter: the app's permissions on iOS, behind the Kotlin PermissionChecker port.
// iOS has one Bluetooth permission. Reading CBManager.authorization never prompts; the
// prompt appears when the app first uses Bluetooth, here by creating a CBCentralManager.
// The camera (Extension E2) has an API of its own: AVCaptureDevice reads and requests it.
@MainActor
final class IosPermissionChecker: NSObject, @preconcurrency PermissionChecker,
    @preconcurrency CBCentralManagerDelegate {
    private var manager: CBCentralManager?
    private var waiting: [CheckedContinuation<Void, Never>] = []

    func check(permission: Permission) -> PermissionStatus {
        switch permission {
        case .bluetooth: Self.bluetoothStatus()
        case .camera: Self.cameraStatus()
        }
    }

    // The Kotlin suspend fun. SKIE keeps the name `request` for the async function Swift
    // calls, so the one Swift implements is `__request`.
    func __request(permissions: [Permission]) async throws -> [Permission: PermissionStatus] {
        var result: [Permission: PermissionStatus] = [:]
        for permission in permissions {
            switch permission {
            case .bluetooth: await requestBluetooth()
            case .camera: await requestCamera()
            }
            result[permission] = check(permission: permission)
        }
        return result
    }

    func openSettings() {
        guard let url = URL(string: UIApplication.openSettingsURLString) else { return }
        UIApplication.shared.open(url)
    }

    private func requestBluetooth() async {
        guard CBManager.authorization == .notDetermined else { return }
        await withCheckedContinuation { continuation in
            waiting.append(continuation)
            if manager == nil {
                manager = CBCentralManager(
                    delegate: self, queue: nil,
                    options: [CBCentralManagerOptionShowPowerAlertKey: false]
                )
            }
        }
    }

    // Shows the camera prompt the first time; after that it returns the user's answer at once.
    private func requestCamera() async {
        guard AVCaptureDevice.authorizationStatus(for: .video) == .notDetermined else { return }
        _ = await AVCaptureDevice.requestAccess(for: .video)
    }

    // Called on the main queue (queue: nil) whenever the manager's state changes, including
    // once the user has answered the prompt.
    func centralManagerDidUpdateState(_ central: CBCentralManager) {
        guard CBManager.authorization != .notDetermined else { return }
        manager = nil
        let answered = waiting
        waiting = []
        answered.forEach { $0.resume() }
    }

    private static func bluetoothStatus() -> PermissionStatus {
        switch CBManager.authorization {
        case .notDetermined: .notRequested
        case .restricted: .restricted
        case .denied: .permanentlyDenied // iOS never shows the prompt again
        case .allowedAlways: .granted
        @unknown default: .restricted
        }
    }

    private static func cameraStatus() -> PermissionStatus {
        switch AVCaptureDevice.authorizationStatus(for: .video) {
        case .notDetermined: .notRequested
        case .restricted: .restricted
        case .denied: .permanentlyDenied // as for Bluetooth: no second prompt
        case .authorized: .granted
        @unknown default: .restricted
        }
    }
}

// view or a view controller can present them, so the photo screen is the presenter, as an Android

protocol MediaPresenter: AnyObject {

    func takePhoto() async -> UIImage?

    // closed the picker; throws if the image couldn't be loaded.
    func chooseImage() async throws -> Data?
}

// Outbound adapter: the system camera and photo picker behind the Kotlin MediaPicker port. The
// photo screen sets `presenter` while it's on screen. Every photo becomes a file in the app's
// Caches folder, under media/, and only the newest is kept.
@MainActor
final class IosMediaPicker: @preconcurrency MediaPicker {
    // One for the app: the app start hands it to Koin, and the photo screen lends it a presenter.
    static let shared = IosMediaPicker()

    weak var presenter: MediaPresenter?

    private let folder = FileManager.default.urls(for: .cachesDirectory, in: .userDomainMask)[0]
        .appendingPathComponent("media", isDirectory: true)

    // Whether UIKit can show a camera here. False when the camera is in use, too.
    func hasCamera() -> Bool {
        UIImagePickerController.isSourceTypeAvailable(.camera)
    }

    // The Kotlin suspend funs. SKIE keeps their names for the async functions Swift calls, so
    // the ones Swift implements are `__capturePhoto` and `__pickMedia`.
    func __capturePhoto() async throws -> PickedMedia {
        guard let presenter else { return PickedMediaFailed(reason: "no screen can show the camera") }
        guard let image = await presenter.takePhoto() else { return PickedMediaCancelled.shared }
        // The camera hands over pixels, not a file: JPEG is how the copy is stored.
        guard let data = image.jpegData(compressionQuality: 0.9) else {
            return PickedMediaFailed(reason: "the photo couldn't be turned into a JPEG")
        }
        return save(data, from: .camera)
    }

    func __pickMedia() async throws -> PickedMedia {
        guard let presenter else { return PickedMediaFailed(reason: "no screen can show the photo picker") }
        do {
            guard let data = try await presenter.chooseImage() else { return PickedMediaCancelled.shared }
            return save(data, from: .library)
        } catch {
            return PickedMediaFailed(reason: error.localizedDescription)
        }
    }

    // Writes the bytes as they are, reads their type and size, then keeps only this copy.
    private func save(_ data: Data, from source: MediaSource) -> PickedMedia {
        guard let image = UIImage(data: data),
              let imageSource = CGImageSourceCreateWithData(data as CFData, nil),
              let typeId = CGImageSourceGetType(imageSource) as String?,
              let type = UTType(typeId) else {
            return PickedMediaFailed(reason: "iOS can't read this file as an image")
        }
        let file = folder.appendingPathComponent("photo-\(UUID().uuidString)")
            .appendingPathExtension(type.preferredFilenameExtension ?? "img")
        do {
            try FileManager.default.createDirectory(at: folder, withIntermediateDirectories: true)
            try data.write(to: file)
            let others = try FileManager.default.contentsOfDirectory(at: folder, includingPropertiesForKeys: nil)
            for other in others where other.lastPathComponent != file.lastPathComponent {
                try? FileManager.default.removeItem(at: other)
            }
        } catch {
            return PickedMediaFailed(reason: error.localizedDescription)
        }
        // UIImage's size already allows for the EXIF orientation: it's the photo the way up.
        let info = MediaInfo(
            path: file.path,
            source: source,
            type: type.preferredMIMEType ?? typeId,
            width: Int32(image.size.width * image.scale),
            height: Int32(image.size.height * image.scale),
            sizeBytes: Int64(data.count)
        )
        return PickedMediaPhoto(info: info)
    }
}

@MainActor
@Observable
final class SwiftUIMediaPresenter: MediaPresenter {
    var showingCamera = false
    var showingLibrary = false
    var chosen: PhotosPickerItem?
    @ObservationIgnored private var photoTaken: CheckedContinuation<UIImage?, Never>?
    @ObservationIgnored private var imageChosen: CheckedContinuation<PhotosPickerItem?, Never>?

    func takePhoto() async -> UIImage? {
        await withCheckedContinuation { continuation in
            photoTaken = continuation
            showingCamera = true
        }
    }

    func cameraClosed(_ image: UIImage?) {
        showingCamera = false
        photoTaken?.resume(returning: image)
        photoTaken = nil
    }

    func chooseImage() async throws -> Data? {
        chosen = nil
        let item = await withCheckedContinuation { continuation in
            imageChosen = continuation
            showingLibrary = true
        }
        // The picker hands over an item, not the bytes: loading them can take a moment.
        return try await item?.loadTransferable(type: Data.self)
    }

    // Called when the selection changes and when the picker closes: a selection ends the trip
    // with a photo, a picker closed without one ends it with nothing.
    func libraryChanged() {
        guard let waiting = imageChosen else { return }
        if let chosen {
            imageChosen = nil
            waiting.resume(returning: chosen)
        } else if !showingLibrary {
            imageChosen = nil
            waiting.resume(returning: nil)
        }
    }
}

    // Called for a pick and for Cancel alike: Cancel gives no results. The picker hands over an
    // item provider, not the bytes, and loading them can take a moment.
    func picker(_ picker: PHPickerViewController, didFinishPicking results: [PHPickerResult]) {
        picker.dismiss(animated: true)
        guard let continuation = imageChosen else { return }
        imageChosen = nil
        guard let provider = results.first?.itemProvider else { return continuation.resume(returning: nil) }
        provider.loadDataRepresentation(forTypeIdentifier: UTType.image.identifier) { data, error in
            if let data {
                continuation.resume(returning: data)
            } else {
                continuation.resume(throwing: error ?? CocoaError(.fileReadUnknown))
            }
        }
    }

    // The one place that touches views: every new state ends here.
    private func render(_ state: MediaUiState) {
        renderPermission(state.camera)
        takePhotoButton.isEnabled = state.canTakePhoto
        choosePhotoButton.isEnabled = !state.busy
        busyRow.isHidden = !state.busy
        errorLabel.text = state.errorMessage
        errorLabel.isHidden = state.errorMessage == nil
        detailsLabel.text = state.details
        // Loads the file once per path: every new photo has a new path.
        if state.photo?.path != shownPath {
            shownPath = state.photo?.path
            photoView.image = shownPath.flatMap { UIImage(contentsOfFile: $0) }
        }
        photoView.isHidden = photoView.image == nil
    }

    // One message and at most one action per permission status, as for Bluetooth on the main screen.
    private func renderPermission(_ status: PermissionStatus) {
        let (message, action): (String, String?) = switch status {
        case .granted: ("Camera permission: allowed", nil)
        case .notRequested: ("Device Monitor needs the camera permission to take photos.", "Allow camera")
        case .denied: ("Camera permission was denied. Taking photos needs it.", "Ask again")
        case .permanentlyDenied: ("Camera permission is off. You can turn it on in Settings.", "Open Settings")
        case .restricted: ("The camera is restricted on this device.", nil)
        }
        permissionLabel.text = message
        permissionLabel.textColor = switch status {
        case .granted: .secondaryLabel
        case .notRequested: .label
        case .denied, .permanentlyDenied, .restricted: .systemRed
        }
        permissionButton.configuration?.title = action
        permissionButton.isHidden = action == nil
    }
